METHOD
  JacksonShapeParity.java in this directory asks a mapper for the value serializer of every
  class carried by the project's own artifacts on the WAR classpath, and writes the properties
  it will serialize IN ORDER, with their declared types.  That ordered property list is what
  decides the shape of a serialized response, so comparing it class by class compares response
  shape across the whole model surface rather than asserting something about it.
  Both runs used the resolved classpath of the WAR module, differing only in the value of the
  fasterxml-jackson-core.version property, on OpenJDK 17.0.19.

RECONCILIATION WITH THE MULTI-TRIAL ORDER PROBE — THE NINE ARE REFLECTION NOISE
  This file records ONE run per version.  That is sufficient for the two findings it exists to
  establish, because a serializer class and a property NAME SET do not vary between runs of the
  same version -- and both of those differences are zero here.  It is NOT sufficient for the
  third row, property ORDER, and this section says so rather than leaving the nine to be read as
  version-attributable.
  Jackson collects getter-only properties in Class.getDeclaredMethods() order, which the JVM does
  not guarantee to be stable between runs of the SAME version.  A single run per version therefore
  cannot separate a version effect from that instability.  The probe at
  smoke-evidence/jackson-order/ was built to make that separation: it runs SIX trials per version
  over the same two versions, 2.10.3 and 2.12.7, and attributes a difference to the upgrade only
  when a class's order is identical across all six runs of each version AND the two differ.  It
  finds ZERO such classes, out of 2302 compared.  Where the two probes address the same question,
  that one governs, and this row is superseded by it.
  Each of the nine listed above is accounted for individually against that probe, so the claim is
  checkable class by class rather than in aggregate:

  instability.  None of the nine is a change this dependency advance made.

  request type rather than an internal bean: this file shows two adjacent members transposed
  between two single runs, and the multi-trial probe shows the same type producing one identical
  order in all twelve.  Nothing about that type's serialised shape changes across the advance.
