WHAT THE TWO DIFFERING ENTRIES ACTUALLY DELIVER
  Both were installed twice, in full, and their delivered trees compared file by file.

  jsog
    The prescribed form regenerates the file the asset layout consumes.  The repository's
    own publish hook recompiles lib/JSOG.js from CoffeeScript with an unpinned compiler, so
    npm packs the regenerated output rather than the committed one:
      commit archive   sha256 47e0b992868f2ba27a86e0d098fcadff34e2ecbfec4cfd0e0e12da7e630182c2
                       3802 bytes, banner "Generated by CoffeeScript 1.9.1"
      prescribed form  sha256 de08989003a6da1e4f74175842b045b729f2e483b17a78bafaf7378694f231cf
                       3803 bytes, banner "Generated by CoffeeScript 1.12.7"
    The banner is the only textual difference, and it is enough: config/env/all.js names
    this exact path, so it reaches assets/dist/vendors.min.js.  Because the compiler is an
    open range rather than a pin, the regenerated output is not stable between checkouts
    either, which is precisely what the lockfile-governed-graph rule exists to prevent.

  multi-download
    The prescribed form delivers FOUR files - index.js, readme.md, license, package.json -
    and browser.js is ABSENT, because packing a prepared clone applies the cloned manifest's
    own file allowlist and that allowlist names only the entry module.  The commit archive
    delivers eleven files including browser.js.  config/env/all.js names
    node_modules/@bower_components/multi-download/browser.js literally, so under the
    prescribed form the vendor bundle would silently lose the library while the build still
    exited zero - the forced-execution setting in the pipeline masks exactly that.

WHY 16 CANNOT RESOLVE
  Two distinct causes, both properties of the upstream repository at an immutable commit and
  therefore not addressable by any npm setting or any rewrite of the specification:

  no manifest at the pinned commit          12 entries, exit 254, "Could not read package.json"
    They are asset packages of the pre-npm era: they ship a component manifest and no npm
    manifest.  npm reads a manifest out of the archive and then out of a clone before it can
    resolve anything, and fails on the same absence both times.

  preparation of the clone fails             4 entries, exit 1, "git dep preparation failed"
    npm prepares a Git dependency before packing it whenever the cloned manifest declares a
    lifecycle script, and preparation runs a full dependency install inside the clone.  For
    these four that install executes the repository's own decade-old development toolchain -
    a headless-browser binary that is no longer retrievable, a native addon that no longer
    compiles, and in one case the very component tool this migration removes - and terminates.

WHAT THIS DOES AND DOES NOT ESTABLISH
  It establishes that the prescribed representation is unavailable for all eighteen entries,
  and that the deviation is a measured necessity rather than a preference, per entry rather
  than as a group.  It does NOT establish that the archive form is equivalent in every
  respect: the two forms differ in how npm obtains the package, and that difference is
  exactly what the two DIFFERENT-BYTES rows above are.  What both forms share is the pinned
  commit, so no checkout can resolve either form to different source.

  A credentials explanation for the archive form was considered and is DISPROVEN, and is
  recorded here so it is not reintroduced: reinstalling the whole graph from the committed
  lockfile with the SSH transport forced to fail and interactive prompting disabled still
  completed and still produced every literal asset path, so the 58 plain-form entries need no
  credential material and the 18 archive-form entries are not retained for want of an HTTPS
  resolved URL.  They are retained because the plain form does not work.
