does the jsog representation difference actually reach a build artifact?  measured
================================================================================

WHY THIS MEASUREMENT EXISTS
  probe-git-spec-form.sh proves that two of the eighteen archive-form dependencies deliver
  DIFFERENT BYTES when re-expressed in the prescribed owner/repo#<sha> form, and it names the
  files.  That is a finding about node_modules.  It is not yet a finding about the application:
  a reader is entitled to ask whether a one-line difference in an installed file survives
  concatenation and minification at all, or whether the pipeline flattens it away.

  dependency-change-inventory.md asserted that it survives, and quoted a bundle digest for the
  alternative representation.  That digest was a real measurement, but it was not recorded
  anywhere a reader could check - so it was an unbacked figure in a register whose whole purpose
  is that its figures are checkable.  This file is that measurement, taken again, in isolation,
  with its control.

WHAT WAS VARIED, AND WHAT WAS HELD STILL
  Exactly ONE file was changed between the two builds:
    node_modules/@bower_components/jsog/lib/JSOG.js
  Everything else was held byte-identical - the same staged tree, the same node_modules produced
  by  npm ci  from the committed lockfile, the same manifest, the same Gruntfile, the same asset
  configuration, the same tracked profiles.js, the same Node 20.20.2, and assets/dist deleted
  before each build so neither run could inherit output from the other.

  This is deliberately NOT a re-install of the alternative specification form.  A re-install
  changes the whole dependency graph and would leave the cause of any difference ambiguous.
  Substituting the single file isolates the variable, which is the only way the result attributes
  cleanly.

    control       JSOG.js sha256 47e0b992868f2ba27a86e0d098fcadff34e2ecbfec4cfd0e0e12da7e630182c2
                  the bytes the committed archive-form specification delivers
    alternative   JSOG.js sha256 de08989003a6da1e4f74175842b045b729f2e483b17a78bafaf7378694f231cf
                  the bytes the prescribed owner/repo#<sha> form delivers, taken from the
                  recorded probe install at install/_bower_components_jsog.plain
  The two differ in ONE line, and it is a comment:
    control       // Generated by CoffeeScript 1.9.1
    alternative   // Generated by CoffeeScript 1.12.7

  artifact               control                        alternative                    verdict
  application.js         3c0aeb4d2b02dc74…              3c0aeb4d2b02dc74…              identical
  application.min.js     c1a4cb56e4b644c4…              c1a4cb56e4b644c4…              identical
  application.min.css    04228704205f51db…              04228704205f51db…              identical
  home.html              43c5eb7d7735fc28…              43c5eb7d7735fc28…              identical
  vendors.min.js         70187246b480eebb…              28fdd694f97b8093…              CHANGED

  vendors.min.js         3,986,503 bytes                3,986,504 bytes                +1 byte
  first differing byte   char 3018594, line 15036
  differing lines        1, and it is the generator banner above - nothing else in the bundle moves
  cache-busted name      vendors.min.59439035604af96f.js  vendors.min.2501fcbc4520a74d.js  CHANGED

  So the comment survives minification into the vendor bundle, and because the cache-busting task
  derives its filename from the bundle's content hash, the DEPLOYED FILENAME changes too.  That is
  the substantive part of the result: the difference is not confined to a comment inside a file
  nobody serves, it changes the name of an artifact the deployment publishes.

  home.html is unaffected, and the reason is worth recording so the row is not misread as an
  inconsistency: this build's home.html contains ZERO cache-bust hashes - grep for
  \.[0-9a-f]{16}\.(js|css) returns 0 matches - so a change in a cache-busted filename cannot
  propagate into it.  The other nine names in the dist listing are unchanged; the listing diff
  names vendors.min.<hash>.js and nothing else.

THE CONTROL IS ALSO A FOURTH REPRODUCTION OF THE COMMITTED DIGESTS
  The control build ran in a STAGED COPY at a different absolute path from the working tree, and it
  reproduced all five committed migrated digests exactly.  That is worth more than a sanity check:
  it demonstrates the five compared artifacts are PATH-INDEPENDENT, which is the standing caveat in
  historical-frontend/comparison.txt confined to its true scope - the source map embeds file paths,
  the five artifacts do not.

WHAT THIS DOES AND DOES NOT SUPPORT
  It supports the register's claim that the archive form is not cosmetic: adopting the prescribed
  form for this entry would change a published artifact and its filename, and because the
  CoffeeScript compiler in that repository's publish hook is an open range rather than a pin, the
  regenerated output is not stable between checkouts either.  That is the R-T5 reproducibility
  failure, evidenced.
  It does NOT establish anything about the OTHER seventeen entries; sixteen of those cannot resolve
  in the prescribed form at all and one loses a file outright, and those results are recorded in
  git-spec-form-probe.txt rather than here.

REPRODUCING IT
  1  stage a copy of the frontend resources directory, including a node_modules produced by
     npm ci  from the committed lockfile
  2  rm -rf assets/dist  &&  npx grunt        -> the control digests above
  3  overwrite node_modules/@bower_components/jsog/lib/JSOG.js with the de08989003a6da1e… bytes
  4  rm -rf assets/dist  &&  npx grunt        -> the alternative digests above
  Both builds exit zero, which is exactly why the assertions here are made on digests: the
  Gruntfile sets force:true, so exit status carries no information about whether output changed.
