BPMN SCRIPT-ENGINE EVIDENCE — before and after reinstating the standalone JavaScript engine
===========================================================================================

WHAT THIS DIRECTORY PROVES
--------------------------
personnelSecurityBackgroundInvestigation_v11.bpmn20.xml drives seven complete-event
ScriptTaskListener blocks whose language field is javascript, at lines 48, 68, 88, 110, 121,
144 and 155. Those listeners executed at the base commit on Java 8, where the Nashorn engine
shipped inside rt.jar. JEP 372 removed the engine from the JDK in 15 while javax.script stayed
behind in java.scripting, so on Java 17 the request compiled, returned null, and failed on the
next dereference.

That is a behavioural regression introduced by the runtime move, not a pre-existing defect, and
AAP 0.1.1 (no altered observable behaviour), 0.9.2 ("A failure with no matching row is a
migration regression"), R-5 (no exclusion for a non-baseline failure) and R-7 (baseline is the
tie-breaker) all require it closed. It is closed the way Goal A2 closes the JEP 320 removals:
the platform module is reinstated as an ordinary Maven artifact, org.openjdk.nashorn:nashorn-core
15.4, declared at runtime scope by acm-personnel-security-plugin — the one module whose resources
request it. No source file changed and no javax.script call site changed.

AAP 0.6.1's instruction not to add a standalone engine is scoped to the two dead
JavaScriptEvaluatingPredicate call sites it analyses. Those remain unreachable, are not made
functional by this change, and stay registered as a defect in pre-existing-defects.md. AAP 0.6.5's
assertion that the BPMN corpus contains "zero script tasks and zero script-format declarations" is
true of script *tasks* and false of *task listeners*, which is why these seven were missed.

REPRODUCTION COMMAND (identical for both captures)
--------------------------------------------------
export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64
mvn -B -ntp -o -pl acm-plugins/acm-extra-plugins/acm-personnel-security-plugin -am verify \
  -Dtest=NONE -Dsurefire.failIfNoSpecifiedTests=false \
  -Dit.test=BackgroundInvestigationBusinessProcessIT -Dfailsafe.failIfNoSpecifiedTests=false \
  -Dmaven.test.failure.ignore=true -Djacoco.skip=true

-am is required on a cold reactor: with -pl alone the upstream modules resolve from installed
siblings and a 2.1-vintage XML-binding pair fails before the test runs. Once the reactor is
installed, -pl alone reproduces identically.

BEFORE — before-TEST-BackgroundInvestigationBusinessProcessIT.xml
-----------------------------------------------------------------
Captured at commit 6f779b7fbc, with no engine on the graph.

Both errors are one fault. The first is the missing engine. The second is its downstream
consequence: the two methods share one jdbc:h2:mem:activiti instance, so the process instance the
first method could not complete is still present when the second queries for a single result.

SUPPORTING GRAPH FACTS
----------------------
Reinstating the engine required two companion pins, because Nashorn's MethodEmitter loads
org.objectweb.asm.Handle and dies in its static initialiser if an incompatible provider of that
package sorts first:

  net.minidev:json-smart      2.4.10   pinned in the root aggregator
  net.minidev:accessors-smart 2.4.9    pinned in the root aggregator
  asm:asm                     excluded on acm-service-ecm, for this module only

accessors-smart 1.1 bundles a stripped ASM 4 under the real org/objectweb/asm package, and
asm:asm 3.3.1 declares org.objectweb.asm.FieldVisitor as an interface where ASM 4 made it a class.
Verified after the change, this module resolves exactly one provider of the core ASM package:

  org.ow2.asm:asm:jar:9.8:compile
  org.openjdk.nashorn:nashorn-core:jar:15.4:runtime
  org.ow2.asm:asm-analysis / asm-commons / asm-tree / asm-util :jar:7.3.1:runtime
  asm:asm — absent

Nashorn's own asm-commons, asm-tree, asm-util and asm-analysis transitives are deliberately left
at the versions it ships with: asm-util supplies org.objectweb.asm.util.Printer, which Nashorn
loads while emitting a compile unit.
