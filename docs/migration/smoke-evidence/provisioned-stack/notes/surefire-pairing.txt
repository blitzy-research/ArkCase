A suite archived at baseline with no migrated counterpart proves nothing:
something that used to run either stopped running or stopped being archived,
and there is no longer anything to compare it against.  A missing required
suite, an unlisted suite, or any lost suite therefore makes this capture
INCOMPLETE rather than merely noteworthy.

A suite archived only on the migrated side is an ADDITION, not a hole.  It has
no baseline counterpart for one of exactly two reasons: either the class did
not exist at the base commit, or it existed and the baseline runner did not
select it -- the baseline built with the implicitly bound surefire 2.12.4,
whose default includes match no class name ending in "Tests", while the pinned
3.5.2 does.  Which reason applies to which suite cannot be read out of the
archive, so it is recorded per suite in docs/migration/baseline-test-failures.md
rather than assumed here.  Demanding a counterpart either way would make every
newly added test an evidence gap.  Additions are listed by name below instead,
which is what keeps them accountable.

why the four archive-carry lines above exist.  The archive under surefire/ is
not written by the capture producer at all: install-surefire-evidence.sh
installs it from a raw test harvest, with its own checksum manifest and its own
run provenance.  A full capture, however, writes into a fresh staging directory
and is then moved into place over the destination, which is what makes a
published capture exactly one run output.  Two things followed from that, both
observed: the pairing check read an empty staging subtree and recorded every
required suite as missing, and publication deleted the installed archive.  The
archive is therefore carried into the staging tree before anything asserts on
it, and the carried copy is re-verified against the digests the archive ships
for itself.  A failed or unverifiable carry makes this capture INCOMPLETE,
because an archive that did not reach the staging tree is one this run is about
to remove.
