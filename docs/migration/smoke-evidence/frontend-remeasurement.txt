the migrated frontend build, RE-MEASURED, and what the re-measurement settles
=============================================================================

GENERATED FROM MEASUREMENT.  Every digest, filename and status below was copied out of the
output of capture-frontend-artifacts.sh, which sits beside this file, by the command recorded
under HOW TO REPRODUCE.  Nothing in it was transcribed by hand.

WHY IT EXISTS.  The ten per-side digest records in baseline/artifacts/ and migrated/artifacts/
were overwritten with the token ABSENT by a consolidation run of the capture producer taken
against a tree whose build outputs had been cleaned.  Restoring them from a committed
measurement is one thing; showing that the measurement still holds is another, and only the
migrated side can be shown that way - the pre-migration side was built on the historical Node
line against a deployment that cannot be rebuilt from this tree.  So the migrated side was
rebuilt from scratch and re-digested, and this file is that result.

WHAT IT DOES NOT SETTLE.  It says nothing about the pre-migration side and therefore nothing
  about the byte-identity criterion, which compares the two.  That verdict is computed by
  compare-frontend-artifacts.sh and stated in migrated/artifacts/diff-result.txt, and it
  remains a FAIL on two of the five rows.  Re-measuring the migrated side cannot move it,
  because the difference is produced by the runtime move itself.

  THE SOURCE-MAP RECORD NEEDS ITS OWN WORD, because a first pass of this restoration deliberately
  left it out and that was wrong.  The map is NOT one of the compared five and is not counted in the
  verdict - it embeds file paths, so it is only comparable when both sides build from the same
  relative path - and the first pass read that scoping decision as a reason to withhold the record
  too.  The consequence was visible in the output it produced: the adjudication record's advisory
  paragraph says the map is reported there "so that scoping decision can be checked rather than
  trusted", and with no record on either side it printed RECORD-ABSENT twice, so the single thing
  that paragraph exists to let a reader check was the one thing they could not.  Excluding an
  artifact from a comparison is a scoping decision; declining to record its measured digest is an
  evidence gap wearing that decision's clothes.  Both sides carried the record before the
  consolidation run deleted it, the digests are measured and corroborated - pre-migration
  60ea8616dfa29ed8cc57910a838024d3172be23693d378b2610adcde68159762 and post-migration
  84a7efde28457effd813db74a816936d6c0b434196f79d1eec6c4aaa0697c2b8, both byte-identical to the
  records committed at 0e13c8620d, and the post-migration value reproduced by the re-measurement
  above and by historical-frontend/artifact-digests-node20-basecommit-yarn.txt - so it is restored
  with the other five and marked advisory rather than omitted.  The adjudication record now prints
  both values and reports "differs - advisory scope, not counted in the verdict", which is the
  checkable form of the same scoping decision.

  NOT touched, deliberately: notes/artifact-gate.txt, notes/completeness.txt, notes/manifest.txt and
  comparison.txt.  Each of them makes a statement ABOUT the digests - the gate counts five produced
  and none failed, completeness counts zero absent, the comparison lists the five pairs - and every
  one of those statements was TRUE when the run wrote it.  They became false only because the records
  beneath them were later overwritten.  Restoring the records makes them true again, and editing a
  measured observation to agree with a later state of the tree is the authenticity defect this
  evidence set has already had to remove once.  So they were left exactly as their runs computed
  them, and re-checked afterwards: both gate notes read state PASSED with 5 required, 5 produced and
  0 failed, both completeness verdicts read zero absent digests, and comparison.txt lists the same
  five pairs the adjudication record now reads off disk.

  One caveat about those files, stated rather than corrected.  Each notes/manifest.txt reports the
  path count of the run that wrote it - baseline 73, migrated 75 - and the capture directories
  now hold 83 and 87 non-report files respectively.  The difference is post-run additions by
  other producers, of which this restoration contributes exactly three files per side: the two notes
  named above and the re-created source-map record.
  The counters are left as measured because they are a record of a run, not a live inventory; the
  live check is restore-frontend-artifact-records.sh --verify-only, which reads the records
  themselves and fails closed.
