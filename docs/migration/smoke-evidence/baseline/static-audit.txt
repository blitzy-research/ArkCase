===== how this capture was produced =====

The working tree on this branch is already migrated, so running the gate against it
produces the after-capture and not this one.  Every .java file of the base commit
was materialised into a scratch directory outside the repository working tree, and
the gate was run there, so the output carries the same ./ path prefixes the command
produces in an ordinary checkout.

The scratch directory must sit outside the working tree.  Extract the base commit
into a subdirectory of the checkout instead and the after-capture re-discovers those
historical files, because the gate recurses from the repository root and its
--include filter does not care that they are a copy.  That manufactures a
convincing false failure of 7 where 0 is expected, on a tree which is in fact fully
migrated.

===== consequence: the gate is textual, not semantic =====

Because the gate matches text, all seven must be eliminated.  A build could compile
perfectly, deploy perfectly, and pass every functional smoke flow, and still fail
this gate on four comment and string occurrences.  Those four produce no diagnostic
of any kind, at any stage, on any runtime, and they are exactly as disqualifying as
the three that do, because the gate reads bytes in files rather than symbols in a
symbol table.  Anyone who reads the requirement as removing the compile errors
produces a change set that fails validation for reasons which look inexplicable in
a build log, the build log being clean.

Conversely, a module-access JVM argument, meaning one that opens or exports an
otherwise-encapsulated JDK package to the unnamed module, could never have
satisfied this gate under any reading of the rules.  Such an argument alters what
the JVM permits at run time and removes no character from any source file, so all
seven occurrences would survive it verbatim and the count would still read 7.  The
rules forbid that shortcut and the gate's textual nature independently forecloses
it; the two constraints agree, so one set of edits complies with both.

===== rules provenance, both facts stated together =====

There is no on-disk user rules document for this project.  The rules facility was
queried four times, plainly with no range, with a forced complete read, and with
two explicit ranges, and returned exactly "No user rules provided." on every call,
so there is no external full-text source to defer to.

Rules are nonetheless present and binding.  The requirements embed an explicit,
numbered block of seven rules that govern this work in full, exactly as an external
rules document would, plus seven transformation rules.  Recording only the first
fact would imply that best practice is the sole standard here, which is wrong;
recording only the second would misrepresent where the rules came from.  The
identifiers R-1 through R-7 and R-T1 through R-T7 are the migration plan's own
navigational convention rather than quoted titles.  No rule has been invented and
none has been softened: enterprise-standard best practice applies on top of them,
never as a substitute.
