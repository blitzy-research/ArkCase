MIGRATION PATH EXERCISED
    The search client on Java 17 - UNCHANGED BY DESIGN, and that is a
    deliberate decision rather than an omission.  The client speaks HTTP, it
    manipulates no bytecode, and it touches no encapsulated JDK package, so it
    was cleared by a specific mechanism instead of being upgraded on suspicion.
    Its cleanliness is also part of why the JDK access exceptions register is
    delivered empty: this client asks for nothing the platform encapsulates.
    R-1 CONTRAPOSITIVE, recorded explicitly because flow 4 is its clearest
    case: "A change without a reason is out of scope."  Holding the client
    version is as much a rule-compliant decision as changing one would be, and
    bumping it without a demonstrated compatibility reason would itself have
    been a violation.  The same restraint was applied to the reflection-based
    scanning library used in index-related work, which was verified to scan a
    class file at major version 61 and then left exactly where it was.
    CONSEQUENCE, and it is what makes this flow worth running: because nothing
    changed on this path, any difference between the baseline capture and the
    replay is a genuine regression with no expected-consequence explanation
    available.  Flow 4 is the clean control among the eight.
    Wire behaviour toward the search engine is on the preserve list - the same
    endpoints, the same formats, the same authentication - and search
    round-trips are assigned to this gate as the confirmation of it.

COMPARISON CRITERION
    Identical result set AND identical ranking.
    Both halves are stated because both are required.  Recording only that the
    same documents came back would omit half the criterion: RANKING IS
    BEHAVIOUR, NOT PRESENTATION, so the order the engine chose is part of the
    answer and not a rendering detail.  The set half is the match count and the
    membership of the identifier list; the ranking half is the position of each
    identifier within it.

NORMALISATION / REDACTION APPLIED
    Stripped, because each differs between two runs for reasons that are not
    behaviour:
        ISO-8601 timestamps, and the wall-clock response headers - the Date,
            Last-Modified and Expires headers - which carry the hour a
            response was produced
        entity validators of the ETag kind, which are server-generated
        session identifiers and Set-Cookie material, which are redacted rather
            than normalised because a live session identifier is
            credential-equivalent; only the EXISTENCE of a session is recorded,
            as a separate observed field
        generated request and correlation identifiers, and values shaped like a
            universally unique identifier
        absolute filesystem paths that name this host rather than the
            application
        THE REPORTED QUERY-TIME AND ELAPSED-TIME FIGURE.  Named specifically
            because it is the one value inside a search response that is
            removed: it is wall-clock cost rather than behaviour, and leaving
            it in would make this flow report a difference on a search that
            returned exactly the same documents in exactly the same order.
    Preserved, because each IS the behaviour under observation:
        the match count, recorded as a token in its own right
        the document identifiers
        THEIR ORDER
        the relevance scores, where the response exposes them
    AFFIRMATIVELY: the results were NOT sorted, NOT deduplicated, NOT
    reordered and NOT truncated.  The identifiers are transcribed in the order
    the engine returned them, by a reader that emits matches in file order, so
    the order is preserved by construction rather than by a sort that could be
    got wrong.  A normalisation pipeline that tidied this list to make the diff
    read better would destroy the only signal this flow carries, and no local
    check would catch it.
    The configured credential is replaced by the fixed placeholder <REDACTED-CREDENTIAL>
    by the redaction pass, which every byte this script writes passes through.
    The credential value itself is never recorded, in this file or any other.

INDEX-READINESS NOTE
    A search index has to have finished indexing before its answer means
    anything.  An empty or short result set from a query issued before indexing
    completed is an artefact of TIMING, not of behaviour, and comparing it
    against the other capture would either manufacture a difference or hide a
    real one behind a matching pair of premature answers.  The query is
    therefore re-issued until two consecutive observations agree on the count,
    at most 12 times at 5s intervals, and a matching pair of ZEROES is not
    accepted as settled - an empty answer to a match-everything query is an
    unpopulated index.  Whether readiness was established is recorded below in
    the RESULT_COUNT_STABLE token; where it could not be established that is
    recorded plainly rather than papered over.
