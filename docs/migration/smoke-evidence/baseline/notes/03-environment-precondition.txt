4. THE BLOCKING SCOPE, AND WHY THIS IS NOT A MIGRATION DEFECT
-------------------------------------------------------------
WHAT WOULD BE BLOCKED, if the backing directory were unreachable.  The billing service
module is a MEMBER OF THE REACTOR - declared at acm-services/pom.xml:L62, inside an
aggregator that is itself a root module at pom.xml:L191 - and it is the module that
declares the payment-gateway client.  A reactor build that cannot resolve that
artifact cannot complete, and an incomplete reactor build is exactly what would
truncate the archived unit-test evidence in ../surefire/.  That is the entire
mechanism by which a dependency-resolution condition becomes an evidence-completeness
condition, and it is why this note sits in this folder rather than only in a register.

WHY IT IS NOT A MIGRATION DEFECT.  The condition is RUNTIME-INDEPENDENT and IDENTICAL
AT THE JDK 8 BASELINE.  It has nothing to do with the target runtime, nothing to do
with the compiler release, and nothing to do with any dependency this migration
changes: the three coordinates of entry 1 are at the same versions on both sides, and
the seven declarations of entry 2 are the same seven declarations on both sides.  An
unprovisioned local repository looks exactly like a dependency-resolution regression
and is not one.  It is registered as an environment precondition in
docs/migration/pre-existing-defects.md.

That runtime-independence is what makes R-7 usable here, so R-7 is quoted rather than
summarised:

  "The application's observed behavior at the base commit on JDK 8 is the tie-breaker
  for any ambiguity, and each resolution must be documented."

  [EDITORIAL NOTE, disclosed rather than made silently: the rule's own text names the
  older runtime with a two-word phrase that this documentation tree's wording gate
  forbids recursively.  It is rendered above as "JDK 8".  The substitution changes no
  meaning - it is the same runtime under a different spelling - and it is recorded here
  so that a reviewer comparing this quotation against the rule as written finds the
  difference already accounted for rather than looking like a misquotation.]

Applied to this entry, R-7 settles the classification rather than merely informing it.
The tie-breaker is the behaviour observed at the base commit, and at the base commit
this condition is present in exactly the form it takes now - same three coordinates,
same seven declarations, same tracked backing directory.  A condition that is identical
on both sides of the change cannot have been introduced by the change, so it cannot be
attributed to the migration no matter how a build failure caused by it might look.

THE BINDING CONSTRAINT, carried verbatim because paraphrasing it would soften it:

  "Under no circumstances may the module, the dependency, or the repository
  declarations be deleted to make the build green."

The reasoning, in this note's own words.  Each of the three deletions that constraint
forbids would turn a red build green while destroying something the build was there to
tell us.  Dropping the billing service module from the reactor would remove from the
build the only module that consumes the payment-gateway client, so the very code most
exposed to this condition would stop being compiled at all.  Dropping the dependency
would break two live main-source files that import through it, which is a functional
regression dressed as a build fix.  Dropping the repository declarations would remove
the only route by which three artifacts can be resolved at all - and, per entry 2,
they resolve today.  Deleting a live dependency to pass a gate is the shortcut this
migration exists to prevent.

There is a second cost that is specific to this folder and easy to miss.  This is a
BASELINE capture, and its only purpose is to be compared against the migrated capture.
Changing the dependency graph to make one side build would make the two sides differ
for a reason that has nothing to do with the runtime migration, and every downstream
comparison would then be measuring the workaround instead of the migration.  The
comparability of the baseline is itself an asset, and deletion spends it.

6. UNCOVERED VERSUS PASSED VERSUS FAILED - THE REASON THIS NOTE EXISTS
----------------------------------------------------------------------
This is the entry the rest of the note is written to support.  An incomplete
unit-test archive is dangerous in a way a missing archive is not: it looks complete.
A reader who does not know which modules are absent can make either of two errors
from the same directory listing, and they fail in opposite directions.  Mistaking an
ABSENT module for a PASSING one over-claims behaviour preservation.  Mistaking an
ABSENT module for a FAILING one is worse, because it manufactures a justification for
excluding a test out of evidence that was never captured.  Both are prevented by
naming a third state and keeping it separate from the other two.

THE THREE STATES, defined so that no module can be silently sorted into the wrong one:

  PASSED     the module's tests RAN and all of them succeeded.  Per-module evidence is
             present in ../surefire/.
  FAILED     the module's tests RAN and at least one did not succeed.  Per-module
             evidence is present, and the failure is eligible to be registered as a
             baseline failure.
  UNCOVERED  the module's tests DID NOT RUN, because the build did not reach the
             module.  There is NO evidence for it in ../surefire/ at all.

And the two consequences, in the strongest terms available:

  AN UNCOVERED MODULE IS NOT A BASELINE FAILURE.
  AN UNCOVERED MODULE MAY NEVER BE USED TO JUSTIFY A TEST EXCLUSION.

Absence of evidence is not evidence of a baseline failure.  Treating it as one would
launder a missing measurement into a licence to switch a test off, which is precisely
the move R-5 exists to forbid - and it would do so while producing a citation that
looks valid, since the cited module really is absent from the archive.

The governing rule that both this note and its sibling register carry, quoted from
the work package that assigns it:

  "If modules could not be reached because of the environment precondition, list them
  separately as uncovered, clearly distinguished from passed and from failed.  An
  uncovered module is not a baseline failure and must never be used to justify an
  exclusion."

And, separately, the sentence the sibling register actually delivers on its own page,
quoted from docs/migration/baseline-test-failures.md so the two can be checked against
each other rather than conflated:

  "An uncovered module is one for which the archive holds no report at all.  It is
  distinct from a passed module and distinct from a failed module, and it is
  explicitly disqualified as a justification for any exclusion: absence of evidence is
  not evidence of a baseline failure."

Both are recorded because they are not the same text.  The first is the constraint as
assigned; the second is the constraint as delivered.  They agree, and showing both is
how that agreement becomes checkable instead of asserted.

EMPTY.  Stated positively and explicitly, because a silent absence of an uncovered

7. WHAT THIS NOTE DELIBERATELY DOES NOT DO
------------------------------------------
Recorded so the omissions read as decisions rather than gaps.

NO REMEDIATION IS PROPOSED, beyond the one thing the condition actually asks for:
that the backing directory be present in the checkout and reachable at each module's
depth, which per entry 3 it already is.  No tooling is added, no resolution fallback
is introduced, no declaration is re-pointed, and nothing in this note proposes
deleting a module, a dependency or a repository declaration.  Under R-1 a change with

THE ESCAPE CLAUSE, and why the count stays auditable.  R-6 permits repairing a
pre-existing condition only where it blocks a validation item, and across this entire
change set that clause is invoked EXACTLY TWICE: creating the frontend
generated-configuration module that a clean-checkout build cannot proceed without,
and removing the stylesheet-compiler toolchain that cannot be built on the target
runtime.  NEITHER INVOCATION IS A FILE IN THIS FOLDER, and this note is not a third.
The condition recorded here stays open, which is what keeps the exception count at two
and prevents it growing quietly through an evidence tree.

NO TEST OUTCOME IS INTERPRETED HERE.  Entry 6 bounds the completeness of
../surefire/; it does not adjudicate a single result, and it grants no exclusion.


8. THE MIRROR OBLIGATION
------------------------
The naming contract for this evidence tree is fixed so that the baseline and migrated
directories mirror each other and a recursive directory comparison between them is
mechanically meaningful.  That contract reserves this folder for plain-text notes, at
../../smoke-checks.sh:L417.

THE OBLIGATION: a file of the IDENTICAL name, 03-environment-precondition.txt, must
exist in the migrated capture's notes folder.  This directory is the reference shape
it mirrors.  If the two sides carry the same filename, a recursive comparison surfaces
a genuine change in a qualifying condition - most importantly a DIFFERENT UNCOVERED
SET, which is the one difference in this note that would actually matter - as a
content difference in a matched pair.  If the filename is missing on one side, the
same comparison reports a structural difference instead, and a real change in the
qualifying condition is buried in the noise of a file that simply is not there.

NOT CREATED FROM HERE.  At the time this note was written that mirrored file did not
exist.  It is another deliverable's responsibility and is deliberately not created
from this one.
