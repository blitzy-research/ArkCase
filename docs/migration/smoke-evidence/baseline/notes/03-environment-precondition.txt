why the completeness bound needs a file of its own
==================================================
An archive of green reports invites one specific misreading: that everything is
green.  It is not the same claim.  A module with no report in this archive has
not passed and has not failed — it was not observed by the runner that produced
the archive, and the honest word for it is UNCOVERED.  Collapsing UNCOVERED
into PASSED is the single easiest way for a migration to look better than it is,
and it needs no dishonest sentence anywhere to happen: it happens by a reader
counting failures, finding none, and stopping.

This note exists so that count has a denominator.

Every test class in all ten is an INTEGRATION test by filename.  The unit-test

runner instead.  So the ten are absent from a UNIT-test archive by construction,
and their absence says nothing whatever about their outcome.

the environment precondition the backend build depends on
=========================================================
The migration plan records that three artifacts do not resolve from the public
repository and are expected from a local file-backed repository that may not
exist on a given host, and that this blocks a full reactor build.  The condition
is runtime-independent — it is identical at the base commit — so it is a
precondition to be satisfied, never a migration defect and never something to
be worked around by deleting a module or a dependency.

Measured on the host that produced this capture:

  com.touchnet:tlink-client:1.0                tlink-client-1.0.jar      PRESENT
  org.eclipse.persistence:logging-slf4j:1.0.1  logging-slf4j-1.0.1.jar   PRESENT

Both are real dependencies of the reactor rather than merely managed versions:
the first is managed in the root POM and declared by the billing service, the
second is declared in the root POM's own dependency block at runtime scope.  The
precondition is therefore SATISFIED here, which is why an archive exists at all
— and it is stated as a measured local fact rather than a general one, because
on a host where it is not satisfied the archive under ../surefire/ could not
have been produced and its absence would be a precondition failure rather than
a test failure.  A reader who cannot reproduce this archive should check this
row before concluding anything about the tests.

this capture's own manifest does not name every file in this directory, and the
gap is enumerated here rather than left to a directory diff
==========================================================================
The accounting at manifest.txt is written by the capture script during the run
that produced this directory, so it names what THAT RUN produced and nothing
else.  Eight files sit beside that run's output and were authored rather than
produced, so its counts do not include them.  They are named here in full, and
the arithmetic is stated so a reader can close it:

  notes/01-artifact-comparison-scope.txt        the numbered note series, which
  notes/02-node-env.txt                         bounds what the artifact
  notes/03-environment-precondition.txt         comparison covers, names the
  notes/04-no-flaky-test-tooling.txt            interpreter of record, and
  notes/05-coverage-vs-test-exclusions.txt      bounds this archive
  startup/error-scan.txt                       the ERROR-grade classification
  startup/startup.status                       the startup gate outcome
  smoke-run-summary.txt                        the closing index

  files in this directory outside the report subtree     71
  paths the run's own manifest accounts for              63
  authored files listed above                             8
  63 + 8 = 71, so nothing is unaccounted for

Note 06 is deliberately NOT in that list: it is produced by the capture script's
own redaction ledger on every run, so the manifest does name it.

WHY THE MANIFEST IS NOT SIMPLY REGENERATED to absorb the eight.  It cannot be,
and the reason is the same reason this side exists: the accounting is computed
during a capture run, and a capture run of this side would require a live
deployment of the base commit on the older runtime.  That deployment is gone and
is not reproducible from the delivered tree — which is precisely why this half of
the evidence was captured once and then frozen.  Regenerating the manifest by
hand would mean authoring a file whose entire purpose is to state what a run
mechanically produced, which is the substitution this deliverable refuses
everywhere else.  So the manifest stays as the run wrote it, and this note
carries the reconciliation.

The current-state accounting that DOES cover every file is in smoke-run-summary.txt
beside this directory: its mirror section measures both path sets at the moment it
is written, and it is regenerable without any deployment because every value in it
is read back off disk.  Read the manifest for what the run produced and the
closing index for what the directory now holds.

what else this capture does not cover
=====================================
Named here so the boundary is one paragraph rather than an inference across ten
files.  The reference stack this capture ran against does not include every
service the deployment integrates with, and the flows that depend on an absent
service are recorded as NOT EXERCISED with the reason attached, in their own
flow files and in the run-level summary.  Those recorded gaps are the other half
of this note's subject: this note bounds the unit-test evidence, and the flow
files bound the runtime evidence.  Neither may be read as covering the other.

mirror obligation
=================
The migrated counterpart carries this exact filename — 03-environment-precondition.txt, character
for character — at the mirrored path under migrated/notes/, so that diff -r over
the two trees is mechanical.  A CONTENT difference at this filename is expected
and correct: the two sides state different runtimes, different interpreters and
different measured figures.  A STRUCTURAL difference — this file present on one
side only — is not, and means the mirror has been broken.
