WHY THIS NOTE IS EVIDENCE RATHER THAN COMMENTARY
------------------------------------------------
A row-for-row diff between baseline/ and migrated/ carries meaning only if the
volatile values were removed the SAME WAY on both sides.  A substitution applied in
one run and not the other, or applied to an archive after the fact, does not merely
weaken the comparison - it manufactures agreement, or manufactures disagreement, and
in neither case can a reader tell which.  So the ledger is not documentation of the
capture; it is part of what makes the capture admissible.

A HAND-EDITED CAPTURE IS NOT EVIDENCE.  That sentence is the whole reason this file
exists, and every rule in the next section is a consequence of it.

WHAT EACH GOVERNING RULE REQUIRES OF THIS NOTE
----------------------------------------------
R-T7, evidence over exit codes.  The rule this note's MECHANISM answers.  Every
  substitution is implemented inside the producing script, as a named reusable
  helper, applied through one pipeline that every written byte passes through, with
  a comment beside each pattern naming the value and why it is volatile.  A
  substitution applied outside the script is not reproducible, and a substitution
  that is not reproducible is not evidence.

R-7, baseline behaviour is the tie-breaker.  The rule this note OPERATIONALISES.
  The ledger is what makes the replay reproducible, and therefore what makes any
  behaviour-preservation claim falsifiable.  An undisclosed substitution would
  silently manufacture agreement between the two captures, and a claim that cannot
  fail is not a claim.  The rule reads, with one disclosed substitution: "The
  application's observed behavior at the base commit on JDK 8 is the tie-breaker for
  any ambiguity, and each resolution must be documented."
  [Editorial note that travels with that quote wherever it is reproduced: the rule's
  own text names the older runtime with a phrase this documentation tree's wording
  gate forbids.  "JDK 8" is substituted.  The substitution changes no meaning, and
  it is disclosed here rather than made silently.]
  Note the symmetry, because it is the point rather than a curiosity: that editorial
  disclosure is itself an instance of exactly the discipline this note prescribes - a
  substitution recorded rather than made silently.  The ledger format defined in
  entry 5 is the general form of it, and the same disclosure appears against the
  same quote in every one of the eight flow records.

R-2, no JDK-internal access in production launch configuration, each exception
  documented.  Two properties are asserted here and both were measured.  First, the
  production launch configuration - the startup environment block at
  README.md:L134-L146, duplicated at docs/setup.md:L107 - contains NO argument that
  opens or exports an otherwise-encapsulated JDK package to the unnamed module.
  That is why the register of applied exceptions is delivered EMPTY, with a positive
  statement that none are required.  Second, and this is a constraint on the WORDING
  of this file: those arguments are named nowhere in this tree, so entry 5 describes
  the class of token in words and never writes one.  The register itself is referred
  to by TITLE ONLY, as the JDK access exceptions register, and never by path -
  because its own filename embeds one of the tokens the wording gate forbids.  The
  same convention is already house practice: see the closing cross-references of
  01-artifact-comparison-scope.txt, which state that the register's path is
  deliberately not written and that it is reachable from the documentation
  navigation instead.

R-6, document discovered bugs rather than fixing them.  This ledger DOCUMENTS; it
  fixes nothing.  Where a captured value is volatile because of a pre-existing
  condition, the condition is recorded and the value normalised - never "repaired".
  The mandated instance: one service of the reference stack is EXPECTED to answer
  with HTTP 503, documented at README.md:L50 and again at docs/setup.md:L30, and its
  observed status is captured exactly as observed.  It is not retried into
  submission, not hidden, and not normalised away, because an expected 503 is
  behaviour and a comparison that cannot see it is a comparison of less.  The
  migration's escape clause is invoked EXACTLY TWICE in the whole change set -
  creating the frontend generated-configuration module, and removing the
  stylesheet-compiler toolchain that cannot be built on the new runtime - and
  NEITHER invocation is a file in this folder.  Nothing in this note repairs
  anything, so the exception count stays auditable and cannot quietly grow through
  this evidence tree.

R-1, a change without a reason is out of scope.  Entry 6 records only substitutions
  that were ACTUALLY APPLIED, measured from the capture files themselves.  No
  hypothetical ledger is written, no further normalisation is proposed, and no
  tooling is introduced.  Where the standard pipeline was in force but had nothing
  to replace, entry 6 says so positively rather than leaving a silence a reader must

R-5, no disabling of failing tests.  Not this note's rule, but one boundary of it

1. THE PIPELINE THAT APPLIES SUBSTITUTIONS
------------------------------------------
Every substitution in this capture comes from one of the named helpers below, all of
them in ../../smoke-checks.sh.  The names and line anchors were read back from the
script as actually written rather than assumed, because a ledger that cites a helper
that does not exist is worse than one that cites none: it reads as verified when it
is not.

  sanitise            :L1914  THE SINGLE PIPELINE EVERY BYTE THIS SCRIPT WRITES
                              PASSES THROUGH.  Not "every response body" - every
                              byte, including result records, notes, the closing
                              summary and mined startup-log regions.  It is the
                              composition of the three passes below, in that order.
                              Routing all writers through one function is what makes
                              the coverage claim CHECKABLE: a reviewer confirms it by
                              confirming that nothing writes into the capture tree
                              except through here.
  redact_literal      :L1589  the fixed-literal pass.  Six substitution pairs, none
                              of them a pattern: the configured credential, and four
                              absolute-path prefixes.  A boundary flag stops a path
                              match that runs on into a longer name, so a directory
                              prefix is replaced only where it really is that prefix.
  redact_patterns     :L1669  the credential PATTERN pass.  Every expression is
                              FIXED - no caller-supplied text is interpolated into
                              any of them, so the escaping hazard that pattern
                              substitution normally carries cannot arise.  Its
                              coverage is deliberately wider than "the response
                              body", because a credential reaches a capture by more
                              routes than a body: request and response headers
                              carrying authorisation material, session cookies, which
                              are credential-equivalent for as long as they live,
                              cross-site-request-forgery tokens, bearer and basic
                              material anywhere including inside a diagnostic,
                              credential-shaped fields echoed back by the server, the
                              download endpoint's bearer-equivalent query parameter,
                              a transport configuration line echoed into a
                              diagnostic, and credentials embedded in a URL.
  normalise           :L1707  the visible, auditable pattern pipeline that removes
                              inter-run volatility, with a comment beside each
                              expression naming the value and saying why it is
                              volatile.  It is deliberately NARROW; entry 4 records
                              what it must not touch and why.
  verify_sanitiser    :L1944  the pipeline's SELF-TEST, run before the first capture
                              is written.  It checks three properties: that the
                              pipeline produces output at all, that the real
                              configured credential does not survive it, and that
                              representative credential-bearing header, cookie and
                              structured-field forms do not survive it.  Failure of
                              any one is a REFUSAL TO START.
  digest              :L2134  the artifact digests, with a portable fallback so the
                              run works on either developer platform: the primary
                              tool, then the alternative spelling of it, and if
                              neither is present an explicit unavailable marker
                              rather than a silent empty value.  digest_value :L2161
                              is the same result reduced to the hash alone.
  http_probe          :L2227  writes the paired body and status files for a flow,
                              appending to the flow's .out and .status.  Every byte
                              it writes goes through sanitise.
  record_result       :L3147  writes the flow's plain-text comparison or observation
                              record.  Plain text by design - no pipe tables, no
                              headings, no fenced blocks - because nothing under this
                              folder may be Markdown.  It passes through the
                              sanitiser like everything else, and the reason is worth
                              keeping: its format strings are script-authored, but
                              several of them interpolate values that came back from
                              the server, and a script-authored format string
                              carrying a server-supplied value is exactly as
                              dangerous as a raw body.
  record_skip         :L3666  writes an explicit skipped record with a reason, so an
                              unexecuted flow is VISIBLE in the diff rather than
                              invisible.  The reason travels into the result record
                              as well as into the capture, and the flow's own named
                              observations are each written as an explicit absence -
                              which is what makes a skip COMPARABLE rather than
                              merely honest.

PUBLISHED CORRECTION, because the names above were checked rather than accepted.  A
brief in this work package named a helper for the paired body and status write and a
single helper for redaction.  Neither name exists in the script.  The paired writer
is http_probe, and redaction is two passes, redact_literal and redact_patterns,
composed with normalise by sanitise.  The names published above are the names the
script uses.  This correction is recorded rather than quietly absorbed for the same
reason every substitution below is: an unrecorded discrepancy between a ledger and
the thing it describes is indistinguishable from an error.

THE TWO HARD PROPERTIES OF THIS PIPELINE

  applied by the script, never by hand    A substitution reaches a capture file only
                                          on the write path, before the byte lands.
                                          No file in this directory was edited after
                                          the run that produced it.  A substitution
                                          applied after the fact is not reproducible,
                                          and what is not reproducible is not
                                          evidence - it is an assertion about an
                                          archive that the archive cannot support.
  the same unmodified script writes both  The migrated capture is produced by this
                                          same script, unchanged, with its output
                                          directory pointed at migrated/.  That is
                                          what makes the two directories comparable
                                          at all.  Had the script needed editing
                                          between the two runs, the comparison would
                                          prove nothing, because a difference between
                                          the captures could then be attributed to
                                          the change in the producer rather than to a
                                          change in the system.

A THIRD PROPERTY, WORTH STATING BECAUSE IT WAS LEARNED THE HARD WAY.  The sanitiser
is a pipeline, so a malformed expression anywhere in it makes the whole substitution
program invalid, the utility exits before reading a byte, and EVERY capture file
comes out at zero length while the run still completes and reports success.  Silent
total evidence loss, from a one-character mistake, with no error visible in the
produced artefacts.  That is the worst available failure mode - strictly worse than
having no redactor at all, because it looks like success.  It is why
verify_sanitiser exists, why it runs before the first capture, and why its failure is
a refusal to start rather than a warning.  It is also the clearest illustration of
R-T7 in this whole tree: the exit code said success, and the evidence said nothing.

2. THE GENERIC VOLATILE SET, STRIPPED FROM EVERY FLOW
-----------------------------------------------------
These are removed everywhere, in every flow, because each differs between two runs of
IDENTICAL behaviour by construction.  Left in place, each would report a difference
that has nothing to do with behaviour, and a comparison that reports noise on every
run trains a reader to ignore the one row that matters.  The replacement token is
given so the replay can be checked against the same token rather than a similar one.

  ISO-8601 date-times     created and modified stamps differ by construction,
                          including any fractional part and any timezone offset.
                          Replaced by a timestamp token.
  date-bearing response   the Date, Last-Modified and Expires headers carry wall-clock
  headers                 time and nothing else.  Replaced by an HTTP-date token, with
                          the header NAME and its case preserved so its presence is
                          still evidence.
  entity tags             a server-generated response validator, not behaviour.
                          Replaced by an entity-tag token.
  authentication          the challenge nonce and opaque parameters are regenerated on
  challenge parameters    every response.  The challenge SCHEME survives, which is the
                          part flow-1-login actually asserts on.
  generated request and   supplied per request, so two identical exchanges disagree on
  correlation identifiers them by construction.  Replaced by a single token.
  cookie-setting header   replaced WHOLESALE, and by the redaction pass rather than
  values                  this one, because a live session identifier is
                          credential-equivalent and belongs in the credential pass,
                          not the cosmetic one.  The presence or absence of a session
                          is still recorded, as a separate observed field - see
                          entry 7.
  millisecond epoch       generated instants inside structured bodies, which are
  values                  timestamps in a different clothing and equally volatile.
  absolute filesystem     the capture directory, the repository root, the home
  paths                   directory and the temporary directory all differ by machine
                          and by checkout location, so an unreplaced one would make
                          two captures of identical behaviour disagree on every path
                          they mention.  Each is replaced by its own named token, so a
                          reader can still tell WHICH root a path was relative to.
  surrogate database keys generated by a sequence, so the same behaviour produces a
                          different number on every run and on every database.
                          Matched BY FIELD NAME rather than by value shape - see the
                          note on that choice in entry 4, because it is the single
                          decision that keeps a result count, a queue position and an
                          object number out of the substitution.

ONE ORDERING DEPENDENCY INSIDE THIS SET, recorded because it is invisible and would
be easy to break.  The broker-assigned message identifier of entry 3 EMBEDS a
millisecond instant.  Its expression is therefore placed AHEAD of the epoch
expression: if the epoch expression ran first it would rewrite the middle of the
identifier, and the identifier expression would then no longer match what was left.
The whole identifier collapses to one token, instead of leaving its host and counter
fragments stranded around a normalised instant.

4. WHAT MUST SURVIVE VERBATIM - THE OVER-NORMALISATION GUARD
------------------------------------------------------------
THE MOST CONSEQUENTIAL ENTRY IN THIS NOTE, because the failure it guards against is
the one that leaves no trace.  An under-normalised capture is noisy and a reader can
see that it is noisy.  An OVER-normalised capture is quiet, tidy, and empty: the two
sides agree because the thing that could have disagreed was removed before either
side was written.  A comparison that cannot fail has demonstrated nothing, and it
looks exactly like a comparison that passed.

THE PRINCIPLE: ERR TOWARD CAPTURING MORE AND NORMALISING NARROWLY.  A value stays
unless it is volatile BY CONSTRUCTION and its volatility is understood.  Where an
expression could be written either broadly or exactly, it is written exactly, even
when that makes it longer - which is why the messaging group of entry 3 names its
keys one by one instead of matching a suffix.  Where a doubt could not be resolved,
the value stays and the doubt is recorded.

The values below must NEVER be normalised or redacted, per flow slug.

  flow-1-login              the authorization result; role and privilege names.
                            Whether the credentialed request was authorised, and with
                            which authorities, IS the criterion.

  flow-2-views              case numbers and object identifiers; document names and
                            MIME types; list row ORDERING; the content-hashed asset
                            filenames, which are themselves a content fingerprint and
                            SHOULD match when behaviour matches, so replacing one
                            would discard a free integrity check; every
                            permission-dependent rendered element, because whether an
                            element renders at all is a security outcome.

  flow-3-alfresco-roundtrip the document name; the resolved MIME type on BOTH legs,
                            since a round trip that resolves the type differently on
                            the way back has changed behaviour even though both legs
                            succeeded; the content digest; the declared content
                            length; XML element and attribute names and their
                            ordering, because generated document shape is part of the
                            preserved contract.

  flow-4-solr-search        the result count; the document identifiers; and above all
                            THEIR ORDER; relevance scores.  DO NOT SORT, DEDUPLICATE,
                            REORDER OR TRUNCATE ANY PART OF A SEARCH RESULT.  RANKING
                            IS BEHAVIOUR, NOT PRESENTATION.  Tidying a result list is
                            the single easiest way to make this flow pass while the
                            ranking has silently changed, and the tidied capture would
                            look better than the honest one.  These values sit a few
                            bytes from the query-time figure that IS normalised, and
                            the boundary between them matters in both directions:
                            leaving the timing in makes the flow diff on pure noise,
                            and taking anything else out makes it diff on nothing.

  flow-5-activemq-event     the destination name, because the comparison is
                            per-destination; the payload content, because the
                            criterion IS an identical payload; the payload's declared
                            type; the priority and persistence flags, because
                            quality-of-service settings are behaviour; and every
                            application-set property, because the publisher set it
                            deliberately.

  flow-6-generated-number   THE GENERATED NUMBER IN FULL - prefix, separators,
                            padding and sequence position - plus the object type and
                            the relative order across multiple creations.  This flow
                            exists to observe the numbering that the rules engine
                            produces through the decision tables, so the number IS the
                            observation.  Its parts are not incidental formatting:
                            a changed separator or a lost pad is a changed number.

  flow-7-workflow-start     the process-definition KEY, as distinct from the volatile
                            definition identifier of entry 3 - this is the one place
                            in the pipeline where a stable value lives INSIDE a
                            volatile one, and the expression is built around
                            preserving it; the task name and the task-definition key;
                            the assignee or candidate group; the instance state; the
                            process variables; and the definitions-loaded count.  Each
                            is exactly what this flow's criterion - identical process
                            instantiation and task assignment - compares.

  flow-8-queue-transition   the case or complaint number; the source and destination
                            queue names; the onward-route list AND ITS ORDER, for the
                            same reason ranking is preserved in flow-4-solr-search;
                            the assignee; and any rule-derived reason code, because
                            the reason a routing decision was reached is part of the
                            decision.

TWO CASES THAT LOOK LIKE EXCEPTIONS AND ARE NOT.

  a surrogate key and a behavioural number are both bare integers.  They are told
  apart by FIELD NAME, never by value shape, and that single choice is what keeps a
  result count, a queue position and a generated object number out of the
  substitution.  A shape-based expression would have taken all three.

  an assignee is a user identity, which reads like something to redact.  It is
  deliberately NOT redacted: task assignment is half of flow-7-workflow-start's
  criterion, and redacting it would leave the two captures agreeing on a placeholder
  and demonstrating nothing.  The rule that separates it from a credential is in
  entry 7 - an identity is behaviour, an authenticator is not.

THE GENERAL SPECIAL CASE, WHICH GENERALISES BEYOND THE INSTANCES ABOVE.  If a
behaviour-bearing value CONTAINS a genuinely volatile embedded element - a year inside
a generated number is the obvious example, a definition key inside a version-suffixed
identifier is the one that actually occurs here - RECORD THE WHOLE VALUE AND NOTE THE
VOLATILE PART.  Never mask the embedded element silently.  Masking it destroys the
surrounding value's comparability in exchange for removing one component's noise,
and worse, it does so invisibly: the capture then shows a well-formed value that no
longer means what it appears to mean.  Naming the volatile component in the flow's own
record costs one line and keeps the whole value available to a reader who needs it.

5. THE FORBIDDEN-TOKEN SUBSTITUTION PROTOCOL, AND THE LEDGER FORMAT
-------------------------------------------------------------------
PART ONE - THE PROTOCOL.

A captured body, header, banner or stack trace can arrive carrying a token that this
documentation tree's own wording gates forbid.  Three classes exist:

  a module-access JVM argument   an argument that opens or exports an
                                 otherwise-encapsulated JDK package to the unnamed
                                 module.  Described here in words and NEVER written,
                                 for the reason immediately below.  The production
                                 launch configuration carries none of them - see the
                                 R-2 ruling above - so the only route by which one
                                 could enter this tree is a captured diagnostic that
                                 quoted one back.
  the forbidden two-word phrase  the phrase this tree's wording gate replaces with
  naming the older runtime       "JDK 8" throughout.  Worth stating precisely, because
                                 the obvious worry is the wrong one: a captured
                                 runtime banner does NOT contain the phrase, since a

Where such a token is captured, the pipeline replaces it with a DESCRIBED PLACEHOLDER
and the substitution is noted in that flow's paired result file as well as in the
ledger below.  The surrounding element is kept: only the token is replaced, so the
reader can still see what kind of thing was reported and where.

THE REASON THIS PROTOCOL HAS TO EXIST IS MECHANICAL, AND IS WORTH STATING PLAINLY.
These notes and the flow captures live INSIDE the directory that the wording gates
scan recursively.  A faithful verbatim capture of such a token would therefore fail a
gate all by itself, on a system that was working perfectly.  The gate is textual, not
semantic - it reads characters and has no way to know that the characters it found
were quoted evidence rather than configuration.  So a capture cannot be both faithful
and gate-clean at the same time, and the protocol is how that is resolved: the
faithful thing is recorded ABOUT the token, in words, rather than by reproducing it.
That is a real loss of fidelity, it is bounded, and it is disclosed here rather than
glossed over.

PART TWO - THE LEDGER FORMAT, WHICH THIS NOTE DEFINES.

Every substitution, of any class, is recorded as one numbered block in the eight
fields below, separated from the next by a rule.  The format is prescribed here so
that the migrated replay can be diffed against this capture field by field, and so
that a substitution cannot be recorded in a shape that hides one of the eight facts.

  SUBSTITUTION-ID   a stable identifier, so the replay can cite the SAME one.  The
                    identifier is the join key between the two ledgers; if it drifts,
                    the two ledgers cannot be compared even when they agree.
  APPLIED-BY        the helper that applied it, by the name the script uses.
  SCOPE             which capture files it touched, BY FILENAME.  A scope stated as
                    "the capture" is not auditable; a reader must be able to open the
                    named files and find it.
  PATTERN           what was matched, DESCRIBED.  NEVER THE FORBIDDEN LITERAL ITSELF.
                    This field is where a well-meaning ledger destroys its own tree:
                    the natural way to record a substitution is to quote what was
                    replaced, and for a forbidden token that quotation is the very
                    thing the gate rejects.  The field is specified as a description
                    for that reason, and the specification is not advisory.
  REPLACEMENT       the exact placeholder token written in its place.  This one IS
                    written literally, because a placeholder is chosen precisely so
                    that writing it is safe, and because the replay can only be
                    checked against the same token.
  REASON            exactly one of: volatile value, credential leak path, forbidden
                    token.  A single closed vocabulary, so the ledger can be read as a
                    census rather than as prose.
  REPRODUCIBLE-BY   the statement that the same unmodified script reproduces it in the
                    replay.  A substitution that cannot carry this statement should
                    not have been applied.
  RECORDED-IN       the paired flow result file that also records it, so the ledger and
                    the flow record corroborate each other rather than duplicating one
                    unverified claim.  All eight flow records in this capture do carry
                    their own substitution statements, so this field is a real
                    cross-check and not a formality.

  the fixed placeholder            wherever a credential could leak, a FIXED
                                   placeholder token is written in its place, not a
                                   per-occurrence mask.  A fixed token is what lets the

  the covered write paths          command echoes, request bodies, request and response

                                   an archive through a diagnostic at least as often as
                                   through a body, which is why the coverage is stated

  capture the session's EXISTENCE, the presence or absence of a session is recorded as
  never its value                  an observed field, and the cookie-setting header is

                                   credential-equivalent for as long as it lives, so it

  touch the credential             the producing script.  That is a security decision

8. MIRROR OBLIGATION
--------------------
This directory is the reference SHAPE that ../../migrated/ must mirror.  A file named
06-normalisation-and-redaction.txt must exist under ../../migrated/notes/ under the
IDENTICAL filename, and its ledger must use the IDENTICAL entry format defined in
entry 5 and the IDENTICAL substitution identifiers used in entry 6.

Recorded state at the time this note was written, measured rather than assumed:
../../migrated/notes/ already holds the same set of files this directory holds,
including numbered notes 01, 02 and 03 - but it does NOT yet hold a file with this
name.  So this note creates an asymmetry, deliberately and knowingly, and closing it
is the obligation.  A brief in this work package described the migrated directory as
empty; it is not, and the corrected state is published here so a reader does not
conclude the mirror was never established.  This note does not create the migrated
file: a baseline note cannot author the migrated capture's ledger without inventing
its content, which is the one thing a ledger may never contain.

WHY IDENTICAL SHAPE MATTERS, AND WHAT FOLLOWS IF IT IS NOT ACHIEVED.  A recursive
directory diff between the two captures is meant to reveal a genuine change in a
QUALIFYING CONDITION - a substitution applied in one run and not the other, a
placeholder token that changed, a scope that grew.  If the two files differ
STRUCTURALLY instead, every one of those signals is buried in formatting noise, and
the reader cannot tell a real divergence from a different author's layout.  A missing
file is worse still: the diff reports its absence, which reads as a capture fault
rather than as the open obligation it is.

THE CONSEQUENCE, STATED PLAINLY BECAUSE IT IS THE POINT OF THIS ENTRY: IF THE TWO
LEDGERS DIFFER, THE AFFECTED FLOW COMPARISON IS NOT ESTABLISHED.  Not "is weaker", not
"needs review" - not established.  A flow whose volatile values were removed
differently on the two sides has not been compared, whatever the two files appear to
say about each other, and no amount of agreement elsewhere in the capture repairs it.
The remedy is to reconcile the ledgers and re-derive the comparison, never to record
the flow as compared and footnote the difference.
