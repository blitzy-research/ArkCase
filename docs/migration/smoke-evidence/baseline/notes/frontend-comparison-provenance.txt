WHICH BUILD THIS CAPTURE'S FIVE DIGESTS COME FROM
This is the BASELINE capture, and its five digests under artifacts/ were taken
from the base-commit tree built on the HISTORICAL runtime: Node v8.17.0 with
yarn 1.22.22, the base-commit package.json unmodified with its 76 git
dependency specifications in owner/repo#<semver-range> form, and the base-commit
lockfile of the superseded package manager.  notes/artifact-gate.txt records the
exact directory this run read, and env/toolchain.txt records the node, npm and
java that were on PATH while it read it; both are generated by the capture
script from the run itself rather than typed here.

The staged directory named in notes/artifact-gate.txt is a throwaway build
location and does not exist in a fresh checkout, for the same reason the baseline
Surefire archive names a throwaway checkout of the base commit: a baseline cannot
be produced from the migrated tree.  It is reproducible with
  ../../historical-frontend/capture-historical-frontend.sh

RESULT OF THE COMPARISON THIS CAPTURE TAKES PART IN
Comparing this capture's five digests against the migrated capture's:
  application.js        BYTE-IDENTICAL
  vendors.min.js        BYTE-IDENTICAL
  home.html             BYTE-IDENTICAL
  application.min.js    differs by 2 bytes, in one regular-expression escape
  application.min.css   differs by 789 bytes, in selector grouping only
The source map differs as well.  It is EXCLUDED from the required comparison set
because it embeds file paths, and the two builds ran from different roots by
construction, so its difference carries no information here.

A strict reading of the byte-identity criterion is therefore NOT met, and this
note does not soften that.  What the criterion exists to detect - a changed
dependency graph, a changed pipeline, changed application source - was looked for
specifically and not found; the full analysis is in
  ../../historical-frontend/comparison.txt

THREE BUILDS WERE TAKEN, NOT TWO, AND THAT IS WHAT SETTLES THE ATTRIBUTION
  A  base-commit tree, yarn 1.22.22, Node  v8.17.0    <- THIS capture
  B  base-commit tree, yarn 1.22.22, Node v20.20.2
  C  migrated tree, npm 10.8.2 from the committed lockfile, Node v20.20.2
                                                     <- the migrated capture

B holds the runtime constant against C and varies only the package manager, the
lockfile and the specification form.  B and C are byte-identical on all five
artifacts AND on the source map.  So the two differences between A and C cannot
be caused by the package-manager change, the lockfile change or the manifest
rewrite - those are precisely what B and C differ in.  The only variable left
between A and B is the JavaScript engine the minifier itself ran on.  B's digests
are preserved at
  ../../historical-frontend/artifact-digests-node20-basecommit-yarn.txt
so this reasoning can be checked rather than taken on trust.  Corroborating it
directly: the minifier versions are IDENTICAL on both sides
(grunt-contrib-uglify 0.9.2 / uglify-js 2.8.29, grunt-contrib-cssmin 0.12.3 /
clean-css 3.4.28) and their input, application.js, is byte-identical.

The residual difference is registered as an accepted, evidenced deviation in
docs/migration/ambiguity-resolutions.md and docs/migration/pre-existing-defects.md.
A reader must not extend either capture into a claim the other one makes.

TWO CONDITIONS ENCOUNTERED ON THIS SIDE, RECORDED RATHER THAN SMOOTHED OVER
1. The historical install FAILED its native compilation step.  The failing
   package was node-sass, reached transitively from the Sass Grunt plugin that
   the base-commit manifest declares.  On this host the cause is the absence of
   the Python 2 interpreter its native build driver requires - a host condition,
   not a Node 8 condition - and the same package independently fails to build
   under Node 20, which is what justified removing that plugin.  It did NOT
   prevent the five artifacts from being produced, and the Gruntfile declares no
   Sass task for the missing compiler to serve.
2. profiles.js is not tracked at the base commit and the build requires it, so it
   was created with exactly the content the deployed runtime writes for it.
   Without that step the baseline build could not have run at all - which is the
   condition recorded as one of the two escape-clause invocations, observed here
   rather than argued.

A NOTE ON EXIT STATUS, SINCE THIS RUN DEMONSTRATED IT
The historical Grunt run exited ZERO while reporting a warning: a missing
modules_config/config/modules.json, followed by "Used --force, continuing."  That
is the forced-execution setting masking a task failure, in a real run, exactly as
the governing evidence rule describes.  It is the reason every assertion here is
made against the artifacts and their digests rather than against an exit status.
