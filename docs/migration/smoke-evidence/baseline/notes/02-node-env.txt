why the interpreter needs a file of its own
===========================================
The whole frontend half of this migration is a change of interpreter and
package manager.  If the two sides' artifacts differ, the candidate causes are
the interpreter, the package manager, the dependency graph, the pipeline
configuration and the application source — and only one of those can be ruled
in or out by inspection.  Recording the interpreter as MEASURED, per side, is
what makes the attribution in ../artifacts/diff-result.txt checkable instead of
asserted.

what the repository declares, as distinct from what ran
======================================================
Declaration and observation are different things and are kept apart here on
purpose — a manifest field is a wish, a probe is a fact.

  .nvmrc                             20
  package.json engines.node          >=20 <21
  package.json engines.npm           >=10 <11

None of the three describes the interpreter THIS side ran: they are the
delivered manifest's declarations, and this side is a capture of the base
commit, whose manifest declared no node or npm constraint at all — it
constrained yarn instead — and which carried no .nvmrc.  They are reproduced
here so the two mirrored notes can be read against each other; on this side
they are context, not a description of what ran.

there is NO application-side version gate, and this note says so rather than
implying one
============================================================================
It would be reasonable to assume the deployment refuses to start on the wrong
interpreter.  It does not.  A search of the angular starter module's main source
for a node or npm version check returns ZERO matches: the resource copier
resolves its launchers and runs them, and it does not compare the interpreter it
found against a required major version.  The only constraint expressed anywhere
is the engines field above, which npm treats as a WARNING and not an error.

That is recorded because the alternative — leaving a reader to assume a gate
exists — would misplace where the guarantee comes from.  The guarantee comes
from the pinned interpreter in .nvmrc, the CI image, and the observation below;
not from a runtime check.

what the deployment actually observed, on this side
===================================================
The startup region at ../startup/frontend-build.log carries 1 matched line on
this side and no install or build invocation.  That is the expected reading
and not a gap: the artifacts for this side were produced by the committed
historical capture script under ../../historical-frontend/ rather than by a
deployment's startup path, because the base-commit tree predates the runtime
wiring that performs the build at startup.

mirror obligation
=================
The migrated counterpart carries this exact filename — 02-node-env.txt, character
for character — at the mirrored path under migrated/notes/, so that diff -r over
the two trees is mechanical.  A CONTENT difference at this filename is expected
and correct: the two sides state different runtimes, different interpreters and
different measured figures.  A STRUCTURAL difference — this file present on one
side only — is not, and means the mirror has been broken.
