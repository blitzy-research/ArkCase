MIGRATION PATH EXERCISED

    the reinstated XML binding API and its runtime, and the activation framework's
    MIME-type mapping - the reason the reference implementation was mandatory
    rather than the API-only jar

Recorded so that a reader understands why this flow exists at all, and so that a
future difference here can be attributed rather than guessed at.  Every figure
below was re-derived against the tree at the base commit while writing this
record.

THE BINDING EXPOSURE IS THE LARGEST OF ANY REMOVED PLATFORM MODULE.  The package
javax.xml.bind appears in 84 Java files, 137 occurrences, across 21 Maven modules
- 82 files in main source and 2 in test source.  The removal is compensated by
reinstating the API and its runtime as ordinary javax-namespace Maven artifacts in
the aggregator's global dependencies block, which propagates them to all child
modules by inheritance exactly as the platform's own runtime image once did; the
aggregator records that intent in a comment beside the entries.  The consequence
is zero import edits in all 84 files, which is the single largest scope reduction
in the whole migration, and this flow is where it is exercised end to end.  The
coordinates are javax.xml.bind:jaxb-api 2.3.1 at compile scope and
org.glassfish.jaxb:jaxb-runtime 2.3.1 at runtime scope, pinned as properties in
the aggregator.

PROVIDER CONTENTION WAS SETTLED BY EXECUTION, NOT BY REASONING.  A second binding
implementation is already on the classpath, namely the persistence provider's
object-to-XML component, and it can register itself as the provider.  Had it won
resolution, generated XML could have changed shape, which would be a silent
violation of the requirement to preserve response shapes and document formats.
Three classpath shapes were exercised: reference-implementation-only resolved
correctly; the full deployed shape resolved to the same reference implementation
and produced identical XML; the alternative implementation alone failed outright.
Consequently no provider-selection properties file is required anywhere and none
is added - adding one would be a behavioural change dressed as a safety measure.
The operational reading for this flow: if a payload's XML shape ever differs
between baseline and replay, provider resolution is the first thing to suspect.

THE ACTIVATION ARTIFACT CHOICE IS BEHAVIOURAL, NOT COSMETIC, AND R-7 IS WHAT
DECIDED IT.  Two candidates satisfied the same javax.activation API, and the
coordinates gave no hint that the choice mattered.  Reading both jars showed they
are not equivalent: the API-only jar lacks the META-INF/mimetypes.default and
META-INF/mailcap.default resources, while the reference implementation is a strict
superset and ships both.  Five of the six activation-consuming files use MIME-type
mapping, which reads exactly those resources.  The API-only jar would compile
cleanly, deploy cleanly, and then silently resolve MIME types differently -
precisely the class of regression a behaviour-preserving refactor exists to
prevent.  The selected coordinate is com.sun.activation:javax.activation 1.2.0,
and the aggregator records the reasoning beside its exclusions of the competing
providers for that package, so that exactly one provider supplies it.  This is
one of the migration's documented ambiguity resolutions, recorded as the first
entry of the ambiguity-resolutions register.

    HONEST QUALIFICATION.  This flow's MIME rows are the runtime confirmation of
    that decision, and on this side they are unobserved.  The tie-breaker
    therefore rests on the jar-content inspection recorded in that register, not
    on a captured value from this capture.  Saying otherwise would present a
    measurement that was never taken as though it had confirmed a decision.

THE CONTENT REPOSITORY BINDING IS ATOMPUB, NOT THE REMOTE-CALL BINDING.  Confirmed
in the tree at the base commit: the binding type and the endpoint parameter are set
at CmisConfigurationService.java:366-367, and again at
ArkCaseCMISSessionFacade.java:58-59.  It matters twice over: the alternative
binding would have required the platform's removed remote-call module, and this
finding also makes the existing exclusion of that runtime provably safe to retain.
It is corroborated
independently by the census, which finds zero occurrences of javax.xml.ws,
javax.jws, javax.xml.soap and javax.transaction anywhere in the tree - so despite
the requirements naming the remote-call stack, no such artifact is needed and two
of the four removed platform modules are irrelevant to this codebase.

THE REPOSITORY CLIENT VERSION IS DELIBERATELY UNCHANGED, and so is every other
integration client.  The client stays at 1.1.0, pinned as a property in the
aggregator.  Wire behaviour toward the content repository - the same endpoints,
the same formats and the same authentication - is on the preserve list, so any
difference observed here is a genuine regression rather than an expected
consequence of the migration.  Under R-1's contrapositive, bumping the client
would itself have been a rule violation: a change without a demonstrated
incompatibility is out of scope.

DESIGN OBSERVATION WORTH RECORDING.  Every removed platform module this flow
depends on was reinstated as an ordinary Maven dependency, resolved and versioned
like any other.  That is exactly why the migrated runtime needs no relaxation of
the platform's own boundaries to run this flow, and why the JDK access exceptions
register - referred to here by title only - is delivered empty.  It is empty
because the requirement was removed at its source, not because none was looked
for.

NORMALISATION AND REDACTION APPLIED

The producing script writes every byte through a three-stage pipeline - a literal
substitution pass, a pattern redaction pass, and a narrow normalisation pass - and
the pipeline is proven on the host, against the configured credential, before the
first capture is written.  That self-test exists because a malformed expression
makes the whole pass exit before reading its input, which would turn every capture
file into zero bytes while the run still reported success.

CREDENTIAL HANDLING
    The credential is replaced by the fixed placeholder <REDACTED-CREDENTIAL> by
    the literal substitution pass, which is deliberately unconditional and not
    boundary-aware: a credential has no path-component structure and must be
    removed wherever it appears, including inside a longer token, inside a URL and
    inside base-64 material.  Its value is never written to any capture; only its
    source is recorded, in the run posture archived at env/toolchain.txt, as
    credential-source: environment with credential-value-recorded: never.

SESSION HANDLING
    Only the session's existence is captured.  The observed-session-cookie row of
    the reachability probe reads absent.  The response header that would carry a
    session identifier is REDACTED by the pattern pass rather than normalised by
    the cosmetic pass, because a live session identifier is credential-equivalent.

UPSTREAM CREDENTIAL CHECK, performed because this flow talks to an upstream
repository as well as to the application
    The captured body was checked for an upstream repository credential in
    addition to the application credential.  Result: none present.  Two
    independent reasons, both verifiable from the capture: the reachability probe
    against the upstream host is anonymous by design and sends no credential at
    all, and the probe received no response - zero body bytes and no response
    headers - so there was nothing that could have echoed one back.  A search of
    all three flow-3 capture files for the documented administrator credential
    returns zero occurrences, as does a search for authorization, proxy
    authorization, cookie, session-identifier, bearer, basic, digest, password,
    secret, token and ticket material.  The placeholder token itself also appears
    zero times, which is consistent rather than surprising: nothing arrived that
    would have required substituting.
