7. WHY THIS MODULE AND THIS CLASS ARE ARCHIVED.

  7a. A clean control, and the asymmetry is the point. At the base commit this module's build file
      declares the removed mocking framework twice, version-less and root-managed, at lines 235 to
      238 and 240 to 243. The module is one of the twelve build files declaring that framework, but
      it is NOT one of the six whose test classes are rewritten, and NOT one of the six that gain
      an inline mocking dependency. Verified: not one of the eleven test files in this module
      references that framework, so the removal is a pure build-file deletion with zero source
      impact. That makes these ten reports a clean control. Identical case outcomes are expected on
      the migrated side, so any difference isolates the build file edit or the runtime rather than a
      test rewrite. No inline mocking dependency was added to this module, and neither the mail
      library nor the search client was upgraded; any of those would be a change without a reason.
      On the removal itself: the framework's final release fails on the target runtime with an
      inaccessible object error on a core JDK method, and that final release is the project's last,
      so there is no version to upgrade to and removal is forced. Removal is also the mechanism
      that lifts its hard pins on an older mocking core release and an older unit test framework
      release, which is what allows the retained mocking library to advance to a release whose
      inline mock maker can instrument the newer class file version. It additionally cascades away
      three transitive constraint exclusion blocks in the root aggregator that existed only to
      constrain it; the constrained library appears nowhere else in any build file.
  7b. EasyMock exposure. Nine of this module's ten unit test classes extend the EasyMock support
      base class, and this class is one of them, at line 49. The module declares the library
      version-less at base commit lines 230 to 233, root-managed, so the floor advance reaches all
      nine with zero child build file version edits. That floor advance has the widest build file
      footprint of any change in the migration: the installed release and the intermediate one fail
      identically on the target runtime with an inaccessible object error raised from the library's
      own class proxy factory, and only a much later release succeeds. This report, produced under
      the old release, is part of the before-picture for that upgrade. Every assertion is
      unmodified; this class's four equality assertions are exactly as they were at the base commit.
  7c. THE SEARCH INDEX DOCUMENT PROJECTION. This is what makes this particular report load bearing,
      and it was confirmed by reading the test body rather than inferred from the class name. The
      single test exercises the notification to search transformer, calling its advanced search
      projection and asserting four fields of the returned advanced search document: the state and
      the parseable title, both read back out of the additional properties map under their constant
      keys, and the lower-cased creator and modifier fields. That places this report on the search
      wire surface, where the preservation directive requires the same endpoints, formats and
      authentication toward the external search service, and where the search client's own version
      is deliberately unchanged because a bump would be a change without a reason. A divergence in
      this report would therefore mean the indexed document shape changed, which is a serialised
      field level regression of exactly the kind this archive exists to catch. The corresponding end
      to end search round trip is exercised separately by the scripted smoke flows; this report is
      the unit level guard on the same contract.
  7d. The activation linkage, stated precisely and not overstated. It is at the collaborator level,
      not by direct import. Verified: this module has zero direct occurrences of the activation,
      mail, XML binding and annotation packages across both main and test source. The linkage runs
      through its dependencies on the SMTP email module, declared at base commit line 110, and the
      email module at line 116. The SMTP email module owns the input stream data source class, whose
      lines 33 and 34 import the activation data source and MIME type map types. The sender unit
      tests in this module mock their mail collaborator. The only defensible claim, and the one made
      here, is that these reports evidence that the delegation contract, the template selection and
      this class's document projection are unchanged. They do NOT directly execute MIME mapping, and
      this class in particular touches no mail type at all.
      Why the activation artifact choice still matters. It is behavioural, not cosmetic. The API
      only jar was verified to lack the MIME and mailcap default resources that the reference
      implementation ships, and five of the six activation-consuming files use MIME type mapping,
      verified exhaustively across all eight occurrences in six files, where only one consumer uses
      a data handler rather than the MIME type map. Choosing the API only jar would compile, deploy,
      and then silently resolve MIME types differently. The tie-breaker rule selected the reference
      implementation on exactly that evidence. The activation framework previously arrived
      transitively via the mail library and is now declared explicitly, which is an addition and not
      a substitution.
      Namespace invariance is absolute here. The reinstated activation framework, the XML binding
      API and the annotation API are all javax namespace artifacts, declared once in the root
      aggregator's global dependency block so that they propagate by inheritance to all 144 child
      modules. Every javax import stays as it is; the platform removal is compensated by ADDING
      javax namespace artifacts, never by rewriting source. No successor namespace token appears
      anywhere in this folder or in this note.

10a. The retry library is an application library, NOT test retry tooling. The rerun count setting
     appears in zero of the reactor's 145 build files and no retry plugin is declared anywhere, so a
     baseline failure is real and reproducible and fail-fast is safe. The reactor does contain a
     Spring retry APPLICATION library, a root version property consumed by exactly three child
     modules, with nothing whatsoever to do with test reruns. Both counts were verified by searching
     the tree rather than assumed. This is stated explicitly because a reviewer who searches for the
     word "retry" would otherwise be at risk of concluding the archive is unsound. The risk of that
     inference is highest in precisely this module, where delivery retry semantics make it tempting.

10b. Coverage exclusions are NOT test exclusions. The root coverage plugin configuration carries
     eight exclusion globs which exclude package globs from coverage MEASUREMENT only. No test is
     disabled by them, and none of the eight matches this module's package; both the count of eight
     and the absence of a match were verified at the base commit. Relatedly and bindingly: the
     coverage agent's preparation execution communicates with the test runner through the default
     argument line property export, and its check goal evaluates a line covered ratio rule against a
     configured minimum of 0.02. The newly added unit test runner declaration must therefore NOT set
     a literal argument line element; doing so silently severs instrumentation and leaves the check
     goal evaluating an empty data set, which is a false pass. Instrumentation must be verifiably
     live. Verified at the base commit: the coverage plugin block contains no argument line element
     at all.

     The module path segment is the module directory name only, never the reactor path and never a

12. FORBIDDEN DIRECTORY NAMES: A SILENT FAILURE TRAP THAT WAS TESTED, NOT ASSUMED.

The repository ignore file uses bare, leading-slash-free patterns, which git matches at any depth.
The build output, executables, partition descriptor, message broker data, log and builds directory
names are all such patterns. A negative control was run before anything was written: candidate paths
placed under each of those six directory names inside this evidence tree were every one reported
ignored, each naming the exact ignore file line responsible, while the two paths actually used here,
this report and this note, were both reported not ignored. Such a directory would be silently
uncommitted, so every local check would pass while the committed deliverable was empty, failing the
completion condition invisibly. The sanctioned directory names in this tree are the startup,
surefire, artifacts, environment and notes folders. A log file extension is safe; the hazard is the
directory name.

The report folder is kept flat and contains no subdirectory of any name.
