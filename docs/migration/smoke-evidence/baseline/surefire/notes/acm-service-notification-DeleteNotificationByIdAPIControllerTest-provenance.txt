     appears in zero of the reactor's 145 build files and no retry plugin is declared anywhere, so a
     baseline failure is real and reproducible and fail-fast is safe. The reactor does contain a
     Spring retry APPLICATION library, a root version property with a managed entry, consumed by
     exactly three child modules, none of which is this one, and it has nothing whatsoever to do
     with test reruns. This is stated explicitly because a reviewer who searches for the word
     "retry" would otherwise be at risk of concluding the archive is unsound. The risk of that
     inference is highest in precisely this module, where delivery retry semantics make it tempting.
     There is an additional trap specific to this report: the coordinate belongs to the Spring
     ecosystem and this is a Spring context test, which makes the mistaken association doubly easy
     to draw. It is still mistaken, and this module does not consume that library.

10b. Coverage exclusions are NOT test exclusions. The root coverage plugin configuration carries
     eight exclusion globs which exclude package globs from coverage MEASUREMENT only. No test is
     disabled by them, and none of the eight matches this module's package; that was checked glob by
     glob against the base commit configuration. Relatedly and bindingly: the coverage agent's
     preparation execution declares an output data file but no property name, so it hands its
     configuration to the test runner through the default argument line property export, and its
     check goal evaluates a line covered ratio rule against a configured minimum of 0.02. The newly
     added unit test runner declaration must therefore NOT set a literal argument line element;
     doing so silently severs instrumentation and leaves the check goal evaluating an empty data
     set, which is a false pass. Instrumentation must be verifiably live. Verified at the base
     commit: the root build file contains no argument line element at all.
     INSTRUMENTATION WAS THEN VERIFIED LIVE BY MEASUREMENT, NOT BY INSPECTION. In the working tree
     the unit test runner declaration has since been added under plugin management, and it was read
     directly: it pins a version and carries no argument line element and no exclusions entry, so
     the coverage agent's default property export is intact and no test is excluded. The full suite
     run described at section 3g then proved it end to end. The build log shows the coverage agent's
     preparation goal setting the argument line to a Java agent invocation with the agent jar, the
     execution data file destination and the eight measurement exclusion globs; the report goal
     loading a non-empty execution data file; and the check goal reporting that all coverage checks
     have been met against a real data set. That is the opposite of the false pass this paragraph
     warns about, and it is now a measurement rather than an expectation. Note in passing that the
     only occurrence of the argument line term in the working tree's root build file is inside the
     explanatory comment above the runner declaration, which also states the citation rule this
     archive exists to satisfy: no exclusions entry without a backing row in the baseline test
     failures register.


11. HOW THIS ARCHIVE MUST AND MUST NOT BE COMPARED.

11a. It is NOT byte-identical comparable. Unlike the five frontend artifacts, whose gate genuinely
     is byte identity, report XML unavoidably carries timing, hostname and timestamp attributes and
     a system property dump. Archived in its entirety governs content completeness, not byte
     identity. Judge the comparison on case presence, case outcome and failure message content.
11b. A reinforcement of that point, verified in this module: even a genuine capture could not be
     byte-stable across runs, because the templating engine test prints a rendered template that
     interpolates the current instant twice, once as a date and once as a local date and time, so
     that sibling report's standard output carries wall clock content by construction.
11c. The migrated side folder for this module must mirror this layout exactly, with all ten
     filenames identical, so that a recursive directory diff maps report to report. The migrated
     tree holds no folder for this module yet, which is why this layout is the reference shape for
     it. Two other modules' migrated folders already exist, so the pattern is established.
11d. The citable full form used by the baseline test failures register, which cites evidence files
     by path and whose own validation states that a citation to a non-existent evidence file fails
     its standard, is:
       docs/migration/smoke-evidence/baseline/surefire/<module>/TEST-<fully-qualified-class-name>.xml
     The module path segment is the module directory name only, never the reactor path and never a
     path including a build output directory. Relocation into this folder is mandatory for exactly
     that reason: the repository's ignore file carries a bare build output directory pattern that
     git matches at any depth, so a report left where the test runner wrote it would be invisible to
     version control and the citation contract would break silently.
11e. The single integration test in this module correctly has NO report here. The unit test goal
     stops at the test phase, whereas the integration test runner's two goals are declared with no
     explicit phase element and therefore take their default phases, both of which fall after the
     test phase. An absent integration test is neither a pass nor a failure, and it may never be
     used to justify a test exclusion.
11g. ELEMENT ORDER IS NOT A COMPARISON AXIS, and this is now measured rather than assumed. The
     cross-check of section 3g showed a runner emitting this class's two cases in the opposite order
     to their declaration, because the JUnit 4 default method sorter orders by a deterministic hash
     of the method name. A recursive directory diff of the two trees will therefore report an
     ordering difference for this report even when nothing behavioural has changed. Reconcile on
     case presence and case outcome, matching cases by name rather than by position. An ordering
     difference is not a finding; a missing case, an added case, or a changed outcome is.
11f. This report was structurally diffed against this folder's foundational report before
     publication. The XML declaration, the comment's paragraph sequence and wording, the suite
     element's attribute names and their order, the two-space indentation, the self-closing case
     element form and the closing tag all match. The differences are exactly the intended ones: the
     suite name and both classnames, the case count, the case list, the source path and line numbers
     inside the comment, and the one refinement logged at section 6d.


12. FORBIDDEN DIRECTORY NAMES: A SILENT FAILURE TRAP THAT WAS TESTED, NOT ASSUMED.

The repository ignore file uses bare, leading-slash-free patterns, which git matches at any depth.
The build output, executables, partition descriptor, message broker data, log and builds directory
names are all such patterns, at ignore file lines 6, 7, 24, 25, 26 and 40 respectively. A negative
control was run before anything was written: candidate paths placed under each of those six
directory names inside this evidence tree were reported ignored, each naming the exact ignore file
line, while the report path and this note's path were both reported not ignored. Such a directory
would be silently uncommitted, so every local check would pass while the committed deliverable was
empty, failing the completion condition invisibly. The build output directory name is the acute risk
here precisely because that is where a real test runner report originates. The sanctioned directory
names in this tree are the startup, surefire, artifacts, environment and notes folders. A log file
extension is safe; the hazard is the directory name.

The report folder is kept flat and contains no subdirectory of any name. In particular it contains
no directory named after either segment of the class's web api package; the package is carried in
the filename.


13. MARKDOWN IS EXCLUDED FROM THIS TREE AT EVERY DEPTH.

The documentation site configuration sets its source directory to the documentation folder, so a
non-Markdown file placed there is copied as a silent static asset, whereas a Markdown file becomes a
page absent from the navigation, which a strict site build can warn on. A recursive search for
Markdown files under this evidence tree returns nothing. Nothing in this evidence tree appears in the
documentation site configuration, and a search of that configuration for this documentation
subtree's path returns zero. This note uses the permitted plain text extension and contains no
heading marker at a line start, no table row at a line start, no fenced block and no bullet at a
line start; the same per-line checks were applied to the report.

One observation recorded rather than acted on: at the time this note was written the site
configuration's navigation carried three entries and none of them referenced the migration folder,
whereas the migration plan provides for six navigation entries pointing at Markdown deliverables
that sit directly in the migration folder rather than in this evidence tree. Only one of those
deliverables exists on this branch so far. The navigation edit belongs to the file that owns it and
was deliberately not made from here. What matters for this artifact is unchanged and satisfied: this
evidence tree is referenced nowhere in the site configuration, so nothing here can become an orphan
page.
