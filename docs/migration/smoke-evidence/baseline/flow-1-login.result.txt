NORMALISATION-REDACTION APPLIED:
  pipeline: a plain stream-editor and pattern-scanner pipeline, in
    three passes - literal substitution, credential patterns, then
    inter-run volatility.  No JSON processor, no scripting language
    interpreter and no installed package is involved (R-1).
  stripped, literal pass: the supplied administrator credential; the
    canonical capture root and the output directory; the repository
    root; the home directory; the scratch directory.  Every absolute
    filesystem path is therefore replaced, so the record does not
    depend on where it was taken.
  stripped, credential pass: authorisation and proxy-authorisation
    headers; the request Cookie and the response Set-Cookie headers,
    session cookie values among them; cross-site-request-forgery and
    application ticket headers; scheme-prefixed authorisation material;
    any field whose
    name denotes a password, secret, ticket or key; a user name in a
    transport configuration line; a credential embedded in a URL; the
    servlet session identifier.
  stripped, volatility pass: date-and-time values; the response
    headers carrying wall-clock time and cache validity, that is the
    Date, Last-Modified and Expires headers and the ETag validator;
    authentication-challenge parameters; generated
    universally-unique identifiers; generated
    request and millisecond instants; surrogate database keys assigned
    by the process engine or the message broker, matched by FIELD NAME
    so a bare business number can never be caught by them - namely the
    PROCESS-INSTANCE identifier, the EXECUTION identifier, the TASK
    identifier and the DEPLOYMENT identifier, plus the version and
    sequence components of the VERSION-SUFFIXED PROCESS-DEFINITION
    identifier, whose leading key is kept precisely because the key is
    behaviour while the two numeric components are not; the session
    identifier; absolute filesystem paths; and the engine-reported
    query and elapsed durations.
  DELIBERATELY PRESERVED, verbatim and untouched by every expression
    above: case and complaint numbers, queue names, task and process
    names, MIME types, result counts and result ordering,
    content-derived cache-busting hashes and the artifact digests
    themselves.  A user identity that is part of an observed routing or
    assignment decision is PRESERVED rather than redacted: it is
    behaviour, not a credential.
  preserved for this flow: the authorization result IN FULL - every role, granted authority and privilege name, in the order the application returned them - together with the authenticated principal user name, the anonymous-denial status and the response content types.  The credential itself is REDACTED to a fixed placeholder wherever a command line, a request body, a request or response header or an error message would otherwise have carried it, and the redactor is proven against that exact credential before the first capture file is opened; a live session identifier is redacted too, because it is credential-equivalent for as long as it lives, and only its PRESENCE or ABSENCE is recorded
  why both halves are written down: the pipeline is narrow on purpose.
    Over-normalising would empty this record while leaving it looking
    healthy, so what survives is stated beside what does not.

GOVERNING RULES AND PROVENANCE
------------------------------
Both provenance facts, stated together, because either one alone
misleads.  There is NO on-disk user rules document for this project:
the rules facility was queried and returned "No user rules provided."
on every call, and that read was complete rather than partial.  Rules
are nonetheless present and binding: the migration requirements embed
an explicit numbered block of seven rules that governs this work in
full, exactly as an external rules document would, plus seven
transformation rules.  Reporting only the first fact would imply that
enterprise best practice is the sole standard here, which is wrong
because fourteen specific constraints apply; reporting only the second
would misrepresent where the rules came from.  The identifiers R-1 to
R-7 and R-T1 to R-T7 are the migration plan's own navigational
convention, not quoted rule titles.  No rule has been invented and
none has been softened.

R-7, BASELINE BEHAVIOUR IS THE TIE-BREAKER - the rule that creates
this record.  Quoted with its one substitution disclosed rather than
made silently:

    "The application's observed behavior at the base commit on JDK 8 is
    the tie-breaker for any ambiguity, and each resolution must be
    documented."

    Editorial note, which must accompany the quote wherever it is
    reproduced: the rule's own text names the older runtime with a
    phrase this documentation tree's wording gate forbids.  The
    substitution changes no meaning and is disclosed here rather than
    applied quietly.

R-2 AND R-T3 ARE PARAPHRASED HERE, NEVER QUOTED, AND THAT IS
DELIBERATE.  The text of each names a module-access JVM argument
literally, and this documentation tree is subject to a recursive audit
that requires zero such literals, so quoting either verbatim would
itself introduce the token the audit forbids.  R-2 requires that
production launch configuration not depend on JDK internal access -
that is, on a module-access JVM argument that opens or exports an
otherwise-encapsulated JDK package to the unnamed module - except
where a pinned third-party dependency documentedly requires it, and
that every such exception be documented.  Observed: the production
launch configuration declares no such argument, so the JDK access
exceptions register is delivered empty with a positive statement that
none are required.  That register is referred to here BY TITLE ONLY,
because its filename embeds the very token the audit forbids.
THE REGISTER IS EARNED EMPTY, NOT MERELY EMPTY, and the difference is
the whole of R-2: an empty register that was never populated and one
that came out empty because the requirement was measured and then
removed read identically, and only the second complies.  The audited
configuration is the container launch block recorded at the base commit
in README.md:L111-L127 and duplicated in docs/setup.md, and it declares
no such argument either before or after the migration.  Every strong
encapsulation failure encountered anywhere in this migration was inside
a TEST library, and each was resolved at its source by upgrading or
removing that library rather than by opening a JDK package to the
application - which is R-T3's remedy applied, not avoided.  R-T3
requires exactly that: a dependency failing under strong encapsulation
is upgraded or replaced rather than accommodated by opening a JDK
package - fix the library, do not open the module.

R-5, no disabling of failing tests, verbatim: "Failing tests must not
be disabled, and exclusions are limited to failures already present at
baseline."  Applied here as the absence rule: no flow may be silently
skipped, and zero test exclusions arise from this folder.

R-6, document discovered bugs rather than fixing them, verbatim:
"Pre-existing bugs discovered during the work are documented rather
than fixed, unless one blocks a validation item."  Applied here:
whatever was observed is recorded as observed.  The change set's escape
clause is invoked exactly twice and NEITHER invocation is in this
folder.

R-T7, evidence over exit codes, verbatim: "Validation asserts on
produced artifacts and captured output, never on process exit status
alone.  This is mandatory rather than stylistic because Gruntfile.js
sets grunt.option('force', true), which masks task failures and lets a
broken build exit zero."  Repository proof at the base commit:
Gruntfile.js:143 carries the comment that grunt is made to default to
force so as not to break the project, and Gruntfile.js:144 sets it.
Two pre-existing defects are masked by exactly that setting -
Gruntfile.js:379 registers a synchronisation alias against a
concurrent target that the block at Gruntfile.js:90-98 never declares,
and Gruntfile.js:372 registers a lint alias naming a linter that has
no configuration block anywhere in the file.  Neither alias appears in
the default task graph at Gruntfile.js:376, so neither affects the
produced artifacts, but both prove that a broken build can exit zero.

R-1, justified changes, acting as a scope fence, verbatim: "A change
without a reason is out of scope."  No tool was installed to produce
this record.

R-4 as a wording constraint: the outgoing package manager is named
nowhere in this record, and nothing here presents it as a prerequisite
or a recommendation.  R-T1, namespace invariance: nothing here
references the successor namespace, a newer framework generation, a
typed JavaScript dialect or a module bundler.  All are excluded from
