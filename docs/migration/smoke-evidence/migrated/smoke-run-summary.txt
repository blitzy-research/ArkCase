RULES PROVENANCE — both facts, stated together
================================================================================

The project rules facility reports, verbatim: "No user rules provided."  There
is no on-disk rules document for this project, so there is no external
full-text source to defer to.  Rules are NONETHELESS present and binding: the
requirements embed a numbered block of SEVEN rules that govern this work in
full, exactly as an external rules document would, alongside seven
transformation rules that are the operational form of the preserve and exclude
directives.  Recording only the first fact would imply that general best
practice is the sole standard here, which is wrong; recording only the second
would misrepresent where the rules came from.  Both are therefore stated.

The identifiers R-1 through R-7 and R-T1 through R-T7, and the short labels
used with them, are the migration plan s OWN navigational convention.  The
requirements list the rules as numbered items without names.  The labels exist
so a decision can be traced back to the constraint that produced it; they are
not quoted titles.  No rule has been invented and none has been softened.

R-7, quoted with its one disclosed substitution: "The application s observed
behavior at the base commit on JDK 8 is the tie-breaker for any ambiguity, and
each resolution must be documented."  Editorial note, made openly rather than
silently: the rule s own text names the older runtime with a two-word phrase
that this evidence tree s wording gate forbids, so the equivalent form JDK 8
is used in its place.  The substitution changes no meaning — it names the same
runtime — and it is disclosed here so that the quotation is not mistaken for
the rule s literal wording.

R-T7, and why this file carries observed values instead of a verdict: no
assertion anywhere in this capture is derived from a subprocess exit status.
The repository proves why that discipline is necessary rather than stylistic.
The frontend build configuration at Gruntfile.js:L143 carries the comment that
grunt is made to default to force in order not to break the project, and
Gruntfile.js:L144 is the statement that does it.  With forced execution a task
can fail while the process still exits zero, so a broken build reports success.
Evidence is therefore the produced artefact and the captured output, never the
exit code — here, in every flow entry below, and in every companion capture.

R-6, noted in passing because an index is a place where a reader may expect
defects to be resolved: nothing in this folder is explained away or repaired.
R-6 s escape clause, which permits fixing a pre-existing condition only when
it blocks a validation item, is invoked EXACTLY TWICE in the whole change set,
and NEITHER invocation is in this folder.  Both are frontend conditions and
both were performed only because they block the fresh-checkout build gate.
Nine further registered defects remain deliberately unfixed and are enumerated
in the pre-existing defects register named at the close of this file.

R-4, where the frontend is concerned: the asset pipeline ran on Node 20
through the UNCHANGED task graph declared at Gruntfile.js:L376.  The task
graph, the five artefact names and the asset layout are contract and are not
modified.  Grunt and its command-line interface were verified to install AND
execute on Node 20, so both are deliberately retained rather than replaced;
modernising a tool that runs correctly would be a change with no compatibility
justification, which R-1 forbids as firmly as it forbids an unjustified
omission.  The install step this capture exercised is the lockfile-respecting
clean install on npm 10, recorded in startup/frontend-build.log.
