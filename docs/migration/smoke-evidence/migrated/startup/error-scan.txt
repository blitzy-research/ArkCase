COMPARISON KEY — HOW TWO LINES ARE JUDGED TO DESCRIBE THE SAME BEHAVIOUR
  Published so a reader can re-derive a key rather than trust one.  Two lines
  describe the same behaviour when they differ only in scheduling and identity
  detail, so the key removes: terminal colour sequences; the leading timestamp in
  either of the two forms this log carries; leading indentation on stack frames;
  the runtime build tag appended to a frame; pool thread and worker ordinals for
  every executor in this application; route-assigned exchange and message
  identifiers; universally-unique identifiers; millisecond epochs; object identity
  hashes; generated lambda class names and addresses; persistence session
  identifiers; the line number inside a stack frame; measured durations; and
  absolute paths, to <PATH>.
  It removes NOTHING behaviour-bearing: the severity marker, the logger name, the
  exception type, the whole message text, the result code, and the object or path
  the message names all survive verbatim.
  This rule exists because a first attempt without it reported two shapes as
  present on one side only, in both directions, purely because a thread pool had
  handed the work to a different worker ordinal.
  Every line EXCEPT an error- or severe-severity line is capped at 200 characters
  and marked <TRUNCATED-AT-200>.  The severity classes are exempt deliberately:
  their message text is what a disposition is matched against.
  The scan is line-oriented, so a stack trace contributes only those of its own
  lines that themselves carry a signature — its header, its Caused by lines, and
  any frame whose class name carries one.  No frame is followed and nothing
  matched is dropped.
