WHAT THIS FILE IS, AND WHY IT IS A FILE OF ITS OWN
  This is review annotation on the captured startup region beside it,
  startup/workflow-engine-init.log.  Not one line here is captured output: every
  log line, every deployment line and every count belongs to that file, and
  nothing here contributes to it.
  It is a SEPARATE file because the region file is producer-written and this is
  not.  For a time this annotation was appended below the end-of-region delimiter
  inside the region file itself, which had two consequences, both real.  The
  region file stopped being reproducible: smoke-checks.sh writes that file as a
  fixed header followed by the matched window lines and nothing else, so a
  re-capture would have silently discarded 427 lines of analysis.  And the two
  captures stopped being comparable at the file level - the pre-migration side's
  copy of the region file is 60 lines, exactly what the producer emits, while the
  migrated side's had grown to 487.
  Separating them fixes both.  The region file is now byte-for-byte what the
  producer writes on either side, and this annotation is declared in the capture
  manifest as an AUTHORED COMPANION: a path the producer never writes and, having
  been named, never destroys - a staged run carries it forward from the tree it
  replaces and reports that it did.  See notes/manifest.txt.
  Where this file cites the region file, it cites the line numbers of the region
  file as the producer writes it, which are unchanged by the separation because
  the annotation only ever sat after the region ended.

  This file mirrors its pre-migration counterpart mechanically: same filename,
  same header field set, same field order, same two region delimiters, each
  appearing exactly once.  A field-name comparison between the two files returns
  no difference, and that is the property that lets the whole capture directory be
  compared with a recursive diff instead of by reading.

  for this file also proposed.  The two could not both be satisfied, and the
  disagreement is recorded here rather than resolved silently.  The proposed

  it described the counterpart as already carrying three of them.  The

  and its delimiters are named region rather than capture.  Because the mirror

  mirror won and the substantive content the schema was meant to carry is

  Every line of this annotation is written so that none of it parses as a header
  field.  That is deliberate and it is load-bearing twice over: it keeps the
  field-name comparison against the counterpart returning no difference, and it
  keeps the capture script's own readers intact, since they either read a single
  named header field or read strictly between the two region delimiters.  Nothing
  below this heading can perturb either.

WHAT THIS REGION DOES NOT OBSERVE, AND WHAT THE CAPTURE NOW DOES
  This region still carries no definition total of its own.  The engine's own
  repository is never queried for one anywhere in this window, so nothing in the
  region below adjudicates how many definitions the engine holds, and no line in it
  may be read as doing so.
  The CAPTURE, however, now carries that observation, taken from the engine itself
  rather than from any log:
  DEFINITIONS EXPECTED, FROM THE CORPUS                36
  DEFINITIONS LOADED, ENGINE REPOSITORY TOTAL          9, OBSERVED
  The second figure was read from the process engine's own definition table, the
  table the engine writes one row into per deployed definition, by a query the
  evidence producer was configured with for this capture; it returned the bare
  integer 9 and the producer refuses anything that is not a bare integer.  The
  figure is published in the flow-7 record as DEFINITIONS_LOADED and is repeated
  here only because this file is the artefact that adjudicates it.
  Three properties of that measurement are stated so it is not over-read.
  First, it is an observation of the ENGINE, not of this region.  Region and engine
  are different sources and this file keeps them apart; an earlier generation of
  this capture recorded UNOBSERVED here precisely because no engine-side source had
  been consulted, and the honest correction is to name the new source rather than to
  claim the region had carried the figure all along.
  Second, 9 OBSERVED against 36 EXPECTED is a GAP and is reported as one.  The
  expected figure counts definition files in the repository; the observed figure
  counts what this deployment's engine holds.  They answer different questions, and
  nothing here asserts that the remaining 27 were loaded, that they should have been,
  or that their absence is a migration effect.  The region is consistent with the
  smaller number: it shows eight definitions reconciled from the classpath and all
  eight skipped because they already existed, so this boot deployed none and the
  engine's total was established by earlier boots and by the configuration those
  boots ran under.
  Third, the conflation this file was written to prevent still stands.  A count of
  region lines that merely mention a definition file is NOT a count of definitions.
  An earlier generation of the flow record published 34 on exactly that basis; that
  figure is withdrawn, the producer no longer has that fallback, and with no engine
  query configured it now reports a sentinel and the criterion resting on it is
  treated as unmet rather than satisfied by a number that measured something else.
  This annotation therefore reports the reconciliation figure of eight, the
  newly-deployed figure of zero and the engine repository total of nine, all three
  observed, and asserts no other definition count.
  ONE COMPARISON ROW IS NOT LIKE FOR LIKE, and saying so is the whole point of this
  paragraph.  The cross-capture comparison beside these directories reports the row
  DEFINITIONS_LOADED as 34 on the pre-migration side against 9 on this side, and a
  reader scanning it would reasonably take that as a drop of 25 definitions.  It is
  not: 34 is a count of log lines containing a definition-file token, produced by the
  withdrawn basis described above, and 9 is a count of rows in the engine's own
  definition table.  The two figures measure different things, so their difference is
  not a quantity of anything.  The pre-migration capture cannot be re-taken - it was
  recorded on the pre-migration runtime at the base commit, which is the one thing a
  later run cannot reproduce - so the row is left exactly as the comparison computes
  it and the asymmetry is disclosed here rather than repaired by editing a capture.
  Anyone reading that row must read this paragraph with it.

RISK CLASSIFICATION
  RESIDUAL UNVERIFIED RISK, ASSIGNED TO THIS GATE, PARTLY DISCHARGED AND NOT CLEARED.
  The wording is deliberate and is not softened, and the two halves are separated so
  that neither is read as the other.  DISCHARGED: the engine was observed, on the
  migrated runtime, to hold definitions in its own records - nine of them - and to
  reconcile its classpath corpus without error.  NOT CLEARED: no business-process task
  attributable to a run of this capture was ever observed, so the engine has not been
  shown to EXECUTE a definition on this runtime, and executing one is the behaviour the
  risk is about.  An engine that starts and holds definitions is a weaker statement than
  an engine that runs them, and this file makes the weaker statement only.  The workflow engine is the
  oldest load-bearing component in the reactor, a 2014-vintage release, and it
  could not be bootstrapped for testing in isolation without a database, so it was
  assigned to the deployment and smoke gates rather than declared safe.  Nothing
  in this capture may be read as verifying it, and nothing below reclassifies it.
  Its version is deliberately unchanged.  No compatibility failure was
  demonstrated for it, and a version change without a demonstrated compatibility
  reason is out of scope, so bumping the oldest load-bearing component in the
  reactor would itself be a rule violation and a far larger behavioural risk than
  the one this gate manages.  The honest corollary is stated with it, because the
  first half alone would flatter the result: not having demonstrated a failure is
  not the same as having demonstrated safety.  That gap is exactly what the word
  residual denotes, and it is why the classification stays not cleared even though
  every observed value on this side matches the pre-migration side.

WHY EIGHT IS NOT A SHORTFALL AGAINST THIRTY-SIX
  This is the explanation the previous section is owed, and it is established
  rather than assumed, because presenting a mismatch as a failure without
  establishing that the missing definitions were ever expected to deploy would be
  the more serious error.
  The startup deployer does not scan the corpus.  It scans five classpath name
  patterns, and the region above records them verbatim: definition resources whose
  names begin with acm, ArkCase, DefaultComplaint, Corrective or Media.  Exactly
  nine of the 36 corpus basenames match those five patterns.  The ninth is a
  test-source copy of the default complaint workflow belonging to the workflow
  engine configuration module, which is not on a deployed runtime classpath.
  Eight is therefore the complete and expected set for this mechanism, and the
  observed eight is a match rather than a deficit.
  The remaining 27 main-source definitions are not reachable by this scan at all.
  They are administered through the engine's own definition service rather than by
  the startup classpath scan, so their absence from this region is by design.
  This is an expectation about mechanism, derived from the scan patterns the region
  records and from the corpus census above.  It is not an observation that those 27
  were loaded by some other route; this capture observed no such thing.

THE STARTUP-WINDOW TIMING TRAP, AND HOW IT WAS AVOIDED
  The engine reconciles its definitions during the first-startup window, and the
  repository documents that window twice.  The deployment step in README.md:L175
  states that the first startup will take 5 - 10 minutes, and docs/setup.md:L133
  repeats it in the same terms.  Both anchors are cited because both exist and a
  single citation would look like a transcription rather than a check.
  Those two line numbers were re-derived for this file rather than copied from the
  brief, which cited README.md:L141 and docs/setup.md:L108.  Both of those anchors
  are now stale: this migration updates both documents, so the line numbers moved.
  Recording the correction here keeps the citation checkable instead of merely
  plausible.
  Why the trap matters: a capture cut before that window closes yields a definition
  figure that measures capture timing rather than engine behaviour, and it would be
  indistinguishable from a genuine shortfall.  This capture spans the whole window.
  The evidence for that claim is structural rather than promised.  The window was
  taken as one bounded byte range over a source containing exactly one boot, the
  header records capture-truncated no, and the final line of the region is the
  container's own deployment-finished line for the application archive, so the
  region runs to the end of deployment rather than stopping inside it.
  How the window was determined to have closed: the container's startup-completed
  line, which is the last event of the boot.  That observation belongs to the
  readiness region and is not duplicated here; it is recorded in
  readiness-poll.log in this same startup directory, which was mined from the very
  same single window as this region and carries the identical window digest.
  Cross-referenced by filename, not reproduced.
  The measured deployment on this side was faster than the documented 5 to 10
  minute range.  That is not a finding and is not treated as one: the criterion is
  that the capture spans to the startup-completed line, not that it lasted a
  particular time.  Elapsed figures are inter-run noise and the counterpart's
  differ too.

THREE FINDINGS THAT BOUND THE CONCERN, AND DO NOT CLEAR IT
  Stated first, because it governs all three: these findings BOUND the residual
  concern.  They do not eliminate it, and no combination of them discharges this
  gate.  The engine still could not be executed before deployment, which is why the
  classification above stays not cleared.  Findings one to three are expectations
  derived from configuration and dependency analysis, not observations from this
  capture.
  FINDING 1, and it is the one that has to be stated carefully, because the
  inference originally drawn from it is withdrawn as false.  The two measurements
  are true and were re-derived over this tree: the definition corpus declares zero
  script-task elements and zero script-format attributes.  The inference drawn from
  those two zeros, that the engine therefore never requests a scripting engine, is
  FALSE and is withdrawn here rather than quietly dropped.  The engine also reaches
  a scripting engine through a task listener, which a census of script tasks and
  script formats cannot see.  One main-source definition, the personnel security
  background investigation definition version 11, declares seven complete-event
  script task listeners, at lines 46, 66, 86, 108, 119, 142 and 153, each carrying
  a language field whose value is javascript, at lines 48, 68, 88, 110, 121, 144
  and 155.  The platform's removal of its bundled scripting engine therefore does
  reach the engine along that path.  That is a platform-removal matter rather than
  an engine-version matter, and the lesson is worth stating plainly: a
  pattern-based census over configuration is only as good as its knowledge of every
  element that can reach the capability being censused.  The repository itself
  records the same conclusion, in the comment block at pom.xml:L203-L218, which
  registers the one main definition resource whose task listeners request the
  engine.
  FINDING 2.  The engine's persistence layer reflects over the application's own
  domain classes, through ordinary unrestricted reflection, rather than over
  platform internals.  Strong encapsulation does not bite on that path.
  FINDING 3.  It reads no class bytes and touches no encapsulated platform
  package.  This is also why the register of production launch-configuration
  exceptions for encapsulated-package access is earned empty rather than assumed
  empty: no package needs opening on this engine's behalf.  That register is
  referred to here BY TITLE ONLY, and never by filename or path, because its
  filename embeds a token this evidence tree carries nowhere at any depth.
  Findings 2 and 3 remain sound.  Finding 1 survives only as its two measurements;
  its inference does not.  A reader who takes all three as clearance has
  misread this section.

THE SCRIPTING-ENGINE DEFECT, REGISTERED AND NOT FIXED
  Recorded because it was discovered, and left alone because the governing rule
  says discovered pre-existing defects are documented rather than repaired.
  Nothing in this file proposes, implies or performs a repair.
  THE TWO CALL SITES, re-derived over this tree, are exactly two:
  acm-standard-applications/acm-foia/src/main/java/gov/foia/service/JavaScriptEvaluatingPredicate.java
  at line 94, and the privacy application's counterpart at
  acm-standard-applications/acm-privacy/src/main/java/gov/privacy/service/JavaScriptEvaluatingPredicate.java
  at line 98.  Each asks the script-engine manager for an engine by name.
  WHY IT FAILS SILENTLY, which is what makes it dangerous.  The platform removed
  the engine implementation while leaving the scripting API in place, so both files
  compile cleanly at the new release level.  The lookup returns nothing at run
  time and the next dereference throws.  Neither a compiler nor the change set's
  static audit over main source would surface it, because there is nothing
  textually wrong with either file.
  WHY BOTH COPIES ARE PROVABLY UNREACHABLE DEAD CODE.  In
  acm-standard-applications/acm-foia/src/main/resources/spring/spring-extension-library-foia.xml
  the XML comment region OPENS at line 131 and CLOSES at line 141.  Both
  declarations inside it are therefore commented out: the alternative
  folder-name-equals predicate declared at line 131 and the script-evaluating
  predicate declared at line 139.  There is NO ACTIVE DECLARATION of either at
  all.  The sole consumer, a bean reference at line 150, sits inside a commented
  property block spanning lines 148 to 152.  The privacy application has NO XML
  reference whatsoever, and its apparent cross-module references are declaration
  examples inside documentation comments.
  That reading was verified line by line for this file, and it corrects a
  description elsewhere in the migration plan which treats line 131 as an active
  declaration of a different, non-scripting predicate class.  Line 131 is where
  the comment opens.  Getting this backwards would turn a proof of unreachability
  into a claim that something live had been left broken.
  ONE CLAIM IS WITHDRAWN AS FALSE, AND ITS REPLACEMENT MEASURED.  An earlier
  revision of this annotation asserted that no standalone scripting-engine
  artifact is declared as a dependency anywhere in the reactor, and characterised
  the root build file's comment block as declining to pin the engine and
  forbidding its addition.  Both statements were true of an earlier state of this
  tree and are false of the tree this capture describes.  They are withdrawn here
  rather than quietly dropped, because a reader who carried them forward would
  conclude the opposite of the truth about the classpath.
  WHAT IS ACTUALLY DECLARED, re-derived over this tree rather than recalled.  A
  search for the engine across every build file returns four matches in two files.
  The root aggregator holds three: the version property, pinned at 15.4; the
  comment block at pom.xml:L203-L218 that explains the pin; and the managed
  dependency entry at pom.xml:L1153-L1164, whose own comment records that the

  acm-plugins/acm-extra-plugins/acm-personnel-security-plugin/pom.xml at lines 117

  root comment block is therefore the precise inverse of what was claimed: it pins

  add a standalone engine to the two dead call sites analysed below, which it
  leaves unrepaired.  The fourth match is a version-property key inside this
  evidence tree's own advisory capture script, which is not engine wiring.
  WHY THAT DECLARATION EXISTS, AND WHY IT IS NOT A REPAIR OF THIS DEFECT.  It
  serves the TASK-LISTENER path recorded under finding 1 above, which executed at
  the base commit on Java 8 and stopped executing on the new runtime - a live
  behavioural regression introduced by the runtime move, evidenced by the
  personnel-security background-investigation integration test erroring 2 of 2
  with a message naming a missing javascript engine, against no baseline row.  It
  does not serve, and cannot reach, the two call sites below: neither the freedom
  of information application nor the privacy application declares the engine, and
  both call sites are unreachable in any case for the reasons set out above.
  THE DECISION AND ITS TWO JUSTIFICATIONS.  Nothing was added FOR THESE TWO CALL
  SITES, and neither is on the classpath of a module that declares the engine.
  First, adding one for their sake would introduce a production dependency solely
  to support code that cannot execute, which is not a compatibility-blocking
  upgrade and is therefore out of scope.  Second, it would convert provably dead
  code into live code, which is a behaviour CHANGE measured against pre-migration
  behaviour, and pre-migration behaviour is the tie-breaker.  The defect is
  registered instead.  Note the contrast with the task-listener path, where the
  same two tests point the other way: that path DID execute before the runtime
  move, so restoring it preserves pre-migration behaviour and declining to would
  change it.  Same engine, opposite conclusions, because the two paths had
  opposite pre-migration behaviour.
  A CAUTION FOR ANY READER RECONCILING THIS WITH FINDING 1.  The two dead call
  sites above and the seven task listeners in finding 1 are different paths with
  opposite pre-migration behaviour: the call sites never ran, the listeners did.
  This annotation records both and is careful not to conflate their outcomes.  The
  LISTENER path has been restored, by the runtime-scope declaration measured two
  paragraphs above; the CALL-SITE path has not, and is registered as a defect
  rather than made functional.  An earlier revision of this annotation stated that
  no restoration existed in this tree, which was true when it was written and is
  false now; it is withdrawn here for the same reason the claim above it is.

GOVERNING RULES AND PROVENANCE
  TWO PROVENANCE FACTS, stated together, because either one alone misleads.
  First, there is NO on-disk user rules document for this project: the project's
  rules facility was queried and returned, verbatim, "No user rules provided.",
  and that read was complete rather than partial.  Second, rules are nonetheless
  present and binding: the migration requirements embed an explicit numbered block
  of seven rules that governs this work in full, exactly as an external rules
  document would, plus seven transformation rules that are the operational form of
  the preserve and exclude lists.  Fourteen constraints apply.
  Reporting only the first would imply that enterprise best practice is the sole
  standard here, which is wrong.  Reporting only the second would misrepresent
  where the rules came from.  Best practice is applied on top of them, never as a
  substitute, and the absence of a rules document is not licence to lower the bar.
  The identifiers used to cite those rules across this evidence tree are the
  migration plan's OWN navigational convention, not quoted rule titles.  No rule
  is invented here and none is softened.
  BASELINE BEHAVIOUR IS THE TIE-BREAKER.  This is the rule that creates this file.
  It makes the application's observed behaviour at the pre-migration base commit
  the tie-breaker for any ambiguity, and it requires each resolution to be
  documented.  It is PARAPHRASED here rather than quoted, and that choice is
  disclosed rather than made silently: the rule's own text names the older runtime
  with a phrase this documentation tree's wording gate forbids, so a verbatim quote
  would require substituting JDK 8 into it.  Paraphrase avoids the substitution
  entirely.  The clause requiring each resolution to be documented is what this
  annotation discharges, and the comparison target for this gate is identical
  process instantiation AND identical task assignment.  Both halves are named
  because a start request can answer successfully while no instance was created and
  no task assigned, so the criterion is a matching definition key, a matching task
  name and a matching assignee, not merely a successful response.
  EVIDENCE OVER EXIT STATUS, applied at full strength.  No verdict in this file
  rests on a process exit status.  Every figure above was read back from the region
  after it was written, or re-derived by command over this tree.  The point is
  applied literally to this gate: an engine bean that constructs without throwing
  is not evidence that definitions deployed, so construction is reported as
