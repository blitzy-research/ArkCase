------------------------------------------------------------------------------
WHY THIS FILE EXISTS
------------------------------------------------------------------------------

This file exists because of the transformation rule this plan labels R-T7 --
evidence over exit codes.  A green build with severed coverage instrumentation
is exactly the false positive that rule forbids: the check goal would evaluate
nothing, satisfy a minimum ratio trivially, and exit zero.  Every assertion
below is therefore made on the coverage execution-data file's size and
contents and on the ratio actually evaluated, never on a plugin's exit status.

The repository's own justification for holding evidence above exit codes is in
the frontend build definition, and it was re-verified at base commit
c8f6226105 rather than taken on trust:

  Gruntfile.js:L143  // Making grunt default to force in order not to break
                     the project.
  Gruntfile.js:L144  grunt.option('force', true);

Forced execution masks task failures and lets a broken build exit zero
elsewhere in this same change set.  The coverage equivalent of that hazard is
the subject of SECTION 2B.

SECTION 2B -- THE ASSERTION THIS FILE MAKES ABOUT THE OMITTED ELEMENT
------------------------------------------------------------------------------

THE ASSERTION, IN ONE SENTENCE: the newly added maven-surefire-plugin
declaration sets NO literal argLine element, and that omission is the single
most important property of the declaration.

The causal chain, each link confirmed at source rather than inferred:

  1. The coverage plugin's agent-preparation execution -- the execution whose
     id is pre-unit-test, which binds the prepare-agent goal -- is configured
     in the root pom.xml.  In the migrated tree the plugin block spans
     pom.xml:L554 to pom.xml:L631 and that execution spans pom.xml:L573 to
     pom.xml:L595.  At base commit c8f6226105 the same block spans
     pom.xml:L427 to pom.xml:L490 with the execution's id at pom.xml:L447.
     The anchors are given for both states because the aggregator has been
     edited by this change set and line numbers move; the execution is
     additionally identifiable by its id, which no edit shifts.

  2. That execution declares ONLY a destination file for its execution data,
     at pom.xml:L579 in the migrated tree and pom.xml:L452 at the base commit.
     IT DECLARES NO PROPERTY-NAME ELEMENT.  Verified at source, and verified
     reactor-wide: the property-name element occurs in zero of the 145 POMs.
     The coverage plugin therefore communicates the agent configuration to the
     test runner through its DEFAULT argLine property export, and by no other
     route.

  3. Observed, not assumed: the run logged an argLine export for every one of
     the 142 modules it built, and after reducing machine paths to placeholders
     all 142 reduce to a single shape --

       [INFO] argLine set to -javaagent:{LOCAL-ARTIFACT-REPOSITORY}/org/jacoco/
       org.jacoco.agent/0.8.13/org.jacoco.agent-0.8.13-runtime.jar=destfile=
       {REACTOR-ROOT}/target/jacoco-reports/jacoco.exec,excludes=
       org.drools.compiler.lang.*

     Line-wrapped here for width; it is one line in the run's own output.  The
     two placeholders stand for the local artifact repository and the reactor
     root, replaced for the same reason the archived unit-test reports replace
     them: the two sides of this evidence pair run from different roots by
     construction.

  4. If the Surefire declaration sets a literal argLine, it OVERWRITES that
     export.  The agent is then never attached, instrumentation is severed
     SILENTLY -- no warning, no error, no failed goal -- the execution-data
     file is empty or absent, and the check goal has nothing real to evaluate
     against the 0.02 minimum.  The result is a false pass: a build reporting
     coverage satisfied while having measured nothing.

  5. Therefore: no literal argLine in the Surefire declaration.  If fork
     arguments are ever genuinely required they must be appended in a way that
     preserves the coverage export rather than replacing it.

WHY THE HAZARD EXISTS ONLY ON THIS SIDE: at base commit c8f6226105 the
maven-surefire-plugin was declared in ZERO of the 145 POMs, so unit-test
execution ran on whatever version Maven implicitly bound and there was no
declaration in which a literal argLine could have been written.  The migration
adds the declaration -- pinned so unit-test execution is reproducible and so
baseline-failure exclusions have one auditable home -- and adding it is what
creates the trap.  The baseline side of this evidence pair consequently has
nothing to assert here, which is the whole reason for SECTION 2C.

STATE OF THE DELIVERED DECLARATION: it lives in the aggregator's plugin
management block and carries a groupId, an artifactId and a version and
nothing else.  It has no configuration element at all, and therefore no
argLine element and no excludes element.

R-5 -- INSTRUMENTATION VERIFIED LIVE, AND THE IGNORE COUNT AS AN INVARIANT
------------------------------------------------------------------------------

The rule this plan labels R-5 forbids disabling failing tests and confines
exclusions to failures already present at baseline.  A false coverage pass
violates that rule's intent even though no test is formally disabled: it
reports a pass while measuring nothing, so a test that stopped being exercised
would leave no trace.  This page therefore records, as its first R-5
obligation, that instrumentation was VERIFIED LIVE by the measurements under
SECTION 2A rather than inferred from the build having exited cleanly.

EXCLUSIONS-IN-THE-MIGRATED-SUREFIRE-DECLARATION ..... 0
      The declaration carries no configuration element, so it carries no
      excludes element.  Any exclusion added later must cite a row in
      docs/migration/baseline-test-failures.md, by class and by method, so the
      citation resolves to one test method and one evidence file.  An exclusion
      with no row fails.  At the base commit Surefire was declared in zero of
      the 145 POMs, so there was no location where an exclusion could be
      written down at all, let alone audited; the pinned declaration creates
      that single auditable location and the register is what fills it.

disclosed here rather than left for a directory comparison to surface as an
anomaly.  The other asymmetries a comparison reports are pre-existing, already
documented elsewhere in this capture, and enumerated below so that this

declaration the migration adds.  Manufacturing a baseline counterpart would

cannot arise -- an assertion about an absent declaration, dressed as a
measurement.  An honest asymmetry is preferable to a symmetrical fiction.

A PRE-EXISTING DEFECT ENCOUNTERED IN THE COVERAGE SUMMARY SCRIPT, DOCUMENTED
AND NOT FIXED, because the rule this plan labels R-6 makes a bug found in
passing a documentation event rather than a repair event:

  The repository ships jacoco-summary.sh at its root, and it is the natural
  tool for the aggregation above.  Run on this host it produces a TRUNCATED and
  UNUSABLE summary, which is worse than failing outright because the file it
  leaves behind looks like output.  Each of its five report lines formats a
  percentage with a stray single percent sign after the conversion, at script
  lines 21 through 25, and this host's awk rejects that at run time:

    awk: run time error: improper conversion(number 2) in
      printf("  Instructions: %.2f% (%d/%d)\n")

  It failed that way once per report, on all 69.  Measured, not assumed: the
  summary file it left behind is 10790 bytes over 69 lines and contains 69
  module heading lines and 69 instruction lines, every one of which is cut off
  mid-number with no covered-of-total figure -- the file ends, in this run, on a
  bare instruction percentage with no line terminator after it, and which module
  lands last depends only on directory traversal order.  It contains ZERO
  branch lines, ZERO LINE lines, ZERO complexity lines and ZERO method lines,
  because the run aborted at the first conversion of each invocation.  The LINE
  figure is the one the check rule evaluates, and it is exactly the figure the
  script never gets to.  Reduced to its essentials, an escaped percent sign is
  what the format requires; the single one is the defect.  That file is a build
  by-product of this investigation and is not committed anywhere.
  The script is LEFT EXACTLY AS IT IS.
  It blocks nothing here, because the aggregation above re-runs the script's own

  column positions, the same counters -- with a plain awk invocation instead.

  in fields 8 and 9 and method counters in fields 12 and 13, so the LINE
  covered ratio is field 9 divided by the sum of fields 8 and 9, which is
  exactly the counter the check rule evaluates.
