the distinction, before any anchor detail
=========================================
A COVERAGE exclusion removes packages from the MEASUREMENT.  It disables no
test, skips no test class, changes no assertion, and cannot alter what the suite
runs.  A TEST exclusion is a different thing entirely: it stops a test from
running.  The eight package globs in the root aggregator's coverage
configuration are exclusively the first kind, and all eight predate this
migration.

THEY MAY NEVER BE CITED TO JUSTIFY THE SECOND KIND.  The only admissible
justification for a test exclusion is a row in
docs/migration/baseline-test-failures.md, cited BY CLASS AND BY METHOD, so that
the citation resolves to one test method and one evidence file rather than to a
module or to a package.  Nothing on this page proposes excluding anything, and
nothing on this page is precedent for it.

why this concern needs a file of its own
========================================
The globs LOOK exactly like test exclusions.  They are spelled as package paths,
they sit in the root aggregator beside the test-phase bindings, and two in-file
comments give each set a reason that reads like a reason for skipping something.
A reviewer auditing whether this migration disabled a test will find them, and
two wrong readings are available.  1) Concluding that tests were disabled:
wrong, and refuted further down by measurement rather than by assurance.
2) Treating them as PRECEDENT, and justifying a real test exclusion by pointing
at them: worse, because it converts a measurement decision taken years ago into
authority over the one rule this migration is least free to bend.  Only stating
the distinction explicitly prevents either reading.

The sharper concern is not about the globs at all.  Coverage instrumentation in
this build is attached through a DEFAULT PROPERTY EXPORT, and this migration adds
a unit-test-runner declaration to the very same file.  A single element in that
new declaration would unhook instrumentation while every exit code stayed zero.
That is the hazard this note exists to name, and it is the reason the sibling
liveness record was captured at all.

Both halves are kept out of the capture files on purpose.  A qualification
written into a capture reads as observed output, and this one is an argument
about what the evidence means rather than a part of the evidence.

the severance hazard, stated in full
====================================
R-T7 is why this is worth a whole note rather than a sentence: the failure mode
produces a green build.

1) The agent-preparation execution publishes its agent configuration through the
   default fork-argument property, and the unit-test runner consumes that
   property when it forks.  There is no second route — the agent is passed no
   other way.
2) A unit-test-runner declaration that sets a LITERAL fork-argument override
   REPLACES that exported value.  It does not append to it.
3) The agent is then never attached.  Instrumentation is severed SILENTLY: no
   warning, no error, no failed goal, no diagnostic of any kind.
4) The coverage data file is consequently empty, or never written.
5) The check execution evaluates that EMPTY data set against the minimum ratio.
   An empty data set does not breach a covered-ratio limit.
6) The check execution REPORTS A PASS.  The build states that coverage is
   satisfied while having measured nothing whatsoever.

AN EMPTY COVERAGE DATA SET PRODUCING A PASS IS A GATE FAILURE, NOTWITHSTANDING A
ZERO EXIT CODE.

That is also why this is an R-5 concern and not merely a tooling detail.  A false
green violates R-5's intent even though no test was formally disabled.  Severance
itself excludes nothing, disables nothing and skips nothing: every test still
runs, and still passes or fails on its own merits.  The coverage claim beside
them is nevertheless worthless, and a build that reports a satisfied threshold
having measured nothing is exactly the kind of unfalsifiable green R-5 exists to
prevent.

the corollary constraint on this migration
------------------------------------------
The new unit-test-runner declaration MUST SET NO LITERAL FORK-ARGUMENT OVERRIDE.
As delivered it sets none: at pom.xml:426-430 it carries a group identifier, an
artifact identifier and a version reference and nothing else, with no
configuration element at all and therefore no place for one.  This is a
constraint on a file being edited for an entirely unrelated reason — the file is
opened to pin a version, and the thing that must not happen to it concerns
coverage — which is exactly the kind of coupling that gets missed.  If fork
arguments are ever genuinely required later, they must be added in a way that
PRESERVES the exported value rather than replacing it.

Two further things sharpen the hazard rather than mitigate it, and both are
recorded without any change being proposed.  The capture invocations pass
-Djacoco.haltOnFailure=false explicitly, so during capture a coverage shortfall
would not have failed the build even had the data set been real — that is a
property of the capture command and NOT of the commented-out element in the POM,
which leaves the plugin's failing default in force, as corrected above.  And the
repository's own coverage summary
helper, jacoco-summary.sh at the repository root, aggregates the REPORT output
rather than the execution data, so a severed run yields a summary that prints
zeroes rather than printing nothing — one more reason a reader cannot tell a
severed run from a real one by looking at what the build produced.  That helper
is named in docs/migration/dependency-change-inventory.md as requiring no change,
and it is unchanged.

how the hazard is discharged, by evidence and not by assertion
-------------------------------------------------------------
TWO records discharge it, and they answer two different questions that read
deceptively like one.  ../jacoco-liveness.txt answers "did the agent attach", by
measuring execution-data size off disk, and a byte total is the right instrument
for that and the wrong instrument for anything else.  ../coverage-counters.txt
answers "what did the attached agent MEASURE, and did it clear the configured
minimum", by archiving the class, method, line, branch and instruction counters
the plugin computed — each row bound to the SHA-256 of the execution data file it
was computed from — together with the check goal's own verdict lines quoted
verbatim.  An earlier revision of this note named only the first and treated it as
sufficient; it is not, because eleven megabytes of execution data is consistent
with any ratio whatsoever, and a reader who takes a byte total for a coverage
figure has been handed a number that does not mean what it appears to mean.
../jacoco-liveness.txt, the liveness half: it records coverage data measured off
disk per module: 69 execution data files found, 69 of them NON-EMPTY, 0 empty, a
per-module path-and-bytes listing, a byte total, and a state of LIVE.  The data
set the check execution evaluated was therefore a real one and not an empty one.
That record is NAMED here and pointed at.  It is not duplicated, it is not
summarised in place of itself, and no substitute for it was created.

An illustration of the class of override that would cause the severance is left
in words on purpose.  The obvious example is a module-access JVM argument that
opens or exports an otherwise-encapsulated JDK package to the unnamed module.
Its literal spellings are deliberately not written anywhere on this page, because
the audit proving this migration's production launch configuration free of them
is TEXTUAL, and writing one merely to illustrate a hazard would defeat that audit
from a page that has nothing to do with launch configuration.  The register of
such exceptions is referred to by its title only — the JDK access exceptions
register — for the same reason, and it is delivered empty.

why this evidence is a committed copy rather than a reference into build output
==============================================================================
Both the coverage data file and the per-module test reports are written beneath
the module's build-output directory, whose bare name is a pattern in the
repository-root ignore file matched AT ANY DEPTH.  Verified at line 6 of that
file, alongside four further bare patterns and one trailing-slash pattern at
lines 7, 24, 25, 26 and 40.  Nothing beneath it can be committed in place.

That is why ../surefire/ holds an ARCHIVED COPY of the per-module reports and
../jacoco-liveness.txt holds a RECORDED liveness finding, rather than either of
them being a pointer into a build directory.  It is also why this evidence tree
can be reviewed from a clean checkout at all: re-running the liveness finder on
an unbuilt checkout finds no execution data and answers zero, which the baseline
counterpart records verbatim as a not-measured state with the reason attached and
with the explicit qualification that it is NOT evidence of severance.  The
committed record is the evidence; the build directory is long gone.
