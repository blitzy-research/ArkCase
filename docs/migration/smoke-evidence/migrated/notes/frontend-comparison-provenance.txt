frontend artifact comparison - how both sides were produced, and what the result
does and does not prove

WHICH BUILD THIS CAPTURE'S FIVE DIGESTS COME FROM
This is the MIGRATED capture, and its five digests under artifacts/ were taken
from this checkout built on the target runtime: Node v20.20.2 with npm 10.8.2,
the migrated package.json with its 76 git dependency specifications pinned to
exact commit SHAs, and a clean install from the committed package-lock.json at
lockfileVersion 3.  notes/artifact-gate.txt records the exact directory this run
read, and env/toolchain.txt records the node, npm and java that were on PATH
while it read it; both are generated by the capture script from the run itself
rather than typed here.

RESULT OF THE COMPARISON THIS CAPTURE TAKES PART IN
Comparing the baseline capture's five digests against this capture's:
  application.js        BYTE-IDENTICAL
  vendors.min.js        BYTE-IDENTICAL
  home.html             BYTE-IDENTICAL
  application.min.js    differs by 2 bytes, in one regular-expression escape
  application.min.css   differs by 789 bytes, in selector grouping only
The source map differs as well.  It is EXCLUDED from the required comparison set
because it embeds file paths, and the two builds ran from different roots by
construction, so its difference carries no information here.

A strict reading of the byte-identity criterion is therefore NOT met, and this
note does not soften that.  What the criterion exists to detect - a changed
dependency graph, a changed pipeline, changed application source - was looked for
specifically and not found; the full analysis is in
  ../../historical-frontend/comparison.txt

THREE BUILDS WERE TAKEN, NOT TWO, AND THAT IS WHAT SETTLES THE ATTRIBUTION
  A  base-commit tree, yarn 1.22.22, Node  v8.17.0    <- the baseline capture
  B  base-commit tree, yarn 1.22.22, Node v20.20.2
  C  migrated tree, npm 10.8.2 from the committed lockfile, Node v20.20.2
                                                     <- THIS capture

B holds the runtime constant against this capture and varies only the package
manager, the lockfile and the specification form.  B and C are byte-identical on
all five artifacts AND on the source map, and the content-hash filenames the
cache-busting task derives agree as well:
  application.ef1612bbd7993382.js
  application.min.2fa1cd12f2c4077f.js
  application.min.1ae47d39c0d9d836.css
  vendors.min.59439035604af96f.js
  application.min.js.56da89159ec1b11a.map
That is the strongest statement available about the change this migration actually
makes to the frontend: the manifest rewrite, the lockfile replacement and the
installer change resolved to the same dependency graph and drove the pipeline to
the same bytes.  It also settles the attribution of the two A-against-C
differences, because they cannot be caused by anything B and C differ in.  B's
digests are preserved at
  ../../historical-frontend/artifact-digests-node20-basecommit-yarn.txt
so the reasoning can be checked rather than taken on trust.  Corroborating it
directly: the minifier versions are IDENTICAL on both sides
(grunt-contrib-uglify 0.9.2 / uglify-js 2.8.29, grunt-contrib-cssmin 0.12.3 /
clean-css 3.4.28) and their input, application.js, is byte-identical - so the only
remaining variable is the JavaScript engine the minifier itself ran on.

The residual difference is registered as an accepted, evidenced deviation in
docs/migration/ambiguity-resolutions.md and docs/migration/pre-existing-defects.md.
A reader must not extend either capture into a claim the other one makes.

HOW THIS SIDE WAS PRODUCED, IN THE ORDER THE STEPS RAN
  tree            this checkout
  clean           git clean -xfd over the frontend resources directory, so the
                  install and build could not read a stale node_modules or a
                  stale dist directory
  manifest        the migrated package.json, 76 specifications pinned to exact
                  commit SHAs, engines constraining node and npm rather than the
                  superseded package manager
  lockfile        the committed package-lock.json at lockfileVersion 3
  install         npm 10.8.2, clean install from that lockfile
  build           the Grunt default task graph, unmodified

A NOTE ON EXIT STATUS
The Gruntfile enables forced execution, so a task failure can still exit zero.
Every assertion here is therefore made against the artifacts and their digests
rather than against an exit status, and the gate that records those digests fails
hard on an absent artifact rather than writing a row that reads ABSENT.
