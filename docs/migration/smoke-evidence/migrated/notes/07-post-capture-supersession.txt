===== figures inside this capture that the committed tree has since superseded =====

WHY THIS FILE EXISTS.  A capture is a record of one moment.  The tree it is committed
beside kept moving after that moment, and three of the things this capture counted are
counts OF THAT TREE rather than of the deployment it probed.  Where the tree changed, the
count went stale.  This note enumerates every such figure, gives the measured current
value, and gives the command that measures it, so that a reader who counts and gets a
different answer from the one printed beside it knows which is which and why.

WHAT WAS NOT DONE, and why it matters more than what was.  No observation was edited.
Not one status record, response body, log region, digest or report was changed to make a
number agree with a later state of the tree.  Editing a frozen capture to tidy a
comparison is the authenticity defect this checkpoint's evidence work was spent
eliminating, and re-taking the pair is not available either: the pre-migration side probed a
JDK 8 deployment of the base commit -- its startup region records JVM Version 1.8.0_492 --
and that deployment cannot be rebuilt from this tree, because the shared local artifact
repository now holds the intra-reactor artifacts at class-file version 61 and the older
compiler cannot read them.  So the stale figures stay where they are, and this note stands
beside them.

This file is carried identically in BOTH capture directories, because every figure it
supersedes is a figure about the pair.

the result record is declared the authoritative record for its flow, the discrepancy is set

  for side in baseline migrated; do

WHY NONE OF IT WAS EDITED.  A result record is a produced rendering of a run.  Rewriting one
so that it quotes a status file it never saw would manufacture an observation, and the
capture pair cannot be re-taken: the pre-migration side probed a JDK 8 deployment of the
base commit that cannot be rebuilt from this tree, for the reason given at the head of this
note.  Note what env/toolchain.txt does and does not say about that: it records the tools of
the HOST that ran the producer -- openjdk 17.0.19 and node v20.20.2 on both sides -- and the
runtime of the DEPLOYED SERVER is in the startup region, JDK 8 on the pre-migration side and
Java 17 on the migrated one.  The status files, the .out transcripts and the digests are the observations; where a
result record and its status file disagree, THE STATUS FILE IS THE OBSERVATION AND THE RESULT
RECORD IS A RENDERING OF AN EARLIER ONE.  Every figure published in
../parity-provability.txt has been re-derived from the status files and the .out transcripts
on that basis.
