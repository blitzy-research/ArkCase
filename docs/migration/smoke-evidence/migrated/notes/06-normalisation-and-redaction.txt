WHY THIS NOTE SITS UNDER notes/ AND NOT INSIDE A CAPTURE FILE
-------------------------------------------------------------
A capture file holds observed output.  A qualification placed inside one would be
read as part of that output, which is exactly the confusion a substitution ledger
must not create: a reader has to be able to tell the values the system produced
from the values this script put in their place.

So the ledger lives beside the captures rather than in them.  This note owns
exactly one concern, and it is the last of the six reviewer notes in this folder:
what was substituted, by which helper, where, with which token, and on what
grounds.  It records no observation and reaches no verdict.

It also deliberately does not restate its siblings.  01-artifact-comparison-scope.txt
scopes the artefact-level comparison, names the five digest files and records the
source-map caveat; 02-node-env.txt records the build-time environment value the
migrated frontend build ran under.  Those two govern the ARTEFACT half of the
evidence.  This note governs the OUTPUT half.  Read 01 and then 02 first; nothing
here repeats their analysis.


WHAT THIS LEDGER IS FOR, AND THE AMBIGUITY IT REMOVES
-----------------------------------------------------
The whole behavioural claim of this migration rests on captured output from the
pre-migration run matching captured output from the migrated run.  But raw output
is full of values that MUST differ between two runs of identical behaviour -
wall-clock stamps, measured durations, broker-assigned identifiers, generated
surrogate keys - and values that MUST NOT differ, such as result ordering,
generated object numbers and resolved MIME types.  Substitution is therefore both
necessary and dangerous: without it every comparison drowns in noise, and applied
one step too widely it erases precisely the difference the comparison exists to
detect, invisibly and with no local check that would catch it.

Publishing the ledger is what makes the comparison auditable instead of merely
tidy.  A reviewer can take any placeholder in any .result.txt, find the entry here
that put it there, and check the entry against the committed script.  The audit
runs in both directions: every placeholder declared here is accounted for against
the captures, and every placeholder appearing in a capture has an entry here.  An
unexplained placeholder in a capture is a gap in this ledger, not a curiosity.

And because the ledger is replayed identically on both sides, a difference between
two .result.txt files is unambiguously behavioural.  If the two ledgers diverged,
a difference could be a behavioural change or a substitution change and no reader
could tell which - which would quietly destroy the evidential value of the whole
tree while leaving every file looking healthy.


RULES PROVENANCE - BOTH FACTS, STATED TOGETHER
----------------------------------------------
Two facts have to be given together, because either one alone would mislead.
1) The project's rules facility returns, in full, that no user rules were
   provided.  There is no on-disk user rules document for this project, so there
   is no external full-text source to defer to for the constraints cited below.
2) Rules are nonetheless present and binding.  The requirements embed an explicit
   numbered block of seven rules, together with seven transformation rules that
   are the operational form of the PRESERVE and EXCLUDE lists - fourteen specific
   constraints in total.

Reporting only the first would imply that enterprise best practice is the sole
standard here, which is wrong.  Reporting only the second would misrepresent
where the constraints came from.

DISCLOSURE: the identifiers R-1 to R-7 and R-T1 to R-T7 used below, and their
  descriptive labels, are the migration plan's own navigational convention.  They
  are not quoted titles.  No rule is invented here, and none is softened.

THE RULES THAT GOVERN THIS NOTE, and what each one requires of it.
R-2 is the defining rule: it is why a substitution protocol exists at all for
  the three module-access argument spellings, and why the register of exceptions
  is named by title only throughout this tree.
R-7 makes identical replay the governing property, and requires every value here
  to be re-derived from the committed script rather than assumed.
R-T7 forbids any conclusion drawn from a process exit status, so every entry is
  verifiable against the script and against the captures themselves.
R-6 forbids normalising a pre-existing defect out of existence to make a
  comparison read better.
R-1 is applied here as a two-sided scope fence: every substitution carries a
  reason, and a value that CAN be compared is not substituted.
R-5 requires that a skip be a distinct, visibly-labelled outcome carrying a
  reason, and never readable as a pass.
R-T6 constrains the path substitutions: only the volatile prefix goes, and the
  repository-relative remainder survives verbatim.
R-3 fixes the vocabulary: JDK 8 in this note denotes the pre-migration baseline
  runtime and nothing else.  It is never a compile target of the migrated build,
  which compiles at release 17 and at no other release.


HOW IDENTICAL REPLAY IS ACHIEVED, AND HOW A DIVERGENCE WOULD BE DECLARED
------------------------------------------------------------------------
Identical replay is not achieved by copying the baseline ledger.  It is achieved
because both ledgers are derived from ONE artefact: the single committed script at
docs/migration/smoke-evidence/smoke-checks.sh, which is the same file on both
sides of the comparison and is not modified between the two runs.

MECHANISM: every byte either capture writes passes through one function, sanitise
  at smoke-checks.sh:L1914, which is the fixed three-pass composition
  redact_literal, then redact_patterns, then normalise.  Not "every response
  body" - every byte, including result records, status tokens, mined log regions
  and the run summary.  Routing all writers through one function is what makes
  the coverage checkable: a reviewer confirms it by confirming that nothing
  writes into the capture tree except through there.
CONSEQUENCE: the substitution set, the pass order and the placeholder tokens
  cannot differ between the two sides, because there is only one definition of
  them.  Identity holds by construction rather than by transcription.
DIVERGENCES DECLARED ON THIS SIDE: none.  No entry below differs from its
  baseline counterpart in helper, scope, pattern, placeholder or reason.  The
  only thing that differs between the two ledgers is the RESULT-FILES field,
  which records where each placeholder was actually observed, and that field is
  an observation about the run rather than a property of the substitution.  It is
  reported per entry and summarised in the placeholder audit near the end of this
  note.
WHY THAT DISTINCTION IS DRAWN EXPLICITLY: a reader who found a populated
  RESULT-FILES field on one side and an empty one on the other could mistake it
  for a substitution change.  It is not.  It records which expressions had
  anything to fire on, which on this side is governed by how much of the
  reference stack was reachable, not by how the pipeline is configured.


THE REASON CLASSES - A CLOSED SET OF FOUR
-----------------------------------------
Every entry carries exactly one reason class in its REASON field, drawn from this
set and no other.  R-1 applied to substitutions means a substitution without a
reason does not belong in the ledger at all.

VOLATILE: the value differs between any two runs of identical behaviour, so
  keeping it would make the comparison report a difference that carries no
  signal.  Generated by construction: a clock reading, a measured duration, a
  database sequence value, a broker-assigned identifier.
SECRET: the value must never be written to a tracked file.  Credential material
  and anything credential-equivalent for as long as it lives, a live session
  identifier included.
ENVIRONMENT: the value identifies the host or the deployment rather than the
  behaviour.  An absolute filesystem prefix, a scratch directory, a launch
  argument.
SIZE: a body is replaced by a content digest so that the capture stays reviewable
  and so that arbitrary bytes are never piped through a text pipeline.  The
  digest is then the assertion.

CLOSURE RULE: no other reason class may be introduced without being added here
  first.  A ledger whose reason vocabulary grows at the point of use is not
  auditable, because a reader cannot tell an established justification from one
  invented to fit the case in front of them.


THE ENTRY FORMAT, DECLARED ONCE AND THEN FOLLOWED EXACTLY
---------------------------------------------------------
Each entry is a block of KEY: value lines, separated from the next by a rule of
hyphens.  The fields are fixed and appear in this order in every entry.

SUBSTITUTION: a stable identifier for the entry, cited from elsewhere in the tree
HELPER: the smoke-checks.sh function that applies it, with its line anchor
SCOPE: which captures it applies to - all flows, or a named flow
PATTERN: the class of value matched, DESCRIBED IN WORDS.  No expression is
  reproduced here: an expression pasted into prose invites a reader to trust the
  copy instead of the script, and a copy is exactly the thing that goes stale.
  The script is the definition; this field says what it means
PLACEHOLDER: the literal replacement token written into the capture
REASON: one class from the closed set above
REPRODUCIBLE: the statement that re-running the helper over the same raw input
  yields the same output, so a reviewer can replay it rather than take it on
  trust
RESULT-FILES: where the placeholder is observed in this side's .result.txt set,
  or the explicit record that no capture on this run exercised it
NOTE: an optional eighth field, present only where an entry needs a
  qualification.  It is declared here so that its appearance in some entries and
  not others is part of the format rather than a drift in it

DIVERGENCE-1: there is no helper named redact.  The script splits redaction into
  redact_literal and redact_patterns, and the split is deliberate: the literal
  pass substitutes caller-supplied values and so must be boundary-aware, while
  the pattern pass substitutes fixed expressions and so cannot suffer the
  escaping hazard that interpolating a caller value into an expression would
  create.  Publishing one combined name would have hidden a distinction the
  ledger depends on.
DIVERGENCE-2: there is no helper named capture_http.  The request-and-response
  capture function is http_probe.
DIVERGENCE-3: record_skip has a capture-side companion, record_skip_capture,
  which the folder convention did not anticipate.  record_skip is the FLOW-level
  device that writes one verdict, one status line and one result record and marks
  the whole run incomplete; record_skip_capture writes the capture-side section.
  Both are named here because a reviewer looking for the skip machinery needs
  both.

ONE ORDERING CONSTRAINT INSIDE THE VOLATILITY PASS IS LOAD-BEARING, and it is
recorded because a future edit that reorders the expressions would silently
weaken the ledger.  The broker-assigned message identifier expression runs AHEAD
of the millisecond-instant expression, because the identifier embeds a
millisecond start time.  Reversed, the instant expression would rewrite part of
the identifier, the identifier expression would then no longer match, and the
capture would be left with the host and counter fragments of an identifier
arranged around a placeholder - a half-substituted value, which is worse than
either outcome, because it reads as though it were verbatim.


PASS 1 OF 3 - THE LITERAL PASS
------------------------------
Six fixed pairs, applied in the order given, by redact_literal at
smoke-checks.sh:L1589.  Five ledger entries, because the capture directory
contributes two pairs that share one placeholder.

THE BOUNDARY CONSTRAINT ON EVERY PATH PAIR (R-T6).  A path pair substitutes only
where the character following the match cannot continue a path component: end of
line, a slash, whitespace, a quote, a comma.  Where the next character is a
letter, a digit, a dot, an underscore or a hyphen, the match was merely the
beginning of a LONGER name and is left exactly as it was.  Only the volatile
PREFIX is ever replaced; the repository-relative remainder survives verbatim,
because dependency keys and asset paths are contract and a rewritten path
component is a behaviour-bearing value silently altered.

That constraint is not defensive theory.  The script records the failure it was
written for: on a host whose home directory is /root, the unconditional form
rewrote the tracked source file services/websockets/rootScope-decorator.js into
services/websockets, then a home-directory placeholder, then Scope-decorator.js,
because the home directory was a prefix of the filename.  A behaviour-bearing
filename was altered inside a capture that presents itself as verbatim.  Short
generic home directories make that likely rather than exotic.

A second consequence of the same constraint belongs in this ledger explicitly,
because the folder is one directory away from it.  Runtime data directory names
that the repository ignores at any depth - the message-broker data directory and
the partition-descriptor directory among them - would otherwise reach the
captures inside absolute paths.  The prefix substitutions keep those absolute
paths out while leaving the relative remainder intact, so no capture depends on
where it was taken and no ignored directory name is reproduced as part of a host
path.

PASS 2 OF 3 - THE CREDENTIAL PATTERN PASS
-----------------------------------------
Seven entries, applied by redact_patterns at smoke-checks.sh:L1669.  Every
expression in this pass is FIXED: no caller-supplied text is interpolated into
any of them, which is why the escaping hazard that governs the literal pass
cannot arise here.  All seven write the same placeholder, because a reader does
not need to know WHICH route a credential took to reach a capture in order to
know that it did not survive.

The coverage is deliberately wider than "the response body", because a credential
reaches a capture by more routes than a body: request and response headers,
session cookies, cross-site-request-forgery tokens, scheme-prefixed material
anywhere including inside a diagnostic, credential-shaped fields echoed back by a
server, a bearer-equivalent query parameter, a transport configuration line
echoed into a diagnostic, and a credential embedded in a URL.

ONE PROPERTY OF THIS PASS IS RECORDED BECAUSE IT WAS A REAL FAILURE, and it is
the sharpest illustration in the whole tree of why a redactor must be proven
rather than reviewed.  The expression delimiter in this pass is a character that
appears in none of the expressions and in none of the replacements, and it is
NOT the alternation character.  An earlier revision used the alternation
character for both, which produced a malformed expression, which made the whole
substitution program invalid, which made the utility exit before reading a byte -
and because the sanitiser is a pipeline, EVERY capture file came out at zero
bytes while the run still completed and reported success.  A redactor that
silently discards the evidence it was asked to clean is worse than no redactor at
all.  It was found by running the script, not by reading it, and the self-test at
smoke-checks.sh:L1944 now makes that class of failure impossible to repeat
silently.

THE GENERIC CLASSES THE FOLDER CONVENTION ANTICIPATES, AND HOW EACH IS HANDLED
------------------------------------------------------------------------------
The convention for this note names seven generic classes.  Five of them have their
own expression above.  Two do not, and saying so is more useful than inventing an
entry for them, because R-1's contrapositive means an absent substitution is a
decision that has to be justified exactly as a present one does.

1) Wall-clock timestamps and dates: entries V1 and V2.
2) Elapsed durations: entry V7, and for the search engine's own figure, entry S1.
3) Host-and-port authorities: NO EXPRESSION OF ITS OWN, deliberately.  The
   reference-stack authorities are fixed configuration, identical on both sides of
   the comparison, and they are part of what is compared: every flow records the
   request line it issued verbatim so that a reader can see WHICH endpoint
   answered.  Substituting them would remove a compared value to solve a problem
   that does not exist.  The one place an authority IS volatile is inside a
   broker-assigned message identifier, which embeds a host and a port, and there
   the whole identifier collapses under entry M1 rather than the authority being
   picked out of it.
4) Process and thread identifiers: NO EXPRESSION OF ITS OWN, deliberately.  A
   bare process or thread number has no distinguishing shape, so an expression
   for it would have to match a bare number - and a bare-number expression is the
   single most dangerous thing that could be added to this pass, because a result
   count, a queue population and a generated object number are all bare numbers
   and all three are behaviour.  Where a process fragment appears inside a
   broker-assigned identifier it is absorbed by entry M1.  Where one appears in a
   mined container-log line it is part of that log's own layout and is left
   exactly as the container wrote it.
5) Session identifiers: NOT in this pass at all.  They are REDACTED by entries C2
   and C7, because a live session identifier is credential-equivalent.  Entry C2
   records why the treatment was moved.
6) Correlation identifiers: entry V5 for the universally-unique form, and entry
   M2 for the broker-GENERATED form.  A correlation identifier the APPLICATION
   supplies would be behaviour-bearing and would have to be exempted; this
   application supplies none, which is recorded as an observed field in the
   messaging flow rather than assumed here.
7) Generated surrogate keys carrying no business meaning: entries W1, W2 and W3,
   matched BY FIELD NAME rather than by value shape for the reason given in item
   4 above.

THE FORBIDDEN-TOKEN SUBSTITUTION, AND THE NAMING RULE THAT GOES WITH IT
-----------------------------------------------------------------------
This entry exists because R-2 is the defining rule for this note.  R-2's register
of exceptions is delivered EMPTY with a positive statement, and that emptiness is
only credible if no capture anywhere in this tree leaks a module-access argument
token: a captured launch command line, a container startup banner or an echoed
environment variable would put one into the tree and contradict the register on
its own evidence.

--------------------------------------------------------------------------------
SUBSTITUTION: X1-MODULE-ACCESS-ARGUMENT
HELPER: none.  No expression implements this one, and that is stated plainly
  rather than glossed: it is a WRITING RULE observed by every capture region and
  by every note in this folder, declared in the committed script's own header at
  smoke-checks.sh:L218 to L230.  It is verifiable by the recursive textual audit
  rather than by reading a substitution table, which is a stronger check than an
  expression would be, because it catches prose as well as captured output
SCOPE: every file in this evidence tree, at every depth - captures, status
  tokens, mined log regions, result records, the run summary and these notes
PATTERN: any captured or written region that would print a module-access JVM
  argument that opens or exports an otherwise-encapsulated JDK package to the
  unnamed module.  Three literal spellings exist; none of them is reproduced
  anywhere in this tree, in code, in comments, in an echoed string or in a
  variable name
PLACEHOLDER: none.  The argument is DESCRIBED IN WORDS - as a module-access JVM
  argument that opens or exports an otherwise-encapsulated JDK package to the
  unnamed module - and never reproduced.  A placeholder token would have been the
  tidier design and is deliberately not used, because a token in place of an
  argument still records that an argument was there, and no argument was
REASON: ENVIRONMENT.  A JVM launch argument records how a deployment was started
  rather than what the application did, so removing it costs the comparison no
  behavioural signal.  The reason the removal is MANDATORY rather than merely
  permitted is separate and is stated in the next paragraph
REPRODUCIBLE: yes, and it is the one entry a reviewer can verify without running
  anything: a recursive search of this tree for the three spellings returns
  nothing, and it returns nothing at every depth
RESULT-FILES: none, by construction and by intent.  No .result.txt on either side
  contains any of the three spellings
NOTE: the substitution and the rule agree, which is worth recording because they
  arrive from different directions.  R-2 forbids relying on such an argument; and
  two sibling validation gates search recursively over directories that contain
  this file and both must return zero, so a working, deploying, fully passing
  build would still fail on a comment or a captured banner.  A runtime access
  flag could therefore never have been the shortcut here even if the rule had
  permitted one, because the gate is textual and not semantic

THE EMPTINESS IS EARNED, NOT ASSUMED.  The audited production launch
configuration - the container environment block recorded in the repository
prerequisites and duplicated in the setup documentation - contains no such
argument today.  That is checkable in about a minute by reading the block, and it
is why a faithful capture of it stays clean and why the register is delivered
empty.  The register did not start empty as a convenience; it is empty because
the requirement is gone.

WHY IT COULD BE KEPT EMPTY.  Every accessibility failure encountered anywhere in
this migration was inside a TEST library, and every one was resolved AT THE
LIBRARY - by advancing it to a release that works under strong encapsulation, or
by removing it where its final release does not - never by relaxing a module
boundary.  Production code has nothing to open: the application's reflective code
targets the application's own classes, and no security manager is installed.  The
one production call site that could not be compiled as it stood was rewritten to
a supported form instead, and that rewrite is recorded in the flow that exercises
it rather than here.

THE NAMING RULE, STATED AS A RULE OF THIS LEDGER AND NOT MERELY OBSERVED.  The
sibling register that catalogues these arguments is referred to BY TITLE ONLY
throughout this evidence tree - as the JDK access exceptions register - and never
by its filename and never by its path, because the path itself embeds one of the
three forbidden spellings.  A reference that looked entirely innocent, being only
a citation, would fail the gate exactly as a captured argument would.  This is a
genuinely non-obvious trap, and this note is where it is written down for the
whole folder.


================================================================================
THE COUNTER-LIST - BEHAVIOUR-BEARING VALUES THAT SURVIVE VERBATIM
AND MAY NEVER BE SUBSTITUTED BY ANY ENTRY IN THIS LEDGER
================================================================================

THE RULE, IN ONE LINE: if a value could differ because BEHAVIOUR differed, it is
not volatile and must not be substituted.

This is the list that protects the evidence, and it is the half of the ledger to
read first.  Over-normalising a capture empties the comparison while leaving every
file looking healthy, and no local check would catch it - which makes an
over-broad substitution strictly more dangerous than an absent one.  Each of the
five headline members below is named because a plausible expression would have
reached it, and each of those expressions was declined.

1) RESULT ORDERING, in the search flow.  RANKING IS BEHAVIOUR, NOT PRESENTATION.
   The order the engine chose is part of its answer, so the identifiers are
   transcribed in the order they were returned, by a reader that emits matches in
   file order.  Nothing is sorted, nothing is de-duplicated, nothing is reordered
   and nothing is truncated, and the order is therefore preserved by construction
   rather than by a sort that could be got wrong.  Normalising the order would
   erase a ranking regression, and the comparison would pass while the ranking had
   changed.  The match count, the membership of the identifier list and the
   relevance scores where the response exposes them are preserved for the same
   reason.  Only the query duration is removed, under entry S1.
2) GENERATED OBJECT NUMBERS, IN FULL.  Prefix, separators and padding intact.  The
   numbering flow exists to detect a change in sequence AND in format, so a
   partial substitution would be as destructive as a total one.  These are the
   single most behaviour-bearing values in the whole capture: they are produced
   through the live decision tables that the rule-language runtime advance
   touches, which makes the numbering flow the flow with the most to lose from a
   careless expression.  Nothing in this ledger matches a bare business number by
   shape - entry V6 is bounded to a thirteen-digit instant, and every engine
   identifier is matched by field name - and entry W2's note records that
   constraint as the reason for the field-name form.  The number's value and its
   observed format live in the flow's own capture and are recorded there
   verbatim.
3) RESOLVED MIME TYPES, ON BOTH LEGS OF THE DOCUMENT ROUND TRIP.  The
   content-type row is present on the store leg and on the retrieve leg and is
   written exactly as the server resolved it.  This is half the round-trip
   flow's criterion, because the resolved type is the observable output of the
   activation framework's MIME mapping - and the resource-bearing reference
   implementation was mandated over the tidier interface-only artifact precisely
   because the interface-only artifact lacks the default MIME and mailcap
   resources and would resolve types differently while still compiling and
   deploying perfectly.  A MIME difference is exactly the regression this flow
   detects, so normalising that one value away would erase the only signal it
   carries.  The field set is emitted on EVERY path, so a leg that did not run
   carries the same rows with explicit not-observed values and the two sides
   still line up row for row.
4) QUEUE NAMES, in the messaging flow and in the queue-transition flow.  The
   comparison is per-destination, so the destination name is what makes an
   observation addressable at all.  Every broker expression above names its keys
   exactly rather than matching a suffix, which is what keeps the destination
   name out of them; entry V8's note records that this exact-key form was chosen
   over the shorter suffix form for this reason.  The payload content, the
   payload's declared type, the priority and persistence flags and every
   application-set property are preserved alongside them.
5) ONWARD-ROUTE ORDERING, in the queue-transition flow.  The candidate set is
   written on ONE line in the order the rules emitted it, so that a reordering is
   a one-line difference rather than a silent one.  The transition, the source
   queue, the destination queue, the candidate count, the object identifier and
   the object number pass through the same sanitiser as every other byte and are
   untouched by it.

AND, FOR COMPLETENESS, THE REST OF WHAT NO ENTRY ABOVE TOUCHES.  Case, complaint
and object numbers.  Process and task names, task definition keys, assignees and
candidate groups.  The process definition KEY, which entry W1 is written to
preserve inside the identifier it does substitute.  The instance state, the
process variables and the definitions-loaded count.  The authorisation result and
every role, granted authority and privilege name.  Result counts.  The
content-derived cache-busting hashes, which are derived from artefact content and
so SHOULD match when behaviour matches.  The artefact digests themselves.  And a
USER IDENTITY that forms part of an observed routing or assignment decision, which
is preserved rather than redacted: in that position it is behaviour, not a
credential, and redacting it would remove the very value the decision is judged
by.

THE ASYMMETRY IS INTENTIONAL.  Under-normalisation costs a reader some noise and
is visible the moment they look.  Over-normalisation costs the tree its evidence
and is invisible.  So where a value's status was genuinely unclear, it was left
alone, and the residual noise is accepted as the cheaper of the two failures.


CREDENTIAL POSTURE - THE EXISTENCE OF A SESSION, NEVER ITS VALUE
----------------------------------------------------------------
Stated plainly, because this is the note whose subject is credentials.

WHAT IS CAPTURED: the EXISTENCE of an established session, as a separate observed
field carrying present or absent.  The headers are inspected for it before they
are sanitised, purely to record that one fact, and the identifier itself is
redacted out of the captured headers by entries C2 and C7 and never reaches the
evidence.
WHAT IS NEVER WRITTEN TO ANY TRACKED FILE: no password, no token, no cookie value,
no authorisation header value, no session identifier value.  Recording any of them
would put a live credential-equivalent into version control, which is a worse
outcome than having no capture at all.
HOW THE ACCOUNT IS NAMED: by role.  The authenticated flow uses the default
administrator account documented in the repository README, and this ledger refers
to it that way and never reproduces the account or its password.  The same
applies to the launch-configuration password material, which is referred to by
role and never by property name or value.  Neither the README line that documents
the account nor the launch-configuration line is quoted anywhere in this folder.
NO COMMAND-ECHO REGION MAY TOUCH THE CREDENTIAL, and the capture helper is built
so that none can.  http_probe at smoke-checks.sh:L2227 supplies the credential
through a transport CONFIGURATION FILE READ FROM STANDARD INPUT, never as a
command-line argument - so it does not appear in this host's process table, and
there is no command line carrying it that a trace region or a diagnostic could
echo.  Both fields are escaped for that configuration file's quoting rules before
they are written to it, because an unescaped quote would terminate the value
early and let the remainder be parsed as further configuration directives, which
for a credential-bearing line is an injection.
AND THE REDACTOR IS PROVEN BEFORE IT IS TRUSTED.  verify_sanitiser at
smoke-checks.sh:L1944 runs before the first capture file is opened and checks
three properties: that the pipeline produces output at all, which is what catches
an invalid expression program; that the REAL configured credential does not
survive it, rather than a sample credential, including whatever metacharacters it
happens to contain; and that representative credential-bearing header, cookie and
JSON forms do not survive it.  Failure of any one of them is a refusal to start.
Capturing administrator session material with an unproven redactor is not an
acceptable alternative.


A SKIP IS NOT A PASS
--------------------
R-5's ruling reaches this ledger through one property: a flow that genuinely
cannot be executed must leave evidence of its own absence, and that evidence must
be impossible to mistake for a pass.

record_skip at smoke-checks.sh:L3666 writes a distinct, visibly-labelled SKIPPED
outcome into all three of the flow's files, ALWAYS carries a reason, and marks the
whole run incomplete so that the run-level record reflects it too.  The result
record additionally carries the line stating that a SKIPPED verdict is not a pass
and must not be read as one.  A skip is reserved for a genuine inability to
execute and is never used to make an inconvenient observation disappear.

Two consequences bear on this ledger specifically.  First, a skip is COMPARABLE
rather than merely honest: the flow's named observations are each recorded as an
explicit absence, with the same keys in the same order as they would carry if the
flow had run, so the two sides still diff row for row.  Second, an absence is
never rewritten into an apparent observation - which is precisely the property
entry W3 enforces at value level, by requiring an all-digits value before it will
reduce an identifier to a placeholder.

AND A SKIP IS NOT THE ONLY NON-PASS VERDICT ON THIS SIDE, which is worth stating
here so that this section and the placeholder audit agree.  Re-read from the eight
result records: four carry SKIPPED, and four carry a more specific non-pass
verdict naming what did not happen - state mutation not permitted, for two of
them; no event produced, for one; no workflow started, for one.  Keeping them
distinct rather than collapsing all eight into one word is R-5's doctrine applied
one level finer: an unreachable stack and a run that was not permitted to create
the object a flow acts on are different facts, and a reader who could not tell
them apart would not know which of the two a later replay had fixed.  None of the
four verdicts is a pass, and none is readable as one.

The register any test exclusion must cite is docs/migration/baseline-test-failures.md,
and the absence of retry or rerun tooling that makes a single observed failure a
real failure is the subject of the sibling note 04-no-flaky-test-tooling.txt.
Neither is restated here.


A PRE-EXISTING CONDITION IS CAPTURED AS OBSERVED, NEVER NORMALISED AWAY
-----------------------------------------------------------------------
R-6's ruling on this ledger is a prohibition rather than a permission: where a
substitution reveals a pre-existing oddity in output - an inconsistent format, a
stale value, a documented service that answers with a server-error status - the
oddity is recorded and left alone.  Normalising a defect out of existence would
both hide the defect and weaken the evidence, and it would do so under cover of
making the comparison tidy.

THE NAMED CASE.  One documented endpoint in the reference stack is EXPECTED to
answer with a server-error status.  That expectation is recorded at the base
commit in two places - README.md:L53 and docs/setup.md:L33, which in the current
working tree have moved to README.md:L50 and docs/setup.md:L30 as surrounding
prose changed - so it is a documented pre-existing condition and not a
regression.  Where a run surfaces it, the status is captured exactly as observed
and recorded as an expected condition or as a skip carrying that reason.  NO
ENTRY IN THIS LEDGER MATCHES A STATUS TOKEN, so there is no expression that could
rewrite it even by accident.

WHERE THAT CONDITION IS ACTUALLY WRITTEN DOWN, checked for this note rather than
assumed.  It is recorded inside the capture tree, at notes/reference-stack.txt on
both sides, where the expected status is stated beside the status this run
observed and the record states that it is captured as observed under R-6 - not
repaired, not retried into submission, not hidden, and not a migration
regression.  It is NOT an entry in the pre-existing defects register, and this
ledger does not claim that it is; that register holds the two forced-execution
alias defects named further below.  The distinction is recorded because a
cross-reference to the wrong register is exactly the kind of claim a reviewer
cannot check without doing the work again.

NOTHING IS FIXED HERE.  This note records; it does not repair.  It proposes no
change, adds no tooling, no dependency and no navigation entry, and it leaves
every condition it names exactly as it found it.  The change set invokes R-6's
escape clause - which permits repairing a pre-existing condition only where the
condition blocks a validation item - EXACTLY TWICE: creating the frontend
profiles module, and removing the stylesheet-compiler toolchain that cannot build
on Node 20.  NEITHER INVOCATION IS IN THIS FOLDER, so the exception count stays
auditable and cannot quietly grow.


EVIDENCE, NEVER AN EXIT STATUS
------------------------------
R-T7's ruling on this note is absolute: no entry above is justified by a step
having succeeded, and no pass or fail conclusion is drawn anywhere here from a
process exit status.  Every entry is verifiable against two things a reviewer can
open - the committed script, and the captures themselves.

The reason this matters beyond principle is supplied by the repository.
Gruntfile.js:L143 carries the comment "Making grunt default to force in order not
to break the project." and Gruntfile.js:L144 acts on it, setting the force option.
Forced execution masks task failures, so a frontend build can fail a task and
still exit zero; an exit status therefore carries no information about whether the
pipeline did its work.  Two registered pre-existing defects are masked by exactly
that mechanism, and both are recorded in the pre-existing defects register rather
than fixed.

The same doctrine has already been demonstrated inside this pipeline.  A malformed
expression in the credential pass once produced zero-byte captures across the
whole run while the run reported success, as entry C2's pass preamble records.
That failure passed every exit-status check available and would have passed any
number more.  It was caught by looking at the produced files.

MIRROR OBLIGATION
-----------------
This note is paired with a counterpart at the identical filename on the other
side, docs/migration/smoke-evidence/baseline/notes/06-normalisation-and-redaction.txt.
The two notes folders mirror one another one-for-one so that a recursive diff of
the baseline and migrated capture directories is mechanical.  For this filename
that diff is expected to report a CONTENT difference and never a structural one:
the file must be present on both sides, and no counterpart may be missing.  The
filenames are therefore fixed and match character for character; a rename on
either side would turn a content difference into a structural one and break the
comparison for every reader who runs that diff.

AND ONE OBLIGATION SPECIFIC TO THIS FILENAME, because this is the ledger.  The two
ledgers are compared ENTRY BY ENTRY, not merely file against file.  The
substitutions, the helpers, the order and the placeholders must be identical, and
any entry that has to differ states the difference and the reason inside its own
block rather than letting the divergence pass silently.  On this side, no entry
diverges: the only per-entry difference from the baseline ledger is the
RESULT-FILES field, which is an observation about which expressions this run gave
work to and not a property of the substitution itself.  That distinction is drawn
where it is made, under identical replay above and again in the placeholder audit,
so that a populated field on one side and an empty one on the other can never be
read as a change in the pipeline.
