why this concern needs a file of its own
========================================
If the suite could silently retry a failing test, then "the migrated run
matched the baseline register" would prove nothing.  A flake could pass on
one side and fail on the other, or be retried into a pass on both, and a
row-for-row comparison would then be measuring the retry policy rather than
the runtime change.  Establishing that no retry machinery exists is what
makes fail-fast safe here and what makes this archive admissible as
evidence at all.

It is also the precondition for the rule that confines exclusions to
failures already present at the baseline.  That rule is only enforceable if
a baseline failure is real: "already present" says nothing if the failure is
not reproducible.  This note supplies that guarantee, and it is deliberately
kept out of the capture files, where a qualification would read as observed
output.

rules provenance — both facts, stated together
==============================================
There is NO on-disk user rules document for this project: the rules facility
returns, in full, that no user rules were provided.  Rules are nonetheless

Reporting only the first fact would imply that enterprise-standard best
practice is the sole standard here, which is wrong.  Reporting only the
second would misrepresent where the rules came from.  The identifiers R-1 to
R-7 and R-T1 to R-T7 used below, and their descriptive labels, are the
migration plan's OWN navigational convention rather than quoted titles.  No
rule has been invented and none softened.

what the archive itself says, which is where R-T7 puts the burden
=================================================================
The census above is an inspection of build configuration.  The archive is
then made to speak for itself, because R-T7 puts the burden on captured
evidence and never on a process exit status or a build summary line.  This
matters because a runner that repeats a failing test RECORDS the repetition
in the report: the extra attempt is written into the affected test case as a
rerun or flaky element, so a rerun cannot happen invisibly.  Neither archive
contains one.  A flake-count attribute is searched for alongside those
elements as a belt-and-braces measure, some report writers carrying one, and
it is absent too.

the accessibility failures, and where they were
===============================================
R-T3 requires that where a dependency fails under the JDK's strong
encapsulation, the DEPENDENCY is fixed and never the launch line.  Adding a
module-access JVM argument that opens or exports an otherwise-encapsulated
JDK package to the unnamed module was PROHIBITED, and none was added.  The
argument spellings are deliberately not written anywhere on this page.

Two such failures bear directly on this archive, because both were inside
TEST libraries and a test library is what runs the suite:

1) The dominant mocking library in this suite failed on Java 17 with an
   inaccessible-object error raised from its own class proxy factory, and the
   release between the pinned one and the one adopted failed in the same way.
   Resolution: the library was UPGRADED.
2) The static-and-constructor mocking framework failed on Java 17 with an
   inaccessible-object error raised from its reflection helper against a
   core JDK method, and the version in use was that project's FINAL release,
   so there was no version to advance to.  Resolution: the library was
   REMOVED outright.  That removal is additionally what lifted its hard
   version pins on the mocking core and on the test framework, which is what
   allowed the mocking core to advance to a release whose inline mock maker
   can instrument a class file at major version 61.

Six test classes depended on the removed framework.  All six were REWRITTEN
onto the retained mocking library, NOT EXCLUDED, and EVERY ASSERTION IS
UNMODIFIED; the six classes and the shape of the rewrite are recorded in
docs/migration/baseline-test-failures.md.  The three library rows themselves
— the upgrade, the removal and the mocking-core advance — carry their
measurements in docs/migration/dependency-change-inventory.md and are not
restated here, which is the scope fence R-1 imposes.

ArkCase's own production CODE encountered no accessibility failure: every
call site in it that widens reflective access targets ArkCase's own classes,
and no security manager is installed.  Together with every failure having
been resolved at the library, that is why the JDK access exceptions register
ships EMPTY.  That register is named here BY TITLE ONLY.

delta-explanation: the migration plan asserts that EVERY accessibility
  failure encountered anywhere in this migration was inside a test library.
  The delivered JDK access exceptions register records FIVE in total: the two
  test-library failures above, and three more in production DEPENDENCIES.
  All five were resolved at the library and none became a launch-configuration
  exception, so that register is legitimately empty — but "all of them were
  in test libraries" is not what the delivered evidence says, and R-7
  requires the difference to be visible rather than smoothed over.  The two
  recorded above are the two this archive's soundness actually rests on; the
  register holds the other three with their measurements.

the single auditable exclusion location, recorded honestly
==========================================================
The migration adds ONE pinned unit-test-runner declaration, in the root
aggregator's plugin management.
observed: pom.xml:391-395 — a groupId, an artifactId and a version reference,
  and nothing else.  No configuration element, therefore no excludes element,
  therefore no exclusions.
version-property: maven.surefire.plugin.version at pom.xml:173, set to 3.5.2
  and shared with the integration-test runner at pom.xml:434 so unit and
  integration forking cannot drift apart.
guardrail-comment: pom.xml:387-390, which names in the POM itself the two
  things that must stay out of the declaration.

its three justifications:
1) reproducible unit-test execution on the new runtime
2) a single auditable home for baseline-failure exclusions, where the
   reactor previously had none at all
3) control over fork arguments

NOT A HARD BLOCKER, and recorded as such rather than dressed up as a
compatibility fix: the version the build tool implicitly bound did execute
the suite successfully on Java 17.  Its row in
docs/migration/dependency-change-inventory.md carries the same honest
classification, under R-T4 for explicit pinning.

It ships with NO exclusions, and it may carry none unless a row in
docs/migration/baseline-test-failures.md justifies one.  Any exclusion added
later must cite its row BY CLASS AND BY METHOD, so that the citation resolves
to one test method and one evidence file rather than to a module or a
package.  Before this declaration existed there was no such location in any
of the 145 POMs, so an exclusion could not have been reviewed even in
principle.  Nothing in this note proposes excluding anything.

One further constraint governs the same declaration and belongs to
05-coverage-vs-test-exclusions.txt, which owns the analysis: it must set no
literal fork-argument override, or coverage instrumentation is silently
severed.

mirror obligation
=================
The baseline counterpart carries this exact filename —
04-no-flaky-test-tooling.txt, character for character — at the mirrored path
under baseline/notes/, so that diff -r over the two trees is mechanical.  A
CONTENT difference at this filename is expected and correct: the two sides
state different runtimes, different archive sizes and a different
unit-test-runner version.  A STRUCTURAL difference — this file present on one
side only — is not, and means the mirror has been broken.
