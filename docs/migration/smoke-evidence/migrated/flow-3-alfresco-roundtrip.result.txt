MIGRATION PATH EXERCISED

    the reinstated XML binding API and its runtime, and the activation framework's
    MIME-type mapping - the reason the reference implementation was mandatory
    rather than the API-only jar

Recorded so that a reader understands why this flow exists at all, and so that a
future difference here can be attributed rather than guessed at.  Every figure
below was re-derived against the tree while writing this record, and where a
figure differs between the base commit and the replay tree, both are given.

THE BINDING EXPOSURE IS THE LARGEST OF ANY REMOVED PLATFORM MODULE.  The package
javax.xml.bind appears in 84 Java files, 137 occurrences, across 21 Maven modules
- 82 files in main source and 2 in test source.  Re-derived on the replay tree
and, with the repository history, at the base commit: both counts are identical on
both, so the change set added no consumer and removed none.  The removal is
compensated by reinstating the API and its runtime as ordinary javax-namespace
Maven artifacts in the aggregator's global dependencies block, which propagates
them to all child modules by inheritance exactly as the platform's own runtime
image once did; the aggregator records that intent in a comment beside the
entries, and the same block already carried a logging artifact for a comparable
build-infrastructure reason, so the pattern is pre-existing rather than invented
here.  The consequence is ZERO IMPORT EDITS in all 84 files, which is the single
largest scope reduction in the whole migration, and this flow is where it is
exercised end to end.  The coordinates are javax.xml.bind:jaxb-api 2.3.1 at
compile scope and org.glassfish.jaxb:jaxb-runtime 2.3.1 at runtime scope, pinned
as properties in the aggregator and re-read there while writing this record.

PROVIDER CONTENTION WAS SETTLED BY EXECUTION, NOT BY REASONING.  A second binding
implementation is already on the classpath, namely the persistence provider's
object-to-XML component, and it can register itself as the provider.  Had it won
resolution, generated XML could have changed shape, which would be a silent
violation of the requirement to preserve response shapes and document formats -
the largest unquantified behavioural risk in the whole backend track.  Three
classpath shapes were exercised on the target runtime: reference-implementation-
only resolved correctly; the full deployed shape resolved to the same reference
implementation and produced identical XML; the alternative implementation alone
failed outright.  Two conclusions follow and both are recorded here.  First, NO
PROVIDER-SELECTION PROPERTIES FILE IS REQUIRED ANYWHERE AND NONE IS ADDED -
adding one would be a behavioural change dressed as a safety measure.  Second,
the reference-implementation addition is both MANDATORY and SUFFICIENT: mandatory
because the alternative cannot serve the API on its own, sufficient because it
wins resolution in the shape that actually deploys.  The operational reading for
this flow: IF A PAYLOAD'S XML SHAPE EVER DIFFERS between the baseline capture and
the replay, PROVIDER RESOLUTION IS THE FIRST THING TO SUSPECT, ahead of the
application code, because nothing in the application changed on this path.

THE ACTIVATION ARTIFACT CHOICE IS BEHAVIOURAL, NOT COSMETIC, AND R-7 IS WHAT
DECIDED IT.  Two candidates satisfied the same javax.activation API, and the
coordinates gave no hint that the choice mattered.  Reading both jars showed they
are not equivalent, and the reading was repeated on this host while writing this
record: the API-only jar, javax.activation:javax.activation-api 1.2.0, carries 31
classes and LACKS the META-INF/mimetypes.default and META-INF/mailcap.default
resources, while the reference implementation, com.sun.activation:javax.activation
1.2.0, carries 42 classes and ships BOTH.  A class-by-class comparison confirms
the reference implementation is a strict superset: no class of the API-only jar is
absent from it.  Five of the six activation-consuming files use MIME-type mapping,
re-derived by name - two batch-capture listeners, an email-attachment extractor
and its test, and a stream data source - and the sixth uses only a data handler.
MIME-type mapping reads exactly those two resources.  The API-only jar would
compile cleanly, deploy cleanly, and then SILENTLY RESOLVE MIME TYPES DIFFERENTLY
- precisely the class of regression a behaviour-preserving refactor exists to
prevent.  Baseline behaviour requires those resources, so R-7 SELECTED THE
REFERENCE IMPLEMENTATION, and the aggregator records the reasoning beside its
exclusions of the competing provider for that package, so that exactly one
provider supplies it.  This is one of the migration's documented ambiguity
resolutions, recorded as the first entry of the ambiguity-resolutions register.

    TIED TO WHAT THIS FLOW CAPTURES.  The decision is observable in exactly three
    rows of this capture: the Content-Type resolved on the store leg, the
    Content-Type resolved on the retrieve leg, and the MIME type the application
    records for the stored object.  Those three rows are the runtime confirmation
    of the artifact choice, and they are why Content-Type is preserved verbatim
    on BOTH legs by the normalisation policy below rather than being stripped as
    a header.

    HONEST QUALIFICATION.  On this side those three rows read not-observed, as
    they do on the baseline side.  The tie-breaker therefore rests on the
    jar-content inspection recorded in that register and re-derived above, not on
    a captured value from either capture.  Saying otherwise would present a

THE CONTENT REPOSITORY BINDING IS THE REST-STYLE ONE, NOT THE REMOTE-CALL
BINDING.  Confirmed in the tree and re-read while writing this record: the binding
type and the endpoint parameter are set together at
CmisConfigurationService.java:366-367, and again at
ArkCaseCMISSessionFacade.java:58-59, in both cases naming the publishing-protocol
