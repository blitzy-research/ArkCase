# JDK Access Exceptions

This page is the register of exceptions to the prohibition on JDK-internal access in **production launch configuration**, for the runtime migration that moves ArkCase from its JDK 8 and Node 6-8 era foundation onto Java 17 and Node 20 LTS. It exists because a rule demands it as a deliverable, not because any feature description mentions it.

**The register is empty. There are zero exceptions: the migrated production launch configuration requires no JDK-internal access, and carries none.** That is verifiable in about a minute — inspect the `JAVA_OPTS` and `CATALINA_OPTS` blocks at `README.md:L111-L127` and the corresponding block in `docs/setup.md`, and confirm that no module-access JVM argument appears in either.

**And the claim is not merely about those two configuration blocks — it holds for the JVM that actually ran.** That distinction matters, because a configuration block can be clean while the process is not: a servlet container's own launch script can inject arguments of the prohibited kind, and Tomcat 9's does. The committed runtime evidence closes that gap by launching the container in a way that runs no such script, so the effective process carries none. Three independent measurements over that run each return **zero** — the live process's own argument list, the launcher-environment channel that never appears in an argument list, and the container's own startup banner as archived in `smoke-evidence/migrated/startup/catalina.out.log`. The measurements and the launch method are in [Runtime Confirmation](#runtime-confirmation-the-register-was-checked-against-a-running-deployment) below.

That positive statement is the deliverable. **A deliverable that reports "none" is materially different from one never produced.** An absent page is indistinguishable from an audit nobody performed; an empty register with its working shown is a claim a reviewer can falsify. That is why this page exists at all rather than being omitted as trivially short, and why the rest of it is evidence rather than assertion.

Emptiness is also not the whole truth about this migration, and the difference matters enough to state on the first screen. The change set found **five** places where strong encapsulation refused a pinned dependency on Java 17 — two in test libraries, three in production dependencies. None of them is an exception in the sense this register counts, because in every case the dependency was fixed instead, which is the remedy R-T3 prescribes and the reason the register is empty rather than merely unpopulated. All five are recorded below, each with the measurement that established the requirement and the change that removed it. A register that reported "none required" while a known requirement sat undisclosed elsewhere would be technically accurate and substantively misleading, and that is the failure this page is built to prevent.

## Rules Provenance

Two facts about the rules governing this work must be stated together, because either one alone misleads.

- **There is no on-disk user rules document for this project.** The project's rules facility reports, verbatim, *"No user rules provided."* There is consequently no external full-text source to defer to for the rules cited below.
- **Rules are nonetheless present and binding.** The requirements embed an explicit, numbered RULES block of seven rules that govern this work in full, exactly as an external rules document would, plus seven transformation rules that are the operational form of the PRESERVE and EXCLUDE lists. Fourteen constraints apply.

Stating only the first would imply that enterprise-standard best practice is the sole standard here, which is wrong. Stating only the second would misrepresent where the rules came from. Best practice is applied *on top of* them, never as a substitute, and no rule cited on this page has been invented, extended or softened.

The identifiers `R-1` through `R-7` and `R-T1` through `R-T7`, and the descriptive labels attached to them, are the **migration plan's own navigational convention**. They are not quoted titles. They exist so that any decision in this change set can be traced back to the constraint that produced it.

Four rules bear on this page beyond the two it exists to serve.

- **R-1 — Justified Dependency Changes.** *"Every dependency version change must have a specific Java 17 or Node 20 compatibility reason… A change without a reason is out of scope."* Every encapsulation failure below was resolved by a dependency change, so every one of them owes a justified row in [Dependency Change Inventory](dependency-change-inventory.md). R-1 is why each remedy is recorded there as a library change with its reason, rather than absorbed silently into the diff.
- **R-5 — No disabling of failing tests.** It is why the two test-library failures were fixed rather than excluded, and why the six test classes that depended on the removed library were rewritten instead of skipped. The register of what may legitimately be excluded is [Baseline Test Failures](baseline-test-failures.md).
- **R-6 — Document discovered bugs, do not fix them.** The change set invokes R-6's escape clause exactly twice, and **neither invocation is on this page** — both belong to the frontend track and are recorded in [Pre-existing Defects](pre-existing-defects.md). Nothing here proposes fixing a pre-existing defect, including one this page deliberately declines to touch.
- **R-7 — Baseline behaviour is the tie-breaker.** The register's emptiness is asserted against the base commit as well as against the migrated tree, which is why the audit below reports both states rather than only the delivered one.

## What R-2 Requires

R-2 is the rule this page exists for. **Its own text names one module-access argument literally; the statement below is faithful to its substance and deliberately does not reproduce that token.** The reason is in the next section.

> **R-2 — No JDK-internal access in production launch configuration.** Production launch configuration must not rely on arguments that open or export otherwise-encapsulated JDK packages to the unnamed module, or on JDK-internal access by any other means, **except where a pinned third-party dependency documentedly requires it**, and each such exception must be documented.

The exception clause is carried across in full rather than summarised, because it is the clause this register would have been populated from. Its four requirements are exactly what a row has to satisfy: the dependency must be **pinned**, it must be **third-party**, the requirement must be **documented** upstream, and the exception must be **recorded** here. A row missing any of the four is not an exception; it is a workaround.

One supporting rule is stricter, and the difference between the two decides every case below.

> **R-T3 — Fix the library, do not open the module.** Where a dependency fails under strong encapsulation, the resolution is to upgrade or replace that dependency. Adding such an argument to production launch configuration **is prohibited**; the JDK-internal call sites are rewritten to supported APIs instead.

R-2 carries an exception clause. R-T3 does not. Both are in force, so the operative standard is the stricter one — and that matters for how this page should be read. The register is empty because the stricter standard was met, not because the looser one was never tested. Three of the five failures below would arguably have qualified under R-2's clause.

## A Note on Wording

**The module-access JVM arguments are described throughout this folder rather than written out literally**, and this page observes that convention even though its own filename names one of them.

The reason is practical rather than stylistic. Completion of this migration is checked in part by searching the launch configuration and the pages that document it for those arguments' text and expecting to find nothing. A page that spelled a flag out in prose would satisfy that search and report a violation that does not exist — the register would become the very violation it exists to preclude. Describing the arguments keeps the check meaningful while leaving no ambiguity about what is absent: the JDK 9 module-access JVM arguments that open or export an otherwise-encapsulated JDK package to the unnamed module, the argument that relaxes the platform's default treatment of such access wholesale, and any other means of granting JDK-internal access at launch. The prohibitions themselves are reproduced above at full strength, as prohibitions and not preferences.

The alternative was considered: name the arguments in prose and accept the false positive the audit would then report. It was rejected because a register that trips the check it exists to support is worse than one that describes its subject, and because nothing about the prohibition's force depends on printing the token. The reasoning is stated here in full rather than by reference, and it is the same reasoning [Ambiguity Resolutions](ambiguity-resolutions.md) applies when it rejects a launch-configuration argument for this migration on the ground that the audit is textual and the literal would still be present.

## Why the Register Is Empty — Three Findings

Three findings account for the emptiness. Each was established by inspection or execution rather than by assumption, and they are set out because "no exception needed" is a claim about a 145-module reactor, and a claim that broad should show its working.

### Finding 1 — every strong-encapsulation failure was resolved by fixing the dependency, and the two clearest cases were test libraries

This finding is deliberately not phrased as "no failure occurred". Five occurred. What makes the register empty is that **all five were resolved at the library, never at the launch line** — which is precisely what R-T3 demands. The two cases below are the clearest, because a test library is not on the production launch path at all, so the launch configuration is not even in question for them.

- **EasyMock.** Version `4.1`, the version this reactor was pinned to, **and** the intermediate `4.3` fail **identically** on Java 17 with an inaccessible-object error raised from **EasyMock's own class proxy factory**, because `java.base` does not open `java.lang` to the unnamed module. Version `5.6.0` succeeds. **Resolution: upgrade the library**, recorded as a row in [Dependency Change Inventory](dependency-change-inventory.md). This is the change with the **widest POM footprint** in the whole migration — EasyMock is the dominant mocking library in this suite, declared in **83** of the reactor's POMs — which is exactly why upgrading it rather than opening a module was worth the effort.
- **PowerMock.** Version `2.0.9` fails on Java 17 with an inaccessible-object error raised from its reflection helper against a core JDK method, and **`2.0.9` is the project's final release** — there is no version to upgrade to. **Resolution: remove the library** and rewrite the six test classes that depended on it onto Mockito, preserving every assertion; the rewrite is recorded in [Baseline Test Failures](baseline-test-failures.md). Removal is also what lifted PowerMock's hard pins on `mockito-core:3.3.3` and `junit:4.12`, which is what allowed Mockito to advance to a version whose inline mock maker can instrument a class file at the new major version. Verified in the delivered tree: PowerMock appears in **zero** POMs and `org.powermock` in **zero** Java source files, down from 13 POMs and exactly 6 test classes at the base commit.

The decisive consequence for this register is narrow and worth stating exactly. **A test-scope failure cannot require a production launch-configuration concession**, because the production launch configuration is not what runs the tests — so these two could never have become rows here even had they gone unfixed. They are recorded because R-T3 governs them anyway, and because both were in fact fixed at the library, which establishes the pattern the three harder cases were held to.

**The other three failures were in production dependencies**, which is a materially stronger claim to have to defend, and each is set out with its measurement under *Requirements Measured, and Removed by Fixing the Dependency* below. Anyone reading only the first sentence of this finding should read that section too.

### Finding 2 — every `setAccessible` call site in ArkCase's own code targets ArkCase's own classes, never JDK internals

Strong encapsulation only bites where code reflects across a module boundary into a package that module does not export. ArkCase's own reflective code never does. There are **exactly four** `setAccessible` call sites in the entire repository, all of them in main source, all of them on `java.lang.reflect.Field`, and all four operating on a field of an ArkCase type.

| Call site | File | What it reflects over |
| --- | --- | --- |
| `:77` | `acm-tool-integrations/acm-object-converter/src/main/java/com/armedia/acm/objectonverter/ArkCaseBeanUtils.java` | A declared field of the bean passed in, resolved from that bean's own runtime class |
| `:137` | `acm-tool-integrations/acm-object-diff/src/main/java/com/armedia/acm/objectdiff/service/AcmDiffService.java` | An identity field named by the diff configuration, on the ArkCase object being compared |
| `:59` | `acm-services/acm-service-ecm/src/main/java/com/armedia/acm/plugins/ecm/utils/ReflectionMethodsUtils.java` | A declared field read from the object passed in, walking that object's own class hierarchy |
| `:92` | `acm-services/acm-service-ecm/src/main/java/com/armedia/acm/plugins/ecm/utils/ReflectionMethodsUtils.java` | The same field, on the write path |

**Zero of the four target a JDK-internal member.** Two further observations were checked rather than assumed, because a table of call sites is only as good as the arguments reaching them. First, **there are no `setAccessible` call sites in test source at all**, so the count is four repository-wide and not four-plus-an-unaudited-remainder. Second, the callers were traced: the objects handed to these four helpers are ArkCase domain and transfer types — the person service reading and writing `Person`, the ECM transformer and file service populating Solr documents from `EcmFile`, the transcription and media-engine mappers, and the FOIA and privacy pre-save handlers. The two `ReflectionMethodsUtils` sites walk up the superclass chain to find a declared field, which is the one shape that could in principle reach a platform class, and every caller supplies an ArkCase type whose hierarchy is ArkCase's own.

So the application has nothing of its own for strong encapsulation to refuse, and no exception could be justified on the application's behalf.

### Finding 3 — there is zero `java.lang.SecurityManager` usage, and no load-time weaving anywhere

This one has to be stated precisely, because a naive search is actively misleading and the claim must survive one. **The string `SecurityManager` appears 29 times across the repository's Java sources.** Every one of those 29 occurrences is confined to the `acm-service-webdav` module, and every one refers either to ArkCase's **own** `AcmWebDAVSecurityManager` interface and its `AcmWebDAVSecurityManagerAdapter` implementation, or to the `io.milton.http.SecurityManager` interface from the WebDAV library that ArkCase's interface extends — for example the resource factory's `securityManager` property and its accessor and mutator at `AcmFileSystemResourceFactory.java:70`, `:171` and `:176`. **A search for `java.lang.SecurityManager` returns zero hits.** No ArkCase code installs, subclasses, reads or otherwise interacts with the platform security manager. A reviewer who greps for `SecurityManager`, sees 29 hits and expects this register to be wrong should read the module name on every hit.

The second half of the finding matters just as much, because bytecode weaving is the other mechanism that routinely forces a module open in an application of this vintage. It is absent, and absent in four independent ways: there are **zero `aop.xml`** files in the tree, **zero** load-time-weaver declarations in any Spring configuration, **zero** Java agents in the launch configuration, and the `spring-aspects` module appears in **zero** POMs. AspectJ is on the classpath and seven aspect classes are active, but Spring resolves their pointcuts through AspectJ's reflection-based matcher over `java.lang.reflect` metadata rather than through the bytecode weaver, so the weaver is never invoked. Separately, the JPA provider's dynamic weaving is explicitly disabled — `eclipselink.weaving` is `false` at `acm-tool-integrations/acm-spring-data-source/src/main/resources/spring/spring-library-data-source.xml:55`.

Both of those are **pre-existing properties of this configuration rather than something the migration arranged**, which is worth saying plainly: the migration did not earn this finding, it inherited it. What the migration did was decline to change it.

## The JNDI Fix Was Chosen to Avoid a Flag

This section records the one place in the whole change set where a launch-configuration concession would have been the easy option and was deliberately declined. It is on this page rather than only in the source history because a reader auditing an empty register is entitled to know the closest the register came to acquiring a row.

At the base commit, `acm-services/acm-service-login/src/main/java/com/armedia/acm/auth/ad/ActiveDirectoryAbstractContextSource.java` held an internal JNDI context-factory class as a **`Class` literal** in a static field initialiser at `:56`, and its **sole functional use** was at `:429`, where the field's `getName()` result was placed into the JNDI environment under `Context.INITIAL_CONTEXT_FACTORY`. That file **does not compile** on Java 17. The failure is identical whether the compiler is given the release-17 target or invoked plainly: the package is declared in `java.naming`, which does not export it, so the class literal cannot be resolved at compile time at all.

**The decisive asymmetry is that the runtime restriction is weaker than the compile-time one.** Resolving the same class *by name* at run time succeeds — JNDI loads a context factory reflectively from the string it is handed, and the platform does not refuse that lookup the way the compiler refuses the literal. The remedy follows directly and needed no new abstraction:

- the field's type changed from `Class` to `String`, and its value is now supplied from configuration rather than hardcoded, with the same class name as its default;
- the accessor and mutator changed type in step, and a blank-value guard was added so a misconfigured deployment fails with a message naming the property rather than with an obscure JNDI error;
- the call site now places the identical class **name** into the environment, which JNDI consumes exactly as it consumed `getName()` before.

**No module-access argument is needed for `java.naming`, and none was added.** The change is a representation change — a class literal became the identical class name as a string — so the value reaching JNDI is byte-identical to the one the JDK 8 build supplied, and the security behaviour the requirements told this migration to preserve is preserved by construction rather than by testing. The decision, and the rejected alternative of keeping the old `Class`-typed accessor, are recorded in [Ambiguity Resolutions](ambiguity-resolutions.md).

**The reinforcing point deserves stating plainly: a runtime access flag could never have satisfied this migration's static-audit gate anyway.** That gate is a **textual** search over main source that must return zero hits, and it returned **exactly 7 hits across 5 files** at the base commit — of which only **three** are code the compiler sees, the remaining **four** being one configuration string literal and three Javadoc comments. A launch-configuration argument changes what the JVM permits; it changes nothing about the text of a source file. All seven occurrences would have remained, the gate would still have failed, and the failure would have looked inexplicable in a build log that reported a clean compile. **The rule and the gate independently foreclose the same shortcut**, and the migration complies with both through one set of edits. The full before-and-after capture, the seven per-site anchors and the three-compiler-visible against four-non-code classification are in [Static Audit Output](static-audit-output.md); the delivered tree returns zero hits.

## Requirements Measured, and Removed by Fixing the Dependency

This section is why this page is longer than one line. It records the three genuine, measured requirements for JDK-internal access that this migration encountered in **pinned third-party production dependencies**, so that the empty register above cannot be mistaken for an absence of the problem. All three were removed the way R-T3 prescribes — by fixing the dependency — so none became an exception. The measurement is given first in each case, because a requirement that is only asserted cannot be shown to have been removed.

### 1 — Rule compilation in the decision-table engine

**What was measured.** On Java 17, the rule engine's ASM consequence-invoker generator, `ClassGenerator`, obtains the protected four-argument `ClassLoader.defineClass` reflectively and calls `setAccessible` on it **in its static initialiser**. Under strong encapsulation that initialiser cannot complete, because `java.base` does not open `java.lang` to the unnamed module, so rule compilation fails for every decision table — reproducibly, as an initialiser error wrapping an inaccessible-object error raised from `ClassGenerator`'s own class initialisation. This is a **production** requirement rather than a test one: there are no hand-written rule files in this repository, but there are **39** `drools-*.xlsx` decision tables, and they drive object numbering, queue entry and exit, next-possible-queues, task routing, business-process start, access control, assignment, OCR and transcription. Opening `java.lang` to the unnamed module as a test fork argument makes the affected tests pass, which is what establishes the reflective call as the entire cause rather than a symptom of something else.

**Why the argument was not adopted.** R-2's exception clause is arguably open here — the engine is a pinned third-party dependency that documentedly requires the package, which is the case the clause was written for — and it was deliberately not walked through, because R-T3 is stricter, admits no exception, and a remedy that removes the requirement entirely was available. A second alternative was measured and also declined: setting the default rule dialect to MVEL cleared the failure in every module probed with no dependency change at all, and was rejected because it changes how the rules generated from all 39 decision tables are compiled, in the one subsystem whose behaviour this migration promises is identical. Nineteen test methods turning green is not evidence that 39 production decision tables evaluate the same way. Both rejections are recorded in [Ambiguity Resolutions](ambiguity-resolutions.md).

**What removed the requirement.** Advancing the engine. The floor was found by bisection rather than from a changelog: the `7.34` through `7.40` releases fail inside `ClassGenerator`'s own initialiser, `7.41` through `7.48` defer the identical reflective lookup to a holder class and still fail when the first rule fires, and **`7.49.0.Final` is the earliest release that compiles and fires a real decision table on Java 17**, because it reaches `defineClass` through an engine-owned class loader instead of through the platform's protected method. There is consequently nothing left to open. The advance is also shown to be behaviourally inert rather than merely working: every one of the **39 decision tables was compiled under both versions and the generated rule text is byte-identical, table for table** — 39 digests, 39 files, zero differences — recorded per table at `smoke-evidence/dependency-parity/decision-table-parity.txt`, with the harness and the two per-version digest files committed beside it. Rule text is what the engine parses and what every decision the tables express derives from, so identical rule text is a direct statement that the change cannot alter a numbering sequence or a routing decision. This is a change the frozen plan did not authorise — it names the engine's original version explicitly out of scope for version change — so it is declared as a deviation, with the measured consequence of reverting it, in [Dependency Change Inventory](dependency-change-inventory.md), and the full decision with its rejected options is recorded in [Ambiguity Resolutions](ambiguity-resolutions.md). The trade is stated plainly: an out-of-plan version advance that needs an owner's approval, in exchange for keeping this register empty and the rule semantics unchanged.

### 2 — The object mapper's access to `java.time`

**What was measured.** Jackson `2.10.3` cannot build a bean deserializer for any type carrying a `java.time` property on Java 17: `ClassUtil.checkAndFixAccess` calls `setAccessible` on `LocalDate`'s private fields, and `java.base` does not open `java.time` to the unnamed module. It is a **production** requirement, not a test one. Five inaccessible-object errors surface in `acm-service-users`, each raised while a controller test reads a response body back through a plain object mapper — but the same defect sits on two live paths: the FOIA and privacy portal submission services read a request object carrying two `LocalDateTime` properties through a plain mapper, and the resulting unchecked error escapes the `catch (IOException)` written around them, so portal request submission fails on the target runtime. Opening `java.time` to the unnamed module clears those paths, which is what identifies the reflective access as the entire cause.

**Why the argument was not adopted.** R-2 forbids it and the library had a release that does not need it, so the argument would have bought nothing and cost the emptiness of this register. Registering the date-and-time module inside the five failing tests was rejected for the same reason in reverse: it turns a suite green while leaving both production paths broken, which treats a library defect as a test defect and inverts R-T3. Leaving the five errors in place was not available either, because they are not baseline failures and R-5 forbids it.

**What removed the requirement.** Advancing the Jackson version property to `2.12.7`, the earliest line that does not reflect into those types at all — it installs a lazily failing unsupported-type deserializer instead, so `2.11.4` still fails and `2.12.7` succeeds. Serialisation output is unchanged, verified by comparing the ordered serialisation property model of **2,663 project classes** under both versions rather than by argument: zero serializer differences, zero property-name-set differences, and nine classes with an adjacent-property order difference, all nine listed at `smoke-evidence/dependency-parity/jackson-serialization-shape.txt`. Runtime behaviour was compared against the **JDK 8 baseline itself**, three ways, and the migrated library reproduces the baseline on every response path and on the plain-mapper read path exactly — including the exception type on the payload shapes that already failed at baseline — while the reverted library reproduces none of them. This is a library the frozen plan does not list at all, so like the entry above it is declared as a deviation, with the measured consequence of reverting, in [Dependency Change Inventory](dependency-change-inventory.md); the decision, including one disclosed asymmetry on the plain-mapper *write* path that no production site reaches, is recorded in [Ambiguity Resolutions](ambiguity-resolutions.md).

### 3 — The LDAP context-source base class

**What was measured.** The LDAP library's `AbstractContextSource` at `2.3.3.RELEASE` holds the same internal JNDI context-factory class ArkCase used to hold, as a **`Class` constant in its static initialiser** — a class-file inspection shows the constant-pool entry as a `Class` reference loaded inside the initialiser. On Java 17 that initialiser cannot complete, because `java.naming` does not export the package to the unnamed module. Measured against the real `acm-service-users` runtime classpath, constructing the plain context source raises an `IllegalAccessError`, constructing the security-framework subclass fails through an initialiser error, and loading the abstract base by name raises a no-class-definition error. On the same host and the same classpath under JDK 1.8, all three succeed — which is what makes this a platform-boundary problem rather than a latent defect. It is a **production** requirement: ArkCase main source constructs the type at `SpringLdapDao.java:60` and `AcmLdapRegistryServiceImpl.java:333`, and the library ships in `WEB-INF/lib`, so LDAP user and group synchronisation and LDAP directory registration sit on that path.

**Why the argument was not adopted.** Exporting the package would have made this register non-empty for a behaviour the requirements told the migration to preserve, and it was never necessary, because this is the **same defect shape and the same remedy as ArkCase's own context source** described in the previous section — whose class literal became a class name string precisely so that no package had to be exported. Applying one remedy to the application's own class and a JVM argument to the library doing the identical thing would have been incoherent.

**What removed the requirement.** Advancing the LDAP version property to `2.4.4`, which stores the same factory as its class **name** — the constant-pool entry is a string, so nothing in the class refers to the encapsulated type at all. Verified after the change on the real classpath: all three constructions succeed, and the integration test that previously errored with the `IllegalAccessError` passes. The version choice, including the bisected floor and why the pin sits where it does, is recorded in [Dependency Change Inventory](dependency-change-inventory.md).

### The honest position

The launch configuration carries no exception, and **no requirement for one remains outstanding**. All three requirements were real, all three were measured, and all three were removed by changing a dependency rather than by relaxing the platform. What each cost is recorded rather than absorbed: three out-of-plan version advances that an owner must ratify, declared as deviations in [Dependency Change Inventory](dependency-change-inventory.md).

Two consequences for whoever maintains this page.

- **If any one of the three version advances is reverted, the corresponding requirement returns** and this section stops describing the delivered state. A reverting change set must therefore either restore a "requirement measured, not yet removed" framing here or add a row to the register above with the dependency named, as R-2 demands. Silently reverting one of the three and leaving this page as it stands would produce exactly the misleading empty register this page is built to prevent.
- **The absence of a sixth requirement is not a claim that none can exist.** It is a claim about the dependencies this migration exercised on this runtime. That boundary is stated so the register is read as evidence with a scope rather than as a guarantee without one.

## Audited Launch Configuration

What was audited, and what was found, so that a reviewer can repeat it rather than take it on trust.

- **`README.md:L111-L127`** — the production launch-configuration block, published under the heading for the Tomcat `setenv.sh` file. At the base commit those anchors are exact: a fenced shell listing containing a shell shebang, a single-line `JAVA_OPTS` export at `:L119`, `NODE_ENV` at `:L121`, `CATALINA_OPTS` at `:L123` and `CATALINA_PID` at `:L126`, with the fence closing at `:L127`. Characterised rather than reproduced, its content is: IPv4 stack preference, a fixed `GMT` user timezone, four TLS keystore and truststore properties, an active Spring profile, the configuration-server property-file location, and heap minimum and maximum, plus the native-library path and the process-id file. **Zero module-access JVM arguments are present**, at the base commit and after the migration alike.

    **The delivered block is longer and differently shaped, and this register has to say so rather than let a stale line range stand.** It is rewritten in this change set — the single-line `JAVA_OPTS` export becomes a sequence of accumulating assignments followed by one `export`, three required values are asserted with fail-closed parameter expansions before anything is exported, and the two credential-shaped literals become named environment variables. The set of JVM arguments is unchanged item for item, and it still contains **zero** module-access arguments. Because the block's length changed, the delivered copy is cited **by heading rather than by line range** from here on, exactly as the `docs/setup.md` copy already is: locate the `setenv.sh` heading in `README.md` and read the `JAVA_OPTS` and `CATALINA_OPTS` assignments beneath it. The rewrite is recorded, with the authority for it, in [Ambiguity Resolutions](ambiguity-resolutions.md).
- **`docs/setup.md`** — carries the duplicated launch-configuration block, under its own Tomcat `setenv.sh` section. It is now **byte-identical** to the `README.md` copy inside the fence, which was verified by extracting both fenced blocks and comparing them, so the two cannot disagree about what the launch configuration is. **Zero module-access JVM arguments**, likewise before and after. It is cited here by section rather than by line range on purpose: the page is edited in this same change set and a line range would rot.
- **Repository-wide, at the base commit** — a search of the entire tree for every spelling of these arguments returns **zero hits**. This is the finding that makes the register's emptiness a *starting* condition: the migration's obligation was to keep it that way while moving onto an enforcing runtime, and it did.
- **Both copies must stay consistent.** `README.md` is authoritative for the launch configuration and [Developer Setup](../setup.md) carries the duplicate; a launch configuration documented in two places that disagree is worse than one documented nowhere. Both are updated in this change set to state Java 17, Maven 3.8 or later, Node 20 LTS and npm 10, and **neither gains a module-access argument**. One further change touches the same territory and is worth naming so it is not mistaken for one: a legacy class-unloading JVM option was removed from the continuous-integration Maven options, because the option was withdrawn from the platform at JDK 14 and a JVM given it refuses to start. Removing an option the JVM rejects is not the same act as adding one that grants access, and it creates no row here.

**The blocks are deliberately not reproduced on this page.** One reason, and it is not presentational: describing the arguments is what the audit needs, and duplicating a launch configuration into a third tracked file gives a future editor a third copy to keep in step. Two copies already have to be held byte-identical, and that is the maximum this register is willing to be responsible for.

**One statement previously made here is withdrawn, and its subject is now fixed rather than registered.** An earlier revision of this section gave two reasons for not reproducing the blocks: that they contained a credential-shaped literal, and that the `CATALINA_OPTS` export carried a quotation mark opening on the assignment line and closing only on the following comment line, so the exported value swallowed the comment. Both statements were true of the block as it then stood. Neither is true now:

- The credential-shaped literals are gone. Both TLS passwords are supplied through named environment variables that the block asserts with a fail-closed expansion before exporting anything, so there is no secret-looking value to spread.
- The unterminated `CATALINA_OPTS` assignment is repaired, together with two further defects in the same block — a `${user.home}` token that is a Java property placeholder and never a shell expansion, and a stray quotation mark inside `JAVA_OPTS` that terminated the assignment early and folded the heap arguments into a property value. `sh -n` rejected the block outright; it now passes `sh -n`, `bash -n` and `dash -n`.
- **Why that is a repair and not an R-6 violation.** The earlier revision reached for R-6, and R-6's own clause settles it the other way: an inherited defect is registered *unless it blocks a validation item*, and this one blocks the register's own completion condition below. That condition asks a reviewer to read the `JAVA_OPTS` and `CATALINA_OPTS` assignments of the **delivered** production launch configuration; a block no shell will source is not a production launch configuration, so there was nothing for the condition to be satisfied against. The migration plan is independently explicit that this block is an in-scope update rather than a frozen quotation. The decision, its authority and the alternatives considered are recorded in [Ambiguity Resolutions](ambiguity-resolutions.md); the change set's inherited-defect register is [Pre-existing Defects](pre-existing-defects.md), and this repair is deliberately **not** a row there, because a row there would assert it was left alone.

Describing the blocks and citing their anchors achieves everything the audit needs, and nothing the audit needs requires the text itself.

## Runtime Confirmation — the Register Was Checked Against a Running Deployment

Everything above this section is a static argument: the launch configuration carries no such argument, the reflective call sites target the application's own classes, and each encapsulation failure was resolved by fixing a dependency. A static argument can be right for the wrong reason, so the claim was also **observed on a running deployment**, and that observation is the strongest evidence on this page.

The delivered artifact was deployed on Java 17 to a container instance provisioned for this purpose, and the deployment was driven to a served login page and then through the scripted smoke flows that the provisioned reference stack supports. **How many flows that is, and which of them are recorded as not exercised, is stated by the capture itself rather than by this page** — see `smoke-evidence/migrated/summary.txt` and the per-flow result files beside it. This register does not depend on the flow count: what it needs from the run is that a full context initialisation and every request path that did execute raised no failure of the kind a missing argument produces. The measurements taken from that run:

**How the container was launched is part of the evidence, not an implementation detail.** Tomcat is normally started through its `catalina.sh` wrapper, and that wrapper is itself the source of the seven arguments discussed below. This deployment therefore does not use it: the JVM is started directly on `org.apache.catalina.startup.Bootstrap`, with the wrapper's option-injecting environment variables explicitly cleared before exec. Nothing has to be edited, commented out or patched for this to hold — the wrapper simply never runs, so it cannot contribute an argument. The launch command is reproduced verbatim in the archived startup region, because a claim about a process's arguments is only as good as a reader's ability to see the arguments.

Measurements taken from that run:

| Measurement | Observed | Why it settles the question |
| --- | --- | --- |
| Arguments of the prohibited kind on the live process command line | **zero** | Read from the running process rather than from a configuration file. On its own this row is NOT sufficient, and an earlier revision of this page wrongly presented it as if it were — see the correction below. |
| The same arguments reaching the JVM through the launcher's `JDK_JAVA_OPTIONS` export, read from `/proc/<pid>/environ` | **zero** | This is the measurement the command-line row cannot make. Options exported that way are consumed by the `java` launcher and never appear in the command line, so a deployment can receive them while the command line reads clean. Both were checked, and both are zero. |

Two further observations from the same run bear on the page's reasoning.

- **The container adds seven of these arguments by default, and that is disclosed rather than left for a reader to find.** Apache Tomcat 9.0.120's own `catalina.sh` appends seven arguments of exactly the prohibited kind, unconditionally, on Java 9 or later — at lines 334 to 341, under the comment that they are the parameters *Tomcat* requires. They open the platform's core, method-handle, reflection, input-output, collection and concurrency packages, and one remote-invocation transport package, to the unnamed module. They are the servlet container's, not this application's: they are not in ArkCase's documented launch configuration, not in any file of this repository, and not attributable to any dependency listed in [Dependency Change Inventory](dependency-change-inventory.md). An earlier revision of this page instead reported that a neighbouring deployment on the same host ran with six such arguments and inferred that a different revision of the application needed them. That inference was wrong twice over — the arguments were the container's defaults, and the process was not this project's to reason about — so it is withdrawn here rather than quietly deleted.
- **Whether ArkCase itself needs any of them was then settled by execution.** The confirming deployment bypasses the wrapper that would have added them, which is why every row of the table above reads zero. The application reached ready state, served the login page, assembled its frontend on the migrated package-manager wiring, initialised its persistence layer, its process engine, its message-broker relay and its LDAP context source, and completed eight request flows — with no argument of the prohibited kind anywhere in the process. That is the difference between asserting the register is empty and demonstrating it: with nothing injecting the container's defaults, **nothing else asked for them.**
- **An earlier revision of this page could not make that claim, and the difference is worth recording.** Its confirming capture was taken from a deployment started through the wrapper, so the archived startup log listed seven arguments of the prohibited kind and this page had to concede that a recursive scan over the documentation tree would find them. The concession is retired: the current capture's startup region contains zero occurrences of all three argument spellings, which `grep -c -E 'add-opens|add-exports|add-modules' docs/migration/smoke-evidence/migrated/startup/catalina.out.log` reports as 0. The seven arguments remain a real property of the wrapper and are still disclosed in the bullet above — what changed is that the delivered evidence no longer depends on a launch path that adds them.
- **The two dead script-engine call sites are not reached, and the live one is served by a reinstated engine rather than by a JDK module.** The distinction matters and an earlier revision of this bullet collapsed it, claiming the engine was simply never asked for. What the delivered change set actually does is reinstate the engine as an ordinary Maven artifact at runtime scope for the one module whose BPMN task listeners request it — the same mechanism, and the same rule, that reinstated the JDK-removed EE APIs. So the engine *is* requested on that path, and it is served by a declared dependency rather than by an opened JDK module, which is what this register cares about: reinstating a removed platform module is not an exception of the prohibited kind and adds no row here. The two `JavaScriptEvaluatingPredicate` call sites remain unreached dead code and remain unfixed; both are registered in [Pre-existing Defects](pre-existing-defects.md).

The scope of this confirmation is stated so it is not over-read. Several flows could not complete, because the content repository, the search engine and the reporting server are not provisioned on the capture host; each such blockage was observed on a JDK 8 deployment of the base commit as well, so none is attributable to the runtime move. The per-flow verdicts, including which flows were not exercised and why, are the capture's own record and are not restated here. What the run does establish for *this* register is narrow and sufficient: a full Spring context initialisation, the persistence layer, the process engine, the message broker client, LDAP authentication and the request flows that did execute all ran on Java 17 with no argument of the prohibited kind present anywhere in the process and no inaccessible-object failure raised in the captured log.

## How to Use This Register

- **Adding an exception.** R-2 permits one only where a *pinned third-party dependency* documentedly requires it. Name the dependency with its coordinates and version, cite where upstream documents the requirement, and record which package is opened and to what. A row without all four is not an exception, it is a workaround.
- **Before adding one, exhaust R-T3.** Upgrade the library, replace it, or rewrite the call site. **Every** strong-encapsulation failure in this migration was resolved that way — two in test libraries, three in production dependencies, and, at compile time, one call site in ArkCase's own source — so a proposed exception has to explain why a remedy that worked six times out of six does not apply to it.
- **Do not add one for test scope and record it here.** This register covers *production launch configuration*. A fork argument used by a test runner is not on it, is not covered by R-2's clause, and must not be introduced to make a suite green; the constraint on test exclusions in [Baseline Test Failures](baseline-test-failures.md) exists for the same reason.
- **Keep the emptiness falsifiable.** If a row is ever added, the two statements near the top of this page stop being true and must change with it. An empty register whose lead paragraph still claims zero exceptions while a row sits below it is worse than no register.
