# JDK Access Exceptions

This page is the register of exceptions to the prohibition on JDK-internal access in **production launch configuration**, for the runtime migration that moves ArkCase from its JDK 8 and Node 6-8 era foundation onto Java 17 and Node 20 LTS. It exists because a rule demands it as a deliverable, not because any feature description mentions it.

**The register of applied exceptions is empty. The migrated production launch configuration requires none, and carries none.**

That positive statement is the deliverable. A register that reports "none" is materially different from a register that was never produced, which is why this page exists at all rather than being omitted as trivially short.

It is not, however, the *whole* truth about this migration, and the difference matters enough to state on the first screen: the change set found **three** places where a pinned third-party dependency genuinely did require an encapsulated JDK package to be opened before it would work on Java 17. None of them is an exception in the sense this register counts, because in every case the dependency was fixed instead — which is the remedy R-T3 prescribes and the reason the register above is empty rather than merely unpopulated. All three are recorded in full below, each under its own heading, with the measurement that established the requirement and the change that removed it. A register that reported "none required" while a known requirement sat undisclosed elsewhere would be technically accurate and substantively misleading, and that is the failure this section exists to prevent.

## Rules Provenance

Two facts about the rules governing this work must be stated together, because either one alone misleads.

- **There is no on-disk user rules document for this project.** The project's rules facility reports, verbatim, *"No user rules provided."* There is consequently no external full-text source to defer to for the rules cited below.
- **Rules are nonetheless present and binding.** The requirements embed an explicit, numbered RULES block of seven rules that govern this work in full, plus seven transformation rules that are the operational form of the PRESERVE and EXCLUDE lists. Fourteen constraints apply.

The identifiers `R-1` through `R-7` and `R-T1` through `R-T7`, and the descriptive labels attached to them, are the **migration plan's own navigational convention**. They are not quoted titles. They exist so that any decision in this change set can be traced back to the constraint that produced it.

Two constraints bind this page directly, and they are not equally strict — which turns out to be the crux of the one open question on it.

> **R-2 — No JDK-internal access in production launch configuration.** Production launch configuration must not rely on arguments that open or export otherwise-encapsulated JDK packages to the unnamed module, **except where a pinned third-party dependency documentedly requires it**, and each such exception must be documented.

> **R-T3 — Fix the library, do not open the module.** Where a dependency fails under strong encapsulation, the resolution is to upgrade or replace that dependency. Adding such an argument to production launch configuration **is prohibited**; the JDK-internal call sites are rewritten to supported APIs instead.

R-2 carries an exception clause. R-T3 does not. Both are in force.

### A note on wording, so its absence is not read as vagueness

The two JVM arguments in question are **described throughout this folder rather than written out literally**. Every page here observes that convention, and this page observes it too even though its own filename names one of them.

The reason is practical rather than stylistic. The completion criteria for this migration require that the production launch configuration contain no such argument, and the cheapest way to check that is to search the launch configuration and the pages that document it for the argument's text. A page that spelled the flag out in prose would satisfy that search and report a violation that does not exist. Describing the arguments keeps the check meaningful. The prohibitions are reproduced above at full strength, as prohibitions and not preferences.

## The Launch Configuration Under Audit

The audited artefact is the production `JAVA_OPTS` block published in the repository `README.md`, duplicated in [Developer Setup](../setup.md). The two copies are kept consistent deliberately; a launch configuration documented in two places that disagree is worse than one documented nowhere.

Its complete content, characterised rather than reproduced: IPv4 stack preference, a fixed `GMT` user timezone, four TLS keystore and truststore properties, an active Spring profile, the configuration-server property file location, and heap minimum and maximum. Plus a `CATALINA_OPTS` addition for the Tomcat native library path and a `CATALINA_PID` location.

| Property of the launch configuration | Before the migration | After the migration |
|---|---|---|
| Arguments opening or exporting an encapsulated JDK package | none | **none** |
| Arguments naming a JDK-internal package | none | **none** |
| `-XX:+CMSClassUnloadingEnabled` | present in CI, absent here | removed from CI; the JVM refuses to start with it from JDK 14 onward |
| Anything else added by this change set | — | nothing |

The change set therefore does not *reduce* a set of exceptions from some number to zero. The set was empty before and is empty after, and the migration's task was to keep it that way while moving to a runtime whose module boundaries are enforced.

## Why No Exception Was Needed

Three findings, each established by inspection or execution rather than by assumption, account for the emptiness. They are given because "none needed" is a claim about the whole codebase, and a claim that broad should show its working. They are not a claim that no failure occurred: **five** strong-encapsulation failures were found, and every one of them was resolved by fixing the dependency, which is why none reached the launch configuration.

**Two of the five were inside a *test* library, where the launch configuration is not even in question.** EasyMock `4.1` and `4.3` both fail identically on Java 17 with an inaccessible-object error raised from EasyMock's own class proxy factory, because `java.lang` is not open to the unnamed module; EasyMock `5.6.0` succeeds. PowerMock `2.0.9` fails with an inaccessible-object error on a core JDK method, and `2.0.9` is the project's final release, so there is nothing to upgrade to and it was removed. Both were resolved the way R-T3 prescribes — by fixing the library — and neither touches production launch configuration, because a test library is not on the production launch path at all. **The other three were in production dependencies**, which is a materially stronger claim to have to defend, and they are set out with their measurements in *Requirements Measured, and Removed by Fixing the Dependency* below.

**ArkCase's own reflective code only ever targets ArkCase classes.** Every `setAccessible(true)` call site in the codebase was examined; all of them operate on the application's own types. None reaches into a JDK package, so strong encapsulation has nothing of the application's to refuse.

**ArkCase installs no `SecurityManager`,** and no load-time weaving is configured anywhere — no `aop.xml`, no load-time-weaver declaration, no Java agent in the launch configuration. EclipseLink's dynamic weaving is explicitly disabled in the data-source configuration. The two mechanisms that most often force a module to be opened in an application of this vintage are therefore both absent, and their absence is a pre-existing property of this configuration rather than something the migration arranged.

One near-miss is worth recording, because it is the kind of case that produces an unnecessary exception. `ActiveDirectoryAbstractContextSource` referred to an internal JNDI context-factory class as a class literal, which **does not compile** on Java 17 — the package is declared in `java.naming`, which does not export it. Adding an export argument would have made it compile, and would have been an exception on this register forever. The runtime restriction turns out to be weaker than the compile-time one: resolving the same class *by name* at run time succeeds. So the field became the class name as a string, supplied from configuration, and JNDI resolves it exactly as before. No argument was needed, and the register stayed empty. The reasoning is recorded as an R-7 decision in [Ambiguity Resolutions](ambiguity-resolutions.md); the call sites are itemised in [Static Audit Output](static-audit-output.md).

## Requirements Measured, and Removed by Fixing the Dependency

This section is the reason this page is longer than one line. It records the three genuine, measured requirements for JDK-internal access that this migration encountered in **pinned third-party production dependencies**, so that the empty register above cannot be mistaken for an absence of the problem. All three were removed the way R-T3 prescribes — by fixing the dependency — so none of them became an exception. The measurement is given first in each case, because a requirement that is only asserted cannot be shown to have been removed.

### 1 — Drools rule compilation

**What was measured.** On Java 17, `org.drools.core.rule.builder.dialect.asm.ClassGenerator` obtains `ClassLoader.defineClass` reflectively and calls `setAccessible(true)` **in its static initialiser**. Under strong encapsulation that initialiser cannot complete, so rule compilation fails for every decision table — reproducibly, as `ExceptionInInitializerError` → `InaccessibleObjectException` raised from `ClassGenerator.<clinit>:71`, and all 39 live decision tables are on that path, so object numbering and queue routing are affected in the deployed application rather than only in tests. Opening `java.lang` to the unnamed module as a fork argument makes the affected tests pass, which is what establishes the reflective call as the entire cause rather than a symptom of something else. The diagnosis and the affected test inventory are in [Baseline Test Failures](baseline-test-failures.md) under *The Migrated Run*.

**Why the argument was not adopted.** R-2's exception clause is arguably open here — Drools is a pinned third-party dependency that documentedly requires the package, which is the case the clause was written for — and it was deliberately not walked through, because R-T3 is stricter, admits no exception, and a remedy that removes the requirement entirely was available. The completion criteria likewise state the requirement as an absolute rather than as a default. Two alternatives were measured instead. Setting the default rule dialect to MVEL cleared the failure in every module probed, with no dependency change at all — and was **declined**, because it changes how the rules generated from all 39 decision tables are compiled, in the one subsystem whose behaviour this migration promises is identical; nineteen test methods turning green is not evidence that 39 production decision tables evaluate the same way. That decision is recorded in [Ambiguity Resolutions](ambiguity-resolutions.md).

**What removed the requirement.** Advancing the engine. The floor was found by bisection rather than from a changelog: 7.34 through 7.40 fail inside `ClassGenerator`'s own initialiser, 7.41 through 7.48 defer the identical reflective lookup to a holder class and still fail when the first rule fires, and **7.49.0.Final is the earliest release that compiles and fires a real decision table on Java 17**, because it reaches `defineClass` through the Drools-owned `ByteArrayClassLoader` instead of through the platform's protected method. The requirement therefore no longer exists: there is nothing left to open, and `acm-drools-rule-monitor` passes on it. The advance is also shown to be behaviourally inert rather than merely working: every one of the **39 decision tables was compiled under both versions and the generated rule text is byte-identical, table for table** — 39 digests, 39 files, zero differences — recorded per table at [`smoke-evidence/dependency-parity/decision-table-parity.txt`](smoke-evidence/dependency-parity/decision-table-parity.txt) with the harness committed beside it, so the change provably cannot alter a numbering sequence or a routing decision. This is a change the frozen plan did not authorise — it names Drools `7.34.0.Final` explicitly out of scope for version change — so it is declared as such, with its measured consequence of reverting, in [Dependency Change Inventory](dependency-change-inventory.md), and the full decision with its rejected options is entry 10 in [Ambiguity Resolutions](ambiguity-resolutions.md). The trade is stated plainly: an out-of-plan version advance that needs an owner's approval, in exchange for keeping this register empty and the rule semantics unchanged.

### 2 — The object mapper's access to `java.time`

**What was measured.** Jackson `2.10.3` cannot build a bean deserializer for any type carrying a `java.time` property on Java 17: `ClassUtil.checkAndFixAccess` calls `setAccessible` on `LocalDate`'s private fields, and `java.base` does not open `java.time` to the unnamed module. It is a **production** requirement, not a test one: five controller tests in `acm-service-users` fail on it, and the FOIA and privacy portal submission services read a request object carrying two `LocalDateTime` properties through a plain `new ObjectMapper()`, where the resulting unchecked error escapes the `catch (IOException)` around them. Opening `java.time` to the unnamed module clears those paths, which is what identifies the reflective access as the entire cause.

**Why the argument was not adopted.** R-2 forbids it, and the library had a release that does not need it — so the argument would have bought nothing and cost the emptiness of this register. Registering the JSR-310 module inside the five failing tests was rejected for the same reason in reverse: it turns a suite green while leaving the two production paths broken, which treats a library defect as a test defect and inverts R-T3.

**What removed the requirement.** Advancing `fasterxml-jackson-core.version` to `2.12.7`, the earliest line that does not reflect into those types at all — it installs a lazily failing unsupported-type deserializer instead, so `2.11.4` still fails and `2.12.7` succeeds. Serialisation output is unchanged, verified by comparing the ordered serialisation property model of **2,663 project classes** under both versions rather than by argument. This is a library the frozen plan does not list at all, so like the entry above it is declared as a deviation, with its measured consequence of reverting, in [Dependency Change Inventory](dependency-change-inventory.md); the decision, including one disclosed asymmetry on the plain-mapper *write* path that no production site reaches, is entry 11 in [Ambiguity Resolutions](ambiguity-resolutions.md).

### 3 — Spring LDAP context sources

**What was measured.** `org.springframework.ldap.core.support.AbstractContextSource` at `2.3.3.RELEASE` holds `com.sun.jndi.ldap.LdapCtxFactory` as a **Class literal** in its static initialiser — `javap -v` shows the constant as a `Class` entry loaded by `ldc` inside `<clinit>`. On Java 17 that initialiser cannot complete, because `java.naming` does not export the package to the unnamed module. Measured against the real `acm-service-users` runtime classpath: `new LdapContextSource()` raises `IllegalAccessError`, `new DefaultSpringSecurityContextSource(url)` fails through `ExceptionInInitializerError`, and `Class.forName` on the abstract base raises `NoClassDefFoundError`. On the same host and the same classpath under JDK 1.8.0_492, all three succeed — which is what makes this a platform-boundary problem rather than a latent defect. It is a **production** requirement, not a test one: ArkCase main source constructs the type at `SpringLdapDao.java:60` and `AcmLdapRegistryServiceImpl.java:333`, and the jar ships in `WEB-INF/lib`, so LDAP user and group synchronisation and LDAP directory registration sit on that path.

**Why the argument was not adopted.** Exporting the package would have made the register non-empty for a preserved security behaviour, and it was never necessary: this is the **same defect shape, and the same remedy, as ArkCase's own `ActiveDirectoryAbstractContextSource`**, whose class literal became the class name as a string precisely so that no package had to be exported. Applying one remedy to the application's own class and a JVM argument to the library that does the identical thing would have been incoherent.

**What removed the requirement.** Advancing `spring.ldap.version` to `2.4.4`, which stores the same factory as its class **name** — the constant is a `String` entry, so nothing in the class refers to the encapsulated type at all. Verified after the change on the real classpath: all three constructions succeed, and `com.armedia.acm.auth.ContextIT#addAndRemoveChildContext`, which errored with the `IllegalAccessError` before, passes. The version choice, including the bisected floor and why the pin sits above it, is recorded in [Dependency Change Inventory](dependency-change-inventory.md).

### The honest position

The launch configuration carries no exception, and — unlike the position this page recorded before both remedies were measured — **no requirement for one remains outstanding**. All three requirements were real, all three were measured, and all three were removed by changing a dependency rather than by relaxing the platform. What each cost is recorded rather than absorbed: three out-of-plan version advances that an owner must approve, declared as deviations in [Dependency Change Inventory](dependency-change-inventory.md).

Two consequences for whoever maintains this page. First, if any one of the three version advances is reverted, the corresponding requirement returns and this section stops describing the delivered state — so a reverting change set must either restore this section's earlier "not applied" framing or add a row to the empty register above with the dependency named, as R-2 demands. Second, the absence of a *fourth* requirement is not a claim that none can exist: it is a claim about the dependencies this migration exercised. A new library, or a code path these tests never reach, could surface another.

## How to Use This Register

- **Adding an exception.** R-2 permits one only where a *pinned third-party dependency* documentedly requires it. Name the dependency, cite where the requirement is documented, and record which package is opened and to what. A row without all four is not an exception, it is a workaround.
- **Before adding one, exhaust R-T3.** Upgrade the library, replace it, or rewrite the call site. **Every** strong-encapsulation failure in this migration was resolved that way — two in test libraries, three in production dependencies, and, at compile time, one call site in ArkCase's own source — so a proposed exception has to explain why a remedy that worked six times out of six does not apply to it.
- **Do not add one for test scope and record it here.** This register covers *production launch configuration*. A fork argument used by a test runner is not on it, is not covered by R-2's clause, and must not be introduced to make a suite green — the constraint on test exclusions in [Baseline Test Failures](baseline-test-failures.md) applies for the same reason.
- **Re-deriving the emptiness.** Read the `JAVA_OPTS` block in the repository `README.md` and in [Developer Setup](../setup.md) and confirm neither contains an argument that opens or exports a JDK package. That is the whole check; it is deliberately something a reviewer can complete in a minute without building anything.
