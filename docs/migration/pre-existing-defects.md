# Pre-existing Defects

This page is the register of defects that were **discovered during** the runtime migration onto Java 17 and Node 20 LTS and **deliberately not fixed**. It exists because a rule demands it as a deliverable, not because any feature description mentions it.

The headline figures, so they do not have to be inferred: **Numbers 1 to 98 are used and 57 is withdrawn, so 97 entries are live: 95 are not fixed and 2 are.** The first **eleven** are the ones the governing plan mandated; the rest were added by later verification passes, described under *Register* below. Entry numbers run 1 to 56 and 58 to 98 — **57 is withdrawn and not reused**, because the condition it described turned out to be a migration regression rather than an inherited one and has been fixed; see *Withdrawn from this register*.

**The two that are fixed are entries 94 and 95**, both conditions of the documented Tomcat launch-configuration block: a pair of literal credentials, and the fact that the two properties shared one value which opened only one of the two stores. They are repaired under the **same authority** as R1 to R3 below — the migration plan places that block in the change set on its own initiative — and therefore **not** under R-6's escape clause. **The escape clause is still invoked exactly twice**, and neither invocation repairs an entry. Three further launch-configuration defects are described but deliberately **not numbered**, because they were repaired before ever being registered: they are labelled R1 to R3 under *Three repaired launch-configuration defects*.

**Count the register yourself rather than trusting these figures**, and use the Fixed cell as the discriminator: this page carries a **second** numbered table — the client-contract table under entry 21 — whose rows also begin with an integer, so a bare row count folds it in and reports 107. Two earlier revisions of this page published a wrong figure for exactly that reason, and a third published 86 when the register held 94.

```bash
P=docs/migration/pre-existing-defects.md
grep -cE '^\| [0-9]+ \|.*\| (Yes|No)[^|]*\|$' $P   # 97  — live entries
grep -cE '^\| [0-9]+ \|.*\| No[^|]*\|$'       $P   # 95  — not fixed
grep -cE '^\| [0-9]+ \|.*\| Yes[^|]*\|$'      $P   #  2  — fixed: entries 94 and 95
```

The `[^|]*` matters and is not defensive clutter: four rows carry a **reasoned** verdict — `No — <reason>` — so the narrower `\| No \|$` form that an earlier revision of this page and the provisioned-stack capture both used undercounts by four and reports 91.

**Three committed smoke captures publish a smaller figure, and they are right to keep it.** `smoke-evidence/provisioned-stack/smoke-run-summary.txt` and two of its flow records report *"69 entries, 0 fixed"*, together with the narrow command that produced it. That was the **measured** size of this register on the day that capture ran, and it is not edited here for the same reason no other observation in a capture is edited: a capture is a record of one moment, and rewriting its arithmetic to agree with a later tree state is the authenticity defect this deliverable has already had to remove once. Two things have changed since, and both are visible from this page rather than from the capture: the register has grown by later verification passes, and two entries have since been repaired. So a reader who runs the capture's own command today gets **91**, not 69 and not 97 — 91 because that command undercounts by the four reasoned rows, and neither 69 nor 0-fixed because both figures are older than the tree. **This page is the authority for the count; the captures are the authority for what they observed.**

Its completion condition has two halves, and the second is the one that makes the page useful: every entry is present, and the escape clause is shown invoked exactly twice. A register listing defects without accounting for the exceptions to its own rule would let the exception count grow quietly, which is the failure mode it exists to prevent.

Every anchor on this page was verified against the working tree rather than copied from a plan. Where a measurement differs from what was expected, the measured value is given.

## Rules Provenance

Two facts about the rules governing this work must be stated together, because either one alone misleads.

- **There is no on-disk user rules document for this project.** The project's rules facility reports, verbatim, *"No user rules provided."*
- **Rules are nonetheless present and binding.** The requirements embed an explicit, numbered RULES block of seven rules, plus seven transformation rules that are the operational form of the PRESERVE and EXCLUDE lists. Fourteen constraints apply.

The identifiers `R-1` through `R-7` and `R-T1` through `R-T7` are the **migration plan's own navigational convention**, not quoted titles.

One rule mandates this page:

> **R-6 — Document discovered bugs, do not fix them.** Pre-existing bugs discovered during the work are documented rather than fixed, **unless one blocks a validation item.**

The clause after "unless" is an escape hatch, and an escape hatch that is used freely is not a constraint at all. It is invoked twice in this change set. Both invocations are labelled as such, both are in the frontend track, and both block the same validation gate.

Four further rules shape what this page may and may not say. They are summarised here in the plan's terms, not transcribed:

- **R-1 — Justified dependency changes.** Every dependency change needs a specific Java 17 or Node 20 compatibility reason, and *"a change without a reason is out of scope."* This is why the four dead dependencies in entries 8 to 11 are **registered rather than removed**, and why no script engine was added to the two modules in entry 7.
- **R-5 — No disabling of failing tests.** Exclusions are limited to failures already present at the baseline. It appears here as a boundary: nothing on this page is grounds for excluding a test.
- **R-7 — Baseline behaviour is the tie-breaker.** The behaviour observed at the base commit settles any ambiguity, and each resolution must be documented. This is the deeper reason R-6 exists in a behaviour-preserving change set: repairing an inherited defect *is* a behaviour change measured against the baseline.
- **R-T7 — Evidence over exit codes.** Validation asserts on produced artifacts and captured output, *never on process exit status alone* — and the rule states plainly that this is mandatory rather than stylistic because the Gruntfile's forced-execution setting masks task failures and lets a broken build exit zero. Entries 3, 4 and 49 are that mechanism caught in the act, so the rule is a repository fact here rather than a preference.

Best practice applies on top of these, never as a substitute for them. No rule is invented and none is softened; where restraint looked wasteful, the rule won, and the entry below says so.

## Why Documenting Beats Fixing Here

The instinct that a bug found should be a bug fixed is a good instinct, and it is the wrong one for this change set. The reason is specific to what a behaviour-preserving migration can prove.

Every claim this migration makes is comparative: the artefacts are byte-identical, the numbering sequence is unchanged, the routing decision is the same, the failure that was failing before is failing now. A comparison only carries weight if exactly one thing changed. Fix a pre-existing bug in the same change set and every subsequent difference has two candidate explanations — the runtime move, or the fix — and no evidence can separate them. The bug that was there before is a *constant* in the comparison, and constants are what make it a comparison.

This is why several entries below would take minutes to correct and are nevertheless left alone. The two `config.js` logic errors in particular are a handful of characters each.

### 1 and 2 — Two logic errors in the frontend asset resolver

`config/config.js:16` loads the active profiles with `var activeProfiles = require('./../profiles');`. The module it loads exports an **object** with a `profiles` key, not an array. The second error compounds the first. **The defect.** Two build packages produce output that depends on the JavaScript engine they happen to run on, rather than only on their input:

- **`clean-css` 3.4.28** sorts with comparators that return a **boolean**. `lib/selectors/restructure.js` declares `naturalSorter(a, b) { return a > b; }` and `fitSorter(fit1, fit2) { return fit1[1] > fit2[1]; }`, and both are passed to `Array.prototype.sort` — at `:125` and `:349` — inside the pass that regroups selectors sharing a body; `lib/selectors/clean-up.js:53` and `:69` sort selectors the same way. A boolean coerces to `0` or `1` and is never negative, so such a comparator can say "equal or greater" but never "less". `sort` is then free to produce any permutation consistent with that, and which one it produces is decided by the engine's sorting algorithm. Demonstrated directly: a 24-item array sorted with that comparator shape comes back scrambled on the older engine and in its original order on the newer one.
- **`uglify-js` 2.8.29** emits a regular-expression literal by round-tripping it through a `RegExp` object, so whatever `RegExp.prototype.toString` produces lands in the bundle. The two engines serialise the same pattern differently: the older re-escapes a forward slash inside a character class, the newer returns the source text as written. The application source carries the unescaped form, so the newer engine's output is the **more faithful** of the two — the older one was adding characters that were never written.

Recorded, not fixed, and **not closed**. The measurement is archived beside this page at `smoke-evidence/historical-frontend/comparison.txt` with the capture script next to it; the adjudication that the criterion is a FAIL is at `smoke-evidence/migrated/artifacts/diff-result.txt`, which both capture summaries now quote verbatim rather than leaving to be found; and the decision — including the options rejected — is entry 6a of [Ambiguity Resolutions](ambiguity-resolutions.md). **This entry does not consume an escape-clause invocation**: the escape clause covers pre-existing defects that were *fixed* because they blocked a validation item, and this one is neither pre-existing nor fixed.
**Why it is pre-existing rather than introduced.** Both packages are pinned at the versions the base-commit lockfile resolved, both trees were compared **file by file** between the two builds and found identical, and the inputs are byte-identical. The defect sits in code that predates this change set entirely; all the migration did was run it on a different engine and thereby make the latent behaviour visible.

**Why it is not fixed.** Replacing a build package is permitted only where it cannot run on the target runtime, and both install and run there. A version change would alter far more of the output than the difference it was meant to remove, and for the script minifier a newer version yields the target-runtime bytes rather than the baseline ones, so it would not close the gap even setting the rule aside. Patching a file inside an installed dependency tree was not considered a candidate: it would make the build unreproducible from its own lockfile, which is the property the lockfile exists to provide.

**Evidence.** Isolated, reproducible, and independent of the task runner, the package manager and every migration change: `smoke-evidence/historical-frontend/minifier-engine-dependence.txt`, produced by the probe committed beside it, which compares the two minifier trees and then calls each minifier directly as a library over one input under each runtime. **This entry does not consume an escape-clause invocation.** The escape clause covers pre-existing defects that were *fixed* because they blocked a validation item; this one is not fixed. The change set's two invocations remain the untracked configuration module and the unbuildable stylesheet toolchain.

**What the previous script measured, and why that was not a population.** It scraped both sides flat. It keyed entity results by *table*, so the 91 classes carrying both `@Entity` and `@Table` collapsed to 88 rows. It ignored preconditions. It recorded whether an annotation attribute *name* occurred rather than its *value*, so `@Column(length = 4000)` against a `VARCHAR(255)` read as agreement. And it **flattened composite constraints onto each named column**, which is not a rounding error: it is what hid the six cardinality mismatches now registered as entries 69 to 74, because a column declared `unique = true` looked satisfied by a composite key that does not constrain it.

**What the new implementation does.** It resolves the real changelog graph. Liquibase is wired three times in this reactor — `spring-library-data-source.xml:164-166` for the core schema, and one `SpringLiquibase` bean each in the FOIA and privacy extension libraries at `spring-extension-library-foia.xml:10-12` and `spring-extension-library-privacy.xml:10-12` — and each root is walked in execution order through its `include` and `includeAll` elements with classpath-resource semantics and a deterministic sort. `includeAll` is treated as **non-recursive**, and that is corroborated rather than assumed: the archived startup captures show Liquibase 3.1.1 emitting *"included file … /com/armedia/acm/ddl/tables/person is not a recognized file type"* for each subdirectory of an `includeAll` path, which is what a non-recursive listing looks like; the subdirectory changelogs are reached instead through per-module aggregator changelogs that `include` them relative to themselves. Properties are resolved with their `dbms` filters, first definition winning. Every structural operation is then applied in graph order, and **composite constraints stay composite**.

The mapping side is parsed structurally rather than scraped. Annotation bodies are read with a balanced-delimiter scanner so nested annotations survive; comments are stripped first, so a `@Column` inside a Javadoc block or a commented-out mapping no longer counts as a mapping; attribute *values* are read; inheritance and mapped superclasses are resolved so a `SINGLE_TABLE` subclass's columns land in the table it actually shares; and **join tables, collection tables and element collections receive their own columns** instead of being credited to the owning entity. Relationship semantics are captured with them — cardinality, `cascade`, `orphanRemoval`, `mappedBy`, `fetch`, and the owning and inverse join columns separately — which is what makes entries 71 to 74 findable: of the 16 `@JoinTable` relationships, 15 declare a cascade, 3 declare `orphanRemoval`, and **4 declare their inverse join column unique**. `@AttributeOverride` column re-points are handled too, and there are 0 of them in this codebase. ### 69 to 74 — Six ORM-to-DDL cardinality mismatches the flattened measurement hid

These six are the mirror image of entry 21. Entry 21 counts constraints the DDL states and the mapping does not; these are constraints the **mapping states and the effective schema does not enforce**. They are registered separately because the consequence is different in kind: an unstated length is inert while `generateDdl` is `false`, whereas a uniqueness the application believes in and the database does not enforce is a data-integrity assumption that can be violated by any writer that is not the entity manager.

They were not in an earlier revision of this page, and the reason is worth stating because it is a lesson about measurement rather than an oversight. The previous script flattened a composite unique constraint onto each column it names, so `addUniqueConstraint columnNames="cm_person_id, cm_identification_id"` was recorded as uniqueness on `cm_person_id` **and** on `cm_identification_id` separately. Against that model every one of these six looked satisfied. The rewritten measurement keeps composites composite and asks a narrower question — *is this one column constrained alone?* — and the six fall straight out of it. They are emitted by the script as `divergence.cardinalityGaps` in [`orm-ddl-omissions.json`](smoke-evidence/orm-ddl/orm-ddl-omissions.json) and printed under *CARDINALITY GAPS* in [`measurement.txt`](smoke-evidence/orm-ddl/measurement.txt), each with the changeSet that declared the DDL, so none of the rows below is typed from a reading.

**Two columns carry no uniqueness whatsoever in the effective schema.**

- **69** — `AcmOutlookFolderCreator.java:63` maps `@Column(name = "cm_system_email_address", unique = true)`. `outlook-db-tables-1.0.xml:21-23` declares that column `VARCHAR(256)` with `nullable="false"` and nothing else, and a search of every changelog in the reactor finds exactly one occurrence of the column name — the declaration itself. There is no unique constraint, no unique index and no primary key on it anywhere.
- **70** — `ZylabMatterCreationStatus.java:65` maps `@Column(name = "cm_zylab_id", unique = true)`. `zylab-integration-database-tables.xml:14` and `:32` declare `<column name="cm_zylab_id" type="LONG"/>` with no constraints element at all. The sibling column in the same table shows this is not an oversight of style: `cm_matter_name` at `:12` and `:30` carries `unique="true" uniqueConstraintName="uk_matter_name"`, so the changelog author knew how to state it and did so for one column and not the other.

**Four one-to-many inverse join columns are declared individually unique and covered only by a composite key.** In each case the mapping is a `@OneToMany` whose `@JoinTable` gives the inverse join column `unique = true`, which is how JPA expresses *"this child belongs to at most one parent"*. The join table enforces only a composite constraint over the pair, and a composite over `(parent_id, child_id)` permits the same `child_id` beside a different `parent_id` — which is precisely the case the mapping declares impossible.

- **71** — `Organization.java:114-118`, join table `acm_organization_identification`, inverse column `cm_identification_id` `unique = true`; `organization-db-tables-1.0.xml:106` creates the table and `:114` adds `addUniqueConstraint columnNames="cm_organization_id, cm_identification_id"`.
- **72** — `Person.java:167-170`, join table `acm_person_identification`, same inverse column and flag. This table is declared five times across `person-db-tables-1.0.xml`, once per DBMS variant, so the row that matters depends on which variant runs. On MySQL it is changeSet `30-rename-person-identification` at `:556`, whose `createTable` at `:582` is paired with `addPrimaryKey columnNames="cm_person_id, cm_identification_id"` at `:586`; the Oracle and PostgreSQL variant is the same pairing at `:543`/`:547` and the SQL Server variant at `:621`/`:631`, and an earlier pair of variants creates the table at `:406` and `:441`. A **composite primary key** rather than a unique constraint — the effect on the single column is identical.
- **73** — `PersonContact.java:103-108`, join table `acm_person_cntct_ident`; `person-contact-db-tables-1.0.xml:80` creates it and `:88` adds the composite unique constraint over `(cm_person_contact_id, cm_identification_id)`.
- **74** — `BillingInvoice.java:122-127`, join table `acm_billing_invoice_item`; `billing-invoice-db-tables-1.0.xml:99` creates it and `:107` adds the composite unique constraint over `(cm_billing_invoice_id, cm_billing_item_id)`.

**Entry 69 is compounded by a reader that assumes the constraint holds.** `JPAAcmOutlookFolderCreatorDao.getFolderCreator` builds `SELECT ofc FROM AcmOutlookFolderCreator ofc WHERE ofc.systemEmailAddress = :systemEmailAddress` with no ordering, and at `:146` takes `resultList.get(0)`. With the uniqueness the mapping declares, `get(0)` is correct and total. Without it, two rows for one system address are possible and which credential the service decrypts and uses is decided by whatever order the provider happens to return — a nondeterministic selection among stored credentials rather than an error. Nothing in this change set makes that more or less likely; it is recorded because the DAO is the place the missing constraint would first be felt, and a reviewer looking only at the annotation would conclude the code is safe.

**All six are documented, not fixed, and R-6's escape clause does not reach them.** Fixing one means choosing between two behaviour changes, and both are outside what this change set is allowed to do. Adding the missing single-column constraint is a **schema change** — a new migration against tables that may already hold data the constraint would reject, so it needs a duplicate-data audit before it could even be attempted, and the migration plan's PRESERVE list freezes the schema and the effective DDL of every persistence mapping outright. Correcting the mapping instead — dropping `unique = true` where the relationship is genuinely many-to-many — is a **cardinality change** to the object model, which changes what the application permits. Neither is a repair that can be made blind, and neither blocks a validation item. What they need is a deliberate decision, recorded here so it can be taken: for each of the six, establish whether the relationship is truly one-to-many, then either enforce child-column uniqueness in the schema after auditing for existing duplicates, or correct the ORM cardinality — in a change set whose purpose is that decision.

### 65 and 66 — Two further security defects

- **65** — The document viewer encrypts an authenticated session ticket with a construction that is weak in three independent ways and then fails open. `snowbound-viewer.client.service.js`'s `buildSnowboundUrl` concatenates `ecmFileId`, `acm_ticket`, `userid`, `userFullName`, `caseNumber`, `documentName`, `parentObjectId`, `parentObjectType` and `selectedIds` into one string and passes it to `Util.encryptString` with the passphrase from `ecm.viewer.snowbound.encryptionKey`, placing the result in a URL as `?documentId=<ciphertext>&refreshCacheTimestamp=<epoch-ms>`.

  `encryptString` at `util.client.service.js:795-805` calls `CryptoJS.AES.encrypt(string, passphrase)` with a **string** passphrase. That overload does not use PBKDF2 — which matters, because npm's advisory for this package is about PBKDF2 and quoting it would describe the wrong weakness. It uses OpenSSL's `EVP_BytesToKey`. The library is pinned at `package.json:70` as `brix/crypto-js#0596faee7aa619f6f25e43e770e545ae7233b095`, which resolves to version 3.1.9, and its defaults are `keySize: 128/32`, `hasher: MD5`, `iterations: 1` — one iteration of MD5. The salt comes from `WordArray.random`, which in this version derives from `Math.random()` rather than a cryptographic source (CWE-338). Both are verifiable after an install at `node_modules/@bower_components/crypto-js/evpkdf.js:38-40` and `core.js:318`, `:323`; the paths are given as installed rather than as tracked, because `resources/.gitignore` excludes `node_modules/` and the package arrives from the pinned commit. The cipher is AES-CBC with no authentication tag, so the ciphertext is malleable (CWE-327).

  The fail-open is the part that turns a weak-crypto finding into a disclosure one. `encryptString` returns its argument **unchanged** when `passphrase` is falsy, and its `catch` block logs `"Error on encryption, returning plain query string"` and also returns the argument unchanged. No caller learns that encryption did not happen. On that path the session ticket travels in a URL in cleartext (CWE-311, CWE-319) — into proxy logs, browser history and an iframe `src`.

  Documented rather than fixed: both files are application JavaScript, which the migration's exclusion list freezes and which the plan's Goal B5 states requires no modification; and `crypto-js` 4.2.0 is a served library, so upgrading it changes `vendors.min.js` and destroys the artifact evidence the frontend gate depends on. The remediation is a backend change — issue a short-lived opaque handle for the viewer instead of encrypting a session ticket client-side — and it needs its own authorisation.

- **66** — This one is **not in this repository**, and it is recorded here so that it is not lost between the two — but it is recorded at a deliberately reduced level of detail, and the reduction is itself part of the entry. The reference deployment's Spring Security configuration comes from the separate `.arkcase` configuration repository, and several of its authentication chains declare an unauthenticated filter-chain exemption whose matching expression is **broader than the resource it was written to exempt**, so the exemption can be satisfied by requests it was never intended to cover. The consequence is an authentication bypass affecting that deployment's protected surface.

  **The exact mechanics are deliberately not published here.** The matching expression, the request tokens that satisfy it, and the per-file locations are withheld, because this register is broadly readable migration documentation and the defect is **unremediated in a live configuration repository** — reproducing it here would be a working recipe against any deployment built from that repository, including ones whose owners have not yet been told. That is a disclosure decision, not an omission: the withheld material exists, it was measured file by file, and it belongs in a restricted security advisory raised with the configuration repository's owner and coordinated with a fix before wider disclosure. A reader who needs the specifics should obtain them through that channel rather than from this page. Nothing about the defect's *existence* is withheld, which is what keeps this entry honest — what is withheld is only what would let it be exercised.

  **What a reader of this page needs, and can act on.** It is a **deployment precondition** owned by the configuration repository, not a code defect here, so there is nothing in this change set to change and nothing an ArkCase build can fix. It is **independent of this migration** — the same configuration produced the same exemption on the older runtime, so it is neither caused nor worsened by moving to the new one. It is registered because the migration's validation ran against that reference deployment, and anyone reproducing those results should know that the deployment they reproduce them on does not enforce authentication uniformly. Treat that deployment as one whose authentication boundary is not trustworthy: do not host real data on it, do not expose it beyond a controlled network, and do not read a passing smoke flow on it as evidence that an authentication control works.

  **One claim an earlier revision of this entry made is withdrawn, because it was false and it was false in the more dangerous direction.** It stated that this repository contains no unauthenticated filter-chain exemption at all, "verified by search". It does contain them: `acm-web/src/main/resources/spring/spring-security-config.xml` declares **24**, and the reference deployment activates **17** of them — the ones the captured startup evidence shows as `Will not secure Ant [pattern='…']` on both sides. The 17 decompose exactly, which is what makes the figure checkable rather than asserted: **9** sit in an unconditional `<beans:beans>` block and cover static resources and branding, and **8** more come from the `profile="ldap,kerberos,mfa-okta,externalAuth,externalSaml"` block, which this deployment activates because it authenticates against LDAP — those are the login, password-reset and forgotten-credential endpoints. The remaining **7** are the `profile="oidc,externalOidc"` block's four and the `profile="ssoSaml,externalSaml"` block's three, neither profile being active here. Asserting there were none invited a reader to conclude that anything found in the startup log must have come from elsewhere, which is exactly the wrong inference to hand someone auditing an authentication boundary.

  **What actually distinguishes this repository's exemptions from the registered defect is the kind of matcher, not the existence of one** — and that is checkable in one line each. All 24 in-repository exemptions are **Ant path patterns**: every one is `pattern="/…"`, **zero** declare `request-matcher="regex"`, and **zero** contain an `=` in the pattern, so not one of them can be satisfied by a query parameter. Each is scoped to a named path that must be reachable before authentication for the login flow to work at all. The registered defect is the other kind: a **regex** chain that matches on a request parameter rather than a path, which is what makes it satisfiable against any path. That chain does not come from this repository, and the captured startup evidence shows exactly one such chain per side, masked. This change set touches that in-repository file for one unrelated reason, visible in its diff — the security schema reference becomes version-less so the namespace handler accepts it under the upgraded Spring Security — and **adds no exemption, removes none, and alters no pattern**.

### 97 and 98 — Two further security defects, on one shared reachable path

These two were registered later than 65 and 66 and they are treated together, because **they lie on the same single call path** and neither is reachable except through it. Both were verified present and **byte-identical at the base commit**, so both are inherited.

- **97** — `SignatureAPIController.signObject` reads the confirming password with `String password = body.get("confirmPassword")` at `:70` and passes it directly to `getLdapAuthenticateManager().authenticate(userName, password)` at `:75`. There is **no check between those two lines**: `Map.get` on an absent key returns null, an empty JSON string value arrives as `""`, and either reaches a directory bind. The failure mode is a *guard that is not there* rather than a check that is wrong, which is why it is registered against the controller and not against the directory client.

- **98** — the method it calls builds its filter as `String filter = "(" + userIdAttributeName + "=" + userName + ")"` at `LdapAuthenticateService.java:73`, from a principal name that has had only `StringUtils.substringBeforeLast(userName, "@")` applied to it. That strips a domain suffix; it escapes nothing. LDAP filter metacharacters in the principal are therefore parsed as filter syntax rather than matched as literal characters.

**Reachability, measured rather than assumed — and it is narrow.** A search of all main source for callers of that authentication method returns **exactly one**:

```bash
grep -rn "getLdapAuthenticateManager()\.authenticate\|ldapAuthenticateService\.authenticate" \
  --include=*.java . | grep -v /test/
  -> acm-services/.../SignatureAPIController.java:75      (one hit, main source)
```

So entry 98 is reachable **only** through entry 97's endpoint, and that endpoint requires an already-authenticated session — `authentication.getName()` at `:73` supplies the principal, so the caller does not choose it. That bounds entry 98 considerably: the injectable value is the *session's own* principal name, not an arbitrary caller-supplied string, so exploiting it requires a directory account whose identifier already contains filter metacharacters. It is registered at full strength anyway, because "hard to reach today" is a property of the current directory's naming rules rather than of the code, and a synchronised directory is not this repository's to constrain.

**What the blank-password condition actually costs, measured against the reference directory rather than predicted.** The outcome depends on directory configuration, and on the directory this migration's evidence was captured against it **does not fail open**. Three binds as a real user DN, run against the provisioned directory:

| Bind attempt | Directory response |
| --- | --- |
| Correct password | **succeeds** — returns the bound DN |
| Wrong non-empty password | rejected, LDAP result **49**, `Invalid credentials` |
| **Empty password** | rejected, LDAP result **53**, `unauthenticated bind (DN with no password) disallowed` |

That third row is the one that matters and it cuts both ways. The reference directory refuses the unauthenticated bind, so on that deployment the missing guard is **latent rather than exploitable** — which is honest to state and is why this entry does not claim a live bypass. But the refusal comes from the *directory's* configuration, not from anything in ArkCase: RFC 4513 defines an empty-password simple bind as an anonymous bind, and a directory that permits one would return success, at which point `authenticate` returns `true` and the signature is applied without the confirming password ever being verified. The application must not depend on a directory setting for a control it is itself asserting.

**Registered, not fixed, and the authority is R-6 with nothing ambiguous about it.** Neither file is in the migration plan's file list — measured: `git diff c8f6226105..HEAD` reports **0 changed lines** in each, `acm-service-electronic-signature` has **0** files changed by this change set, and the single file changed in `acm-service-users` is an unrelated **test** class. Both conditions are JDK-independent and behave identically on either runtime, neither blocks any validation item, and repairing either would change authentication behaviour, which **R-1** has no compatibility justification for. Neither is an escape-clause invocation and the count below is unaffected.

**Fixing them later, and they should be fixed together.** Reject a null or blank `confirmPassword` in the controller before the LDAP call, returning the same `Invalid password` error the wrong-password path already returns, so the response does not distinguish the two cases. Replace the concatenated filter with an escaped or parameterised one — `spring-ldap-core` is **already a declared dependency of that module** (`acm-service-users/pom.xml:72-73`), so `org.springframework.ldap.support.LdapEncoder.filterEncode` is on the classpath and needs no new dependency. Do both in one authorised functional change, with a test for a blank password and one for a principal containing filter metacharacters.

### 67 — Sixteen classes have no stable serialised property order, at either Jackson version

Of the remainder, five varied only in the 2.12.7 trials and one — `AcmParticipant` — varied only in the 2.10.3 trials. Those two rows are read together: six trials establish "did not vary in six runs", not "provably deterministic", and instability that shows up on the *older* version and not the newer one is a finite-sample effect that no upgrade can explain.

Documented rather than fixed, and the reason is worth stating because the fix looks free. Adding `@JsonPropertyOrder` to these sixteen would make their order deterministic — at an order the baseline never had, since the baseline had no single order for them. ### 86 — A `@PrePersist` hook iterates a collection another thread is mutating

`AcmFolder.beforeInsert` calls `setupChildPointers`, which iterates the folder's participant collection to stamp the owning object's identity onto each participant. The iteration is unsynchronised and the collection is a plain list, so a concurrent modification during the same flush throws `ConcurrentModificationException` from inside the persistence callback. **Observed, not theorised.** Creating the same object four times in this environment produced the exception once; the other three attempts produced two rejections from an unrelated pre-existing condition and one success. The exception's stack is captured in the deployment log with the callback frame at the head of it. Its intermittency is the point: a defect that appears in one attempt out of four is exactly the kind that a single green run hides.

**Recorded, not fixed.** The file is a persistence entity outside the plan's scope list and the defect is unchanged at the base commit. Any repair — copying the collection before iterating, or synchronising the callback — changes the entity's behaviour under concurrency, which is a behaviour change the plan is defined not to make, and no validation item is blocked: the flow that hit it records its own unmet criterion with the measured cause.

### 87 — A privilege decision that depends on map iteration order

### 45 — An error-path test that passes without executing its error path

### 50 — A stylesheet endpoint answers 500 where 406 belongs

`GET /branding/customcss` returns **HTTP 500** with the `text/plain` body `Could not find acceptable representation` (40 bytes) to a client sending `Accept: */*`, no `Accept` header at all, `Accept: text/plain`, `Accept: text/html` or `Accept: application/json`. It returns **200** with 3,778 bytes of `text/css` to `Accept: text/css` and to the Accept string a real browser sends for a stylesheet, `text/css,*/*;q=0.1`. Measured on the deployed application across a 24-cell matrix; `/login`, `/assets/css/login.css` and `/branding/loginlogo.png` return 200 for every one of the same headers, so it is this endpoint alone.

Two pre-existing pieces combine to produce it, and neither is in this change set:

1. `servlet-context.xml:46-48` declares a `ContentNegotiationManagerFactoryBean` with `defaultContentType = application/json`, wired into `<mvc:annotation-driven content-negotiation-manager=…>` at `:59`. Spring's `ContentNegotiationManager.resolveMediaTypes` **skips** any strategy that returns exactly `[*/*]` and falls through to the next one, so a request whose `Accept` is `*/*` — or absent, which Spring treats identically — resolves to the fixed `application/json`. That is incompatible with the handler's `produces = "text/css"` (`CustomCssRetrieveFile.java:52`), and Spring raises `HttpMediaTypeNotAcceptableException`. This also explains, exactly, why the browser Accept string succeeds: it is not equal to `[*/*]`, so the header strategy wins and its `*/*;q=0.8` term is compatible with `text/css`.
2. `AcmSpringMvcErrorManager.lastChanceHandler` — the `@ExceptionHandler(Exception.class)` catch-all at `AcmSpringMvcErrorManager.java:135-140`, already registered as entry 32 above — maps any otherwise-unhandled exception to `INTERNAL_SERVER_ERROR` and writes its message into the body. That is what turns what Spring's own `DefaultHandlerExceptionResolver` would have reported as a 406 into a 500 carrying the exception text.

**Not user-facing.** All nine consuming JSPs load it with `<link rel="stylesheet">`, and every real browser Accept string yields 200; the deployed login page received 200 for it on all four verification loads and the branding CSS visibly applied, with no unstyled flash.

Registered rather than fixed for a reason stronger than R-6 alone: **the migration plan's preservation list forbids the repair.** Both candidate fixes — dropping `produces = "text/css"` and setting the content type explicitly, or returning a `ResponseEntity<String>` — change a controller's request mapping or its signature, and the plan states plainly that no controller signature, request mapping or serialized field changes anywhere. Changing `defaultContentType` instead would alter negotiation for *every* endpoint in the application, which is a far larger behavioural change than the defect it repairs. The correct repair belongs to a change set that owns the content-negotiation configuration and can re-test every endpoint against it. Recorded as [Ambiguity Resolutions](ambiguity-resolutions.md) entry 15, because the decision needed a tie-breaker rather than just a note.

From any other queue the table evaluates through its default row and answers 200 with an empty candidate set, which is the routing decision the core profile's tables actually produce; that is what the smoke evidence captures and compares. The environment is configured to place the seeded case file in a real queue rather than in the sentinel, so the flow observes the decision the tables produce instead of manufacturing this failure.

A second, adjacent condition is worth recording beside it, because it is what exposed this one and it is equally pre-existing, and it is registered separately as entry 76: the endpoint dereferences `caseFile.getQueue().getName()` with no null guard, so a case file that is in **no** queue makes it answer 500 as well. In the core profile the Liquibase changelog creates the `acm_queue` table and inserts no rows — a queue set ships with the FOIA profile — so on a core deployment every case file is queue-less and the endpoint cannot be exercised at all until queues are seeded. Also unfixed, and for the same reason.

### 85 — A delete that succeeds and then throws

`DELETE /api/latest/service/ecm/id/{fileId}` removes the stored document and publishes a moved-to-recycle-bin event. `EcmFileMovedToRecycleBinListener.onApplicationEvent` at line 49 then calls `EcmFileServiceImpl.checkAndSetDuplicatesByHash`, which at line 2605 dereferences the active version without a null guard:

```
NullPointerException: Cannot invoke
  "com.armedia.acm.plugins.ecm.model.EcmFileVersion.getFileHash()"
  because "ecmFileVersion" is null
    at EcmFileServiceImpl.checkAndSetDuplicatesByHash(EcmFileServiceImpl.java:2605)
    at EcmFileMovedToRecycleBinListener.onApplicationEvent(...:49)
```

The removal itself has already happened when this throws. Verified on both sides: after the 500, the row is gone from `acm_file` and the document's identifier returns a result count of **0** from the search index, where a document that exists returns **1**. So the caller is told the delete failed and the delete succeeded.

Pre-existing: `git log c8f6226105..HEAD` returns **empty** for `EcmFileServiceImpl.java` and for `EcmFileMovedToRecycleBinListener.java`.

Not fixed — a null guard in a listener is a source change to the ECM service, outside this migration's change surface. It does have one consequence worth recording, because it changed how the evidence is gathered rather than what it says: the smoke capture's cleanup step used to treat any non-2xx removal as litter left behind, so it reported one object abandoned on every run when nothing had been abandoned. Cleanup now **verifies every removal it can verify, after a 2xx as well as after a failure**, and draws its conclusion from the verification rather than from the removal status. That is stronger than checking only the failures, and this application is the reason it has to be: it answers 500 with the object gone here, and — by entry 77 — 500 with the object still present elsewhere, so neither status can be read on its own in either direction. For a document the instrument is an index query, chosen because it is the only one that answered unambiguously: fetching the deleted object returned 403 on one occasion and 500 on another, and neither distinguishes absence from a different failure, while a result count of 0 does. For a process instance the instrument is the task's own status, because that removal marks tasks `TERMINATED` and re-indexes them rather than deleting their documents, so an absence check would report litter that is not there.

## The Escape Clause, Invoked Exactly Twice

R-6 permits fixing a pre-existing defect when it blocks a validation item. Two conditions blocked the fresh-checkout frontend build gate, which runs a clean checkout, deletes every untracked file, installs from the lockfile and runs the build. Both were fixed. Both are labelled here so the count is auditable and cannot grow quietly.

| # | Condition fixed | Why it blocked the gate | Why the fix is behaviourally inert |
|---|---|---|---|
| E1 | `profiles.js` was absent from version control | `config/config.js:16` requires `./../profiles`, and the gate's clean step deletes every untracked file before installing. The module was written at deploy time, so a fresh checkout could not build at all | The deploy-time writer uses replace-existing semantics, so a deployed environment continues to overwrite the tracked default with its own value. The tracked file exports `{ profiles: [ ] }`, matching what that writer emits |
| E2 | The Sass toolchain could not build on Node 20 | Its transitive native compiler fails to install — the only failure among eighteen legacy packages tested — so the install step could not complete | Removal, not replacement, and output-neutral by entry 5 above: no Sass task is declared and the SCSS globs are never consumed. Modern replacements were verified to install and were **declined on evidence, not availability** |

**Neither invocation is a register entry, and no third invocation exists.** The arithmetic is exact: **97 live register entries — 95 not fixed and 2 fixed — plus 2 escape-clause invocations and 3 repaired-but-unnumbered defects, with no overlap between any of the four sets.** The entries are numbered 1 to 56 and 58 to 98; number **57 is withdrawn and deliberately not reused**, because the condition it described was a migration regression rather than an inherited one and has been fixed — leaving the number unreused keeps references to it in earlier reviews unambiguous. E1 created a file that was absent from version control, and E2 removed a build package — neither is a row above.

**The two fixed entries do not raise the invocation count, and this is the one piece of arithmetic worth being explicit about.** Entries 94 and 95 are repaired, and R-6's escape clause is nevertheless still invoked exactly twice, because they rest on the same authority as R1 to R3: the migration plan directs that the production launch-configuration block in `README.md` and its duplicate on the setup page be updated as part of the runtime-prerequisite work, so repairing conditions inside a block the plan itself opens is an authorised update rather than an exception. The distinction is checkable rather than rhetorical — an escape-clause invocation is a change to a file the plan does **not** open, and both E1 and E2 are that, while entries 94 and 95 touch only files §0.2.1 lists for update. An earlier revision of this sentence read "94 register entries, 0 fixed": the count was right and the *0* was left behind by that repair.

Ninety-five of the 97 entries are still present in the tree, unmodified, and can be re-verified at the anchor each cites; the remaining two are entries 94 and 95, whose repair is verifiable by the commands under *Verification* below.

Entries 81 and 82 are worth a sentence here, because between them they are the one condition on this page that could have argued for a third invocation and does not get one. Together they leave a deployment unable to start, which blocks the runtime capture — and *blocks a validation item* is the escape clause's own trigger. It is still refused, for a reason that is a fact about the defect rather than a preference: what blocks the capture is a **row of data**, not the code. Repairing the data in the throwaway capture runtime restores startability completely and leaves the product untouched, so the capture proceeds with the defect fully intact and fully observable. Repairing the code, by contrast, would mean editing an ORM cascade and a startup loader — and the plan freezes ORM mappings and the effective DDL they generate, which is the same reason the ORM-to-DDL divergences are registered rather than reconciled. The cheaper repair being available outside the product is what keeps the count at two.

That last point is the one most easily misread, because both invocations land *next to* a registered entry without touching it. E1 creates the module that entries 1 and 2 load, and leaves both logic errors exactly as they were; E2 removes a package whose absence entry 5 explains, and leaves the inert pipeline inert. It is tempting to net the two against the register and conclude that two of the first eleven were dealt with — **they were not**. All eleven of the plan's mandated entries remain unfixed, as do all the rest. The count of invocations and the count of unrepaired entries are separate figures, and both are stated here so neither has to be inferred.

Two things make that narrow reading visible rather than merely asserted. Entries 1 and 2 sit in `config/config.js` — the very file that E1 makes loadable — and were still left alone, even though they are a few characters each and the file was already open. And the security category — entries 22 to 32 plus 65 and 66, thirteen defects in all — carries the strongest pull toward "fix it while you are here"; not one was touched, because none of them blocks a validation item and the migration plan's preservation list requires security outcomes to be **unchanged**, which makes adding an authorization check a deviation from the plan rather than compliance with it.

Entry 45 is the sharpest illustration of the cost of reading the clause that narrowly: a two-character change would make its error path execute, and it is left alone because the assertion behind it would then have to be rewritten, which the preservation list forbids.

## What Is Not on This Page

Three categories are deliberately excluded, because including them would blur what this register means or, in the third case, would cause harm.

**Exploitable mechanics for an unremediated defect in a live external repository are withheld.** This applies to exactly one entry, **66**, and the withholding is stated in the entry itself rather than left for a reader to notice. What is withheld is the matching expression, the request tokens that satisfy it, and the per-file locations; what is **not** withheld is that the defect exists, what class of defect it is, which repository owns it, that it is independent of this migration, and what a reader of this page must therefore assume about the reference deployment. The distinction is the whole point: a register that concealed the defect's existence would be dishonest, whereas a register that published a working recipe against every deployment built from that configuration repository — before its owner has been told and before a fix exists — would be harmful. The specifics belong in a restricted advisory raised with that owner and coordinated with remediation, and a reader who needs them should obtain them there. Two consequences follow for anyone maintaining this page. The captured startup evidence under `smoke-evidence/` is redacted to the same standard by the producer itself, which masks any security filter-chain pattern that matches on a query parameter while leaving every path-matching chain fully legible, so the evidence still shows how many chains exist and which are secured. And the producer's credential-name allowlist does still name one request parameter, deliberately: it is there so that the parameter's *value* is redacted wherever it appears, and removing it to satisfy a keyword search would reintroduce the leak it prevents.

The other two exclusions are about what counts as pre-existing at all.

**A migration-induced failure is not a pre-existing defect, and none is recorded here.** A regression is not an inherited condition, and putting one on this page would launder it into accepted state. The **unit** corpus carries none: the migrated run archived under [Baseline Test Failures](baseline-test-failures.md) records **3 failures and 1 error across 279 suites and 893 test methods, and every one of the four maps to a registered baseline row** — the same three `FileDownloadAPIControllerTest` failures and the same `FolderCompressorTest` error that the JDK 8 baseline produced. The entire delta between the two archives is one added suite and one added test method, and it passes.

There is no migration-attributable red left. The one that existed — the integration test described under *Withdrawn from this register* above — was a genuine regression rather than an inherited condition, and it was fixed rather than accepted; it now passes 2 of 2. Its record lives in that companion page under its own heading, as a resolved migration-attributable failure. That division still holds: this page accepts inherited conditions, and any future failure that does not trace to a baseline row belongs there as a regression, never on this page.

**Dependency advisories have their own registers, one per side.** They are a security posture with a remediation plan and risk-accepted exceptions, not a list of code defects. The npm graph is recorded in [Frontend Dependency Security](frontend-dependency-security.md); the Spring Security, Spring LDAP and Jackson advisories are recorded in [Backend Dependency Security](backend-dependency-security.md).

Backend advisories are kept off this page for a second reason beyond category, and it is worth stating because it looks like it argues the other way. All four backend findings are **inherited rather than introduced** — every delivered version sits in the same unfixed advisory range as the version it replaced — which is exactly the property that would qualify something for this register. What disqualifies them is that this page records defects *in this codebase* that a maintainer could in principle repair here, and these are unfixed ranges in third-party libraries whose only published remedies lie in release lines the migration plan excludes. A row here reading "not fixed" would imply a repair was declined; the disclosure page instead prices the remedy and names the decision as an owner's.

## How to Use This Register

- **Fixing an entry.** Do it in a change set whose purpose is that fix, so the resulting behaviour difference has one explanation. Entries 1 and 2 in particular need a configuration with active profiles to test against, which this change set does not have.
- **Adding an entry.** Verify the anchor against the tree, state what makes it a defect, and state why it is out of scope. An entry without the last part is a to-do list item wearing a register's clothes.
- **Invoking the escape clause.** Name the validation item blocked, and add a row to the table above. If a third row ever appears, the reason it is not simply "we also fixed this one" must be on it.
- **Interpreting a build failure.** Check entry 6 first. An unprovisioned local artifact repository looks exactly like a dependency resolution regression and is neither.
