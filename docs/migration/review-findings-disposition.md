# Review Findings Disposition

## Why this page exists

Code review raised **46** findings against this migration and recorded that none of its own identifiers appeared anywhere in the repository. That was accurate and it is the gap this page closes: a finding with no published identifier cannot be traced, cannot be shown to be answered, and cannot be shown to be *unanswered* either. Every one of the 46 is below, with a stable identifier, what is actually wrong stated as a fact about the code rather than as a pointer back at the review, the verified anchor, what was done, the authority under which it was done or deferred, and the decision a human still owns.

It is the canonical scope manifest for that review. The detailed reasoning for each item lives in the register named in its row; this page exists so that the set is provably complete and so that nothing is answered by silence.

**Read the disposition column with its authority column.** A row marked DEFERRED is not a row that was skipped. It is a row where the fix is barred by a specific clause of the frozen Agent Action Plan, and the clause is named so a reader can check it rather than take it on trust. Where a deferral rests on the plan freezing security outcomes, that is worth stating plainly: **the defect is real and it is not fixed here.** The plan preserves observable behaviour, and an authorization check that did not fire before and fires now is a change in observable behaviour, however much it ought to fire.

### C-01 — Critical — DEFERRED

**What is wrong.** A forgeable principal cookie retrieves a cached `Authentication` from the WebDAV adapter's session cache, and the cached entry survives logout, so a caller who guesses or replays the cookie value resumes an authenticated identity.

**Where.** WebDAV login / cache / adapter / logout paths

**Authority for this disposition.** AAP 0.2.2 *Preserved Without Modification* freezes **security and permission-evaluation outcomes**; replacing the cookie with a signed session-bound token changes an authentication outcome. **Detail.** [Pre-existing Defects](pre-existing-defects.md), WebDAV entry

## Consolidated ratification register

This section answers the half of M-25 that repairing a self-check command does not touch. Review recorded that thirteen changes and risk acceptances are delivered without evidenced owner ratification. That is correct, and **it cannot be resolved by this change set at all**: an agent has no authority to ratify a deviation from a frozen plan, and a page that ratified its own deviations would be precisely the failure the finding names. What can be delivered is a single place where every unratified item is counted and named, so the decision is a bounded piece of work rather than an archaeology exercise.

Two things this register deliberately does **not** do. It does not describe any delivered change as settled — the status token reads `NOT RATIFIED` inside each row so that a reader skimming the table cannot take it as finished. The open question is authority, not correctness, and conflating the two would let a well-evidenced change ratify itself.

## Evidence-tree governance

This section answers N-07, which recorded PII and topology over-collection and indefinite retention with no stated policy. The over-collection half is answered by **measurement rather than assertion**, because the original claim was unmeasured in both directions — it neither counted what was there nor said what it was.

### What is actually in the evidence tree

Every email-shaped string under `docs/migration/smoke-evidence/` was extracted and classified. The tree is **891 files, 14,892,537 bytes**, holding **1,799** email-shaped strings — and only **17 distinct values**, which is what makes an exhaustive classification possible rather than a sample:

| Count | What it is | Personal data? |
| ---: | --- | --- |
| 1,194 | `arkcase-admin@arkcase.org`, the smoke-test administrator whose credentials are published in `README.md` | No — a documented test fixture |
| 348 | `git@github.com`, the SSH pseudo-address in a Git remote URL | No — a protocol constant, not a mailbox |
| 247 | `ARKCASE_*@ARKCASE.ORG` LDAP authority and group names | No — directory group identifiers that happen to be address-shaped |
| 4 | `i@izs.me` in the npm CLI's own licensing notice, printed into the build log | No — upstream boilerplate, already public |
| 3 | `user@example.com` in an HTML placeholder on the rendered login page | No — the reserved `example.com` domain |
| 1 | `tonghuaroot@gmail.com`, a researcher credit line inside a published GitHub advisory in the corpus | No — published by the advisory itself |
| 1 | `premium-server@thawte.com`, the DN of a CA certificate in the JDK truststore, printed by Tomcat at startup | No — a certificate authority contact |
| 1 | `somepass@example.invalid` in the redaction self-test fixture | No — the reserved `.invalid` TLD |

**The conclusion, stated as the measurement supports it and no further: the evidence tree contains no email address belonging to any ArkCase user, employee or data subject.** Two of the seventeen values are real addresses of real people — an npm maintainer and a security researcher — and both arrive as published upstream metadata that this repository copied rather than collected. They are named here rather than quietly grouped into a residual bucket.

**Why the addresses are not redacted, which is the recommendation review made.** The captures are compared between a baseline and a migrated run, and the comparison is over SHA-256 digests of the captured records. Redacting a value changes the digest, so redacting after capture would destroy the evidence the capture exists to provide, and redacting before capture would mean the two sides were never compared on equal terms. The fixture address is also the one value a reader needs in order to reproduce a flow. Where redaction *is* appropriate — credentials and bearer tokens — it is applied at capture time by the redactor in `smoke-checks.sh`, which has its own self-test; a defect in one of its rules was found and fixed during this work, in a rule whose missing left boundary made it rewrite `browserUser="…"` as well as `user="…"`.

**Topology.** The captures name `localhost`, container names and ports on the reference stack. That is deployment topology for a disposable local stack provisioned from public images, not for any customer environment, and it is required to make a flow reproducible. No customer hostname, address or credential appears.

### Retention and access policy

The retention half of N-07 was a genuine gap: no policy was stated anywhere. One is stated here, and its limits are stated with it, because a policy this repository cannot enforce should not be written as though it can.

- **Purpose limitation.** The tree exists to evidence one migration against one baseline. It is not an operational log store and nothing should be added to it that a gate does not assert on.
- **Retention.** Retain while the migration is under review and until the change set is accepted, plus one release cycle so a regression can be diffed against it. After that the captures may be deleted; the registers and the digests that summarise them are the durable record and are what later readers need.
- **Access.** Read access follows repository access. The tree carries no secret — verified by the redactor's self-test and by the classification above — so it needs no access class narrower than the source it sits beside. That is a statement about what is in the tree, not a licence to add secrets to it.
- **On adding to it.** Any new capture must pass the redactor before it is committed. The self-test exists so that a redaction rule cannot silently stop matching, which is the failure mode that would put a credential here.
- **What this repository cannot enforce.** Deletion at the end of the retention window, and access control wherever the tree is mirrored or exported, are operator actions. Git also retains deleted content in history, so deletion from the working tree is not erasure — if a future capture ever did contain personal data, history rewriting would be required and that is a decision outside this change set.
