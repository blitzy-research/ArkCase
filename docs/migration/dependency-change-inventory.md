# Dependency Change Inventory

This page is the authoritative register of every dependency change made by the runtime migration that moves ArkCase from its JDK 8 and Node 6-8 era foundation onto Java 17 and Node 20 LTS. It exists for exactly one reason: rule R-1 mandates it. No feature description would have produced it.

R-1's completion condition is strict, and it cuts in both directions. Every changed artifact must appear here with its registry, its old version, its new version, and a **specific** Java 17 or Node 20 compatibility reason. A row whose reason reads only "compatibility", "modernization" or "upgrade for Java 17" fails. An artifact that is changed in the diff but absent from this page fails. And a row that has no corresponding change in the diff fails too — that last check is what catches an unjustified version bump, which R-1 forbids just as firmly as it forbids an unjustified omission.

Nothing about the application's observable behaviour changes. REST contracts, the database schema, integration wire behaviour, security outcomes and existing test assertions are held constant; the delta is concentrated in build configuration and the dependency graph. Every entry below is therefore either a compatibility fix, an explicitly classified supportability or reproducibility change, or a removal — never a discretionary upgrade.

## Rules Provenance

Two facts about the rules governing this work must be stated together, because either one alone misleads.

- **There is no on-disk user rules document for this project.** The project's rules facility reports, verbatim, *"No user rules provided."* There is consequently no external full-text source to defer to for the rules cited below.
- **Rules are nonetheless present and binding.** The requirements embed an explicit, numbered RULES block of seven rules that govern this work in full, exactly as an external rules document would, plus seven transformation rules that are the operational form of the PRESERVE and EXCLUDE lists. Fourteen constraints apply.

Recording only the first fact would imply that enterprise best practice is the sole standard here, which is wrong. Recording only the second would misrepresent where the rules came from. Enterprise-standard best practice is applied *on top of* the fourteen, never as a substitute for them, and no rule has been invented or softened. Where best practice would have permitted something a rule forbids — a JVM argument that opens an encapsulated JDK package, a test exclusion, a convenient dependency bump — the rule wins.

The identifiers `R-1` through `R-7` and `R-T1` through `R-T7`, and the descriptive labels attached to them, are the **migration plan's own navigational convention**. They are not quoted titles. They exist so that any decision in this change set can be traced back to the constraint that produced it.

The rule that mandates this page:

> **R-1 — Justified Dependency Changes.** Every dependency version change must have a specific Java 17 or Node 20 compatibility reason, and that reason must be recorded in a delivered inventory naming the artifact, its old and new versions, and the justification. **A change without a reason is out of scope.**

Its stated scope is all manifests and POMs. The rules that shape individual entries below are R-2 (production launch configuration must not rely on access to encapsulated JDK internals, and any exception must be documented), R-3 (no release-8 escape hatch), R-4 (the frontend must genuinely run on Node 20, with no container pinned to an old runtime and no vendored dead packages), R-6 (pre-existing bugs are documented rather than fixed, unless one blocks a validation item), R-7 (behaviour observed at the base commit on JDK 8 is the tie-breaker for any ambiguity), R-T1 (namespace invariance: `javax.*` stays `javax.*`, and artifact eligibility is decided by inspecting a jar's package prefixes rather than its coordinates), R-T3 (fix the library rather than open the module), R-T4 (explicit version pinning, and removal of dead or plain-HTTP repository declarations) and R-T5 (a lockfile-governed frontend graph with every Git dependency pinned to an exact commit).

## Method

Documentation alone was treated as insufficient evidence. For libraries of this vintage, published support matrices are frequently silent, ambiguous or simply wrong about the exact release at which a compatibility problem stops, and several of the findings below contradict what a reasonable documentation review would have concluded. Every version floor recorded here was therefore established by **executing** the library on the target runtime.

The toolchain of record:

| Component | Version | Role |
| --- | --- | --- |
| OpenJDK | 17.0.19 | Target runtime — every Java 17 floor, blocker and disproven risk was established by execution here |
| Apache Maven | 3.8.7 | Reactor builds and dependency resolution; also the source of the blocked plain-HTTP repository behaviour |
| Node.js | 20.20.2 | Target frontend runtime — all package install and execution probes |
| npm | 10.8.2 | Lockfile generation at version 3, Git specification resolution, credential-independence testing |

Three properties of this inventory follow from that method.

- **Every target coordinate was resolved against its registry and confirmed to exist.** All twenty-one Maven coordinates named in the table below returned a successful response and both Node artifacts were installed locally; the coordinates in the supplementary section were confirmed the same way. Each was additionally re-confirmed present in the resolved local repository this branch builds against.
- **No version is a placeholder, and no version is expressed as a floating or newest-available reference.** Every target is an exact release.
- **Where a change is not a hard blocker, the row says so.** Two entries — the Surefire pin and the JaCoCo advance — are classified explicitly as reproducibility and supportability changes rather than as fixes for an observed failure. Presenting them as blockers would be more flattering and less true.

Claims about jar contents were verified by reading the archives rather than by trusting coordinates, which is what R-T1 demands. Line anchors were verified against the source branch at base commit `c8f6226105`; where a published figure differs from the migration plan's prose, the verified figure is given first and the plan's figure is noted, so the delta is visible rather than silently contradicted. Those deltas are collected in a section of their own below.
