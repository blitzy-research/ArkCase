# Dependency Change Inventory

This page is the authoritative register of every dependency change made by the runtime migration that moves ArkCase from its JDK 8 and Node 6-8 era foundation onto Java 17 and Node 20 LTS. It exists for exactly one reason: rule R-1 mandates it. No feature description would have produced it.

R-1's completion condition is strict, and it cuts in both directions. Every changed artifact must appear here with its registry, its old version, its new version, and a **specific** Java 17 or Node 20 compatibility reason. A row whose reason reads only "compatibility", "modernization" or "upgrade for Java 17" fails. An artifact that is changed in the diff but absent from this page fails. And a row that has no corresponding change in the diff fails too — that last check is what catches an unjustified version bump, which R-1 forbids just as firmly as it forbids an unjustified omission.

Nothing about the application's observable behaviour changes. REST contracts, the database schema, integration wire behaviour, security outcomes and existing test assertions are held constant; the delta is concentrated in build configuration and the dependency graph. Every entry below is therefore either a compatibility fix, an explicitly classified supportability or reproducibility change, or a removal — never a discretionary upgrade.

## Rules Provenance

Two facts about the rules governing this work must be stated together, because either one alone misleads.

- **There is no on-disk user rules document for this project.** The project's rules facility reports, verbatim, *"No user rules provided."* There is consequently no external full-text source to defer to for the rules cited below.
- **Rules are nonetheless present and binding.** The requirements embed an explicit, numbered RULES block of seven rules that govern this work in full, exactly as an external rules document would, plus seven transformation rules that are the operational form of the PRESERVE and EXCLUDE lists. Fourteen constraints apply.

Recording only the first fact would imply that enterprise best practice is the sole standard here, which is wrong. Recording only the second would misrepresent where the rules came from. Enterprise-standard best practice is applied *on top of* the fourteen, never as a substitute for them, and no rule has been invented or softened. Where best practice would have permitted something a rule forbids — a JVM argument that opens an encapsulated JDK package, a test exclusion, a convenient dependency bump — the rule wins.

The identifiers `R-1` through `R-7` and `R-T1` through `R-T7`, and the descriptive labels attached to them, are the **migration plan's own navigational convention**. They are not quoted titles. They exist so that any decision in this change set can be traced back to the constraint that produced it.

The rule that mandates this page:

> **R-1 — Justified Dependency Changes.** Every dependency version change must have a specific Java 17 or Node 20 compatibility reason, and that reason must be recorded in a delivered inventory naming the artifact, its old and new versions, and the justification. **A change without a reason is out of scope.**

Its stated scope is all manifests and POMs. The rules that shape individual entries below are R-2 (production launch configuration must not rely on access to encapsulated JDK internals, and any exception must be documented), R-3 (no release-8 escape hatch), R-4 (the frontend must genuinely run on Node 20, with no container pinned to an old runtime and no vendored dead packages), R-6 (pre-existing bugs are documented rather than fixed, unless one blocks a validation item), R-7 (behaviour observed at the base commit on JDK 8 is the tie-breaker for any ambiguity), R-T1 (namespace invariance: `javax.*` stays `javax.*`, and artifact eligibility is decided by inspecting a jar's package prefixes rather than its coordinates), R-T3 (fix the library rather than open the module), R-T4 (explicit version pinning, and removal of dead or plain-HTTP repository declarations) and R-T5 (a lockfile-governed frontend graph with every Git dependency pinned to an exact commit).

## Method

Documentation alone was treated as insufficient evidence. For libraries of this vintage, published support matrices are frequently silent, ambiguous or simply wrong about the exact release at which a compatibility problem stops, and several of the findings below contradict what a reasonable documentation review would have concluded. Every version floor recorded here was therefore established by **executing** the library on the target runtime.

The toolchain of record:

| Component | Version | Role |
| --- | --- | --- |
| OpenJDK | 17.0.19 | Target runtime — every Java 17 floor, blocker and disproven risk was established by execution here |
| Apache Maven | 3.8.7 | Reactor builds and dependency resolution; also the source of the blocked plain-HTTP repository behaviour |
| Node.js | 20.20.2 | Target frontend runtime — all package install and execution probes |
| npm | 10.8.2 | Lockfile generation at version 3, Git specification resolution, credential-independence testing |

Three properties of this inventory follow from that method.

- **Every target coordinate was resolved against its registry and confirmed to exist.** All twenty-one Maven coordinates named in the table below returned a successful response and both Node artifacts were installed locally; the coordinates in the supplementary section were confirmed the same way. Each was additionally re-confirmed present in the resolved local repository this branch builds against.
- **No version is a placeholder, and no version is expressed as a floating or newest-available reference.** Every target is an exact release.
- **Where a change is not a hard blocker, the row says so.** Two entries — the Surefire pin and the JaCoCo advance — are classified explicitly as reproducibility and supportability changes rather than as fixes for an observed failure. Presenting them as blockers would be more flattering and less true.

Claims about jar contents were verified by reading the archives rather than by trusting coordinates, which is what R-T1 demands. Line anchors were verified against the source branch at base commit `c8f6226105`; where a published figure differs from the migration plan's prose, the verified figure is given first and the plan's figure is noted, so the delta is visible rather than silently contradicted. Those deltas are collected in a section of their own below.

### The Eighteen Git Specifications That Cannot Take the Prescribed Form

The prescribed representation is `owner/repo#<40-hex commit SHA>` and nothing else. Fifty-eight of the seventy-six use it. The remaining eighteen use the **codeload tarball fallback the plan itself documents** — described there as *"the documented fallback ... the codeload tarball form, which is the only form that records an HTTPS resolved URL"* — and they use it for one reason only: **npm 10 physically cannot resolve them in the prescribed form.** That is a measured fact about the upstream commits, not a preference, and it is recorded here as a deviation rather than smoothed over by declaring the two forms equivalent. They are not equivalent, and this document does not say they are.

What was measured, on Node 20.20.2 with npm 10.8.2:

- **Eleven of the eighteen carry no `package.json` at the pinned commit.** They are Bower-era asset packages that ship a `bower.json` and nothing else. npm's Git handler reads a manifest out of the clone before it can resolve anything, so it aborts with `ENOENT: no such file or directory, open '.../git-clone…/package.json'`. Verified for `components/font-awesome` under `npm install --package-lock-only`, under `npm install --package-lock-only --ignore-scripts`, **and under a full `npm install`** — the failure is in manifest resolution, so no npm flag reaches it. The eleven are `ziscloud/angular-slimscroll`, `PascalPrecht/bower-angular-translate`, `PascalPrecht/bower-angular-translate-loader-partial`, `angular-ui/ui-ace`, `angular-ui/angular-ui-router-bower`, `angular-ui/ui-utils`, `components/font-awesome`, `FortAwesome/Font-Awesome`, `danialfarid/angular-file-upload-bower`, `danialfarid/angular-file-upload-shim-bower`, `mbenford/ngTagsInput-bower` and `cdwv/ui-grid-draggable-rows` — twelve names for eleven manifest-less packages plus the one below that fails both ways.
- **The remaining seven do carry a manifest, and fail differently.** Resolving a Git specification makes npm clone the repository and run its preparation script, and those scripts are of the same vintage as the packages: `jquery/jquery-dist` fails in `node-gyp` attempting a native build, and `cdwv/ui-grid-draggable-rows` pulls a headless-browser package whose installer aborts on Node 20. Passing `--ignore-scripts` does resolve the seven, but only by suppressing preparation for the whole install, which would change how the twenty-nine registry dependencies install as well — a behavioural change made to satisfy a representational preference, which **R-7** settles against, since baseline behaviour is the tie-breaker.
- **A tarball is a packed artifact, so none of that applies to it.** npm extracts it and synthesises the manifest from the specification, runs no preparation script, and needs no clone.

What the fallback does **not** cost:

- **Immutability is identical.** Every one of the eighteen URLs ends in the same 40-character commit SHA the prescribed form would carry, mined from the superseded lockfile. A commit cannot move, so no checkout can resolve differently — which is the entire purpose **R-T5** assigns to the pinning.
- **Nothing is mutable anywhere.** Across all 105 dependency keys: 76 exact-commit pins, 29 registry ranges resolved and frozen by the lockfile, **zero** semver-qualified Git ranges and **zero** branch or tag references.
- **No dependency key changes**, so the frozen asset layout that resolves literal `node_modules/...` paths is untouched.

### Git Specification Form — Per-Entry Record

The row above states the rule. This record discharges it one entry at a time, because a rule applied to a group is not a justification for any member of it. Every outcome below was produced on Node 20.20.2 with npm 10.8.2 by declaring that single dependency, in the plain `owner/repo#commit` form, in an otherwise empty project and capturing what npm did. **Not one of the 18 can be moved to the plain form: sixteen do not install at all, and the remaining two install content that differs from the commit they pin. The archive form is therefore a measured necessity for every one of them and a precaution for none.** Both forms name the same commit, so no entry's identity, and no entry's version, differs between them.

A credentials explanation was considered and **disproven**, which matters because it is the explanation this record replaces. Reinstalling the whole graph from the committed lockfile with the SSH transport forced to fail and interactive prompting disabled still completed successfully and still produced every literal asset path, so the 58 plain-form entries need no credential material and the 18 archive-form entries are not retained for want of an HTTPS resolution.

Three distinct blocking classes were observed, and they are named in the table's third column.

- **No manifest at the pinned commit.** The repository contains no `package.json` at that commit. npm first requests the commit archive, cannot read a manifest from it and reports the payload as corrupt, then clones the repository and fails on the same absence, ending in `enoent Could not read package.json` with exit status 254. This is a property of the upstream repository at an immutable commit, so **no npm setting, and no rewrite of the specification, can change it.**

## Installed Graph Parity Against the Superseded Lockfile

Replacing the lockfile replaces the resolver, and the two resolvers do not agree. The superseded one and npm 10 differ in peer handling and in the order they choose versions, so a lockfile regenerated from an unchanged manifest can still install a **different set of packages** than the one it supersedes. That is a reproducibility question rather than a version question, so it does not belong in either table above — but leaving it unstated would be the omission **R-T5** and **R-T6** exist to prevent, and it is recorded here in full.

The comparison was made by reconstructing the superseded graph from the deleted lockfile at the base commit and walking it against the committed `package-lock.json` **by install path**, which is the contract that matters: the asset resolver at `config/env/all.js` addresses **87 literal `node_modules/...` file paths covering 65 distinct dependency keys**, and any path that stops resolving breaks the pipeline silently.

Four name-and-version pairs were present in the npm graph and absent from the superseded one. Each was traced to its cause and disposed of individually.

### R-6 escape-clause count is unchanged at two

**R-6's escape clause is invoked exactly twice in this change set** — the Sass toolchain removal and the tracked `profiles.js`, both stated as such in the Node table above. Nothing on this page is a third.

- **The plan enumerates the POMs that may change, and these go beyond it.** The frozen plan lists the twelve child POMs that drop PowerMock, the five that drop the EasyMock class extension and the six that gain the inline mock maker, and then states, in its own words, *"No other POM changes."* It also states its basis for that claim: *"zero child POMs hardcode a test-library version, so every version bump is a root-POM property edit and child POMs change only where an artifact disappears or appears."* That basis is about **test** libraries. ### Scope note — why the Groovy row touches a child POM

The Groovy row is the only one on this page that edits a POM outside the root aggregator, so its scope is stated in
full rather than left to inference.

**What each of the two edits reaches, measured rather than assumed.** `mvn dependency:tree` was run across the whole
reactor and the resolved graphs collected: **142 modules** produce a tree, **79** of them resolve `groovy-all`, and
exactly **one** of the 79 — `acm-service-search` — declares it directly. The other **78** receive it transitively
through that module, which means the root `dependencyManagement` entry governs all 78 of them and none of them needed a
POM change. Maven resolves a version declared on a direct dependency ahead of any managed version, so the same root
entry could not reach the 79th. The child edit therefore changes the resolved version for **one module**, and the
78-module effect belongs entirely to the root entry, which sits inside the aggregator surface the plan already opens.

**Why the module needs the newer version even though nothing in it uses Groovy.** No Java file in the reactor imports
Groovy and there is no `.groovy` script anywhere; the declaration carries the comment `this entry is needed for IDEA
v12` and exists for IDE support. Groovy is loaded regardless, because Spring's `DelegatingSmartContextLoader` selects
`GenericGroovyXmlContextLoader` as soon as `groovy.lang.Closure` is on the test classpath, and that loader constructs a
`GroovyBeanDefinitionReader` even when every declared location is `.xml`. Four of the module's test classes are
`@ContextConfiguration` classes under `web/api` and run through that loader. On JDK 17, initialising Groovy's
`GroovySystem` from 1.8.6 fails, because Groovy's class cache calls `setAccessible` on a `java.lang` member that
`java.base` does not open. The consequence was measured in the module itself: `mvn clean test` reports `Tests run: 23,
Failures: 0, Errors: 12` with the literal 1.8.6 and `Tests run: 23, Failures: 0, Errors: 0` once the pinned version
applies, with every one of the 12 errors carrying `Could not initialize class groovy.lang.GroovySystem` raised from
`GroovyBeanDefinitionReader.<init>`.

**Reconciliation with the plan's “no other POM changes” statement.** The plan restricts child-POM edits to modules where
a test artifact is removed or added, and rests that restriction on a specific measurement: that **zero child POMs
hardcode a test-library version**, so every version bump can be a root-POM property edit. That premise holds for test
libraries and does not extend to this declaration, which is **compile scope**. The plan itself records the same class of
exception when it registers three hardcoded non-test versions in a child POM — `spring-ws-core` `1.5.9`, `axis` `1.4`
and `commons-discovery` `0.5` in `acm-service-billing/pom.xml` — and those are left alone precisely because they are
never loaded. This one is loaded, on a code path the migration itself moves onto JDK 17, which is what separates it from
them. Leaving it at 1.8.6 would leave 12 unit-test errors that do not exist in the JDK 8 baseline, and those errors
could then only be accepted by excluding tests that were passing before the migration — which R-5 forbids and which
gate 1 fails on.

**Alternatives considered and rejected.**

- *Leave the literal `1.8.6` untouched.* Rejected on measurement: 12 of the module's 23 unit tests error on JDK 17. The
  only way to make the build green while keeping the literal is to exclude tests that pass at baseline.
- *Rely on the root `dependencyManagement` entry alone.* Rejected: managed versions apply to transitively resolved
  copies, and a direct declaration wins. Verified — with the literal in place the module's tree still resolved 1.8.6
  while all 78 transitive consumers resolved 2.4.21.
- *Declare `groovy-all` in the aggregator's global `<dependencies>` block.* Rejected: an inherited dependency is
  overridden by the child's own declaration of the same coordinates, so the module would keep resolving its literal.
- *Keep Groovy off the test classpath with Surefire `classpathDependencyExcludes`.* Rejected: it would strip Groovy
  reactor-wide and change which context loader Spring selects for tests in every module, a far broader behavioural
  change than one version reference, and it would suppress the failure in test configuration rather than fix its cause.
- *Constrain the version with `maven-enforcer-plugin`.* Rejected: enforcer rules can fail a build on a version but
  cannot substitute one, so the module would still compile and test against 1.8.6 until it was edited anyway.
- *Delete the dependency, since no source imports Groovy.* Rejected: removing it takes `groovy.lang.Closure` off the
  test classpath and so changes which loader Spring selects for the module's four `@ContextConfiguration` classes. That
  is a change to how those tests run rather than a runtime-compatibility fix, and R-6 keeps discovered cruft registered
  rather than removed.

**The edit that was made.** One `<version>` element in `acm-services/acm-service-search/pom.xml` changes from the

That is a narrower improvement than pinning, and it is recorded as such rather than as a fix: the residual exposure — a mutable default tag — is registered in [Pre-existing Defects](pre-existing-defects.md), because the control that would close it lives on the runner rather than in this repository.

**The strongest CI check is structural rather than textual, and it is the one that enforces job-command invariance.** Load both files at the base commit and at this branch and compare them key by key: the only permitted differences are the `image` value and the four job scripts that lose the collector flag. Anything else — a new top-level key, a job gaining or losing a command, a stage renamed — fails.

```bash
python3 - <<'EOF'
import subprocess, yaml
for path in ['.gitlab-ci.yml', '.gitlab-ci-release.yml']:
    b = yaml.safe_load(subprocess.check_output(['git','show',f'c8f6226105:{path}'], text=True))
    h = yaml.safe_load(open(path).read())
    assert set(b) == set(h), (path, set(b) ^ set(h))
    for k in sorted(b):
        if b[k] != h[k]:
            print(path, k)
EOF
```

It must print exactly four lines: `.gitlab-ci.yml image`, `.gitlab-ci.yml .build_backend_snapshot`, and the three release jobs `release`, `release_candidate_X` and `release_hotfix`. That is five lines counting the image, and every one of the four job differences must be the collector flag and nothing else.

The bidirectional cross-check:

- **Forward.** For every change visible in `git diff` across `pom.xml`, the child POMs, `package.json` and the CI files, confirm that a row here — or an entry in the two supplementary sections — covers it. **An artifact changed in the diff but absent from this page fails.** A version-line grep is not sufficient for this direction and must not be relied on: three whole classes of change on this page carry **no version at all** — an added exclusion, a version-less declaration that inherits a managed version, and an agent-scoped exclusion with no coordinates — so a check that greps `version` passes straight over every one of them. That is the specific failure that let three exclusion entries and one declaration go unrecorded in an earlier revision. Enumerate changed coordinates instead, which catches all of them:

```bash
BASE=c8f6226105
PAGE=$(git ls-files '*dependency-change-inventory.md')
for f in $(git diff --name-only $BASE..HEAD -- '**/pom.xml' 'pom.xml'); do
  git diff $BASE..HEAD -- "$f" \
  | grep -oE '^[-+][[:space:]]*<artifactId>[^<]+' | sed 's/.*<artifactId>//' | sort -u \
  | while read -r a; do grep -q -- "$a" "$PAGE" || echo "UNACCOUNTED $a in $f"; done
done; echo "forward check complete"
```

  It must print the completion line and **nothing else**. As delivered it does: across the **25** changed POMs the enumeration yields **68** net coordinate deltas and all 68 resolve to an entry on this page. Two properties are worth knowing before relying on it. It has real discriminating power rather than passing vacuously — pointed at a sibling register that does not enumerate coordinates it reports every delta as unaccounted. And it is deliberately a name-level check, so a hit confirms the coordinate is *mentioned*; whether the entry describes the change correctly is the reading step below, not something a grep can settle. Version-line changes are a separate, smaller sweep, and all **nine** of them are covered too — the removed `2.1.0` override on the JPA API, the Groovy literal, the two duplicate Failsafe pins and the five `easymock-extension.version` references that leave with their declarations:

```bash
for f in $(git diff --name-only $BASE..HEAD -- '**/pom.xml'); do
  git diff $BASE..HEAD -- "$f" | grep -qE '^[+-][[:space:]]*<version>' && echo "$f"
done
```
- **Contrapositive.** For every row here, confirm a corresponding real change exists in the diff. **A row with no corresponding change also fails** — this is the check that catches an unjustified bump, which R-1 forbids as firmly as a missing justification. One row legitimately records no version movement: `junit:junit`, whose target column reads UNCHANGED and explains that what moved was its constraint. The contrapositive section records absence of change by design, and its rows must therefore be absent from the diff.
- **The seventeen unchanged libraries must not appear as changed versions in the diff.** Their version properties are listed with anchors above precisely so that this can be checked line by line rather than re-derived.
