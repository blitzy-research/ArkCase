# Ambiguity Resolutions

This page records every decision in the runtime migration onto Java 17 and Node 20 LTS where the requirements admitted more than one defensible answer, and where **the platform's observed behaviour at the base commit on JDK 8 was used as the tie-breaker**. It exists because a rule demands it as a deliverable, not because any feature description mentions it.

Each entry states what was chosen, **what was rejected and why**, the evidence that settled it, and the baseline property the choice protects. The rejected options are the part that makes this page worth reading: a register that recorded only the chosen option would be a changelog. The recurring pattern is that baseline behaviour selected the **less obvious** option — the larger jar, the uglier version specifier, the extra exclusion, the more laborious test rewrite. Without the rejected alternative beside it, a later reader cannot tell that a choice was made at all.

## Rules Provenance

Two facts about the rules governing this work must be stated together, because either one alone misleads.

- **There is no on-disk user rules document for this project.** The project's rules facility reports, verbatim, *"No user rules provided."*
- **Rules are nonetheless present and binding.** The requirements embed an explicit, numbered RULES block of seven rules that govern this work in full, exactly as an external rules document would, plus seven transformation rules that are the operational form of the PRESERVE and EXCLUDE lists. Fourteen constraints apply.

The identifiers `R-1` through `R-7` and `R-T1` through `R-T7`, and the short labels attached to them throughout this folder, are the **migration plan's own navigational convention** — not quoted titles. They exist so that a decision can be traced to the constraint that produced it. No rule has been invented and none has been softened: enterprise-standard best practice is applied *on top of* the fourteen, never as a substitute for them, and where best practice would have permitted something a rule forbids, the rule won.

That pairing is itself an ambiguity that had to be resolved, so it is recorded on the same terms as everything else on this page.

- **Decision.** Disclose both facts, together, wherever the provenance of the rules is stated.
- **Alternatives considered and rejected.** *Report only "no user rules provided".* Rejected because it implies enterprise best practice is the sole standard here, which is false — fourteen specific constraints apply, and several of this page's entries exist only because one of them demanded it. *Report only the embedded rules block.* Rejected because it misstates where the rules came from, and would let a reader assume there is an authoritative on-disk document to consult when there is not.
- **Evidence.** The rules facility was queried and returned that exact sentence. The requirements were then read for their own RULES block, which is present, numbered, and prescriptive.
- **Baseline property preserved.** None — this is a provenance-disclosure resolution, not a behavioural one. It is recorded here because an undisclosed provenance gap is indistinguishable from an overlooked one.

## What R-7 Requires

One rule is the reason this page exists:

> **R-7 — Baseline behaviour is the tie-breaker.** The application's observed behaviour at the base commit on JDK 8 is the tie-breaker for any ambiguity, and each resolution must be documented.

*[Editorial note: the rule as written names the older runtime in the form "Java" followed by the major version. It is rendered here as "JDK 8" to comply with this folder's wording policy, recorded as the final entry on this page. The substitution changes no meaning, and it is disclosed rather than applied silently, because quietly altering a quoted rule is worse than the wording problem it solves.]*

R-7's completion condition for this page is that every baseline-as-tie-breaker decision is recorded **with its rejected alternatives**. An entry that names only the option taken fails that condition.

Eight further rules bear on individual entries and are cited where they do:

- **R-T1 — Namespace invariance.** *"Every `javax.*` import remains `javax.*`. JEP 320 removals are compensated by adding javax-namespace artifacts, never by rewriting source to `jakarta.*`. Artifact eligibility is decided by inspecting the jar's package prefixes, not its groupId or artifactId."* Entries 2 and 17 turn on it, and both apply it at the **artifact** level rather than only at the import level, which is stricter than a literal reading.
- **R-T5 — Lockfile-governed frontend graph.** *"The frontend dependency graph is fully reproducible from a committed `package-lock.json`, with every Git dependency pinned to an exact commit SHA. No dependency may resolve differently between two checkouts."* Entry 3.
- **R-T6 — Asset-layout contract immutability.** *"The literal `node_modules/...` paths in `config/env/all.js`, the `Gruntfile.js` task graph, and the five output artifact names are contract. Dependency keys cannot be renamed and the install topology cannot be flattened or restructured."* Entries 3 and 6.
- **R-T7 — Evidence over exit codes.** *"Validation asserts on produced artifacts and captured output, never on process exit status alone. This is mandatory rather than stylistic because `Gruntfile.js` sets `grunt.option('force', true)`, which masks task failures and lets a broken build exit zero."* Entry 6.
- **R-T3 — Fix the library, do not open the module.** Where a dependency fails under strong encapsulation, the remedy is to upgrade or replace that dependency. Adding a module-access JVM argument — one that opens or exports an otherwise-encapsulated JDK package to the unnamed module — to production launch configuration is prohibited, and JDK-internal call sites are rewritten to supported APIs instead. Entries 5, 7, 10 and 11.
- **R-1 — Justified dependency changes.** *"Every dependency version change must have a specific Java 17 or Node 20 compatibility reason… A change without a reason is out of scope."* Entries 4, 12, 17 and 19 — and note that R-1 binds in both directions: it forbids an unjustified bump as firmly as it forbids a missing fix.
- **R-5 — No disabling of failing tests.** *"Failing tests must not be disabled, and exclusions are limited to failures already present at baseline."* Entries 10, 13 and 16.
- **R-6 — Document discovered bugs, do not fix them.** Its escape clause is invoked exactly **twice** in the whole change set — the frontend `profiles.js` creation and the Sass toolchain removal — and **neither invocation is in this folder**. Entry 6's discussion of the Sass toolchain explains why *removal* was chosen over *replacement*; it is not an additional invocation.

## How Each Resolution Is Recorded

Every entry has the same four parts, in the same order. The consistency is what makes the page auditable rather than merely readable.

- **Decision.** What was chosen, in one or two sentences.
- **Alternatives considered and rejected.** Each option that lost, with the specific reason it lost. This part is mandatory and is never empty.
- **Evidence.** How the decision was established — by executing on the target runtime, by inspecting a jar's contents, or by reading the repository at the base commit. The artefact or the anchor is named.
- **Baseline property preserved.** The specific observable behaviour at the JDK 8 base commit that the decision protects. Where an entry is a documentation decision rather than a behavioural one, it says so plainly instead of manufacturing a claim.

Two conventions govern how entries are identified, both settled as decisions in their own right in entry 18.

- **The entry number is a stable identifier, not a position.** Sibling registers cite entries of this page by number, so numbers are never reused and never reassigned; a new entry takes the next unused number regardless of where it reads best.
- **The sections below run in the order the requirements specify**, which for the first ten is the order of the mandatory resolution set. Numeric order and reading order therefore differ, and the summary table below is the map between them.

## 1 — The Activation Framework Artifact

JEP 320 removed the JavaBeans Activation Framework from the JDK, so it has to be reinstated as an ordinary dependency. Two artifacts satisfy the same `javax.activation` API, and their coordinates give no hint that the choice matters.

- **Decision.** Reinstate the **reference implementation**, `com.sun.activation:javax.activation`, at compile scope in the aggregator's global dependency block. The older activation jar that arrives transitively is excluded at both entries that pull it, so exactly one provider of the package reaches any module.
- **Alternatives considered and rejected.** *The API-only jar.* This is the tidier and more obvious dependency — smaller, and "API only" reads like the disciplined choice. It was rejected because reading both jars showed they are not equivalent: the API-only artifact **lacks** `META-INF/mimetypes.default` and `META-INF/mailcap.default`, while the reference implementation is a strict superset shipping both. *Accepting the transitively-supplied older jar instead of declaring one.* Rejected, but **not for the reason first recorded here.** The original rejection said the older jar's `META-INF/mimetypes.default` differs from the reference implementation's, so MIME resolution would depend on classpath order. Direct measurement withdrew that reasoning: the two resources do differ as bytes (581 against 606, 50 differing lines), but once comments and whitespace are removed their payload is **identical — 22 extension-to-type pairs on each side and zero differences between them** — and executing the consumers' own call against the older jar returned the **same media type as the reference implementation for every one of the 18 probed extensions**. Resolution order therefore could not have changed a MIME answer, and this alternative would most likely have preserved behaviour. It is rejected on the two grounds that survive measurement: R-T4 requires the artifact to be pinned explicitly rather than inherited from whichever dependency happens to carry it, and two providers of one package (38 classes against 42) is a duplicate-provider classpath whose class resolution is order-dependent even where its resource payload coincides.
- **Evidence.** Jar-content inspection, plus a consumer census re-derived from the tree: `javax.activation` appears in **8 occurrences across 6 files**, and **five of those six** import `MimetypesFileTypeMap`, which reads exactly those two resources — four in main source and one in test source. The sixth uses `DataHandler` only. The exclusions carry their reasoning inline at the two managed entries that introduce the competing jar. Jar inspection alone was later judged insufficient for a decision this register calls behavioural, so the call the four main-source consumers actually make is now **executed** against each candidate artifact and the resolutions compared, at `docs/migration/smoke-evidence/activation-mime/`. No smoke flow evidences this choice and none is credited with doing so: the document round trip in flow 3 sends an explicit content type, so it never asks the framework to resolve one and would look identical with the wrong artifact.
- **Baseline property preserved.** MIME-type resolution. The decision stands, and the measurement makes the case for it **harder** than this entry first claimed. The prediction recorded here was that the API-only jar would compile cleanly, deploy cleanly, and then silently resolve MIME types differently. What execution observed is worse: constructing a `MimetypesFileTypeMap` against the API-only artifact does not return a different answer, it **throws** — `NoClassDefFoundError: com/sun/activation/registries/LogSupport`, raised from the constructor, before any file name is examined. The API-only jar ships the API and omits the registry implementation the constructor loads, so all five consumers would fail at the first call rather than quietly disagree. The correction cuts both ways and both halves are recorded: the wrong artifact fails louder than predicted, and the *older* artifact was measured to behave identically to the chosen one. **The artifact choice is behavioural, not cosmetic** — but the behaviour at stake is construction succeeding, not a media type shifting.

## 3 — Pinning the Frontend Git Dependencies

The manifest expresses its Git dependencies in a form the previous package manager accepted and the current one cannot parse at all. Some rewrite is unavoidable; which rewrite is the question.

- **Decision.** Move all **76** Git dependency specifications from `owner/repo#<semver-range>` to an exact 40-character commit, mined from the outgoing `yarn.lock` before that file was deleted, and commit the resulting lockfile. Every dependency **key** is preserved unchanged.
- **Alternatives considered and rejected.** *Leaving the specifications as they are.* The current package manager cannot parse the range form at all; resolution fails with a missing-Git-reference error, so this is less an option than a non-starter. *Rewriting to the idiomatic semver-qualified Git form.* This is the readable, conventional answer, and it is unsafe in two independent ways: an open range **re-resolves to whatever tag exists today**, so two checkouts of the same commit can install different library versions — reintroducing the exact mechanism by which a "no behaviour change" refactor silently changes behaviour — and at least one repository fails the resolution outright with a package-metadata cache error under that form. *Pinning to tags.* Also more readable, and rejected for the first of those reasons: a tag is mutable, and a version range is not a pin. *Forcing all 76 into the plain `owner/repo#<commit>` form so the manifest carries one representation instead of two.* This is the option the prescribed representation asks for and it was probed per entry rather than argued about: 16 of the 18 archive-form entries cannot resolve in it at all, and the 2 that can deliver different bytes at two paths the frozen asset layout names literally. Rejected because it is not available, and because taking the 2 that resolve would change the vendor bundle for the sake of a uniform-looking manifest. *Suppressing install scripts globally so the four preparation failures resolve.* Rejected on four counts recorded in the [Dependency Change Inventory](dependency-change-inventory.md): it needs an extra tracked configuration file in a folder whose change set is fixed at five paths; expressed as an environment variable it would be absent from the install the deployed application performs at startup, so the deployment would behave differently from the gate; it would suppress the legitimate install step of three pinned native transitives; and packing a prepared clone still applies the clone's own file allowlist, so the bytes could differ even where the install succeeds.
- **Evidence.** Re-derived from both revisions of the manifest. At the base commit, 76 of 108 dependencies were Git specifications and **none** named a commit. In the migrated manifest, 76 of **105** are Git specifications and **all 76 name an exact commit**, with zero remaining `#`-ranges. They appear in two forms, which is worth stating because a reader counting one form will come up short: **58** use the short `owner/repo#<commit>` form and **18** use a commit-archive URL carrying the same commit in its path. Both are exact-commit pins. **Why 18 take the second form is a measured necessity, not a preference, and an earlier revision of this entry gave the wrong reason** — it said the archive form was "adopted where it was needed to keep restore working without credentials", and that explanation has since been disproven by execution: reinstalling the whole graph with the SSH transport forced to fail and interactive prompting disabled still completed and still produced every literal asset path. The real reason is that the prescribed form is unavailable for those eighteen. Re-measured per entry by [`probe-git-spec-form.sh`](smoke-evidence/dependency-parity/probe-git-spec-form.sh): **16 of 18 cannot resolve at all** — twelve because the upstream repository carries no npm manifest at the pinned commit (exit 254, `Could not read package.json`), four because npm's preparation of the clone runs the repository's own decade-old toolchain and terminates (exit 1, `git dep preparation failed`) — and the remaining **2 resolve but deliver different bytes** than the commit they pin, at two paths the frozen asset layout names literally. **Zero of eighteen are convertible.** Output in [`git-spec-form-probe.txt`](smoke-evidence/dependency-parity/git-spec-form-probe.txt); per-entry record in [Dependency Change Inventory](dependency-change-inventory.md). The outgoing lockfile recorded a commit for 76 of 77 entries across 75 distinct packages with **no package carrying conflicting commits**, so the mapping was unambiguous; the single entry without one was a transitively-resolved registry version. The committed lockfile is at version 3, and the asset resolver's literal paths name **65 distinct installed packages**, all 65 present after the change.
- **Baseline property preserved.** The exact library versions the previous package manager resolved, and with them the bytes of every concatenated bundle — which is what R-T5 exists to guarantee. One ordering constraint fell out of this and is recorded because it is irreversible: the outgoing lockfile is the **sole authoritative source** of those commits, so it had to be mined **before** it was deleted. Reversing those two steps loses the information permanently.

**The near-miss that required understanding rather than tidying.** One library appears twice. `bootbox` is a direct Git dependency resolving to **4.4.0** and owning the top-level installation slot, while a transitive registry range under a dependent package resolves to **5.5.1** — a later major version — in its own nested slot. The asset resolver names the top-level path literally, and the line that names it carries an in-file comment warning that the newer minified build is broken. Deduplicating or hoisting would have looked like an improvement and would have swapped a major version underneath a path that is contract: **R-T6 forbids it and R-7 confirms it.** Understanding the duplication was necessary in order *not* to remove it.

## 2 — The Duplicated JPA API

The reactor pins the JPA API explicitly and independently of the provider version. Advancing the provider to its last `javax.persistence` line introduces a second JPA API artifact transitively — one whose coordinates carry the forbidden namespace. Reading the coordinates suggests a namespace violation; reading the jars tells a different story. This is the change set's most instructive four-way decision, so all four options are recorded.

- **Context established by jar inspection.** The differently-named artifact contains **209 classes under `javax/` and zero under `jakarta/`** — it is the javax API republished under a different artifactId — and its class set is **identical** to the javax-named `2.2.1` artifact, symmetric difference zero.
- **Decision — Option D of four: advance the javax-named pin to `2.2.1` and, in the same change, exclude the differently-named twin.** The result is exactly one API jar on the classpath, javax-named *and* javax-contented, at the API level the provider implements. **The selected option requires both halves**: a one-line property change advancing the pin, **and** an exclusion added at the managed provider entry that introduces the twin — which conveniently already carried an exclusions block, so the structure existed. Either half alone fails, and the failures are the two rejected options below: the advance without the exclusion produces Option C, and the exclusion without the advance produces Option A. Both halves are present in the migrated build.
- **Alternatives considered and rejected — the other three options, each with the specific reason it lost.**
    - *Option A — keep the API at `2.1.0` and exclude the twin.* **REJECTED:** the migrated provider implements the JPA 2.2 API, so holding the pin at the older level starves it of API classes it expects.
    - *Option B — drop the explicit pin and accept the transitive.* **REJECTED:** this leaves a jar whose coordinates carry the forbidden namespace in the resolved graph, which the EXCLUDE directive prohibits **regardless of the jar's internal package names**. R-T1 directs that artifact eligibility be decided by inspecting package prefixes, and that cuts both ways: contents do not launder coordinates.
    - *Option C — keep both.* **REJECTED:** two content-identical API jars means duplicate `javax/persistence/*` class entries resolved by nearest-wins, which is order-sensitive and therefore not reproducible.
- **Evidence.** Registry metadata and jar-content inspection. The javax-named `2.2.1` artifact holds **213 classes, 209 under `javax/`, zero under `jakarta/`**, and adds exactly **two annotation-container types** over `2.1.0` — **both absent from the source**.
- **Baseline property preserved.** The effective DDL of every persistence mapping. Re-derived from the tree: **1,612** main-source `javax.persistence` occurrences — **1,688** including test source, of which **69** are `javax.persistence.criteria` — all continue to resolve identically, so there is **zero source impact and zero DDL impact**. The migration plan quotes 1,610 for the main-source figure; the verified count is 1,612, and the difference is reported rather than reconciled away, because this register's job is to state what was measured.

## 7 — Widening the Base64 Decoder Cast

A vendor Base64 decoder-stream type had to go, because the package it lives in is one the JDK-internal usage audit forbids. The narrowest possible replacement and the natural supertype were both available.

- **Decision.** Delete the vendor import and widen the cast to `java.io.InputStream` — the supertype the vendor decoder already extends, and precisely the type the consumer on the very next line already accepts.
- **Alternatives considered and rejected.** *Retaining the vendor type.* Fails the audit gate, which is a literal text search rather than a semantic one, so the reference would still be found. *Introducing an adapter class to wrap the decoder.* Unnecessary, and therefore wrong in a behaviour-preserving refactor: the supported abstraction is already the type the consumer wants, so an adapter would add a class, a construction site and a failure mode in exchange for nothing. *Accommodating the internal reference with a module-access JVM argument.* Prohibited by R-T3 — and it could not have satisfied the gate anyway, because a textual search does not care how the JVM was launched. The rule and the gate independently foreclose the same shortcut.
- **Evidence.** Read at the base commit. The import sat at `:33`; its sole use was at `:258`, `BASE64DecoderStream b64ds = (BASE64DecoderStream) p.getContent();`, immediately followed at `:259` by `String imageBase64 = BaseEncoding.base64().encode(ByteStreams.toByteArray(b64ds));` — a byte-stream reader that already takes the supertype. In the migrated file the site sits one line earlier, at `:257`, because the deleted import shifted everything below it. The audit itself moved from **7 hits across 5 files** at the base commit to **0** in the migrated tree.
- **Baseline property preserved — with an asymmetry disclosed rather than buried.** Widening a cast to a supertype is **not perfectly symmetric**: a path that previously threw a cast exception on unexpected content will now proceed instead. **No previously-successful path changes**, which is the property behaviour preservation actually requires. R-7 obliged stating that distinction explicitly, and this entry is where that obligation is met — pretending the change was exactly neutral would have been easier and false.

## 4 — The Removed Script Engine

Code and configuration request a JavaScript engine that JEP 372 removed from the JDK in version 15. `javax.script` stayed behind in `java.scripting`, so a request for the engine **compiles cleanly at release 17**, returns `null` at run time, and fails on the next dereference. This is the most dangerous of the three JDK removals affecting this codebase precisely because it **fails silently** — no compiler, and no textual audit for internal packages, would surface it. Restoring the capability and documenting the defect are both defensible, and the answer differs between the two places that make the request, which is why this entry is longer than its neighbours.

- **Decision, for the two dead call sites: document the latent defect and add no engine.** The two `JavaScriptEvaluatingPredicate` copies are left exactly as they are, registered in [Pre-existing Defects](pre-existing-defects.md), and the engine is deliberately **not** declared by either of their modules, so both still resolve to nothing and still never run.
- **Alternatives considered and rejected, for the dead call sites.** *Adding a standalone engine so the code would work.* Rejected for two independent reasons. It would introduce a library into the production dependency graph **solely to support code that cannot execute**, which R-1 forbids as a change without a specific compatibility reason. And it would convert **dead code into live code** — a behaviour *change* measured against the baseline, which is the one thing R-7 does not permit. It would additionally **mask** a latent defect instead of recording it. *Rewriting the two predicates to evaluate without a script engine.* Rejected as a change with no compatibility justification to unreachable code, which is a larger edit than the defect warrants and would still alter what the classes do.
- **Evidence, for the dead call sites.** Provable unreachability, read from the repository: the only bean declaration sits inside an XML comment region, its consumer and the enclosing property assignment are commented as a whole, the sibling module has no XML reference at all, and the active declaration in the same document names a different, non-JavaScript class. Re-derived across the tree, the engine is named in **exactly two** Java source occurrences, one per copy, and in no properties file or shell script.
- **Baseline property preserved, for the dead call sites.** *That they never run.* Their baseline behaviour is non-execution, and non-execution is what the migration preserves.

**Where the same platform removal produced the opposite decision, and why that is consistent rather than a compromise.** A census correction forced this half of the entry, and it has now been decided **twice** — the first time wrongly. Both decisions are recorded, because a register that shows only its final answer teaches nothing about how the wrong one was arrived at.

The census correction: `personnelSecurityBackgroundInvestigation_v11.bpmn20.xml`, a **main** resource of `acm-personnel-security-plugin`, declares seven `complete`-event `ScriptTaskListener` blocks whose `language` field is `javascript`, at `:48`, `:68`, `:88`, `:110`, `:121`, `:144` and `:155`. The migration plan's §0.6.5 states that the BPMN corpus contains *"zero script tasks and zero script-format declarations"*. That is true of script **tasks** and false of task **listeners**, which is exactly how seven live call sites went unnoticed.

- **First decision, since reversed: register the regression and supply no engine.** The reasoning was that the plan had examined the JEP 372 removal, concluded that supplying a standalone engine would introduce a library solely to support code that cannot execute, and directed that the defect be registered rather than remedied — a decision of the plan rather than a gap in it, and therefore not the implementer's to re-make. The conclusion was recorded honestly, under the heading *Baseline property NOT preserved, stated plainly*, and it was still wrong.
- **Why it was wrong.** The plan's §0.6.1 analysis is **scoped to the two dead call sites it examines**. It reasons from their unreachability — a library "solely to support code that cannot execute" — and that premise is simply false for seven listeners that did execute. A decision taken on a census that missed them cannot govern them, and treating a scoped conclusion as a general prohibition is what produced the error. The clue was in the first decision's own text: it conceded that restoring the engine *"is the correct engineering remedy and it is rejected only on authority"*. A remedy rejected only on authority, where the authority does not reach the case, is not rejected at all.
- **Final decision: restore the engine for that one module.** Four higher-precedence provisions of the same plan require it. §0.1.1 permits no observable behaviour change. §0.9.2 states that *"A failure with no matching row is a migration regression"*. R-5 forbids excluding a failure that has no baseline row. R-7 makes baseline behaviour the tie-breaker. `BackgroundInvestigationBusinessProcessIT` errored 2 of 2 against no baseline row; there was no reading of R-5 under which that could stand. Goal A2 supplies both the mechanism and the precedent: a platform module the JDK removed is reinstated as an ordinary Maven artifact, exactly as JAXB, JSR-250 and the activation framework were reinstated elsewhere in this migration.
- **Alternatives considered and rejected.** *Excluding the integration test.* Forbidden by R-5, which admits only baseline failures. *Rewriting the seven listeners to a supported expression language.* This edits a main BPMN resource and changes how a deployed workflow computes its assignee — a behaviour change in the very artifact the migration is preserving, and far larger in blast radius than a dependency declaration. *Adding `--add-opens` or any launch flag.* Not applicable; no module is being opened, and R-2 forbids production launch-configuration exceptions in any case. *Declaring the engine reactor-wide.* Rejected as needless: one module's resources request an engine, so one module declares it, at runtime scope because no source file in it references the engine.
- **Evidence.** Measured on both runtimes and both graph states. A JDK that shipped Nashorn registers one engine factory whose names include `javascript` and the listeners execute; Java 17 registers zero factories and the lookup returns `null`. With the engine absent the test reports `tests="2" errors="2" failures="0"`, with `Can't find scripting engine for 'javascript'` on the first method and a downstream `Query return 2 results instead of max 1` on the second — one fault, two red methods, because the fixture shares one `jdbc:h2:mem:activiti` database. With the engine present it reports `tests="2" errors="0" failures="0"`. Both XML captures sit beside [`smoke-evidence/bpmn-script-engine/notes.txt`](smoke-evidence/bpmn-script-engine/notes.txt), which names them and carries the reproduction command and the graph verification.
- **Baseline property preserved.** *That the seven listeners execute and set their result variables.* They executed at the base commit and they execute now. No source file changed, no `javax.script` call site changed, and no assertion in the test class was added, removed or modified.

**Why the two halves of this entry are consistent.** The same platform removal, two opposite decisions, one distinguishing fact: whether the code ran at the base commit. The two `JavaScriptEvaluatingPredicate` call sites ran on no runtime ever, so making them work would **add** behaviour the baseline never had — which R-1 has no justification for and R-7 argues against. The seven listeners ran, so failing to run them **removes** behaviour the baseline had. Preservation points in opposite directions in the two cases, and following it is what makes the entry coherent. The engine is declared by exactly one module and deliberately **not** by the two modules the dead call sites live in, so those two still resolve to nothing.

**What the restoration brought with it.** Three dependency-graph changes accompany the engine, because it will not initialise while more than one provider of the `org/objectweb/asm` package reaches that module: `net.minidev:json-smart` pinned at 2.4.10 and `net.minidev:accessors-smart` at 2.4.9 — 1.1 bundles a stripped ASM 4 in which `org.objectweb.asm.Handle` has only the four-argument constructor — and an `asm:asm` exclusion on that module's `acm-service-ecm` dependency, because `asm:asm` 3.3.1 declares `org.objectweb.asm.FieldVisitor` as an interface where ASM 4 made it a class. Each is scoped as narrowly as it can be: the two pins are reactor-wide because they resolve an order-dependent split that R-T4 forbids, and they land on the pair the migrated security stack already required; the exclusion is one module only. All four rows are in the [Dependency Change Inventory](dependency-change-inventory.md), and the residual reactor-wide ASM duplication that remains outside that module stays registered as entry 48 of [Pre-existing Defects](pre-existing-defects.md).

## 6 — Proving the Frontend Is Unchanged

The frontend declares two test frameworks and contains **zero specification files**. With no behavioural tests, what constitutes proof that the pipeline still does the same thing?

- **Decision.** Assert behaviour preservation by **byte-comparing the five build artifacts** against a baseline captured before any edit: `assets/dist/application.js`, `assets/dist/application.min.js`, `assets/dist/vendors.min.js`, `assets/dist/application.min.css`, and the cache-busted `home.html`.
- **Alternatives considered and rejected.** *Relying on the frontend's declared test tooling.* There are **zero `*.spec.js` files** in the tree despite two test frameworks being declared, so there is nothing to run — and the tooling was subsequently found to be removable dead weight, which is entry 12. *Trusting process exit codes.* Worthless here, and R-T7 says so as a rule rather than a preference: `grunt.option('force', true)` masks task failures, so a broken build exits zero, and two registered defects are masked by exactly that mechanism. *Writing new specification files to cover the pipeline.* Rejected because new tests would establish what the code does *now*, which is not the question; only a comparison against the prior state answers it.
- **Evidence that byte-identity is achievable at all** — established before it was relied on, because a pipeline with any nondeterminism would make the criterion meaningless. Three properties were confirmed by reading the build file: cache busting is **content-hash based**, operating over the distribution directory with no timestamp, banner or date injection; minification runs with identifier **mangling disabled**, removing the principal source of benign drift; and concatenation order derives from the frozen asset globs, so preserving every dependency key and the install topology — R-T6 — fixes the order.
- **Honest caveat, scoped rather than hidden — and the scope is now measured rather than reasoned.** Source-map generation is enabled and embeds file paths, so the comparison build must execute from the **same relative path**, or the map file will differ while the JavaScript bundles do not. The comparison is scoped to the five artifacts accordingly. That scoping was subsequently **measured** rather than left as an argument: a control build in a staged copy at a **different absolute path** reproduced all five artifact digests exactly, recorded at [`smoke-evidence/dependency-parity/jsog-bundle-impact.txt`](smoke-evidence/dependency-parity/jsog-bundle-impact.txt). So the five compared artifacts are demonstrably path-independent and the caveat binds the map alone, which is narrower than the caveat originally claimed for itself.
- **The measured result, stated here rather than left to the evidence tree.** This entry previously recorded only the *method* and the *achievability* of byte-identity, which let a reader assume the criterion had been met in full. It was not. **Three of the five artifacts are byte-identical and two are not:** `application.js` (`3c0aeb4d2b02dc74…`), `vendors.min.js` (`70187246b480eebb…`) and `home.html` (`43c5eb7d7735fc28…`) match exactly, while `application.min.js` differs **by 2 bytes** (`938ba106e8dc0b19…` → `c1a4cb56e4b644c4…`) and `application.min.css` differs **by 789 bytes** (`17703f8babbccbcb…` → `04228704205f51db…`). The same five digests and the same two deltas are recorded independently in two places that were produced by different means and agree: [`smoke-evidence/historical-frontend/comparison.txt`](smoke-evidence/historical-frontend/comparison.txt), from a purpose-built Node 8 / Yarn build, and the `artifacts/*.sha256` records of the baseline and migrated smoke captures, which the cross-capture comparison reports as two of its required differences.
- **Why the two that differ are the two that differ, and why that bounds the finding.** Both are minifier output, the concatenated input to one of them is provably identical (`application.js` matches, so the bytes fed to the JavaScript minifier are the same), and a control build of the same tree at a different absolute path reproduced every digest exactly. The dependency graph, the install topology, the task graph and the asset order are therefore all eliminated as causes, leaving the JavaScript engine the minifiers execute on — a twelve-year V8 gap between the two runtimes. That is a change in the *encoder*, not in the program being encoded. It is recorded as an **evidenced divergence rather than a satisfied criterion**, and the AAP basis for accepting it is §0.9.3's own scoping of this comparison plus §0.2.2's prohibition on changing a tool that is not compatibility-blocking: the two minifiers run on Node 20 and are therefore out of scope for replacement, and replacing them to chase byte-identity would itself be an unjustified change.
- **Baseline property preserved.** The bytes of everything the browser loads, for the three artifacts that match; and for the two that do not, the *program* the browser executes, since the un-minified concatenation it is derived from is byte-identical.

**The removal-over-replacement choice this criterion forced.** The Sass toolchain could not build on the target runtime, and it was **removed** rather than replaced with a modern compiler.

- **Alternatives considered and rejected.** *Substituting a modern Sass compiler.* Modern replacements were verified to install successfully, so this was declined **on evidence, not on availability**: a different compiler risks producing **different CSS bytes for zero functional gain**, which fails the very criterion this entry establishes. *Keeping the existing toolchain.* Not available — its native compiler does not build on the target runtime.
- **Evidence that removal is output-neutral.** Re-derived from the build file: the only textual mention of a Sass task is inside a **commented-out** task alias, so no Sass task is registered in any executed graph, and the stylesheet asset globs consume compiled CSS only. Removal therefore cannot change an artifact.
- **Baseline property preserved.** The stylesheet bytes. Note for the record: this is one of the change set's two R-6 escape-clause invocations, and it is recorded as such in [Pre-existing Defects](pre-existing-defects.md) rather than here; this entry explains only *why removal beat replacement*, and is not an additional invocation.

An earlier revision of this sentence said "and as an accepted deviation here", which contradicted the retraction two paragraphs above it — that retraction exists precisely because nothing in this change set has standing to accept a deviation from a frozen criterion, and leaving the phrase standing here would have let a reader take the escalation as already settled.
- **A later reviewer's re-test, added because it was asked for as execution rather than argument, and because a causal claim is only worth as much as the prediction it survives.** Three things were run.
  **One — a falsifiable prediction of the engine attribution.** If the residual is caused by engine behaviour that changed *between* the historical and target runtimes, then two runtimes on the same side of those changes must produce identical output. ## 16 — The Stream-Supplier Seam in the Two AWS Test Rewrites

Removing the retired mocking framework meant re-expressing every idiom it provided. Most had a direct Mockito equivalent. Four did not: three constructor interceptions of a JDK file-stream type in the transcribe tool's test and one in the comprehend-medical tool's test, all intercepting a type the platform loads before any application class exists.

- **Decision.** Introduce a **narrow, test-visible stream-supplier seam** — a single protected method on each service that opens the media stream — and have the test override it from an anonymous subclass. Both AWS tool modules deliberately share **one** seam pattern so the idiom is consistent across them. While the test's override field is unset the override delegates to the production implementation, so the real file-opening path still runs in the tests that do not need to substitute a stream.
- **Alternatives considered and rejected.** *Construction mocking*, the obvious like-for-like substitute for the retired framework's constructor interception. It **cannot intercept a type loaded by the bootstrap class loader**, which is exactly what the file-stream type is — so the substitution fails at the mechanism level, not on style. *Excluding the affected tests.* R-5 forbids it, and the register any exclusion must cite would have no row to offer: none of these methods fails at the base commit, so there is nothing to exclude against. *Weakening or deleting the assertions to fit a simpler substitution.* Forbidden absolutely by the preservation directive, and it is the shortcut a seam exists to avoid. *Retaining a mocking framework capable of intercepting bootstrap-loaded types.* The only one that did has no release that runs on the target runtime — its final version fails there — so there was nothing to retain.
- **Evidence.** Read at the base commit and executed on the target runtime. The interceptions sat at `:147`, `:239` and `:291` in the transcribe test and at `:128` in the comprehend-medical test, alongside two static mocks at `:338` and `:403`. In the migrated tests the statics are ordinary Mockito static mocks in try-with-resources blocks, and the stream substitution goes through the seam, whose declaring method sits at `:315` and `:287` in the two service implementations. The reason is recorded in the test source itself rather than only here. On the version question: both the incumbent and the advanced Mockito lines create ordinary mocks successfully on Java 17, but **static mocking of a class file at major version 61 fails on the older inline mock maker and succeeds on the advanced one** — which is why the advance was necessary and why the floor sits where it does. Construction interception of a bootstrap-loaded type succeeds on neither, which is what made the seam unavoidable rather than merely preferable.
- **Baseline property preserved.** **Every assertion in both classes is unmodified.** Verified by counting rather than asserted: the assertion and verification statements number **49** in the transcribe test and **15** in the comprehend-medical test, identical at the base commit and in the migrated tree. Only the mocking mechanism changed. The awkwardness is the point — this was more work than an exclusion, and it is the only option that preserves the assertions. ## 17 — Splitting the EclipseLink Family Into Two Version Axes

Four persistence artifacts shared a single version property at the base commit: the provider core, the JPA provider, its bytecode companion and the object-to-XML module. Advancing the provider is unavoidable, because the incumbent version predates the target runtime by six years. How to advance a co-versioned family whose members no longer release together is the question.

- **Decision.** Split the family. The provider core, the JPA provider and the object-to-XML module continue to share one property, advanced to the last `javax.persistence` line. The bytecode companion moves to a **new, separate version axis** of its own, and the managed entry that consumes it is re-pointed at the new property, with the constraint recorded as a comment beside it.
- **Alternatives considered and rejected.** *Advancing the single shared property for all four.* This is the one-line change and it **fails resolution outright**: there is **no release of the bytecode companion at the target version** — its 2.x line stops several patches short and then jumps to a 9.x series — so the build would not resolve at all. *Holding the whole family back at the incumbent version.* Rejected because it leaves a persistence provider six years older than the target runtime carrying the application's entire mapping layer, which is the opposite of the migration's purpose. *Moving to the provider's next major line.* Rejected on namespace grounds: that line is a **jakarta** line, which the EXCLUDE directive prohibits and which R-T1 forecloses at the artifact level as well as the import level.
- **Evidence.** Registry metadata for the bytecode companion showed the gap in its release series, and the finding was **independently corroborated** by reading the target provider's own POM, which declares a 9.x companion **by name** rather than a same-versioned one. Re-derived in the tree: the base commit has one property consumed by all four managed entries; the migrated build has two, with the companion's entry pointing at the new axis and the other three unchanged in structure.
- **Baseline property preserved.** A resolvable, deterministic build — and, downstream of that, the persistence behaviour that depends on the provider resolving at all. There is a general lesson worth recording, because it is not specific to this family: **splitting the axis is the standard remedy for a co-versioned artifact family whose members have diverged in release cadence**, and skipping it produces an unresolvable reactor rather than a subtly wrong one. ## 5 — Representing the Internal JNDI Context Factory

The Active Directory context source referred to an internal JNDI factory class as a class literal, which does not compile on Java 17 because the owning module does not export the package. Several routes restore compilation.

- **Decision.** The field holds the class **name** as a `String`, defaulted from a properties resource on the classpath that also supplies the connection-pooling flag key. The same resource is exposed as a bean, so a definition that wants to override either value wires it from one place rather than repeating a literal. A definition that sets neither property behaves exactly as it did before.
- **Alternatives considered and rejected.** *A launch-configuration argument exporting the package to the unnamed module.* Prohibited by R-T3, and it would not have worked anyway: the audit is textual, so the literal would still be present and the gate would still fail. The rule and the gate independently foreclose the same shortcut. *Keeping the value as a literal in the class, merely retyped.* Fails the textual audit for the same reason — the audit searches `src/main/java`, so the value cannot live in a Java file even as a string. *Deriving the factory name from the LDAP framework's own accessor.* Tested rather than assumed: it raises an error on Java 17, so the value has to come from configuration. *Substituting a different context factory implementation.* Rejected as an actual behaviour change to authentication, which is the one subsystem whose security outcomes the requirements name explicitly.
- **Evidence.** The decisive asymmetry is that the **runtime restriction is weaker than the compile-time one**: resolving the same class **by name** at run time succeeds, verified by execution, and JNDI matches the initial context factory by exact class name anyway — so passing the name is not an approximation of the old behaviour, it is what the old code ultimately did. Two further facts constrained the shape of the fix. No context-source bean definition exists in this repository at all; they live in an external configuration repository this repository cannot edit, so a fix that *required* new wiring would leave every existing deployment broken — hence the defaults. And both externalised values are byte-identical to the originals, which the resource file states as a standing constraint on itself.
- **Baseline property preserved.** Authentication outcomes and authorization results. The JNDI environment receives the same factory name and the same pooling key it received before, because JNDI recognises no variation, abbreviation or reassembled equivalent of either. The pooling flag was recovered differently, and the distinction is worth recording as the one place where nothing had to be externalised at all: the LDAP framework exposes that property key as a compile-time constant, which is inlined at compile time and therefore leaves no forbidden text in the class file *or* the source. Anchors in [Static Audit Output](static-audit-output.md).

### 5a — Whether to reinstate the old `Class`-typed accessor and mutator

Changing the field's type also changed the JVM descriptors of two public methods: the getter's return type and the setter's parameter type both moved from a class to a string. A caller compiled against the old descriptors would fail to link. Whether to reinstate them, or a bridge for them, on top of the new pair is a real question.

- **Decision.** Keep the `String` accessor and mutator, and decline to reinstate the old descriptors. The finding is recorded here rather than closed silently, because a declined finding that leaves no trace is indistinguishable from one that was missed.
- **Alternatives considered and rejected.** *Adding a `Class`-typed setter overload*, restoring the mutator descriptor while leaving the directed one in place. This was probed rather than dismissed: with both setters present, the JavaBeans introspector and the framework's own bean wrapper both resolve the property to the `String` write method, so the overload would not have broken configuration on this runtime. It is rejected on two grounds. It buys back **half** a binary contract that no caller in the deployed artifact uses, since the accessor half is unrestorable. And the mechanism it relies on is the introspector's tie-breaking between overloaded write methods, which is a resolution rule rather than a guarantee — accepting a subtle, environment-dependent resolution risk on the property that selects the LDAP provider, in the one subsystem whose security outcomes must be preserved, in exchange for a contract nobody is holding, is the wrong side of that trade. *A differently-named `Class`-returning accessor.* Not a binary bridge at all: a caller compiled against the original method name is not helped by a method with another name.
- **Evidence.** Three measurements, in the order they matter. The transformation mapping **directs this exact change** — the field type from `Class` to `String` with matching accessor and mutator — and the plan is the frozen contract, so a resolution contradicting it is not available here regardless of its merits. The old accessor **cannot be reinstated at all**, because the language permits no two methods differing only in return type; restoring the old getter therefore means deleting the directed one, so half the finding is unsatisfiable by construction. And **nothing in the deployed artifact calls either method**: every class file in the assembled archive was scanned, and the only ArkCase class mentioning them is the declaring class itself. The other hits are unrelated third-party types that happen to declare same-named methods of their own — one of which does declare a `Class`-typed pair, but the class under discussion does not extend it, so no interface or superclass contract requires the old shape. The property is reached from configuration, by name, as a string.
- **Baseline property preserved.** The configuration-driven behaviour that actually exists: the property is set by name from XML, which is unaffected by the descriptor change. No binary caller of the old descriptors exists to preserve.

## 10 — Whether to Advance a Library the Plan Holds Frozen: the Rule Engine

The rule engine cannot fire a rule at all on Java 17: the bytecode generator the decision-table path reaches asks in its static initialiser for reflective access to a protected platform method, the platform refuses, and the initialiser dies. All live decision tables are on that path, so object numbering and queue routing are affected in the deployed application, not merely in tests. The plan's scope section holds this library frozen, on the stated ground that with no rule files the rule-compilation path is absent — a ground execution contradicts, because compiling a spreadsheet enters exactly that path.

- **Decision.** Advance the family to the release bisection identifies as the earliest that compiles *and* fires a real decision table on Java 17, staying on the same major line so the `javax` namespace and the rule semantics are untouched. **The plan is not amended, and this register does not claim authority to amend it**: the change is recorded as a deviation, raised for **owner ratification**, with the contradiction between the plan's stated ground and the observed behaviour named explicitly.
- **Alternatives considered and rejected.** *Standing still.* Keeps the scope sentence literally intact and leaves the deployed application unable to evaluate a single decision table — the letter of one sentence at the cost of the migration's central objective. *A launch-configuration argument opening the package.* Prohibited outright by R-2, and it would put the first entry into a register delivered empty. *Changing the rule dialect configuration.* An earlier candidate that turns the suite green by altering how rules generated from every table are compiled; rejected because it is a semantic change to the subsystem under preservation, and because the version advance is now better evidenced — identical rule text is a stronger guarantee than a passing suite. *Excluding the failing tests.* R-5 forbids it, because none of them fails at the baseline: the remedy had to make them pass, not make them disappear.

Rule text is what the engine parses, so identical rule text states directly that the change cannot alter a numbering sequence or a routing decision. ## 26 — Whether to Repair the Production Launch Configuration or Register It

The documented Tomcat `setenv.sh` block — the production launch configuration — is not valid shell. Three independent defects, all present byte-identically at the base commit and none introduced by this migration:

- `${user.home}` is a Java property placeholder, not a shell expansion. A shell expands it to nothing, so every keystore, truststore and configuration-server path resolves to a path under `/`.
- A stray quotation mark inside the `JAVA_OPTS` assignment, at `-Dacm.configurationserver.propertyfile="`, terminates the assignment early and folds `-Xms1024M -Xmx1024M` into the *value* of a property rather than passing them to the JVM as heap arguments.
- The `CATALINA_OPTS` assignment opens a quotation mark that never closes on its own line and contains a bare parenthesised placeholder, `(PATH TO THE TOMCAT NATIVE LIBRARY)`.

Measured rather than read: extracting the fenced block and running `sh -n` on it exits **2** with `Syntax error: "(" unexpected` at the `CATALINA_OPTS` line; `bash -n` agrees. Tomcat sources this file with `.`, so a developer following the documentation gets a shell error and no configuration at all. The block also publishes `keyStorePassword=password` and `trustStorePassword=password` as literals, which normalises a weak shared credential in the one place a first-time deployer copies from.

The ambiguity is genuine, and R-6 is the reason: an inherited defect is documented rather than fixed, and an earlier revision of this change set took exactly that route — `docs/setup.md` said so in as many words, promising the block was reproduced verbatim "including its pre-existing formatting and quoting."

- **Decision.** Repair it, in both copies, and hold the two byte-identical inside the fence. The `${user.home}` tokens become `${HOME}`; the `JAVA_OPTS` assignment becomes a sequence of accumulating assignments followed by a single `export`, which removes the quoting hazard structurally rather than by careful escaping; the heap arguments become real JVM arguments; the native-library path becomes a required variable; and the two passwords become named environment variables. All five values that the JVM actually receives are unchanged item for item, and the three required variables are asserted with fail-closed parameter expansions that name themselves in the failure message, so a missing one stops the script with a diagnosis instead of exporting an empty string that surfaces later as a TLS failure.
- **The authority, because R-6 would otherwise forbid this.** Two provisions, and either alone is sufficient. First, R-6's own clause: an inherited defect is registered *unless it blocks a validation item*, and this one blocks the completion condition of the [JDK Access Exceptions](add-opens-exceptions.md) register, which asks a reviewer to read the `JAVA_OPTS` and `CATALINA_OPTS` assignments of the **delivered** production launch configuration and confirm that neither grants JDK-internal access. A block that no shell will source is not a delivered launch configuration, so there was nothing for that condition to be satisfied against. Second, and independently, the migration plan lists this exact block as an in-scope **update** rather than as frozen reference material: `README.md` at the launch-configuration block, and `docs/setup.md` as its duplicate. A block named for update and then left byte-identical is an unmet requirement, not restraint. **This is therefore not a third invocation of R-6's escape clause** — the count stays at two, both on the frontend side — because the clause is not what authorises it; the plan's own scope statement is, and the escape clause merely fails to forbid it.
- **Alternatives considered and rejected.** *Registering all three defects and changing nothing*, which is what the previous revision did. Rejected on the authority above, and on a plainer ground: the change set is required to deliver an updated production launch configuration for a new runtime, and shipping one that cannot be sourced would make every downstream statement about it — including this folder's central claim that it carries no module-access argument — an assertion about text rather than about a configuration. *Fixing only the syntax and keeping the literal passwords*, which is the minimal edit. Rejected because the reviewer's finding is one finding about one block, and leaving a shared literal credential in the file a first-time deployer copies from would preserve the more consequential half. *Replacing the passwords with a comment telling the reader to substitute a value.* Rejected because it fails open: an unsubstituted comment leaves an empty password and Tomcat starts anyway. A fail-closed expansion cannot be ignored by accident. *Deleting the two TLS password properties entirely.* Rejected as a behaviour change — the deployment needs them, and R-7 settles it: the baseline passes both, so the migrated configuration passes both.
- **Evidence.** The corrected block was extracted from both files with a Markdown fence parser and compared: identical, sha256 `90d6ad1da6909722cfd91ce0…`, 30 lines. `sh -n`, `bash -n` and `dash -n` all exit zero on it, where the previous block exited 2. Sourced with the three variables set, it produces exactly the intended `JAVA_OPTS` — IPv4 stack preference, `GMT` timezone, the keystore and truststore paths and passwords, the LDAP Spring profile, the configuration-server property file, and `-Xms1024M -Xmx1024M` as heap arguments — plus `NODE_ENV=development`, `CATALINA_OPTS` carrying only the native-library path, and `CATALINA_PID` under `$CATALINA_HOME/temp`. Sourced with nothing set, it stops at the first missing variable and prints `ARKCASE_KEYSTORE_PASSWORD: set the ArkCase keystore password from your secret manager`. Both files contain **zero** occurrences of `keyStorePassword=password` or `trustStorePassword=password`, and zero module-access arguments.
- **Baseline property preserved.** Every JVM argument the launch configuration passes, item for item, and therefore the deployed application's TLS trust, timezone, active Spring profile, configuration-server location and heap sizing. What changed is only how the file computes those values and whether a shell can read it. One consequence is disclosed rather than left to be discovered: the JVM still receives both passwords as system properties, so they remain visible in the host's process table. That is how ArkCase reads them, it is true of the baseline as well, and it is stated in both copies rather than quietly improved.

The whitespace *is* the evidence: it is raw HTTP status lines whose reason phrase is empty, carriage-return-terminated response headers, and — in the archived unit-test reports — the test's own captured standard output. Stripping it would edit produced and runner-emitted bytes to satisfy a lint that was never asserted over this tree, and the surrounding archive is built on the opposite commitment, that every element the runner wrote is byte-identical to what it wrote.
- **Alternatives considered and rejected.** *Stripping trailing whitespace across the evidence tree.* Rejected: it rewrites captured bytes, and it would silently break the archived reports' structural verification, which checks each installed file against the exact number of angle brackets its one disclosed transformation removed. *Stripping it only in the flow captures and leaving the reports alone.* Rejected as worse than either consistent choice — it would make two halves of one tree obey different rules, and the flow captures are the half where the whitespace is most load-bearing, since an empty HTTP reason phrase is part of the observed response line. *Adding a repository attribute to suppress the warning.* Rejected: it changes what the tool reports without changing what is in the files, which hides the question rather than answering it, and it would apply to files well outside this deliverable.
- **Evidence.** The warnings were classified by path rather than counted: **all** of them fall in produced or runner-emitted files — the comparison, five flow captures, two flow status records, two notes records, two startup regions and 17 archived reports — and restricting the same sweep to authored file kinds returns **zero**, as does restricting it to project files and to non-archive XML. In the archived reports the flagged lines were located precisely: all five in one sampled report sit **inside** `<system-out>`, and the report the runner emitted minutes earlier carries the same five, so the whitespace is the runner's, not an edit. The property is also **pre-existing in the committed tree**: the pre-migration half already carries 874 trailing-whitespace lines and 62 carriage-return-terminated lines in one flow capture alone, plus 15 and 4 in two startup regions. One methodological note belongs with that measurement, because getting it wrong is easy: the pattern `\r` in a POSIX extended regular expression matches a literal `r`, so an early count of carriage returns was wrong and was redone with a Perl-compatible pattern before any of these figures were relied on.
- **Baseline property preserved.** Byte-faithfulness of captured evidence, which is the property the whole `smoke-evidence` tree is organised around. Nothing about the delivered software depends on this decision; what depends on it is whether a reader can trust that a captured line is what the container or the test runner actually emitted.

## 31 — Leaving the Content-Management Integration Enabled, and Publishing the Fixture Failure It Causes

Four of the eight smoke flows are recorded as **not exercised**, and all four trace to one upstream failure: object creation answers HTTP `400`, so no fixture object exists for the document round trip, the broker transit, the workflow start or the queue transition to act on. The cause is measured, not guessed — the creation transaction is rolled back by a Camel route that asks the content-management service for a folder path it cannot answer for, because that service is not provisioned on either capture host. The ambiguity is real and it is tempting in exactly one direction: the configuration switch that would make four flows substantive is one line away.

- **Decision.** Leave the integration enabled and publish the failing creation as it fell. Configuration parity between the two captures is worth more to this comparison than four greener rows, and it is worth more for a specific reason rather than on principle: the two captures already differ in the one variable the deliverable exists to isolate, which is the runtime. Adding a second difference — the configuration — would give every remaining row two candidate causes instead of one, and no amount of later prose recovers that.
- **Alternatives considered and rejected.** *Disabling the record-folder step, or the integration as a whole, on the migrated side.* This is the one-line change and it would have converted four flows from *not exercised* to observed. Rejected because it makes the migrated capture differ from the pre-migration one in configuration as well as runtime, and because the flows it would light up are precisely the ones whose value depends on both sides having been configured identically. *Provisioning the content-management service.* Rejected as not available rather than not wanted: the project's own prerequisites call for 16 GB of memory and the capture host has under 4 GB, with a servlet container, a database, a directory server, a broker and a search engine already resident. *Substituting a stub for the service so the folder lookup succeeds.* Rejected because the flow would then observe the stub. A round trip against something written to answer is not evidence about the application, and it would be indistinguishable in the capture from a real one. *Re-running until the creation succeeds.* Rejected, and this is the alternative that most deserved to be named: creation was measured as **flaky across four runs at the same commit**, answering `200`, `200`, `500` and `400`. Re-running until it answered `200` would have been selecting a favourable run rather than capturing one, which is the same act as disabling the integration with more steps.
- **Evidence.** The rollback is observed in the container's own log: the route `seda://alfresco-getOrCreateFolderQueue` raises `CamelCmisObjectNotFoundException: Can not find object by path :/Sites/acm/documentLibrary/Complaints/…`, and the creation transaction is marked rollback-only as a result. The two switches that put that route in the path are `alfresco_rma_integration_enabled` and `alfresco_rma_create_record_folder_on_complaint_create`, both `true`, and both left `true`. **Configuration parity is confirmed by outcome, not asserted**: creation answers `400` on *both* sides, the flow's verdict is identical on both sides, and both reference-stack records report the content-management service unreachable. The cascade is enumerated rather than summarised — the completeness record names, separately, that the round trip had no fixture to attach to, that the broker had no object number to follow, that no workflow could be started and that no case file could be discovered, and it names creation as the flow that must produce the fixture first. The second observed failure shape, a concurrent-modification error raised from the entity's own pre-persist callback, is registered as a pre-existing defect rather than repaired.
- **Baseline property preserved.** Configuration identity across the two captures, and the honesty of the cascade. What is *not* preserved, and is stated here rather than left to be inferred, is coverage: object numbering, the document round trip, broker transit, process instantiation and queue routing remain **unobserved on both sides**, so this deliverable does not establish them. That is a real gap in the acceptance evidence, it is bounded by a service the capture host cannot run, and it is recorded as a gap instead of being closed with a switch.

## 32 — A Mirror Accounting Measured Before The Files It Counts Were In Place

Each capture directory carries a `summary.txt` whose MIRROR block enumerates every file a recursive comparison finds on one side only, and the producer's contract for that block is explicit in the producer's own words: it is *the authoritative copy of this accounting*, which *both capture directories carry identically*. In the committed tree the two copies were not identical and neither was correct. The migrated copy reported **6 / 1 / 6** one-sided entries; the pre-migration copy reported the right counts, **1 / 3 / 6**, with the wrong membership — it named a file that is now carried on both sides and omitted one that genuinely exists on a single side. The ambiguity is what to do about a producer-written accounting that is wrong inside a tree whose captures are settled and partly digest-bound.

- **Decision.** Correct both published copies to the measured truth, make the MIRROR block byte-identical on the two sides as the contract requires, and leave the producer's measurement code untouched — disclosing the ordering defect in a comment at its call site instead. A second, separate claim inside the same accounting was corrected the same way: a hardcoded sentence asserting that the process-engine startup region *is 60 lines on each* side, which was never a measurement and had gone stale.
- **Alternatives considered and rejected.** *Re-running the full producer so it regenerates both summaries.* Rejected, and it is the alternative that looks most principled: a full run re-takes the startup capture and all eight flows, so it would perturb a comparison whose required differences are settled at fifteen and each accounted for by an entry on this page, and it would rewrite captures that the archived-report manifests bind by digest. The cost is paid in the very evidence the accounting exists to describe. *Changing `run_summary_oneside` so a full run measures correctly.* Rejected because the code is not what is wrong, and that was established by measurement rather than assumed — see below. Editing correct arithmetic to compensate for a wrong call site would leave two defects where there is one. *Leaving the discrepancy and explaining it in prose.* Rejected by the block's own closing sentence, which makes any one-sided entry not named there a finding; prose cannot rescue an enumeration that reads as an assertion.
- **Evidence.** The root cause is the call ordering: `write_summary` runs before `publish_capture`, so it measures the **staging** tree, and the staging tree does not yet hold the paths the authored tier names because publication carries those forward afterwards. That makes the sets wrong in both directions — an authored companion the peer holds is reported as peer-only, and an authored companion only this side holds is dropped. `validate_manifest` and the closing index have the identical property and are re-run post-publish by the index-only pass; `summary.txt` is not re-emitted by that pass, which is why it alone stayed stale. The decisive measurement: extracting `run_summary_oneside` and `run_summary_oneside_count` and invoking them directly against the two **published** directories emits exactly **1 / 3 / 6** with exactly the membership now committed — the property-allowlist register on the pre-migration side; the artifact adjudication, the comparison and the process-engine annotation on the migrated side; six archived reports inside `surefire/`. **The committed text is therefore producer-reproducible**, which is the property that was at stake. Two independent corroborations: the closing index, which *was* written post-publish, already reported the same sets from the opposite side as `9 / 0 / 1`, so before this correction two published files in one directory contradicted each other while one of them claimed to be the authoritative copy of the other; and the pre-migration manifest independently reports the authored tier as **6 named, 4 present, 2 absent**, naming the same two files, which is what supports the corrected wording that two of the six authored companions are one-sided. Timestamps show the drift plainly — the migrated summary was written 25 minutes before the pre-migration closing index existed. The stale line-count sentence was corrected against a re-measurement: the region is **60** lines on the pre-migration side and **64** on the migrated side, and the annotation beside it already traced the four additional lines as two configuration-watcher notices plus the two events they raise, with every other line matching logger for logger, 24 from the deployment service and 10 from the classpath deployer on both sides. Both manifests still report `COMPLETE-AND-EXACT`, and the manifest binds no digest to `summary.txt`, so neither correction can invalidate it.
- **Baseline property preserved.** The mirror accounting's own promise — that the enumeration is measured rather than remembered, so an unnamed one-sided file is a real finding. What is **not** fixed, and is stated here rather than left to be inferred: a future full run will publish the stale accounting again, because the post-publish pass re-emits the manifest and the closing index but not `summary.txt`. A human re-running the capture must re-measure the MIRROR block against the published pair afterwards, or extend the post-publish pass to re-emit that file; the call-site comment records both the mechanism and the verification that the arithmetic is sound.

## 33 — Broker Counters That Differ Because The Broker Is Shared, Not Because Behaviour Changed

This resolution exists because making one flow's evidence honest created a difference where there had been an apparent match, and the apparent match had been the more misleading of the two.

Flow 5's captured transcript carried a complete, successful read of the message broker's destination — the management surface answering, the destination named, and the whole counter set. Its status file recorded **every** broker row as `not-probed`. Both halves of one flow's evidence, disagreeing about whether an observation had happened. And because both captures carried the identical false claim, the row-for-row comparison read `MATCH on every recorded row`: two identical false statements comparing equal, which is the same failure mode this deliverable warns about for two empty files.

Correcting the status rows from the bodies the transcript already held moved the comparison from that clean match to a difference on six rows. Measured, from the two captured management responses:

| Broker counter | Pre-migration | Migrated |
| --- | --- | --- |
| `EnqueueCount` | 2 | 12 |
| `DequeueCount` | 2 | 7 |
| `DispatchCount` | 3 | 13 |
| `InFlightCount` | 0 | 5 |
| `ConsumerCount` | 9 | 8 |
| `QueueSize` | 0 | 5 |

- **Decision.** Let the six rows differ, keep them **verbatim**, and account for them here. They are cumulative counters for the life of the broker instance, not figures scoped to a run, and the two captures shared a broker with a neighbouring instance — so the divergence describes the host's history and not either runtime. The comparison now classifies differing rows and names these six as ambient, and it excuses a row **only** by naming it, so the list cannot quietly grow to cover a regression.
- **Alternatives considered and rejected.** *Normalising the counters away, as volatile values.* The most tempting option, and the one that would have restored the clean match. Rejected: the answer to a difference that needs explaining is to explain it, not to delete it. A normaliser that erased these rows would also erase the only broker-side observation the capture holds. *Leaving the `not-probed` rows in place.* Rejected as simply false — a captured response body is stronger evidence than a token asserting no response was captured. *Rewriting the tokens automatically when the contradiction is detected.* Rejected because the run cannot know which run produced the surviving transcript section, and converting a contradiction into a confident assertion is worse than reporting it; the producer marks the capture incomplete instead. *Treating the difference as a regression.* Rejected on the measurement: a lifetime total on a shared broker cannot attribute traffic to either capture.
- **Evidence.** The six values above, read from each side's own captured management response. Alongside them the flow now records **same-run deltas** — the destination read once to open the delivery window and once to close it — because a delta over a window the flow defines *is* attributable where a lifetime total never is. Those delta rows are deliberately **not** on the ambient list: a delta that differed would be a finding. In these two captures they read `not-derivable-no-window-opened-in-this-capture`, because both were taken before the second reading existed, and that is recorded rather than left to be discovered.
- **Baseline property preserved.** Message transit, which these counters do not establish in either capture and are not offered as establishing. The flow's verdict is identical on both sides — `OBSERVED-EVENT-TRANSITED-AND-INDEXED` in the committed capture, where the flow executed on both sides and all 38 of its projected records agree — so the three counters are the whole of the difference; correcting the broker rows changed what the capture *says it observed*, not what it observed.
- **What a human must decide.** Nothing about the runtime. If a future capture needs broker counters to be comparable rather than merely honest, it must run against a broker private to the capture — which is a provisioning decision, and the same one entry 88 of the defects register raises for the directory.

## How to Use This Register

- **Adding an entry.** State the decision, the alternatives rejected with their reasons, the evidence, and the baseline property preserved. Take the next unused number. An entry with no rejected alternatives is not a resolution — it is a note, and it fails this page's completion condition.
- **Revisiting an entry.** The evidence is the load-bearing part. If the measurement is wrong, the resolution may be wrong; if it is right, a later preference does not override it.
- **Interpreting a choice that looks untidy.** Several of these deliberately chose the less elegant option — the larger jar, the 40-character version specifier, the extra exclusion, the hand-written test seam. Elegance was not the criterion, and tidying one of them would be a behaviour change with no compatibility justification.
- **When a remedy exists and was not applied.** Entries 4, 13 and 15 are of this kind for the paths they deliberately leave alone, and each records the remedy in enough detail that nobody has to rediscover it. That is the intended handover: the decision is documented as open, not closed.
- **When a change the plan does not authorise was nevertheless made.** Entries 10, 11 and 6a are of this kind. Neither amends the plan and neither claims the authority to: each states the constraint chain that leaves no other remedy, supplies the measurement showing the change is behaviourally inert, and is raised for owner ratification. If ratification is declined, the consequence recorded in the entry is what follows — not a quiet reversal.
