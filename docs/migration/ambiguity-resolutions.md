# Ambiguity Resolutions

This page records every decision in the runtime migration onto Java 17 and Node 20 LTS where the requirements admitted more than one defensible answer, and where **the platform's observed behaviour at the base commit on JDK 8 was used as the tie-breaker**. It exists because a rule demands it as a deliverable, not because any feature description mentions it.

Each entry states what was chosen, **what was rejected and why**, the evidence that settled it, and the baseline property the choice protects. The rejected options are the part that makes this page worth reading: a register that recorded only the chosen option would be a changelog. The recurring pattern is that baseline behaviour selected the **less obvious** option — the larger jar, the uglier version specifier, the extra exclusion, the more laborious test rewrite. Without the rejected alternative beside it, a later reader cannot tell that a choice was made at all.

## Rules Provenance

Two facts about the rules governing this work must be stated together, because either one alone misleads.

- **There is no on-disk user rules document for this project.** The project's rules facility reports, verbatim, *"No user rules provided."*
- **Rules are nonetheless present and binding.** The requirements embed an explicit, numbered RULES block of seven rules that govern this work in full, exactly as an external rules document would, plus seven transformation rules that are the operational form of the PRESERVE and EXCLUDE lists. Fourteen constraints apply.

The identifiers `R-1` through `R-7` and `R-T1` through `R-T7`, and the short labels attached to them throughout this folder, are the **migration plan's own navigational convention** — not quoted titles. They exist so that a decision can be traced to the constraint that produced it. No rule has been invented and none has been softened: enterprise-standard best practice is applied *on top of* the fourteen, never as a substitute for them, and where best practice would have permitted something a rule forbids, the rule won.

That pairing is itself an ambiguity that had to be resolved, so it is recorded on the same terms as everything else on this page.

- **Decision.** Disclose both facts, together, wherever the provenance of the rules is stated.
- **Alternatives considered and rejected.** *Report only "no user rules provided".* Rejected because it implies enterprise best practice is the sole standard here, which is false — fourteen specific constraints apply, and several of this page's entries exist only because one of them demanded it. *Report only the embedded rules block.* Rejected because it misstates where the rules came from, and would let a reader assume there is an authoritative on-disk document to consult when there is not.
- **Evidence.** The rules facility was queried and returned that exact sentence. The requirements were then read for their own RULES block, which is present, numbered, and prescriptive.
- **Baseline property preserved.** None — this is a provenance-disclosure resolution, not a behavioural one. It is recorded here because an undisclosed provenance gap is indistinguishable from an overlooked one.

## What R-7 Requires

One rule is the reason this page exists:

> **R-7 — Baseline behaviour is the tie-breaker.** The application's observed behaviour at the base commit on JDK 8 is the tie-breaker for any ambiguity, and each resolution must be documented.

*[Editorial note: the rule as written names the older runtime in the form "Java" followed by the major version. It is rendered here as "JDK 8" to comply with this folder's wording policy, recorded as the final entry on this page. The substitution changes no meaning, and it is disclosed rather than applied silently, because quietly altering a quoted rule is worse than the wording problem it solves.]*

R-7's completion condition for this page is that every baseline-as-tie-breaker decision is recorded **with its rejected alternatives**. An entry that names only the option taken fails that condition.

Eight further rules bear on individual entries and are cited where they do:

- **R-T1 — Namespace invariance.** *"Every `javax.*` import remains `javax.*`. JEP 320 removals are compensated by adding javax-namespace artifacts, never by rewriting source to `jakarta.*`. Artifact eligibility is decided by inspecting the jar's package prefixes, not its groupId or artifactId."* Entries 2 and 17 turn on it, and both apply it at the **artifact** level rather than only at the import level, which is stricter than a literal reading.
- **R-T5 — Lockfile-governed frontend graph.** *"The frontend dependency graph is fully reproducible from a committed `package-lock.json`, with every Git dependency pinned to an exact commit SHA. No dependency may resolve differently between two checkouts."* Entry 3.
- **R-T6 — Asset-layout contract immutability.** *"The literal `node_modules/...` paths in `config/env/all.js`, the `Gruntfile.js` task graph, and the five output artifact names are contract. Dependency keys cannot be renamed and the install topology cannot be flattened or restructured."* Entries 3 and 6.
- **R-T7 — Evidence over exit codes.** *"Validation asserts on produced artifacts and captured output, never on process exit status alone. This is mandatory rather than stylistic because `Gruntfile.js` sets `grunt.option('force', true)`, which masks task failures and lets a broken build exit zero."* Entry 6.
- **R-T3 — Fix the library, do not open the module.** Where a dependency fails under strong encapsulation, the remedy is to upgrade or replace that dependency. Adding a module-access JVM argument — one that opens or exports an otherwise-encapsulated JDK package to the unnamed module — to production launch configuration is prohibited, and JDK-internal call sites are rewritten to supported APIs instead. Entries 5, 7, 10 and 11.
- **R-1 — Justified dependency changes.** *"Every dependency version change must have a specific Java 17 or Node 20 compatibility reason… A change without a reason is out of scope."* Entries 4, 12, 17 and 19 — and note that R-1 binds in both directions: it forbids an unjustified bump as firmly as it forbids a missing fix.
- **R-5 — No disabling of failing tests.** *"Failing tests must not be disabled, and exclusions are limited to failures already present at baseline."* Entries 10, 13 and 16.
- **R-6 — Document discovered bugs, do not fix them.** Its escape clause is invoked exactly **twice** in the whole change set — the frontend `profiles.js` creation and the Sass toolchain removal — and **neither invocation is in this folder**. Entry 6's discussion of the Sass toolchain explains why *removal* was chosen over *replacement*; it is not an additional invocation.

## How Each Resolution Is Recorded

Every entry has the same four parts, in the same order. The consistency is what makes the page auditable rather than merely readable.

- **Decision.** What was chosen, in one or two sentences.
- **Alternatives considered and rejected.** Each option that lost, with the specific reason it lost. This part is mandatory and is never empty.
- **Evidence.** How the decision was established — by executing on the target runtime, by inspecting a jar's contents, or by reading the repository at the base commit. The artefact or the anchor is named.
- **Baseline property preserved.** The specific observable behaviour at the JDK 8 base commit that the decision protects. Where an entry is a documentation decision rather than a behavioural one, it says so plainly instead of manufacturing a claim.

Two conventions govern how entries are identified, both settled as decisions in their own right in entry 18.

- **The entry number is a stable identifier, not a position.** Sibling registers cite entries of this page by number, so numbers are never reused and never reassigned; a new entry takes the next unused number regardless of where it reads best.
- **The sections below run in the order the requirements specify**, which for the first ten is the order of the mandatory resolution set. Numeric order and reading order therefore differ, and the summary table below is the map between them.

## 1 — The Activation Framework Artifact

JEP 320 removed the JavaBeans Activation Framework from the JDK, so it has to be reinstated as an ordinary dependency. Two artifacts satisfy the same `javax.activation` API, and their coordinates give no hint that the choice matters.

- **Decision.** Reinstate the **reference implementation**, `com.sun.activation:javax.activation`, at compile scope in the aggregator's global dependency block. The older activation jar that arrives transitively is excluded at both entries that pull it, so exactly one provider of the package reaches any module.
- **Alternatives considered and rejected.** *The API-only jar.* This is the tidier and more obvious dependency — smaller, and "API only" reads like the disciplined choice. It was rejected because reading both jars showed they are not equivalent: the API-only artifact **lacks** `META-INF/mimetypes.default` and `META-INF/mailcap.default`, while the reference implementation is a strict superset shipping both. *Accepting the transitively-supplied older jar instead of declaring one.* Rejected because its `META-INF/mimetypes.default` differs from the reference implementation's, so with both on the classpath MIME resolution would depend on resolution order — and a classpath whose behaviour depends on ordering is not a preserved baseline.
- **Evidence.** Jar-content inspection, plus a consumer census re-derived from the tree: `javax.activation` appears in **8 occurrences across 6 files**, and **five of those six** import `MimetypesFileTypeMap`, which reads exactly those two resources. The sixth uses `DataHandler` only. The exclusions carry their reasoning inline at the two managed entries that introduce the competing jar.
- **Baseline property preserved.** MIME-type resolution. The API-only jar would have compiled cleanly, deployed cleanly, and then **silently resolved MIME types differently** from the JDK 8 baseline, where the framework was supplied by the platform. This is the entry that best illustrates why R-7 exists: both options satisfy the compiler, neither produces an error, and nothing short of comparing observed behaviour would have caught it. **The artifact choice is behavioural, not cosmetic.**

## 3 — Pinning the Frontend Git Dependencies

The manifest expresses its Git dependencies in a form the previous package manager accepted and the current one cannot parse at all. Some rewrite is unavoidable; which rewrite is the question.

- **Decision.** Move all **76** Git dependency specifications from `owner/repo#<semver-range>` to an exact 40-character commit, mined from the outgoing `yarn.lock` before that file was deleted, and commit the resulting lockfile. Every dependency **key** is preserved unchanged.
- **Alternatives considered and rejected.** *Leaving the specifications as they are.* The current package manager cannot parse the range form at all; resolution fails with a missing-Git-reference error, so this is less an option than a non-starter. *Rewriting to the idiomatic semver-qualified Git form.* This is the readable, conventional answer, and it is unsafe in two independent ways: an open range **re-resolves to whatever tag exists today**, so two checkouts of the same commit can install different library versions — reintroducing the exact mechanism by which a "no behaviour change" refactor silently changes behaviour — and at least one repository fails the resolution outright with a package-metadata cache error under that form. *Pinning to tags.* Also more readable, and rejected for the first of those reasons: a tag is mutable, and a version range is not a pin.
- **Evidence.** Re-derived from both revisions of the manifest. At the base commit, 76 of 108 dependencies were Git specifications and **none** named a commit. In the migrated manifest, 76 of 100 are Git specifications and **all 76 name an exact commit**, with zero remaining `#`-ranges. They appear in two forms, which is worth stating because a reader counting one form will come up short: **58** use the short `owner/repo#<commit>` form and **18** use a codeload tarball URL carrying the same commit in its path — the one form that records an HTTPS resolved URL, adopted where it was needed to keep restore working without credentials. Both are exact-commit pins. The outgoing lockfile recorded a commit for 76 of 77 entries across 75 distinct packages with **no package carrying conflicting commits**, so the mapping was unambiguous; the single entry without one was a transitively-resolved registry version. The committed lockfile is at version 3, and the asset resolver's literal paths name **65 distinct installed packages**, all 65 present after the change.
- **Baseline property preserved.** The exact library versions the previous package manager resolved, and with them the bytes of every concatenated bundle — which is what R-T5 exists to guarantee. One ordering constraint fell out of this and is recorded because it is irreversible: the outgoing lockfile is the **sole authoritative source** of those commits, so it had to be mined **before** it was deleted. Reversing those two steps loses the information permanently.

**The near-miss that required understanding rather than tidying.** One library appears twice. `bootbox` is a direct Git dependency resolving to **4.4.0** and owning the top-level installation slot, while a transitive registry range under a dependent package resolves to **5.5.1** — a later major version — in its own nested slot. The asset resolver names the top-level path literally, and the line that names it carries an in-file comment warning that the newer minified build is broken. Deduplicating or hoisting would have looked like an improvement and would have swapped a major version underneath a path that is contract: **R-T6 forbids it and R-7 confirms it.** Understanding the duplication was necessary in order *not* to remove it.

## 2 — The Duplicated JPA API

The reactor pins the JPA API explicitly and independently of the provider version. Advancing the provider to its last `javax.persistence` line introduces a second JPA API artifact transitively — one whose coordinates carry the forbidden namespace. Reading the coordinates suggests a namespace violation; reading the jars tells a different story. This is the change set's most instructive four-way decision, so all four options are recorded.

- **Context established by jar inspection.** The differently-named artifact contains **209 classes under `javax/` and zero under `jakarta/`** — it is the javax API republished under a different artifactId — and its class set is **identical** to the javax-named `2.2.1` artifact, symmetric difference zero.
- **Decision — Option D of four: advance the javax-named pin to `2.2.1` and, in the same change, exclude the differently-named twin.** The result is exactly one API jar on the classpath, javax-named *and* javax-contented, at the API level the provider implements. **The selected option requires both halves**: a one-line property change advancing the pin, **and** an exclusion added at the managed provider entry that introduces the twin — which conveniently already carried an exclusions block, so the structure existed. Either half alone fails, and the failures are the two rejected options below: the advance without the exclusion produces Option C, and the exclusion without the advance produces Option A. Both halves are present in the migrated build.
- **Alternatives considered and rejected — the other three options, each with the specific reason it lost.**
    - *Option A — keep the API at `2.1.0` and exclude the twin.* **REJECTED:** the migrated provider implements the JPA 2.2 API, so holding the pin at the older level starves it of API classes it expects.
    - *Option B — drop the explicit pin and accept the transitive.* **REJECTED:** this leaves a jar whose coordinates carry the forbidden namespace in the resolved graph, which the EXCLUDE directive prohibits **regardless of the jar's internal package names**. R-T1 directs that artifact eligibility be decided by inspecting package prefixes, and that cuts both ways: contents do not launder coordinates.
    - *Option C — keep both.* **REJECTED:** two content-identical API jars means duplicate `javax/persistence/*` class entries resolved by nearest-wins, which is order-sensitive and therefore not reproducible.
- **Evidence.** Registry metadata and jar-content inspection. The javax-named `2.2.1` artifact holds **213 classes, 209 under `javax/`, zero under `jakarta/`**, and adds exactly **two annotation-container types** over `2.1.0` — **both absent from the source**.
- **Baseline property preserved.** The effective DDL of every persistence mapping. Re-derived from the tree: **1,612** main-source `javax.persistence` occurrences — **1,688** including test source, of which **69** are `javax.persistence.criteria` — all continue to resolve identically, so there is **zero source impact and zero DDL impact**. The migration plan quotes 1,610 for the main-source figure; the verified count is 1,612, and the difference is reported rather than reconciled away, because this register's job is to state what was measured.

## 7 — Widening the Base64 Decoder Cast

A vendor Base64 decoder-stream type had to go, because the package it lives in is one the JDK-internal usage audit forbids. The narrowest possible replacement and the natural supertype were both available.

- **Decision.** Delete the vendor import and widen the cast to `java.io.InputStream` — the supertype the vendor decoder already extends, and precisely the type the consumer on the very next line already accepts.
- **Alternatives considered and rejected.** *Retaining the vendor type.* Fails the audit gate, which is a literal text search rather than a semantic one, so the reference would still be found. *Introducing an adapter class to wrap the decoder.* Unnecessary, and therefore wrong in a behaviour-preserving refactor: the supported abstraction is already the type the consumer wants, so an adapter would add a class, a construction site and a failure mode in exchange for nothing. *Accommodating the internal reference with a module-access JVM argument.* Prohibited by R-T3 — and it could not have satisfied the gate anyway, because a textual search does not care how the JVM was launched. The rule and the gate independently foreclose the same shortcut.
- **Evidence.** Read at the base commit. The import sat at `:33`; its sole use was at `:258`, `BASE64DecoderStream b64ds = (BASE64DecoderStream) p.getContent();`, immediately followed at `:259` by `String imageBase64 = BaseEncoding.base64().encode(ByteStreams.toByteArray(b64ds));` — a byte-stream reader that already takes the supertype. In the migrated file the site sits one line earlier, at `:257`, because the deleted import shifted everything below it. The audit itself moved from **7 hits across 5 files** at the base commit to **0** in the migrated tree.
- **Baseline property preserved — with an asymmetry disclosed rather than buried.** Widening a cast to a supertype is **not perfectly symmetric**: a path that previously threw a cast exception on unexpected content will now proceed instead. **No previously-successful path changes**, which is the property behaviour preservation actually requires. R-7 obliged stating that distinction explicitly, and this entry is where that obligation is met — pretending the change was exactly neutral would have been easier and false.

## 4 — The Removed Script Engine

Code and configuration request a JavaScript engine that JEP 372 removed from the JDK in version 15. `javax.script` stayed behind in `java.scripting`, so a request for the engine **compiles cleanly at release 17**, returns `null` at run time, and fails on the next dereference. This is the most dangerous of the three JDK removals affecting this codebase precisely because it **fails silently** — no compiler, and no textual audit for internal packages, would surface it. Restoring the capability and documenting the defect are both defensible, and the answer differs between the two places that make the request, which is why this entry is longer than its neighbours.

- **Decision, for the two dead call sites: document the latent defect and add no engine.** The two `JavaScriptEvaluatingPredicate` copies are left exactly as they are, registered in [Pre-existing Defects](pre-existing-defects.md), and the engine is deliberately **not** declared by either of their modules, so both still resolve to nothing and still never run.
- **Alternatives considered and rejected, for the dead call sites.** *Adding a standalone engine so the code would work.* Rejected for two independent reasons. It would introduce a library into the production dependency graph **solely to support code that cannot execute**, which R-1 forbids as a change without a specific compatibility reason. And it would convert **dead code into live code** — a behaviour *change* measured against the baseline, which is the one thing R-7 does not permit. It would additionally **mask** a latent defect instead of recording it. *Rewriting the two predicates to evaluate without a script engine.* Rejected as a change with no compatibility justification to unreachable code, which is a larger edit than the defect warrants and would still alter what the classes do.
- **Evidence, for the dead call sites.** Provable unreachability, read from the repository: the only bean declaration sits inside an XML comment region, its consumer and the enclosing property assignment are commented as a whole, the sibling module has no XML reference at all, and the active declaration in the same document names a different, non-JavaScript class. Re-derived across the tree, the engine is named in **exactly two** Java source occurrences, one per copy, and in no properties file or shell script.
- **Baseline property preserved, for the dead call sites.** *That they never run.* Their baseline behaviour is non-execution, and non-execution is what the migration preserves.

**Where the same platform removal produced the opposite decision, and why that is consistent rather than a compromise.** A census correction forced this half of the entry, and the correction is recorded rather than filed away because two other entries rest on similar censuses. The first pass searched the BPMN process definitions for script-task elements and script-format attributes; both counts are genuinely **zero**, and the conclusion drawn from them — that the process corpus never asks for a script engine — was wrong. The workflow engine also reaches the engine through a **task listener**: one **main** resource of `acm-personnel-security-plugin` declares **seven** `complete`-event script task listeners, each with a `language` field of `javascript` and a `script` field, and each requests the engine exactly as a script task would. The lesson generalises: **a pattern-based census over configuration is only as good as its knowledge of every element that can reach the capability.**

- **Decision, for those listeners: restore the engine.** `org.openjdk.nashorn:nashorn-core` is declared at runtime scope by `acm-personnel-security-plugin` alone — the one module whose resources request it — with its version managed centrally. This is the **same pattern the migration already applies to JEP 320's removed modules**: the platform withdrew a capability the application uses, so it is supplied as an ordinary dependency instead.
- **Alternatives considered and rejected, for the listeners.** *Leaving the live path broken.* Rejected outright: the listeners executed at the baseline and stopped executing on the target runtime, which is a regression rather than a latent defect, and R-7 makes baseline behaviour the tie-breaker. *Rewriting the seven listeners as engine-native delegates or expression-language expressions.* It removes a dependency, but it edits a **main** process definition in the one subsystem whose behaviour this migration promises is unchanged, and each rewritten listener would need a baseline-equivalence argument that no available evidence could supply. *Declaring the engine reactor-wide.* Rejected because it is not needed reactor-wide; a narrow declaration in a module no other POM references leaves the rest of the deployed dependency graph untouched. *Substituting a different JavaScript engine.* Rejected because the standalone build is the platform's own engine extracted, so its semantics are the baseline's semantics — any other engine would be a semantic change on a live path.
- **Evidence, for the listeners.** Measured on both runtimes. The older JDK registers one engine factory whose names include `javascript`, and the listeners execute; Java 17 registers **zero** factories, the lookup by name returns `null`, and the module's integration test errors with the engine-not-found exception from the workflow engine. After the change the engine resolves, evaluation of a listener-shaped expression returns the same value, and the integration test passes.
- **Baseline property preserved, for the listeners.** Execution of seven live task listeners, and with them the behaviour of the background-investigation process. The two decisions differ because the **baselines** differ: one path executed at the base commit and must keep executing, the other never executed and must keep not executing. Reading either decision as the general rule would break the other.

**What it cost, stated rather than absorbed.** Two consequences fell out of restoring the engine and are declared as deviations in [Dependency Change Inventory](dependency-change-inventory.md), because neither was in the frozen plan: the artifact itself, and a classpath collision it exposed. Nothing had generated bytecode at run time in that module before, which had left three different providers of the same bytecode-library package coexisting there harmlessly — an ancient copy reaching it through a web-service frontend nothing uses, a stripped copy **bundled inside** an unrelated jar under the real package name, and the reactor's own current one. The engine loads whichever sorts first, so the collision had to be resolved before the fix could work at all.

## 6 — Proving the Frontend Is Unchanged

The frontend declares two test frameworks and contains **zero specification files**. With no behavioural tests, what constitutes proof that the pipeline still does the same thing?

- **Decision.** Assert behaviour preservation by **byte-comparing the five build artifacts** against a baseline captured before any edit: `assets/dist/application.js`, `assets/dist/application.min.js`, `assets/dist/vendors.min.js`, `assets/dist/application.min.css`, and the cache-busted `home.html`.
- **Alternatives considered and rejected.** *Relying on the frontend's declared test tooling.* There are **zero `*.spec.js` files** in the tree despite two test frameworks being declared, so there is nothing to run — and the tooling was subsequently found to be removable dead weight, which is entry 12. *Trusting process exit codes.* Worthless here, and R-T7 says so as a rule rather than a preference: `grunt.option('force', true)` masks task failures, so a broken build exits zero, and two registered defects are masked by exactly that mechanism. *Writing new specification files to cover the pipeline.* Rejected because new tests would establish what the code does *now*, which is not the question; only a comparison against the prior state answers it.
- **Evidence that byte-identity is achievable at all** — established before it was relied on, because a pipeline with any nondeterminism would make the criterion meaningless. Three properties were confirmed by reading the build file: cache busting is **content-hash based**, operating over the distribution directory with no timestamp, banner or date injection; minification runs with identifier **mangling disabled**, removing the principal source of benign drift; and concatenation order derives from the frozen asset globs, so preserving every dependency key and the install topology — R-T6 — fixes the order.
- **Honest caveat, scoped rather than hidden.** Source-map generation is enabled and embeds file paths, so the comparison build must execute from the **same relative path**, or the map file will differ while the JavaScript bundles do not. The comparison is scoped to the five artifacts accordingly.
- **Baseline property preserved.** The bytes of everything the browser loads.

**The removal-over-replacement choice this criterion forced.** The Sass toolchain could not build on the target runtime, and it was **removed** rather than replaced with a modern compiler.

- **Alternatives considered and rejected.** *Substituting a modern Sass compiler.* Modern replacements were verified to install successfully, so this was declined **on evidence, not on availability**: a different compiler risks producing **different CSS bytes for zero functional gain**, which fails the very criterion this entry establishes. *Keeping the existing toolchain.* Not available — its native compiler does not build on the target runtime.
- **Evidence that removal is output-neutral.** Re-derived from the build file: the only textual mention of a Sass task is inside a **commented-out** task alias, so no Sass task is registered in any executed graph, and the stylesheet asset globs consume compiled CSS only. Removal therefore cannot change an artifact.
- **Baseline property preserved.** The stylesheet bytes. Note for the record: this is one of the change set's two R-6 escape-clause invocations, and it is recorded as such in [Pre-existing Defects](pre-existing-defects.md) rather than here; this entry explains only *why removal beat replacement*, and is not an additional invocation.

### 6a — Which baseline the artifacts are compared against

"Compared against a baseline" has two readings, and they are not the same claim. A baseline built from the base-commit manifest **on the migrated runtime** isolates the package-manager change. A baseline built **on the historical runtime** additionally covers the runtime move, which is the migration's headline change. An earlier revision of this change set captured only the first and said so; a reviewer reasonably asked for the second.

- **Decision.** Capture the historical-runtime comparison as well, publish **both** digest sets, characterise every difference to the byte, and record the residual as an **accepted deviation** — stating plainly that a strict reading of "five artifacts byte-identical to a build on the original runtime" is not met, and that what the criterion exists to detect, a change in what the application loads, was not found.
- **Alternatives considered and rejected.** *Reporting only the same-runtime comparison.* It is the more flattering number and it was already published; leaving it as the whole story is what the reviewer objected to, correctly. *Changing either minifier to close the gap.* Both install and run on the target runtime at the versions the lockfile pins, so neither has a compatibility reason and R-1 forbids the change; it would also make things worse, since a different minifier version changes far more than the observed difference. *Widening what "identical" means so the result reads as byte-identity.* Rejected because the differences are real; they are reported as differences, with their extent measured, leaving the burden of judging them with the reader rather than absorbing it into the wording.
- **Evidence.** The second capture was performed rather than argued about: the historical runtime and the superseded package manager were installed at the versions the base commit used, the base-commit tree was extracted and built with the install command the base-commit runtime wiring invoked, and the output was compared artifact by artifact. **Three of the five are byte-identical** — the concatenated bundle, the vendor bundle and the rewritten entry document. **Two differ**, and both are minifier output: the minified script by **2 bytes**, the minified stylesheet by **789**. The cause was isolated rather than guessed — the minifier versions are identical on both sides and their input is byte-identical, so the difference comes from the JavaScript engine the minifier itself runs on. For the script it is one escaped forward slash inside a regular-expression character class, and normalising that escape makes the two bundles compare **equal**; for the stylesheet it is the CSS minifier grouping the same declarations into different rule blocks, with no declaration found on one side and absent on the other. The full analysis is archived beside this page at `smoke-evidence/historical-frontend/comparison.txt` with the capture script committed next to it.
- **Baseline property preserved.** What the application loads: every declaration and every matched pattern is present on both sides, and the two residual differences are confined to formatting choices made by a minifier running on a different engine.

## 16 — The Stream-Supplier Seam in the Two AWS Test Rewrites

Removing the retired mocking framework meant re-expressing every idiom it provided. Most had a direct Mockito equivalent. Four did not: three constructor interceptions of a JDK file-stream type in the transcribe tool's test and one in the comprehend-medical tool's test, all intercepting a type the platform loads before any application class exists.

- **Decision.** Introduce a **narrow, test-visible stream-supplier seam** — a single protected method on each service that opens the media stream — and have the test override it from an anonymous subclass. Both AWS tool modules deliberately share **one** seam pattern so the idiom is consistent across them. While the test's override field is unset the override delegates to the production implementation, so the real file-opening path still runs in the tests that do not need to substitute a stream.
- **Alternatives considered and rejected.** *Construction mocking*, the obvious like-for-like substitute for the retired framework's constructor interception. It **cannot intercept a type loaded by the bootstrap class loader**, which is exactly what the file-stream type is — so the substitution fails at the mechanism level, not on style. *Excluding the affected tests.* R-5 forbids it, and the register any exclusion must cite would have no row to offer: none of these methods fails at the base commit, so there is nothing to exclude against. *Weakening or deleting the assertions to fit a simpler substitution.* Forbidden absolutely by the preservation directive, and it is the shortcut a seam exists to avoid. *Retaining a mocking framework capable of intercepting bootstrap-loaded types.* The only one that did has no release that runs on the target runtime — its final version fails there — so there was nothing to retain.
- **Evidence.** Read at the base commit and executed on the target runtime. The interceptions sat at `:147`, `:239` and `:291` in the transcribe test and at `:128` in the comprehend-medical test, alongside two static mocks at `:338` and `:403`. In the migrated tests the statics are ordinary Mockito static mocks in try-with-resources blocks, and the stream substitution goes through the seam, whose declaring method sits at `:315` and `:287` in the two service implementations. The reason is recorded in the test source itself rather than only here. On the version question: both the incumbent and the advanced Mockito lines create ordinary mocks successfully on Java 17, but **static mocking of a class file at major version 61 fails on the older inline mock maker and succeeds on the advanced one** — which is why the advance was necessary and why the floor sits where it does. Construction interception of a bootstrap-loaded type succeeds on neither, which is what made the seam unavoidable rather than merely preferable.
- **Baseline property preserved.** **Every assertion in both classes is unmodified.** Verified by counting rather than asserted: the assertion and verification statements number **49** in the transcribe test and **15** in the comprehend-medical test, identical at the base commit and in the migrated tree. Only the mocking mechanism changed. The awkwardness is the point — this was more work than an exclusion, and it is the only option that preserves the assertions. Cross-referenced from [Baseline Test Failures](baseline-test-failures.md).

## 17 — Splitting the EclipseLink Family Into Two Version Axes

Four persistence artifacts shared a single version property at the base commit: the provider core, the JPA provider, its bytecode companion and the object-to-XML module. Advancing the provider is unavoidable, because the incumbent version predates the target runtime by six years. How to advance a co-versioned family whose members no longer release together is the question.

- **Decision.** Split the family. The provider core, the JPA provider and the object-to-XML module continue to share one property, advanced to the last `javax.persistence` line. The bytecode companion moves to a **new, separate version axis** of its own, and the managed entry that consumes it is re-pointed at the new property, with the constraint recorded as a comment beside it.
- **Alternatives considered and rejected.** *Advancing the single shared property for all four.* This is the one-line change and it **fails resolution outright**: there is **no release of the bytecode companion at the target version** — its 2.x line stops several patches short and then jumps to a 9.x series — so the build would not resolve at all. *Holding the whole family back at the incumbent version.* Rejected because it leaves a persistence provider six years older than the target runtime carrying the application's entire mapping layer, which is the opposite of the migration's purpose. *Moving to the provider's next major line.* Rejected on namespace grounds: that line is a **jakarta** line, which the EXCLUDE directive prohibits and which R-T1 forecloses at the artifact level as well as the import level.
- **Evidence.** Registry metadata for the bytecode companion showed the gap in its release series, and the finding was **independently corroborated** by reading the target provider's own POM, which declares a 9.x companion **by name** rather than a same-versioned one. Re-derived in the tree: the base commit has one property consumed by all four managed entries; the migrated build has two, with the companion's entry pointing at the new axis and the other three unchanged in structure.
- **Baseline property preserved.** A resolvable, deterministic build — and, downstream of that, the persistence behaviour that depends on the provider resolving at all. There is a general lesson worth recording, because it is not specific to this family: **splitting the axis is the standard remedy for a co-versioned artifact family whose members have diverged in release cadence**, and skipping it produces an unresolvable reactor rather than a subtly wrong one. Cross-referenced from [Dependency Change Inventory](dependency-change-inventory.md).

## 5 — Representing the Internal JNDI Context Factory

The Active Directory context source referred to an internal JNDI factory class as a class literal, which does not compile on Java 17 because the owning module does not export the package. Several routes restore compilation.

- **Decision.** The field holds the class **name** as a `String`, defaulted from a properties resource on the classpath that also supplies the connection-pooling flag key. The same resource is exposed as a bean, so a definition that wants to override either value wires it from one place rather than repeating a literal. A definition that sets neither property behaves exactly as it did before.
- **Alternatives considered and rejected.** *A launch-configuration argument exporting the package to the unnamed module.* Prohibited by R-T3, and it would not have worked anyway: the audit is textual, so the literal would still be present and the gate would still fail. The rule and the gate independently foreclose the same shortcut. *Keeping the value as a literal in the class, merely retyped.* Fails the textual audit for the same reason — the audit searches `src/main/java`, so the value cannot live in a Java file even as a string. *Deriving the factory name from the LDAP framework's own accessor.* Tested rather than assumed: it raises an error on Java 17, so the value has to come from configuration. *Substituting a different context factory implementation.* Rejected as an actual behaviour change to authentication, which is the one subsystem whose security outcomes the requirements name explicitly.
- **Evidence.** The decisive asymmetry is that the **runtime restriction is weaker than the compile-time one**: resolving the same class **by name** at run time succeeds, verified by execution, and JNDI matches the initial context factory by exact class name anyway — so passing the name is not an approximation of the old behaviour, it is what the old code ultimately did. Two further facts constrained the shape of the fix. No context-source bean definition exists in this repository at all; they live in an external configuration repository this repository cannot edit, so a fix that *required* new wiring would leave every existing deployment broken — hence the defaults. And both externalised values are byte-identical to the originals, which the resource file states as a standing constraint on itself.
- **Baseline property preserved.** Authentication outcomes and authorization results. The JNDI environment receives the same factory name and the same pooling key it received before, because JNDI recognises no variation, abbreviation or reassembled equivalent of either. The pooling flag was recovered differently, and the distinction is worth recording as the one place where nothing had to be externalised at all: the LDAP framework exposes that property key as a compile-time constant, which is inlined at compile time and therefore leaves no forbidden text in the class file *or* the source. Anchors in [Static Audit Output](static-audit-output.md).

### 5a — Whether to reinstate the old `Class`-typed accessor and mutator

Changing the field's type also changed the JVM descriptors of two public methods: the getter's return type and the setter's parameter type both moved from a class to a string. A caller compiled against the old descriptors would fail to link. Whether to reinstate them, or a bridge for them, on top of the new pair is a real question.

- **Decision.** Keep the `String` accessor and mutator, and decline to reinstate the old descriptors. The finding is recorded here rather than closed silently, because a declined finding that leaves no trace is indistinguishable from one that was missed.
- **Alternatives considered and rejected.** *Adding a `Class`-typed setter overload*, restoring the mutator descriptor while leaving the directed one in place. This was probed rather than dismissed: with both setters present, the JavaBeans introspector and the framework's own bean wrapper both resolve the property to the `String` write method, so the overload would not have broken configuration on this runtime. It is rejected on two grounds. It buys back **half** a binary contract that no caller in the deployed artifact uses, since the accessor half is unrestorable. And the mechanism it relies on is the introspector's tie-breaking between overloaded write methods, which is a resolution rule rather than a guarantee — accepting a subtle, environment-dependent resolution risk on the property that selects the LDAP provider, in the one subsystem whose security outcomes must be preserved, in exchange for a contract nobody is holding, is the wrong side of that trade. *A differently-named `Class`-returning accessor.* Not a binary bridge at all: a caller compiled against the original method name is not helped by a method with another name.
- **Evidence.** Three measurements, in the order they matter. The transformation mapping **directs this exact change** — the field type from `Class` to `String` with matching accessor and mutator — and the plan is the frozen contract, so a resolution contradicting it is not available here regardless of its merits. The old accessor **cannot be reinstated at all**, because the language permits no two methods differing only in return type; restoring the old getter therefore means deleting the directed one, so half the finding is unsatisfiable by construction. And **nothing in the deployed artifact calls either method**: every class file in the assembled archive was scanned, and the only ArkCase class mentioning them is the declaring class itself. The other hits are unrelated third-party types that happen to declare same-named methods of their own — one of which does declare a `Class`-typed pair, but the class under discussion does not extend it, so no interface or superclass contract requires the old shape. The property is reached from configuration, by name, as a string.
- **Baseline property preserved.** The configuration-driven behaviour that actually exists: the property is set by name from XML, which is unaffected by the descriptor change. No binary caller of the old descriptors exists to preserve.

## 18 — This Register's Own Wording and Numbering Conventions

Two of this folder's conventions are consequences of a genuine conflict between the rules and the automated audits, and one is a consequence of other pages citing this one. They are recorded as decisions because a convention that looks arbitrary invites a well-meaning editor to undo it.

- **Decision, on wording.** In this documentation tree: write **"JDK 8"** and never the other spelling of the older runtime's name; confine mentions of the superseded package manager to the minimum factual, historical naming of the deleted lockfile artifact, which is entry 3; and **describe** module-access JVM arguments rather than naming them literally, referring to the register of such exceptions **by its title alone** — never by filename, and never as a link.
- **Decision, on numbering.** Entry numbers are **stable identifiers**. A new entry takes the next unused number; existing entries are never renumbered and numbers are never reused. Reading order follows the order the requirements specify, and the summary table is the map between the two.
- **Alternatives considered and rejected, on wording.** *Writing the natural phrasings and letting the audits fail.* The prerequisite-consistency gate greps the documentation tree for older-runtime version strings and for the superseded package manager's name expecting zero hits, while R-1, R-5 and R-7 **mandate** content here that names the JDK 8 baseline and the deleted lockfile. Something had to give, and failing a gate is not it. *Dropping the mandated content to satisfy the greps.* Rejected outright: it breaches three rules to satisfy a lint, which is the wrong way round. *Naming the module-access arguments literally, on the ground that a register describing a prohibition ought to be able to state it.* Rejected because a register that trips the very check it exists to support is worse than one that describes its subject, and because nothing about the prohibition's force depends on printing the token — R-T3 is quoted with its meaning intact in the rules section above.
- **Alternatives considered and rejected, on numbering.** *Renumbering the register so that numeric order matches the requirements' reading order.* Rejected because two sibling-register citations name entries of this page **by number**, so renumbering would silently redirect them to different decisions — the worst kind of documentation defect, because nothing breaks visibly. *Reordering by relabelling entries rather than renumbering them.* The same defect with less visibility. *Leaving the sections in numeric order and ignoring the specified reading order.* Rejected because the specified order is a requirement, and satisfying it costs only a mapping table.
- **Evidence.** The conflict is real and was resolved by **scoping**, which was verified rather than assumed. The version-string and package-manager greps apply strictly to the three prerequisite pages — [Developer Setup](../setup.md), the [documentation home](../index.md) and the [module overview](../overview.md) — while this tree uses the substituted wording. The module-access tokens are subject to a **repository-wide** zero-hit audit, which is why describing beats naming, and which has the consequence that no document in this folder prints that register's own path and that register does not print it either. On numbering, the two by-number citations were read directly: one names a sub-entry of entry 6 and the other names entry 15.
- **Baseline property preserved.** **None.** This is a documentation-consistency resolution, not a behavioural one, and it is labelled that way so it cannot be mistaken for a claim about the application. It appears on this page because the wording substitutions are visible in every other entry, and an undisclosed substitution in a register of disclosed decisions would be self-defeating. The same reasoning explains the bracketed editorial note under R-7 above: the rule's own text contains the string the gate forbids, so the phrase is substituted **and the substitution is declared**, because quietly editing a quoted rule is a worse failure than the wording problem it solves.

## 9 — Whether a One-Sided Test Suite Is an Evidence Hole

The cross-run comparison requires the two archived test-report sets to correspond. When a suite appears on only one side, is that a hole?

- **Decision.** A suite present only at baseline has **lost** its counterpart and makes the capture incomplete, failing the run. A suite present only on the migrated side is counted and listed by name, not treated as a gap.

## 10 — Whether to Advance a Library the Plan Holds Frozen: the Rule Engine

The rule engine cannot fire a rule at all on Java 17: the bytecode generator the decision-table path reaches asks in its static initialiser for reflective access to a protected platform method, the platform refuses, and the initialiser dies. All live decision tables are on that path, so object numbering and queue routing are affected in the deployed application, not merely in tests. The plan's scope section holds this library frozen, on the stated ground that with no rule files the rule-compilation path is absent — a ground execution contradicts, because compiling a spreadsheet enters exactly that path.

- **Decision.** Advance the family to the release bisection identifies as the earliest that compiles *and* fires a real decision table on Java 17, staying on the same major line so the `javax` namespace and the rule semantics are untouched. **The plan is not amended, and this register does not claim authority to amend it**: the change is recorded as a deviation, raised for **owner ratification**, with the contradiction between the plan's stated ground and the observed behaviour named explicitly.
- **Alternatives considered and rejected.** *Standing still.* Keeps the scope sentence literally intact and leaves the deployed application unable to evaluate a single decision table — the letter of one sentence at the cost of the migration's central objective. *A launch-configuration argument opening the package.* Prohibited outright by R-2, and it would put the first entry into a register delivered empty. *Changing the rule dialect configuration.* An earlier candidate that turns the suite green by altering how rules generated from every table are compiled; rejected because it is a semantic change to the subsystem under preservation, and because the version advance is now better evidenced — identical rule text is a stronger guarantee than a passing suite. *Excluding the failing tests.* R-5 forbids it, because none of them fails at the baseline: the remedy had to make them pass, not make them disappear.
- **Evidence.** At the base commit the tables compile and fire, and the migration's promise is that they still do and still produce the same decisions. That eliminates standing still, and it also eliminates any remedy nobody has measured — which is what made an earlier revision of this register decline the change, since the measurement did not then exist. It exists now: **every live decision table was compiled under both versions and the generated rule text is byte-identical, table for table**, with equal counts of tables, digests and differences of zero. Rule text is what the engine parses, so identical rule text states directly that the change cannot alter a numbering sequence or a routing decision. The floor was found by **bisection, not from a changelog**. Recorded per table at `smoke-evidence/dependency-parity/decision-table-parity.txt` with the harness committed beside it.
- **Baseline property preserved.** Object numbering and queue routing — two of the most visible behaviours in the application. If ratification is declined, the honest consequence must be stated with it: the reactor then carries a rule engine that cannot fire a rule on the target runtime, and no other remedy is available inside the rules.

## 11 — Whether to Advance a Library the Plan Does Not List: the JSON Mapper

The JSON mapper at its incumbent version cannot build a bean deserializer for any type carrying a modern date-time property on Java 17, because it reflects into a platform package the platform does not open. Several controller tests fail on it, and two production portal-submission paths read request objects carrying such properties through a plain mapper, failing with an unchecked error that escapes the surrounding handler. The library serialises every REST response, and the plan's dependency inventory does not list it at all — so it is neither authorised nor explicitly frozen.

- **Decision.** Advance to the earliest release that does not reflect into those types at all, and record it as an unlisted change **raised for owner ratification** on the same terms as entry 10.
- **Alternatives considered and rejected.** *Reverting to the incumbent version*, which the review that raised this finding proposed. The baseline comparison refutes it: reverting does not restore baseline behaviour, it removes it, and it breaks portal request submission on the target runtime. *A launch-configuration argument opening the platform package.* Prohibited by R-2. *Registering the date-time module inside the failing tests.* Rejected because it turns the suite green while leaving the two production paths broken, treating a library defect as a test defect — the inverse of R-T3.
- **Evidence.** The probe was run three ways — the older runtime with the incumbent version, which *is* the baseline; Java 17 with the incumbent, which is what reverting produces; and Java 17 with the advanced version, which is what ships. The advanced library reproduces the baseline on every REST-response path and on the plain-mapper read path exactly, including the **exception type** on the payload shapes that already failed at baseline; the reverted library reproduces none of them, failing for *every* payload because the failure happens while the deserializer is being built. Both records are under `smoke-evidence/dependency-parity/`.

One asymmetry is disclosed rather than buried, because R-7 requires it: a plain mapper *writing* a date-time-bearing type produced a bean-shaped rendering at baseline and now raises a clean definition exception. Every plain-mapper write site in production was checked against that, and none carries such a property, so the asymmetry is not reachable from production code.

## 13 — Whether to Repair a Vacuously Passing Error-Path Test

One test method in the transcribe tool's suite reports a pass while executing none of its assertions: the stub that should make the upload throw is matched on a different mock than the one the service receives, so the method completes normally and the block holding three verifications and two assertions never runs. Repairing it and registering it are both defensible, and the repair looks like a two-character change.

- **Decision.** Register it, and leave the test file untouched.
- **Alternatives considered and rejected.** *Fixing the stub matcher alone.* It converts a false pass into a false failure — strictly worse, because the suite then reports a defect in production code that does not exist. *Correcting the interaction count alongside it*, which is the only way to make the test both fire and pass. This is precisely the assertion rewrite the preservation list exists to prevent, and R-6's escape clause does not reach it because nothing is blocked: the test reports what it reported at baseline.
- **Evidence.** The same mismatch exists at the base commit in its pre-migration form, and the baseline archive records the method **passing** on the older runtime — so the migrated test reproduces baseline behaviour exactly, which is what the rewrite was required to do. More decisively, the repair does not stop at the matcher: once the exception fires, the first line of the error block cannot hold, because the production code calls the service it counts twice before the failure point.
- **Baseline property preserved.** The suite's reported outcome, unchanged from baseline. The uncomfortable part is stated rather than smoothed over: the rules require leaving in place a test that proves nothing, and the mitigation is that it is now documented as proving nothing, with the full repair recorded for whoever owns it in [Pre-existing Defects](pre-existing-defects.md).

## 14 — Declaring the Security XML Schema After the Version Advance

Advancing the security framework's version makes every schema declaration naming the older version fatal: the namespace handler checks the document's schema location before parsing a single security element and accepts only its own version's schema, the version-less name, or no security schema declaration at all. Two forms satisfy it, so the choice is real, and a third option — pinning the framework back — was on the table because the failure appears only at deployment.

- **Decision.** Use the **version-less** schema name, in all three stale declarations, including the one where the handler does not currently run.
- **Alternatives considered and rejected.** *Pinning the new version's schema name.* It satisfies the handler and is arguably more explicit. It also re-creates the coupling that produced the defect: the declaration must then be edited in lockstep with every future upgrade, and when it is not, the symptom is a webapp that does not deploy — discovered at deployment time, several files away from the version property that caused it. *Reverting the version so the declarations stay valid.* This changes no XML and is the wrong choice: the security line has to pair with the framework line, and standing still reintroduces the skew the version row exists to avoid. Fixing a declaration has no behavioural surface; reverting a version has a large one. *Correcting only the two documents where the handler actually runs.* The third declares the namespace but uses only non-security elements, so its stale version is inert today. It is corrected anyway, because an inert stale declaration is a trap that springs the first time a security element is added to that document, in a context nobody is watching.
- **Evidence.** The baseline is a root context that builds. At the base commit the declarations matched the version on the classpath and the context initialised; after the advance they do not, and the measured consequence is a 404 for as long as the container runs, with the log ending at a startup failure. One form of match was already present and working in this repository — a library document declares the version-less schema and uses a security element under it — so the version-less form is **observed** to parse under the new version rather than merely believed to, and the framework's own schema mapping resolves that name to the real current schema locally.
- **Baseline property preserved.** A context that initialises, and with it every authenticated request path. What this entry deliberately does not resolve: the same one-line edit is required in eight files the deployment loads from an external configuration repository, `ArkCase/.arkcase`, which no change in this repository can reach. That is recorded as a deployment prerequisite in [Dependency Change Inventory](dependency-change-inventory.md) and on the [Developer Setup](../setup.md) page rather than silently assumed.

## 15 — A Stylesheet Endpoint Answering 500 Instead of 406

One branding stylesheet endpoint returns HTTP 500 to any client that does not name the stylesheet media type, while returning 200 and the stylesheet to clients that do, including the header a browser actually sends. The endpoint is a stylesheet, so nothing about it is obviously out of a runtime migration's reach, and the migration did advance the web framework — which puts content negotiation inside the diff. Fix or register was a genuine question.

- **Decision.** Register it; change no controller and no negotiation setting.
- **Alternatives considered and rejected.** *Dropping the media-type restriction from the request mapping and setting the content type on the response.* This is the fix the finding suggests and it works — but it changes a controller's request mapping, and the preservation list states that no controller signature, request mapping or serialized field changes anywhere. A rule that binds only when it is convenient is not a rule. *Returning a wrapped response entity instead of a body-annotated string.* The same objection with a wider blast radius: it changes the handler's signature as well as its mapping, and would alter how the body is written for the path that currently works. *Removing or changing the default content type on the negotiation manager.* Superficially tidiest, because it addresses the actual cause, and the worst of the three: that setting governs negotiation for **every** handler in the application, so changing it to repair one endpoint alters response-type resolution across the entire REST surface — the opposite of preserving REST contracts, and a change no evidence in this change set could bound.
- **Evidence.** Provenance first: the version history returns **empty** for both the controller and the servlet configuration since the base commit, so neither file moved. Then the mechanism, which settles it: the negotiation manager sets a default content type, and the framework *skips* a strategy returning only the wildcard and falls through to that fixed type — behaviour identical in both framework versions. The resulting not-acceptable exception is then converted into a 500 by a catch-all exception handler already registered as a pre-existing defect. Both halves of the cause pre-date the migration, and the measured response matrix matches the mechanism cell for cell, including the reason a real browser succeeds.
- **Baseline property preserved.** The endpoint's observable behaviour, which is unchanged from the base commit. The deferral is justified rather than asserted: the defect has no user-facing effect — every consuming page uses a stylesheet link element, every browser header yields 200, and the deployed login page received 200 with branding visibly applied on every verification load — and every available repair changes either a request mapping or the negotiation contract of every endpoint. Registered in [Pre-existing Defects](pre-existing-defects.md).

## 19 — Classifying Two Build-Plugin Changes Honestly as Non-Blockers

Two build-plugin changes could plausibly have been presented as hard Java 17 blockers: pinning the test-runner plugin, which the base commit does not declare at all, and advancing the coverage plugin.

- **Decision.** Record them honestly for what they are — the test-runner pin as a **reproducibility** change and an auditable home for baseline-failure exclusions, and the coverage advance as a **supportability** change — and say in the inventory that neither is a hard blocker.
- **Alternatives considered and rejected.** *Presenting both as hard Java 17 blockers.* It is the tidier narrative and would have made every row in the dependency inventory read the same way. Rejected because it is false: the version the build implicitly bound did execute the suite successfully on Java 17, and the incumbent coverage plugin did complete instrumentation and reporting against a current class file. Overstating them would inflate the risk register and violate R-1's demand for a **specific** reason — a rule that is not satisfied by a plausible-sounding one. *Omitting them from the inventory because they are not blockers.* Also rejected: R-1's contrapositive requires every change in the diff to carry a justification, so an unlisted change is as much a violation as an unjustified one.
- **Evidence.** Both incumbents were executed on the target runtime and both worked, which is what makes the honest classification available in the first place. The test-runner pin carries an additional non-version justification that stands on its own: at the base commit the plugin is declared in **none** of the reactor's POMs, so there was no location where a baseline-failure exclusion could be recorded, let alone reviewed. Its declaration deliberately carries no literal fork-argument override, because setting one would silently sever coverage instrumentation and leave the coverage check evaluating an empty data set — a false pass.
- **Baseline property preserved.** The integrity of the evidence the other entries depend on: a coverage check that measures something, and a single auditable place for any exclusion to be declared and cited. Rows in [Dependency Change Inventory](dependency-change-inventory.md).

## How to Use This Register

- **Adding an entry.** State the decision, the alternatives rejected with their reasons, the evidence, and the baseline property preserved. Take the next unused number. An entry with no rejected alternatives is not a resolution — it is a note, and it fails this page's completion condition.
- **Revisiting an entry.** The evidence is the load-bearing part. If the measurement is wrong, the resolution may be wrong; if it is right, a later preference does not override it.
- **Interpreting a choice that looks untidy.** Several of these deliberately chose the less elegant option — the larger jar, the 40-character version specifier, the extra exclusion, the hand-written test seam. Elegance was not the criterion, and tidying one of them would be a behaviour change with no compatibility justification.
- **When a remedy exists and was not applied.** Entries 4, 13 and 15 are of this kind for the paths they deliberately leave alone, and each records the remedy in enough detail that nobody has to rediscover it. That is the intended handover: the decision is documented as open, not closed.
- **When a change the plan does not authorise was nevertheless made.** Entries 10 and 11 are both of this kind. Neither amends the plan and neither claims the authority to: each states the constraint chain that leaves no other remedy, supplies the measurement showing the change is behaviourally inert, and is raised for owner ratification. If ratification is declined, the consequence recorded in the entry is what follows — not a quiet reversal.
